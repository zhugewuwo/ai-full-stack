枝叶#2 ｜ 创建群聊

两点之间是线段，三点之间是平面。维度的跃迁，从来不是数量的简单累加。

上一章给闪讯的用户之间修了路，建立了好友关系系统。但路修好了，通行方式还是一对一的。现实中，我们更多的沟通发生在群体里,比如工作群、家庭群、兴趣群。这一章，我们要让闪讯从"两个人的世界"走向"一群人的广场"。

一、需求分析

群聊涉及的面比好友关系更广。完整的群聊系统包括创建、搜索加入、审批、成员管理等一系列能力，但不需要一口气全做完。这一版我们只聚焦最核心的一件事——创建群聊，让用户能从好友中选人建群、从单聊拉人建群、查看自己的群聊列表。消息收发完全复用已有链路，不需要动一行代码。

二、后端：在会话域上"长"出群聊

群聊的后端逻辑放在独立的 im-group crate 中，和 im-friend 独立的理由一样——会话模块管通讯能力（创建/列表/删除/已读），群的事情归群管。两者共享 conversations 和 conversation_members 表，但职责不同，生长方向不同。

im-group 遵循和其他 crate 一样的三层架构（routes → service → repository），创建群聊后需要调 MessageService.send_system 发系统消息，这个依赖通过 main.rs 组装注入：

// ---> server/modules/im-group/src/routes.rs
#[derive(Clone)]
pub struct GroupApiState {
    pub service: Arc<GroupService>,
    pub msg_service: Arc<MessageService>,
}

1. 数据模型

群聊只需要一张新表 group_info 记录群组信息。
conversations 表和 conversation_members 表在最初设计时就预留了群聊字段（type=1、name、avatar、owner_id），现在终于派上用场了。

-- ---> server/migrations/20260412_005_group.sql
CREATE TABLE IF NOT EXISTS group_info (
    conversation_id UUID PRIMARY KEY,
    join_verification BOOLEAN NOT NULL DEFAULT FALSE,
    max_members INT NOT NULL DEFAULT 200,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

决策 理由
group_info 独立于 conversations 表 群配置字段只有群聊需要，不污染通用会话表。后续扩展群公告、全员禁言只改 group_info
宫格头像用 grid:url1,url2,... 字符串 不额外建表，复用 avatar 字段。前端解析 grid: 前缀渲染九宫格，成员变动时刷新
join_verification 默认 false 新建群聊默认无需审批，降低使用门槛
2. 三层架构

im-group 的内部结构和 im-friend、im-conversation 一致，三层各司其职：

server/modules/im-group/src/
├── models.rs       # CreateGroupRequest, GroupConversation
├── repository.rs   # 数据库操作（事务创建 + 宫格头像）
├── service.rs      # 业务逻辑（校验 + 调用 repo）
├── routes.rs       # HTTP 路由（POST /groups + 系统消息）
└── lib.rs          # 模块入口

routes.rs — HTTP 入口

只有一个路由 POST /groups。handler 做三件事：提取 user_id → 调 service 创建群聊 → 查创建者昵称发系统消息。

// ---> server/modules/im-group/src/routes.rs
async fn create_group(state, headers, req):
    user_id = extract_user_id(headers)
    conv = service.create_group(user_id, req.name, req.member_ids)

    // 查创建者昵称
    creator_name = SELECT nickname FROM user_profiles WHERE account_id = user_id
    // 发系统消息
    msg_service.send_system(conv.id, "{creator_name} 创建了群聊")

    return conv

系统消息的发送放在路由层而不是 service 层，因为它需要 MessageService——这个依赖通过 GroupApiState 注入，service 层不感知。

service.rs — 业务校验

service 层只做校验，不碰数据库。三个规则：群名非空、成员去重后至少 2 人（加群主 ≥ 3）、不超过 200 人。

// ---> server/modules/im-group/src/service.rs
fn create_group(owner_id, name, member_ids):
    name = name.trim()
    if name.is_empty(): return 400

    // 去重，排除群主
    unique = member_ids.filter(id != owner_id).dedup()
    if unique.len() < 2: return 400   // 加群主至少 3 人
    if unique.len() + 1 > 200: return 400

    return repo.create_group(name, owner_id, unique)

repository.rs — 事务操作

repository 层是最重的一层。create_group 在一个事务内完成四步，事务外再生成宫格头像：

// ---> server/modules/im-group/src/repository.rs
fn create_group(name, owner_id, member_ids):
    BEGIN
    // 1. 创建群聊会话
    INSERT conversations (type=1, name, owner_id)
    // 2. 插入群主 + 成员（ON CONFLICT 恢复已删除的成员）
    INSERT conversation_members × N
    // 3. 初始化群配置
    INSERT group_info (join_verification=false)
    COMMIT

    // 4. 事务外：生成宫格头像
    build_grid_avatar(conv.id)
    UPDATE conversations SET avatar = 'grid:...'

ON CONFLICT ... DO UPDATE SET is_deleted = FALSE 是一个细节——如果某个用户之前被踢出过群（is_deleted=true），重新加入时恢复而不是报错。

build_grid_avatar 查前 9 个成员的头像（按 joined_at 排序），拼接成 grid:url1,url2,... 格式。放在事务外面是因为它不影响数据一致性，头像生成失败不需要回滚整个群聊创建。

3. 系统消息

系统消息是这次新增的一个小能力，但非常重要。创建群聊成功后，所有成员的聊天页会看到一条居中的灰色提示："XXX 创建了群聊"。这条消息不是凭空出现的——它走的是和普通消息完全一样的链路。

MessageService 新增 send_system 方法，以 id=0 的系统用户身份发送消息。和普通的 send 相比，它跳过了成员校验（系统用户不是群成员），但后续流程完全一致：

// ---> server/modules/im-message/src/service.rs
fn send_system(conversation_id, content):
    sender_id = 0  // 系统用户

    // 1. 生成序列号（和普通消息共享同一个 seq 序列）
    seq = seq_gen.next(conversation_id)

    // 2. 存储消息（写入 messages 表）
    message = repo.create(msg, seq)

    // 3. 生成预览文本，更新会话最后消息
    UPDATE conversations SET last_message_preview, last_message_at

    // 4. 广播给所有成员（不排除发送者，因为系统用户不在线）
    broadcaster.broadcast_message(message, member_ids, exclude_sender=false)

    // 5. 广播会话更新（让所有成员的会话列表刷新）
    broadcaster.broadcast_conversation_update(conversation_id, preview, member_ids)

系统消息和普通消息共享 seq 序列，这意味着它在消息流中有确定的位置——不会因为时序问题出现在错误的地方。

前端通过 senderId == '0' 识别系统消息，渲染为居中的灰色圆角标签，不显示头像和昵称。这个 ID 在迁移脚本中预置：

-- ---> server/migrations/20260412_005_group.sql
INSERT INTO accounts (id, status) VALUES (0, 0) ON CONFLICT DO NOTHING;
INSERT INTO user_profiles (account_id, nickname) VALUES (0, '系统通知') ON CONFLICT DO NOTHING;

3. 主应用集成与模块协作

home_page.dart 是所有群聊功能的组装点——它不实现业务逻辑，只负责把各个模块的能力串联在一起。好友模块提供数据，群聊模块提供页面，会话模块提供列表，聊天模块提供消息收发。

client/lib/src/home/view/home_page.dart

用户有三条路径进入群聊，都通过 home_page 组装：

  • 主页："+" → 发起群聊 → 选人 → ChatPage
  • 单聊详情："..." → "+"邀请 → 选人（对方预选）→ ChatPage
  • 通讯录：群聊 → 群聊列表 → 点击 → ChatPage

好友列表转换与模块解耦

创建群聊页需要展示好友列表让用户勾选。好友数据在 flash_im_friend 模块的 FriendCubit 里，创建群聊页在 flash_im_group 模块里。最直接的做法是让 flash_im_group import flash_im_friend 的 Friend 类型——但这样做有什么问题？

想象一下：Friend 类型有 20 个字段（id、昵称、头像、签名、手机号、备注、分组、创建时间……），但创建群聊页只需要 4 个（id、昵称、头像、拼音首字母）。如果直接依赖 Friend，以后好友模块加一个"在线状态"字段，群聊模块要重新编译；好友模块改了"备注"的类型，群聊模块的测试可能莫名其妙挂掉——尽管群聊页根本不关心备注。

依赖一个你只用 20% 的类型，意味着你要承受 100% 的变更风险。

解法是让群聊模块定义自己需要的最小接口——SelectableMember，只有选人页真正用到的 4 个字段：

// ---> client/modules/flash_im_group/lib/src/data/group_models.dart
class SelectableMember {
  final String id;
  final String nickname;
  final String? avatar;
  final String letter;  // 拼音首字母
}

转换的责任交给 home_page，它同时认识 Friend 和 SelectableMember，负责在两者之间翻译：

// ---> client/lib/src/home/view/home_page.dart
List<SelectableMember> _friendsToMembers() {
  return context.read<FriendCubit>().state.friends
      .map((f) => SelectableMember(
        id: f.friendId, nickname: f.nickname,
        avatar: f.avatar,
        letter: PinyinUtil.getFirstLetter(f.nickname),
      )).toList();
}

模块之间不直接认识对方的类型，由组装层负责翻译。这和后端 main.rs 组装各个 crate 的思路一样——模块只定义自己需要什么，不关心数据从哪来。

这个设计也为后续扩展留了空间。就像定义好 Type-C 接口，你可以生产任意电子产品，不用担心充电问题。比如

  • 以后要做"从通讯录选人转发消息"，转发页面同样需要一个选人列表——它可以直接复用这套选人交互，不需要再依赖好友模块。
  • 甚至如果 数据源 不是好友而是群成员列表，只要调用方把数据转成 SelectableMember，选人页照样能用。
  • @群成员或权限管理：数据源是当前群成员。

目前 SelectableMember 定义在 flash_im_group 内部，够用。等后续邀请入群、@提醒、转发消息、分享等场景也需要选人时，可以把它提升到 flash_shared 作为通用类型——到那时，选人页就真的变成了一个即插即用的"标准接口"。

四、本章小结

这一章让闪讯从两人对话走向了多人群聊。后端在 im-conversation 上扩展了群聊创建和会话列表 type 过滤，前端新建了 3 个页面和 2 个共享组件（九宫格头像、弹出菜单），功能网络从 65 个节点增长到 71 个。

群聊创建与加入 v0.13.0 commit

核心挑战不在于群聊本身的逻辑有多复杂，而在于如何让新功能"长"在已有架构上而不破坏它。消息链路完全复用，聊天内容的界面不需要改动一个字，对群聊依然成立。conversations 表的预留字段终于启用，对之前项目的破坏性也不大，这些都是之前的设计决策在此刻兑现的红利。

下一步要做的是搜索加群、入群审批，以及群成员管理（踢人/退群/转让/解散）、群详情页等群聊管理功能。也只需要关注 im_group 模块的发展，这种独立性可以在 生长过程中 尽可能减少对其他器官的损伤，这是可持续生长的必要条件。
