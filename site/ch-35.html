果实#1 ｜ 后端部署

现在闪讯已经基本实现了第一版的预期功能，但到目前为止，后端一直住在开发机上运行。客户端也是在局域网内聊天。但这有个问题：你一关电脑，服务就没了。你的朋友想试试？得跟你连同一个 WiFi。是时候给闪讯找个正式的 "家" 了。

一、服务器环境准备

如果你从来没碰过服务器，先别慌。本章会像搬家指南一样，一步步带你走完全程。而且再 AI 的加持下，搬家这件事将变得更加轻松，就像是有了一辆运输机。找个新家的流程，无非就是：

找房子 → 装修 → 搬东西 → 通水电 → 入住。

1. 什么是服务器

服务器 顾名思义，是提供服务的机器。其实之前我们一直在运行服务，本机也可以视为一个服务器。从客户端的访问来看，其实服务器最重要的有两个东西 ip 和 端口号，其中端口号是我们可以自定义的。所以最重要的就是这个 ip。

正是因为本机的 ip 只能在局域网内使用，所以目前只是一个无法对外公开的服务。服务器和你的电脑之前最大的差异性在于:

它可以提供一个公网 ip ，任何人都可以通过这个 ip 接入你的服务。

也就是说，如果你有公网 ip，那本机也完全可以作为服务器，不过公网IP的获取方式目前应该很难了。

2. 如何获取服务器

服务器是一种资源，所以也不会平白无故地得到。服务器根据配置的差异，售价也云泥之别。目前国内主流的云服务商有，腾讯云、阿里云、华为云等。

我们的项目还在初期阶段，配置不需要很高。1 核 2G 足够跑近千个并发连接，千人的用户日常使用应该没有太大问题。我目前用的是腾讯云的 轻量应用服务器 ，之前活动 60 块钱买了 6年半，自己玩玩还是够用的。

现在入手应该也就几十块钱一年，对于了解全栈流程，还是和划算的。拿到服务器后，在控制台，你应该能看看到服务器对于的 ip， 它将成为任何人使用网络，访问你服务的入口。
这里我使用的服务器操作系统是 Ubuntu 22.04 LTS，大家尽量可以保持一致。

3. 访问你的服务器

服务器供应商还会给你三个重要的东西：

  • 公网 IP（比如 82.157.176.209）—— 你服务器在互联网上的门牌号
  • 用户名（通常是 root）—— 最高权限管理员
  • 密码 —— 开门的钥匙

有了这三样，表示你对这个服务器的控制权，就可以从你的电脑"走进"服务器了。打开终端输入：

ssh root@82.157.176.209

把 IP 换成你自己的。第一次连会问你信不信任这台机器，输入 yes。然后输入密码（输入时屏幕不会显示任何字符，这是正常的，盲打完回车就行）。

这样就表示你成功连上了你的服务器：

另外，命令行里是记不住密码的，建议可以用管理工具来维护。比如我习惯使用 tabby 维护连接，它也是一个开源项目。可以记住连接配置，丝滑连接服务器。

二、装修：环境检测与数据库准备

连上服务器之后，第一件事是搞清楚"这个毛坯房现在是什么状态"。就像搬进新房，你得先看看水电通了没、墙刷了没、马桶能不能用。我们的闪讯后端运行起来其实只需要两样东西：

  • PostgreSQL：存数据的地方（用户信息、聊天记录、好友关系，全在这里面）
  • flash-im 二进制文件：编译好的可执行程序（这个从本地编译后上传，不在服务器上编译）

其他的像 Rust 编译器、protoc 这些开发工具，服务器上完全不需要。服务器只负责"跑"，不负责"造"。我们可以本地编译好，传到服务器上。 本文的四个脚本在项目的这个位置：

1. 工作目录

首先在服务端创建一个文件夹，来盛放 flash_im 的项目，比如:

mkdir -p ~/server/flash_im #创建文件夹
cd ~/server/flash_im #进入文件夹

通过 scp 命令可以将本地的文件，传到服务器的置顶地址，比如这里写了一个 env_check.sh 的脚本，检测 flash_im 的环境。

scp scripts/deploy/env_check.sh root@82.157.176.209:~/server/flash_im/

这里给大家一个小任务，scp 命令传输时，总是要输密码。你可以尝试借助 AI ，如何解决这个问题，毕竟后期传文件到服务器上是很常用的操作。

2. 环境检测 env_check.sh

这个脚本是 AI 为我写的，主要是综合检测 flash_im 的运行环境，是否已经准备就绪。上一步已经把文件传到了服务器，需要执行一次 chmod +x 为它赋予可执行权限，然后就能执行检测了：

chmod +x env_check.sh # 可执行权限
./env_check.sh # 执行检测
  • 前两个是基本信息，看一下系统和当前的内存情况

  • 接着是 PostgreSQL 数据库和表的情况

新环境会自动下载并安装 PostgreSQL，以及创建数据库。但是数据表并不会在这里创建，会有警告提示。后续会有单独的数据库管理脚本，来维护数据库表。

  • 然后是配置文件、可执行文件是否存在

  • 最后检查一下端口和防火墙情况

接下来，只需要逐一处理环境中存在的问题即可，首先我们来处理一下数据库表。

3.数据库表的维护

之前数据库表的变更都在 server/migrations 中维护，使用服务端需要依据它们来创建。通过如下命令复制过去:

scp -r server/migrations root@82.157.176.209:~/server/flash_im/

db.sh 是专门为数据管理服务的，比如 ./db.sh migrate 也可执行 migrate ，从而创建数据库，以后的数据库更新迭代，也可以走这个脚本：

./db.sh status 可以查看数据库的状态：

此时再 ./env_check.sh 一下，也可以看到数据库就绪的信息：

三、项目打包和运行

数据库环境准备完毕，接下来就是如何打包，让闪讯的后端在服务器上跑起来。你知道之前本机上，后端能跑起来最重要的东西是什么吗? 可以看出，是构建出了一个在本机上可以执行的二进制文件，然后运行它。

聪明的你可能会想，把它丢到服务器上跑起来，能就行了嘛! 这个想法是很正确的，但只对了一半。

2. 什么是交叉编译

你的开发电脑是 Windows（或 macOS），服务器是 Linux。它们的操作系统不同，编译出来的程序格式也不同：

系统 可执行文件格式 例子
Windows .exe（PE 格式） flash-im.exe
macOS Mach-O 格式 flash-im
Linux ELF 格式 flash-im

在 Windows 上直接 cargo build 出来的是 .exe，传到 Linux 上跑不了。我们需要"交叉编译"：在 Windows 上编译出 Linux 格式的程序。

交叉编译就像翻译：你说中文（Windows），但要写一封英文信（Linux 程序）。你需要一个翻译工具。

这个"翻译工具"就是 Docker。Docker 可以在你的电脑上模拟一个 Linux 环境，在里面编译出 Linux 程序。

当然，构建的事也是 AI 来写脚本处理，我们也不用自己埋头干。项目里的 scripts\deploy\build.py 就是使用 Docker 一套龙的构建流程。第一次运行，它会提示你安装 Docker，你根据提示里的链接下载启动一下即可。

直到编译成功，你会得到一个 flash_im 的编译产物。把它上传到服务器的工作目录即可：

scp server/target/release/flash-im root@82.157.176.209:~/server/flash_im/

3. 在服务器运行 flash_im 后端产物

现在 server/flash_im 的运行目录有这些东西了，此时 flash-im 还没有可执行权限，需要加一下:

chmod +x flash-im

现在环境检测还剩最后一个问题，flash-im 的运行配置信息在 .env 里，可以拿来一下：

scp server/.env root@82.157.176.209:~/server/flash_im/

当所有环境准备，就绪就可以运行后端服务了, 看到熟悉的日志，表示服务重新启动:

./flash_im

4. 端口号放行

一般云厂商在服务器里会有安全组或者防火墙规则，来配置放行的端口，不然外网无法访问这个端口。如下搜索，我在腾讯云的配置里放行了 9600 :

然后浏览器输入 公网ip:9600/v 查看一下，有结果就说明后端服务通了。目前任何人都可以访问你的 flash_im 服务了。

5. 前端使用线上环境

而对于前端来说，它并不在意后端运行在哪，它们的协议是接口格式。唯一的区别是链接的途径，比如说政务大楼搬迁到新的地址，那里办理的业务和流程都没有任何变化。那对你而言，新旧的区别只在于新地址。我们只要把配置里的端口号改一下，就使用了 线上环境 。

而这个线上服务，是任何人都可以访问的。也就是说，目前你的 APP，已经具备异地通信的能力了。有动手能力的，现在就可以打包一个安装包给你的小伙伴(后续会逐一介绍)。

登录 信息

另外，现在手机号登录还是模拟的。如果需要的话，可以购买厂商的短信服务，把后端发假验证码的那块逻辑改成真正发送即可。

四、启动流程优化

现在 build.py 可以打包上传一条龙服务。但启动流程有点单薄，命令行里手动执行可执行文件一个问题：当命令行关闭，服务也就停了。我们需要一个更优雅的方式来管理服务的启停。

1. 使用脚本启停

项目里准备了一个管理脚本 flash.sh 负责维护后端的运行事宜，把它上传到服务器的部署目录：

# 在本地执行
scp scripts/deploy/flash.sh root@82.157.176.209:~/server/flash_im/

上传后，在服务器上就可以用它来管理服务了：

cd ~/server/flash_im
bash flash.sh          # 后台启动（关闭终端不停止）
bash flash.sh stop     # 停止
bash flash.sh restart  # 重启
bash flash.sh status   # 查看状态（PID、内存、运行时间）
bash flash.sh log      # 看实时日志
bash flash.sh clear    # 清空日志文件

flash.sh 用 nohup 在后台运行服务，日志写到 flash-im.log。关闭 SSH 终端不会影响服务。

2. 使用 systemd 创建服务 - 开机自启

目前这还不够，因为 服务器重启后，服务不会自动恢复。你得重新 SSH 连上去手动启动。 对于一个 7×24 小时在线的 IM 服务来说，这不够可靠。我们需要让系统帮我们管理进程：开机自动启动、崩溃自动重启、日志自动收集。Linux 上做这件事的标准工具叫 systemd。

你可以把 systemd 理解为 Linux 的"管家"。它负责管理系统上所有的服务（service）：哪些开机要启动、哪些挂了要重启、日志存在哪里。

systemd 的服务配置是一个 .service 文件，放在 /etc/systemd/system/ 目录下。我们写一个 flash.sh 的子命令来自动创建它：

bash flash.sh install    # 注册为系统服务 + 开机自启
bash flash.sh uninstall  # 移除系统服务

这个命令会做三件事：

  1. 创建 /etc/systemd/system/flash-im.service 配置文件
  2. 让 systemd 重新加载配置
  3. 设置开机自启

注册后，可以直接用 systemd 命令：

systemctl start flash-im # 启动
systemctl stop flash-im # 停止
systemctl restart flash-im  # 重启
journalctl -u flash-im -f    # 查看日志
3. 服务的更新部署

比如这里可以改一下版本号，重新构建上传。另外这里更新优化了一下脚本。指定公网 ip ，会自动上传、重启服务，不需要再登录服务器执行：

python scripts/deploy/build.py root@82.157.176.209

运行完成后，再访问一下们可以看到更新了。

这样一行本地命令，就可以完成服务器后端的更新，而整个过程的脚本都是 AI 完成的。

四、小结

回顾一下这一章做了什么：我们把闪讯后端从开发机搬到了云端，让它变成了一个真正的、任何人都能访问的在线服务。整个部署体系由四个脚本组成，各司其职：

脚本 在哪里跑 做什么
build.py 本地电脑 交叉编译 + 上传 + 自动重启远程服务
env_check.sh 服务器 检测运行环境是否就绪
db.sh 服务器 数据库管理（迁移/重置/状态查看）
flash.sh 服务器 服务管理（启停/日志/注册系统服务）

日常更新只需要一行命令：

python scripts/deploy/build.py root@你的服务器IP

它会自动编译、停止旧服务、上传新二进制、重启。整个过程不需要 SSH 登录服务器。

从"本地 cargo run + 局域网聊天"到"云端 7×24 在线 + 公网可达"，中间隔的不是什么高深技术，而是一系列具体的、可自动化的步骤。而这些步骤，现在都被脚本封装好了。

下一章，我们来处理客户端的部署：把 Flutter app 打包成 APK，连接公网服务器，让你的朋友真正用上闪讯。

小思考: 为什么不能直接把代码丢到服务器里跑

你可能会想：把 Rust 源码传到服务器上，然后 cargo run 行不行？ 理论上可以，但实际上欠佳。原因有两个：

  • 编译太吃资源。Rust 编译器是出了名的"慢但精"，编译一个中等项目需要 2~4G 内存。我们的服务器只有 2G，跑着 MySQL 和 PostgreSQL 之后剩余不到 1G，编译到一半就会被系统杀掉。
  • 没必要在服务器上装开发工具。服务器的职责是"跑服务"，不是"写代码"。装一堆编译工具既浪费空间又增加安全风险。而且服务器资源可谓寸土寸金，被必要做这些没有太大意义的事。

所以正确的做法是：在本地编译好，把编译产物（一个二进制文件）上传到服务器。

这就像开餐厅：你不会在店里现磨面粉、现榨油。你在工厂把半成品做好，运到店里直接加热上桌。服务器就是那个"店"，你的开发电脑就是那个"工厂"。
