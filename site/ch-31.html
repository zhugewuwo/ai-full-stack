桢干#2 ｜ 消息功能扩展

一条消息发出去之后，故事才刚刚开始。

闪讯的消息能发、能收、能存，但发出去之后就像泼出去的水——你不能撤回它，不能回复它，不能删除它，甚至不能复制它。长按一条消息，什么都不会发生。这一章补齐消息的"售后服务"：长按菜单、复制、撤回、引用回复、本地删除、多选批量删除。

长按菜单 消息撤回 引用回复

一、需求分析

消息操作看起来是一堆零散的小功能，但它们共享一个入口（长按菜单）和一套状态管理模式（ChatCubit 扩展）。真正的复杂度藏在细节里：撤回需要前后端协调，引用需要在 extra 里嵌套数据，删除需要"本地不可见但不影响对方"的语义，多选需要整个列表切换交互模式。

1. 交互链分析

六个场景，从"长按弹出菜单"到"批量删除"，覆盖消息的完整操作生命周期：

长按菜单

用户故事：作为用户，我长按一条消息，想看到可以对它做什么。

左侧 右侧

长按消息气泡，弹出微信风格的深色气泡菜单。菜单项不是固定的——文本消息有"复制"，图片没有；自己发的消息有"撤回"（2 分钟内），别人的没有；系统消息不弹菜单。菜单定位在气泡附近，左侧消息左对齐，右侧消息右对齐，不遮挡消息内容。

菜单项 文本消息 图片/视频/文件 自己发的 别人发的
复制 ✅ ❌ ✅ ✅
引用 ✅ ✅ ✅ ✅
撤回 ✅ ✅ ✅（2分钟内） ❌
删除 ✅ ✅ ✅ ✅
多选 ✅ ✅ ✅ ✅

消息撤回

用户故事：作为用户，我发错了消息，想在 2 分钟内撤回。支持重新编辑以便用户基于之前消息修改。

点击"撤回"后，前端发 HTTP 请求到后端。后端做三件事：校验是否本人发的、是否在 2 分钟内、标记 status=1。然后通过 WS 广播 MESSAGE_RECALLED 帧给会话所有成员。所有客户端收到后，将该消息替换为灰色居中标签："你撤回了一条消息"或"对方撤回了一条消息"。

撤回不是删除。消息行还在，seq 连续性不受影响，只是内容被替换了。这和微信的行为一致。撤回后还有一个容易忽略的问题：退出聊天页再进来，撤回状态会不会丢？如果只改内存不写本地，答案是"会丢"。所以撤回后必须同步写入 LocalStore，把撤回后的消息（带 _recalled: true 标记）持久化。

引用回复

用户故事：作为用户，我想回复某条特定消息，让对方知道我在说哪条。

引用预览条 引用气泡

点击"引用"后，输入框上方出现引用预览条，显示被引用消息的发送者和内容摘要。用户输入回复内容后发送，消息的 extra 字段携带 reply_to 对象。对方收到后，消息气泡下方嵌套一个引用气泡，显示被引用的原消息。

引用不需要后端改动。extra 是 JSONB 字段，前端往里塞什么后端照存不误。引用信息是"快照"而非"引用"——存的是发送时的内容摘要，不是消息 ID 的实时查询。原消息被撤回后，引用气泡里的内容不会变。

复制

用户故事：作为用户，我想复制一条文本消息的内容。

点击"复制"，将消息 content 写入系统剪贴板，底部弹出 SnackBar "已复制"。只有文本消息显示复制选项，图片/视频/文件不显示。一行代码的事，但没有长按菜单就做不到。

本地删除

用户故事：作为用户，我想删除某条消息，不想再看到它。

点击"删除"，弹出底部确认弹窗。确认后将消息 ID 写入本地回收站表（local_trash），消息从列表中消失。不通知服务端，不影响对方。

气泡框 确认弹窗

多选模式

用户故事：作为用户，我想批量删除多条消息。

点击"多选"进入多选模式。整个列表的交互模式切换：每条消息左侧出现勾选框，底部输入框替换为操作栏（删除 + 取消），整行点击都响应选择。勾选多条后点击"删除"，弹出确认弹窗，确认后批量标记本地已删除。

多选模式是一个全局状态切换，由 ChatCubit 的 isMultiSelect 标志控制。进入多选时记录初始选中的消息 ID，退出时清空。勾选框不在 MessageBubble 内部——它在 ChatPage 层面用 Row 包裹，这样系统消息和撤回消息也能被选中。

2. 逻辑流程树

消息撤回：前后端协调

时刻 事件 处理
T1 用户点击"撤回" ChatCubit.recallMessage → HTTP POST
T2 后端校验 是否本人、是否 2 分钟内、是否已撤回
T3 校验通过 UPDATE status=1 + WS 广播 MESSAGE_RECALLED
T4 所有客户端收到帧 _replaceWithRecalled → 内存替换 + 写入 LocalStore
T5 会话预览更新 _syncConversationPreview → onConversationChanged

撤回的发起者也会收到 MESSAGE_RECALLED 帧（后端广播给会话所有成员，包括自己）。前端根据 sender_id 判断展示文案："你撤回了一条消息"还是"对方撤回了一条消息"。

为什么发起者也要收帧？因为用户可能在多个设备登录。A 设备撤回，B 设备也要看到撤回效果。统一走 WS 推送，不需要特殊处理多端同步。

引用回复：数据流

时刻 事件 处理
T1 用户点击"引用" ChatCubit.setReplyTo → emit replyTo
T2 输入框上方显示预览条 ReplyPreviewBar 渲染
T3 用户发送消息 sendMessage 读取 state.replyTo，构建 extra.reply_to
T4 发送完成 clearReplyTo，预览条消失
T5 对方收到消息 解析 extra.reply_to，MessageBubble 嵌套 ReplyBubble

extra.reply_to 的结构：

{
  "reply_to": {
    "message_id": "uuid",
    "sender_name": "张三",
    "content": "明天几点开会？",
    "msg_type": 0
  }
}

为什么存内容快照而不是只存 message_id？因为原消息可能被撤回或删除。如果只存 ID，引用气泡需要实时查询原消息，查不到就显示"消息已删除"。存快照更简单，引用气泡永远有内容可显示，不依赖原消息的存在。

本地删除：静默移除

时刻 事件 处理
T1 用户确认删除 ChatCubit.deleteMessage
T2 写入回收站 store.moveToTrash(messageId, 'message')
T3 内存过滤 messages.where(m.id != messageId) + emit
T4 会话预览更新 _syncConversationPreview

这里有两个体验细节：

第一，删除后不能调 loadMessages() 重新加载。重新加载会触发 Loading → Loaded 状态切换，整个列表闪一下。正确做法是在内存中过滤掉被删消息，直接 emit 新列表。用户看到的效果是消息"静默消失"，没有任何闪烁。

第二，删除后会话列表的最后一条消息预览要更新。如果删的是最后一条，会话列表还显示它的内容就不对了。ChatCubit 删除后调用 _syncConversationPreview，更新 LocalStore 里的会话预览，再通过 onConversationChanged 回调通知会话列表刷新。

二、后端实现

消息操作的六个功能里，只有撤回需要后端参与。复制、引用、删除、多选都是纯前端的事。引用回复复用已有的 extra JSONB 字段，后端照存不误。本地删除只操作客户端的 SQLite，服务端完全不知情。

所以后端这一节的代码量不大，但设计决策不少。一个看似简单的"撤回"接口，背后涉及权限校验、时间窗口、状态机、WS 广播、会话预览联动。下面按"协议定义 → 接口实现 → 广播与联动"的顺序展开。

1. 协议与状态机

proto 扩展

ws.proto 新增 MESSAGE_RECALLED 帧类型（第 17 个，从 0 编号）：

// ---> proto/ws.proto
enum WsFrameType {
  // ... 0~15 已有
  MESSAGE_RECALLED = 16;
}

message.proto 新增 MessageRecalled 消息体：

// ---> proto/message.proto
message MessageRecalled {
  string message_id = 1;
  string conversation_id = 2;
  string sender_id = 3;
  string sender_name = 4;
}

四个字段。sender_name 是为了群聊里直接展示"张三撤回了一条消息"，省去前端查昵称的开销。proto 修改后 cargo build 自动触发 build.rs 重新编译，前端的 protobuf_dart 也需要同步重新生成。

消息状态机

messages 表的 status 字段在项目初期就预留了，这次撤回用到了 1：

status 含义 查询行为 前端展示
0 正常 正常返回 正常气泡
1 已撤回 正常返回 灰色居中标签
2 已删除 过滤不返回 不展示

状态转换是单向不可逆的：0 → 1（撤回）、0 → 2（删除）。撤回后的消息仍然返回给客户端——因为 seq 是连续的，如果不返回这一行，客户端翻页时会发现 seq 有空洞，可能误以为消息丢失。

2. 撤回接口实现
POST /conversations/{conv_id}/messages/{msg_id}/recall
Authorization: Bearer {token}

Handler 七步顺序执行，任一步失败通过 AppError 返回对应 HTTP 状态码：

// ---> server/modules/im-message/src/routes.rs
async fn recall_message(
    State(state): State<AppState>,
    Path((conv_id, msg_id)): Path<(String, String)>,
    claims: Claims,
) -> Result<Json<Value>, AppError> {
    let user_id = claims.user_id;

    // 1. 查消息（同时校验 conversation_id，防止跨会话撤回）
    let msg = state.message_repo
        .find_by_id(&msg_id, &conv_id).await?
        .ok_or(AppError::not_found("消息不存在"))?;

    // 2. 校验是否本人发送
    if msg.sender_id != user_id {
        return Err(AppError::forbidden("只能撤回自己的消息"));
    }

    // 3. 校验时间窗口（2 分钟）
    if (Utc::now() - msg.created_at).num_seconds() > 120 {
        return Err(AppError::forbidden("超过撤回时限"));
    }

    // 4. 校验是否已撤回
    if msg.status == 1 {
        return Err(AppError::bad_request("消息已撤回"));
    }

    // 5. 标记撤回
    state.message_repo.update_status(&msg_id, 1).await?;

    // 6. 更新会话预览
    state.message_service.update_conversation_preview(&conv_id).await?;

    // 7. 广播 MESSAGE_RECALLED 帧
    let payload = MessageRecalled { message_id: msg_id, conversation_id: conv_id, ... };
    let frame = WsFrame::new(WsFrameType::MessageRecalled, payload.encode_to_vec());
    for uid in state.conversation_repo.get_member_ids(&conv_id).await? {
        state.ws_state.send(uid, frame.clone());
    }

    Ok(Json(json!({"message": "ok"})))
}

校验顺序的考量：先查消息（404）→ 再校验权限（403）→ 再校验时间（403）→ 最后校验状态（400）。顺序影响错误信息的准确性：消息不存在就说"不存在"，不说"没权限"；不是你的消息就说"没权限"，不说"超时了"。

find_by_id 的 WHERE 条件同时包含 id 和 conversation_id。安全考虑：防止用户猜测 message_id 撤回其他会话的消息。虽然后面还有 sender_id 校验兜底，但多一层过滤更安全。

3. 广播与联动

WS 广播范围：会话所有成员，包括撤回发起者自己。

为什么包括自己？两个原因：

  1. 多端同步：手机撤回，电脑也要看到效果。不广播给自己，其他设备不知道。
  2. 代码简洁：排除发起者需要多一个过滤条件。前端收到自己发起的撤回推送，_replaceWithRecalled 是幂等的（已撤回的消息直接跳过），不需要特殊处理。

会话预览更新：撤回后如果撤回的是最后一条消息，会话列表还显示原始内容就不对了。update_conversation_preview 重新查询最新消息生成预览：

// ---> server/modules/im-message/src/service.rs
pub async fn update_conversation_preview(&self, conv_id: &str) -> Result<()> {
    let latest = self.repo.find_latest_one(conv_id).await?;
    let preview = match latest {
        None => String::new(),
        Some(msg) if msg.status == 1 => "撤回了一条消息".to_string(),
        Some(msg) => match msg.msg_type {
            1 => "[图片]".to_string(),
            2 => "[视频]".to_string(),
            3 => "[文件]".to_string(),
            _ => msg.content.chars().take(50).collect(),
        },
    };
    self.conversation_repo.update_preview(conv_id, &preview).await
}

这个方法抽成 service 层而不是内联在 handler 里，因为未来管理员删除消息也需要调用它。

离线用户的最终一致性：如果撤回时对方离线，不会收到 MESSAGE_RECALLED 帧。但下次上线时 SyncEngine 增量同步会拉到 status=1 的消息，前端据此展示撤回提示。撤回的最终一致性有保障，只是离线用户有延迟。

4. 错误处理与测试

测试覆盖 8 个场景：正常撤回、超时、撤回别人的、重复撤回、撤回后查询（status=1 仍在列表）、撤回后会话预览更新、WS 广播验证（两端都收到帧）。

3. 消息撤回：前后端协调 + 本地持久化

三步：发请求 → 收推送 → 写本地。HTTP 成功后立即本地替换，不等 WS 推送：

// ---> flash_im_chat/lib/src/logic/chat_cubit.dart
Future<void> recallMessage(String messageId) async {
  await _repository.recallMessage(conversationId, messageId);
  _replaceWithRecalled(messageId, isMe: true);
}

WS 推送到达时再次调用，幂等跳过已处理的消息：

// ---> flash_im_chat/lib/src/logic/chat_cubit.dart
void _replaceWithRecalled(String messageId, {required bool isMe}) {
  final updated = messages.map((m) {
    if (m.id == messageId) {
      if (m.isRecalled) return m; // 幂等：已处理过直接跳过
      final extra = <String, dynamic>{'_recalled': true};
      if (isMe && m.type == MessageType.text) {
        extra['_original_content'] = m.content; // 保存原始文本供重新编辑
      }
      return m.copyWith(
        content: isMe ? '你撤回了一条消息' : '${m.senderName}撤回了一条消息',
        extra: extra,
      );
    }
    return m;
  }).toList();
  // emit + 写入 LocalStore + 同步会话预览
}

撤回后 MessageBubble 检测 _original_content，显示蓝色"重新编辑"按钮，点击将原始内容填入输入框。

幂等的重要性：_replaceWithRecalled 被调用两次（HTTP 后 + WS 推送）。不做幂等判断，第二次会把 _original_content 覆盖为"你撤回了一条消息"。

5. 本地删除和多选模式

本地删除后，不能调 loadMessages()（会触发 Loading → Loaded 状态切换），正确做法是内存过滤 + 直接 emit：

// ---> flash_im_chat/lib/src/logic/chat_cubit.dart
Future<void> deleteMessage(String messageId) async {
  final store = _store ?? _repository.store;
  await store.moveToTrash(messageId, 'message');
  final updated = messages.where((m) => m.id != messageId).toList();
  emit(current.copyWith(messages: updated));
  _syncConversationPreview(store, updated);
}

删除前弹确认弹窗使用 tolyui 中的 tolyui_feedback_modal ,便于实现类似微信的底部弹框操作选项。另外红色"删除"按钮只在弹窗里出现，气泡菜单里保持白色。删除后通过 _syncConversationPreview 更新会话列表预览 + onConversationChanged 回调通知刷新。

进入多选后，ChatPage 整体变形：每条消息左侧滑入勾选框，底部输入框替换为操作栏。

四、本章小结

这一章做了六件事，但本质上只做了一件：给消息加上"售后服务"。发出去的消息不再是泼出去的水，用户可以撤回它、回复它、删除它、批量处理它。

存档点 tag 提交点
消息操作 v0.19.0 commit

技术上，这一章的特点是"改动面广但改动深度浅"。不新建模块，不改架构，所有代码集中在 flash_im_chat 内部。ChatCubit 从 200 行膨胀到 400 行，但每个方法都很短，职责清晰。长按菜单是一个独立的 Overlay 组件，和 ChatPage 通过回调解耦。引用回复是三个小组件的协作。本地删除复用了上一章建好的 local_trash 基础设施。

有几个设计决策值得回顾：

  • 撤回用 extra 标记而不是 MessageStatus 枚举。发送状态和内容状态是两个维度，不应该混在一起。extra: {'_recalled': true} 灵活且不侵入已有逻辑。
  • 删除后静默移除而不是重新加载。一个 emit 的区别，但用户体验天差地别。从 ChatLoaded 到 ChatLoaded，BlocBuilder 只做 diff；从 ChatLoading 到 ChatLoaded，整个列表重建。
  • 引用存快照而不是存引用。原消息可能被撤回或删除，存快照保证引用气泡永远有内容可显示。代价是原消息修改后引用不会更新，但消息本身就不支持编辑，所以没有这个问题。
