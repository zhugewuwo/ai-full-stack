桢干#5 ｜ 养护根基，虫害不生

治未病者，不治已病。

《黄帝内经》里有句话：上工治未病，不治已病。意思是：高明的医生在病还没发作时就治好了，而不是等病发了才去治。

软件项目也是一样。大多数团队的日常是：写功能、发版本、出 bug、修 bug、继续写功能。代码质量的维护被动地依赖 "出了问题再说" 。但真正让项目长期健康成长的，不是修 bug 的速度，而是根系在良好的土壤中，来避免 bug 的滋生的。常见的"土壤恶化"征兆有：

  • 不敢动：某个文件 2000 多行，大家都知道该拆，但谁也不愿意动，因为不知道改了会不会坏
  • 改一处崩三处：修了一个 bug，结果引入了两个新 bug，因为模块之间的依赖关系不透明
  • 只加不减：新功能不断往同一个类里塞，因为"放这里最方便"，文件越来越胖
  • 调试靠 print：出了问题就加 print，修完了忘删，控制台全是噪音
  • 新人上手慢：接手一个模块，要花半天时间搞清楚"这个文件到底在干什么"

这些征兆单独看都不致命，但它们会互相叠加。由于不敢删掉已有代码，所以只加不减，只加不减所以越来越难懂，越来越难懂所以更不敢动。恶性循环一旦形成，每次迭代都在给未来埋雷。这一章我们将来聊一聊如何养好这片土壤。

一、从报告到行动

发现问题是第一步，但发现之后怎么办？体检报告列了 13 个问题，不可能一次全修。需要判断哪些值得现在动手，哪些可以等。我们选了 ChatCubit 作为第一个治理目标，因为它是聊天模块的核心，改动频率最高，痛感最强。

1、问题在哪

体检报告里，ChatCubit 被标记为 🟡 一般问题：

chat_cubit.dart 773 行，30+ 个方法，承担了消息收发、文件上传下载、撤回、置顶、多选、转发、已读回执等所有职责。

"职责过多"四个字说起来轻巧，但它意味着：

  • 加一个新功能（比如语音消息），你要在 773 行的文件里找到合适的位置插入
  • 改一个 bug（比如撤回后预览没更新），你要理解整个文件的上下文才能确定影响范围
  • 新人接手这个模块，第一反应是"这文件也太长了"

体检报告给出的处方是"拆分为 mixin"。但怎么拆？拆完怎么保证没改坏？

2、为什么不能直接动刀

"不就是把方法从一个文件搬到另一个文件吗？"

表面上是这样。但 ChatCubit 不是一个简单的工具类，它是一个有状态的对象，内部有 5 个 Stream 订阅、多个 Timer、一个 pending 消息队列。方法之间有隐式依赖：

  • sendMessage 往 _pendingMessages 里写数据，_handleMessageAck 从里面读
  • _handleIncomingMessage 收到消息后调 _reportReadSeq
  • recallMessage 修改消息内容后要同步写缓存、更新会话预览

这些依赖关系编译器看不到。你把方法搬到 mixin 里，编译通过了，但运行时某个状态没同步到，bug 就埋下了。而且这种 bug 不会立刻暴露，可能要在特定时序下才会触发。

所以结论是：先织网，再动刀。

3、单元测试的必要性

很多人觉得"写测试"是锦上添花的事，功能都做不完，哪有时间写测试。但在重构场景下，测试不是锦上添花，是救命绳。

没有测试的重构是什么体验？改完了，编译通过了，你心里没底，只能打开模拟器一个个功能点过。发消息试试、撤回试试、置顶试试、多选删除试试……手动验证 14 个场景，每次改动都要过一遍，半小时就没了。而且手动测试会遗漏，你可能忘了测"发送超时"这个边界情况，bug 就这样上线了。

有测试的重构是什么体验？改完了，跑一遍测试，十几秒出结果，14 个全绿，收工。如果有红的，错误信息直接告诉你哪个行为变了，定位到具体的场景，修复范围极小。

测试的价值不在于"证明代码是对的"，而在于"让你敢改代码"。对于一个 772 行的文件要拆成 5 个文件这种大改动，没有测试兜底，谁都不敢下刀。

说实话，之前前端的开发流程是偷懒了。后端有 Python 脚本做接口测试，每次改完跑一遍就知道接口是否正常。前端却一直裸奔，没有单元测试，全靠手动在模拟器上点。这次重构让我意识到，在一个良好的编码流程里，单元测试不是可选项，是必要环节。特别是状态管理层这种核心逻辑，输入输出明确，非常适合写测试。后续新增的 Cubit 都会同步补上测试，不再欠这笔债。

二、织网：测试基础设施

决定要拆 ChatCubit 之后，第一件事不是动代码，而是搭测试。测试是安全网，网织好了才能放心走钢丝。但要给 ChatCubit 写测试，首先得解决一个前提问题：它当前的代码根本不可测试。

次重构虽然不是新功能，但我们依然走了完整的开发工作流：需求分析（analysis.md）→ 设计（design.md）→ 任务拆解（tasks.md）→ 逐步执行。分析阶段列出了 14 个需要验证的场景，设计阶段确定了接口抽取 + mock 层 + TestFixtures 的技术方案，任务清单把整个过程拆成了 13 个可逐步执行的步骤。即使是重构，也值得用结构化的方式来做，而不是"想到哪改到哪"。

模块名 需求分析 前端设计 前端任务

1、无法完成的测试窘境

前端测试有一个天然的窘境：它依赖的东西太多了。

想测 ChatCubit 的"发送消息"逻辑，你需要：一个能连接的 WebSocket 服务、一个能响应的 HTTP 后端、一个本地数据库。这三样东西在开发机上跑着的时候，你可以手动点一下验证。但要写成自动化测试，你得把这三样东西都启动起来，还得保证它们的状态是干净的、可预测的。

特别是本地数据库。我们用的是 drift + SQLite，它依赖原生平台的 SQLite 库。flutter test 跑在纯 Dart VM 上，根本没有原生环境，SQLite 压根加载不起来。也就是说，只要你的代码里直接引用了 LocalStore 的真实实现，测试就会在启动阶段直接崩溃，连跑都跑不起来。类似的还有摄像头、扫码、文件选择器这些硬件相关的能力，测试环境里压根不存在这些东西。

这就是为什么很多前端项目"没有单元测试"。不是不想写，是写不了。代码和外部环境耦合太紧，脱离了真实环境就跑不起来。解决这个窘境的思路是：把"外部环境"从代码里抽离出来，用替身代替。

2、 mock 模拟测试的可行性

先说什么是 mock，说白了就是 "替身"。电影里有替身演员，不需要真的从楼上跳下去，只需要看起来像跳了就行。测试里的 mock 也一样：不需要真的发 HTTP 请求、真的连 WebSocket，只需要模拟"如果发了请求，会返回什么结果"。

比如测试"发送图片"这个场景，我们不需要真的上传一张图片到服务器，只需要告诉 mock："当调用 uploadImage 时，返回一个 ImageUploadResult"。ChatCubit 拿到这个结果后的处理逻辑，和真实上传返回的结果是一样的。这样前端的 流程 就可以测试是不是通畅的。

有人会问：测试里用的是假数据，真实环境里数据千变万化，mock 测试能说明什么问题？

关键在于理解我们测的是什么。ChatCubit 的职责是"状态管理"：给它一个输入（消息列表、WS 帧、用户操作），它产出一个输出（新的 state）。这个输入到输出的映射关系是确定的，和数据的具体内容无关。

比如"收到 ACK 后消息状态变为 sent"这个行为，不管消息内容是"你好"还是一张图片，逻辑都是一样的：找到 pending 消息，替换 ID，改 status。mock 数据只需要满足"有一条 pending 消息"这个前提条件，具体内容是什么不影响测试的有效性。换句话说:

我们测的不是"数据对不对"，而是"逻辑对不对"。数据对不对是后端接口测试的事（Python 脚本已经覆盖了），逻辑对不对是单元测试的事。两者各管一层，互不替代。

这就引出了 单元测试 和 集成测试 的这两个不同的领域。单元测试验证的是"这个零件本身工作正常"，集成测试验证的是"零件组装在一起能跑通"。我们的 Python 接口测试脚本就是一种集成测试：它真的发 HTTP 请求到后端，验证整条链路。而 ChatCubit 的单元测试是把它从链路中摘出来，单独验证它的状态转换逻辑。

两者不是替代关系，是互补关系。单元测试跑得快（12 秒）、定位精准（哪个场景红了一目了然），适合在开发过程中频繁运行。集成测试跑得慢（要启动后端）、覆盖面广（能发现接口变更导致的问题），适合在发版前跑一遍。先有单元测试保证零件质量，再有集成测试保证组装正确，两层防线叠加才稳。

3、可测试性改造

但要用 mock，代码本身得支持"把真实依赖替换成替身"。这件事之所以可行，是因为前后端分离的架构：前端只在意"能不能拿到数据"，不在意"数据是谁给的"。不管是真实的后端接口返回的，还是 mock 对象伪造的，只要数据结构一致，前端的处理逻辑就是一样的。

但 ChatCubit 原来直接依赖 MessageRepository（一个具体类），内部会发 HTTP 请求。你没法把一个具体类换成替身，除非它依赖的是接口。

// 之前：直接依赖具体类
class ChatCubit {
  final MessageRepository _repository;
}

// 之后：依赖抽象接口
class ChatCubit {
  final IMessageRepository _repository;
}

一行改动，ChatCubit 就变得可测试了。测试时注入 mock，生产时注入真实实现。这不只是为了测试，也是为了扩展性。未来如果要换数据源，只需要写一个新的实现，ChatCubit 一行不用改。

另外 ChatCubit 有三个外部依赖，每个需要不同的 mock 策略：

依赖 Mock 方式 原因
IMessageRepository mocktail 自动 mock 纯接口，方法多，手写太累
WsClient 手写 FakeWsClient 需要精确控制 stream 时序
LocalStore mocktail 自动 mock 已是抽象类，直接 mock

其中 FakeWsClient 是关键。ChatCubit 的很多行为是由 WS 事件驱动的（收到消息、收到 ACK、收到撤回通知），测试时需要精确控制"什么时候触发什么事件"。FakeWsClient 暴露 StreamController，测试代码往里面 add 一个帧，ChatCubit 就会响应：

class FakeWsClient extends WsClient {
  final chatMessageController = StreamController<WsFrame>.broadcast();
  final messageAckController = StreamController<WsFrame>.broadcast();
  // ...
}

// 测试中：模拟服务端返回 ACK
fakeWs.messageAckController.add(ackFrame);
// ChatCubit 收到 ACK，更新消息状态
4、测试数据工厂

mock 层解决了"怎么隔离外部依赖"的问题，但还有一个问题：测试里用的假数据，怎么保证和真实数据结构一致？

如果你在测试里手写一个 Map 来模拟消息，真实代码里的 Message 类改了字段名，测试还是能通过（因为它用的是旧结构），但生产代码已经坏了。这种"测试绿了但代码是坏的"比没有测试还危险。

解决方案：用工厂方法构造测试数据，工厂方法使用和生产代码相同的模型类。

class TestFixtures {
  static Message message({
    String id = 'msg_1',
    String content = 'hello',
    int seq = 1,
  }) => Message(id: id, content: content, seq: seq, ...);
}

如果 Message 类新增了一个 required 字段，TestFixtures.message() 编译就会报错，强制你同步更新。数据一致性靠编译器保证，不靠人记忆。

基础设施就绪后，列出 ChatCubit 的所有核心行为，每个写一个测试。不追求 100% 覆盖率，但要覆盖所有用户可感知的行为路径：

# 场景 验证什么
1 加载消息 emit 正确的状态序列
2 发送文本 本地消息立即出现，WsClient 被调用
3 收到 ACK ID 替换，status 变为 sent
4 发送超时 10 秒后 status 变为 failed
5 接收消息 WS 帧解析正确，列表更新
6 主动撤回 消息内容变为撤回文案
7 置顶 pinnedMessages 列表更新
8 多选删除 选中的消息从列表移除
9 引用回复 replyTo 正确设置和清除
10 收到撤回 WS 帧触发后内容变更
11 已读回执 peerReadSeq 更新
12 加载更多 旧消息合并，去重正确

14 个测试跑一遍 12 秒（其中超时场景要等 11 秒），全绿。这意味着 ChatCubit 当前的所有行为已经被固定下来了。接下来不管怎么拆，只要测试还是绿的，行为就没变。

三、Mixin 拆分

测试全绿，可以放心搬代码了。拆分的原则是按职责域划分：每个 mixin 只管一件事，通过抽象 getter 访问共享状态，不直接依赖 ChatCubit 的内部实现。

1、拆分策略

772 行代码，30+ 个方法，按职责域分成 5 个文件：

flash_im_chat/lib/src/logic/
├── chat_cubit.dart          ~250 行（核心：消息加载/发送/接收/ACK）
├── chat_ws_mixin.dart       ~45 行（WS 订阅注册/取消 + 抽象回调）
├── chat_file_mixin.dart     ~270 行（图片/视频/文件上传下载）
├── chat_pin_mixin.dart      ~100 行（置顶 + 撤回）
└── chat_select_mixin.dart   ~50 行（多选模式）

每个 mixin 通过抽象 getter 访问 ChatCubit 的字段，保持封装性：

mixin ChatFileMixin on Cubit<ChatState> {
  IMessageRepository get repository;  // 抽象 getter
  WsClient get wsClient;
  String get conversationId;
  // ...

  Future<void> sendImageFromFile(String filePath) async {
    // 通过 getter 访问，不依赖具体实现
    final result = await repository.uploadImage(filePath);
    // ...
  }
}

ChatCubit 本体实现这些 getter：

class ChatCubit extends Cubit<ChatState>
    with ChatWsMixin, ChatFileMixin, ChatPinMixin, ChatSelectMixin {

  @override
  IMessageRepository get repository => _repository;
  @override
  WsClient get wsClient => _wsClient;
  // ...
}
2、WS 订阅集中管理

原来 5 个 StreamSubscription 散落在构造函数和 close 里，容易漏掉 cancel。拆出 ChatWsMixin 后，注册和取消集中在一个地方：

mixin ChatWsMixin on Cubit<ChatState> {
  void initWsListeners() {
    _wsSubs.addAll([
      wsClient.chatMessageStream.listen(onChatMessage),
      wsClient.messageAckStream.listen(onMessageAck),
      wsClient.messageRecalledStream.listen(onMessageRecalled),
      wsClient.pinChangedStream.listen(onPinChanged),
      wsClient.readReceiptStream.listen(onReadReceipt),
    ]);
  }

  void disposeWsListeners() {
    for (final sub in _wsSubs) { sub.cancel(); }
    _wsSubs.clear();
  }
}

构造函数只调 initWsListeners()，close 只调 disposeWsListeners()。新增 stream 监听只需在 mixin 里加一行。回调通过抽象方法分发给具体实现，职责清晰。

3、每拆一步，跑一遍测试

拆分不是一次性完成的，而是分步进行：

  1. 创建 ChatFileMixin，搬移文件操作方法 → 跑测试 → 14 个全绿 ✅
  2. 创建 ChatPinMixin，搬移置顶和撤回 → 跑测试 → 14 个全绿 ✅
  3. 创建 ChatSelectMixin，搬移多选模式 → 跑测试 → 14 个全绿 ✅
  4. 创建 ChatWsMixin，集中订阅管理 → 跑测试 → 14 个全绿 ✅

每一步都有测试兜底。如果某一步搬错了（比如忘了把某个状态同步过去），测试会立刻变红，你知道问题出在刚才这一步，修复范围很小。

四、成果与沉淀

这里以一个大文件的拆解优化过程为例，介绍了前端单元测试的意义，以及对现有功能的重构流程。在未来的版本迭代中，每隔几个版本，可以对项目进行一次大体检，尽可能减少滋养虫害的温床。另外，在体检和治理完成后，可以把经验教训沉淀为 规范 ，它可以让树木生长的土壤更加肥沃。这种正向的生长反馈，才是一种可持续发展。

1、数据对比

经过织网、动刀、优化三个阶段，回头看看收获了什么。先看硬指标，重构前后的核心数据变化：

指标 重构前 重构后
chat_cubit.dart 有效代码 772 行 250 行
文件数 1 5（本体 + 4 个 mixin）
单文件最大行数 772 ~270
单元测试 0 14 个场景
可独立测试的单元 1 5

772 行变成 250 行，不是删了代码，而是把代码按职责分散到了各自的文件里。总代码量基本没变，但每个文件只管一件事，认知负担大幅降低。

2、日常开发体感

数字上的变化是表面的，真正的收益体现在日常开发中：

  • 加功能变简单了。 下次要加"语音消息"，只需要在 ChatFileMixin 里加一个 sendVoiceFromFile 方法。文件操作相关的逻辑都在这个 mixin 里，上下文清晰，不需要在 772 行的文件里翻来翻去找位置，不需要担心改动影响到撤回或置顶的逻辑。而且因为有测试，加完新方法后跑一遍，确认没有破坏已有行为，就可以放心提交。
  • 改 bug 变快了。 如果置顶功能出了问题，直接打开 ChatPinMixin 的 100 行代码，问题一定在这里面。不需要理解整个 ChatCubit 的上下文，不需要在脑子里维护 30 个方法的调用关系。100 行代码从头到尾读一遍也就两分钟，bug 在哪里一目了然。
  • 新人上手变容易了。 看到 5 个文件名就知道这个模块管什么事：chat_file_mixin（文件操作）、chat_pin_mixin（置顶撤回）、chat_select_mixin（多选模式）、chat_ws_mixin（WS 订阅）、chat_cubit（核心消息流）。想了解某个功能怎么实现的，打开对应文件就行，不需要读完 772 行才能形成全局认知。
  • 重构变安全了。 14 个测试在那里守着，任何改动 12 秒就能验证。以后再想优化某个 mixin 的内部实现（比如把文件上传改成分片上传），不需要手动验证所有场景，跑一遍测试全绿就行。这种"改完立刻知道对不对"的安全感，是之前裸奔时完全没有的。
3、经验沉淀为规范

重构做完了，但如果不把经验记录下来，下次遇到同样的问题还是会犯同样的错。所以最后一步是把这次踩过的坑、总结出的原则写入 steering 文件，让它成为项目的长期记忆。

Flutter 代码风格（.kiro/steering/flutter/code-style.md）：

## 代码质量

- 单个文件超过 500 行考虑拆分，可以基于 mixin 合理拆分职能。
- 3 个以上参数总是成组传递时，提取为值对象（如 ChatContext）。
- 重复出现的转换逻辑用 extension 封装（如 `Message.toCached()`）。
- async 操作后使用 BuildContext 前必须检查 mounted。

这些规范不是凭空规定的，是踩过坑之后总结的。写进 steering 后，AI 在日常开发中会自动遵守，同类问题不会再出现。

本章小结

回顾这两篇的内容，我们做了一件事：把一个"不敢动"的模块变成了一个"随便改"的模块。772 行变成 250 行只是表象，真正变化的是我们和这段代码的关系——从"小心翼翼绕着走"变成了"放心大胆往里加"。授之以鱼，不如授之以渔，其他的大文件也可以按照这种流程，让 AI 尝试优化一下结构。

这个过程中有几个认知上的转变值得记住：

  • 测试不是负担，是资产。 用写 14 个测试花了大概20分钟，但它们会在未来每一次改动中持续发挥价值。每次跑测试的 12 秒，省下的是耗时的手动验证和不确定性带来的焦虑。投入一次，收益无限次。
  • 重构不是额外的工作，是开发的一部分。 很多人把重构当作"有空了再做"的事，结果永远没空。这次我们把重构当作一个正式的版本（v0.21.0），走完整的工作流，有分析、有设计、有任务清单。它和新功能开发享有同等的地位，因为它对项目健康的贡献不亚于任何一个新功能。
  • 规范是活的，不是死的。 steering 文件里的每一条规则都有它的"出生故事"——是某次体检发现的问题、某次重构踩的坑。它不是某个人拍脑袋写的教条，而是项目在成长过程中自然沉淀出来的智慧。项目在长大，规范也在长大。

最后想说的是：代码质量不是一个终点，而是一个持续的过程。今天的 250 行，明天加了新功能可能又变成 400 行。重要的不是某个时刻的数字，而是你有没有能力在它膨胀时再次治理它——有测试兜底、有规范指引、有工作流保障。这种能力，才是真正的"根基"，才是成长真正的可能性。
