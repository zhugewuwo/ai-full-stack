经络#6 ｜ 生命的时间跨度

万物皆有生灭，最隐蔽的混乱，不是逻辑错误，而是时间错位。

经络卷 从简单地认识分工协作，到认识事物之间的关系，然后理解模块的物理边界，已经基本描绘了一颗种子生长的路径。本卷的最后一篇，我们将在此承上启下，跳出当前的视野范围，站在一个完整 IM 系统的视角，体会各个功能、模块、流程的生命周期全景图。

一、生命周期

代码的组织有两个维度：空间 和 时间 。 空间维度决定了代码"放在哪里"，比如文件、目录、模块包这样的磁盘空间位置。但系统运行起来后，还有一个同样重要的维度：时间。

万物都有自己的生命跨度，一朵花从种子发芽到凋谢，一场雨从乌云聚集到天晴，一颗星从尘埃中凝聚到最终坍缩。在时间的横轴上，某种现象周而复始地重复出现，表现出周期性。这种有一定时间跨度、反复出现的相似现象，我称之为事物的 生命周期 性。

1. 生命跨度的长短

事物存在的时间，有不同的跨度范围。比如你去一座城市旅游：

  • 从开始到结束用了 7 天；
  • 到这个城市的博物馆参观，从进门到出来，两三个小时。
  • 去路边面摊吃了一碗面，坐下、吃完、抹嘴走人，十几分钟。
  • 临走前给老板竖个大拇指说"好吃"，这个交互几秒钟就结束了。

这些事物过程从天到几秒钟，在同一趟旅程中交织。城市不会因为你离开就消失，你也不会因为一碗面吃完就结束旅程。每种东西有自己的生死节奏，互不干扰，但又彼此依赖。

软件系统也是如此。一个应用里同时存在着，跨度从毫秒到数天的各种对象，它们各自出生、各自死亡，但在存活期间需要协同工作。理解这些不同的跨度，是看透软件系统的重要一环。

一棵树能活几百年，一只蜉蝣只活一天，这是由事物本身的 基因 所决定的。之前我们把功能网络，比喻成一个应用产品的基因，也就是说功能需求本身就决定着事物生命的跨度。

2. 生命跨度的周期性

旅游不是一辈子只去一次。你可能每年都去旅游，每次都经历"出发 → 游玩 → 回家"的过程。每一趟旅程都是独立的，但模式是相似的，这就是周期性。软件中也处处可见：

  • 用户登录、使用、退出，下次再登录，每次会话都是一个独立的生命，但结构相似。
  • 打开聊天页、聊天、关闭，再打开另一个聊天页，每个页面也是一个独立的生命，但模式相同。
  • 发一条消息、再发一条，每次发送都是一个瞬间的生命，但流程一致。

不同跨度的生命，周期的频率也不同。会话可能一天只有一两次，页面可能几分钟就一次，消息发送可能几秒钟就一次。频率越高，每一轮的创建和销毁就越需要轻量。你不会为了发一条消息就建一个数据库连接，也不会为了打开一个页面就重新登录一次。

周期性意味着同样的生命会反复出现。这带来两个重要的推论：

第一，每一轮生命都应该是干净的。

上一次会话的用户数据，不应该残留到下一次会话。上一个聊天页的滚动位置，不应该影响下一个聊天页。每一轮新生命开始时，状态应该是全新的。

第二，生命的开始和结束是资源管理的关键时刻。

用户登录后要初始化，拉取用户资料、加载缓存数据；退出时要清理，清除身份信息、释放内存。页面打开时要准备，加载数据、注册监听；关闭时要善后，释放控制器、取消订阅。

3. 生命跨度中的数据

每一段生命，都伴随着属于它的数据。用户从登录开始，用自己的身份和应用进行交互；退出登录时，取消了这个身份。用户在此期间的 Token、昵称、头像，都是和这次登录绑定的。
在此之内，用户打开一个聊天页，页面里的消息列表、滚动位置、输入框里正在打的那半句话，是和这个页面绑定的。用户点了一下"发送"，这条消息从构建到收到确认，也有属于它的临时数据。

数据的生命跨度，应该和它所服务的那段生命一致。

如果数据活得比它服务的生命更长，退出登录了，上一个用户的头像还显示在界面上。如果数据死得比它服务的生命更早，页面还在，数据已经被清掉了，用户看到一片空白。数据放错了位置，本质上就是放错了生命跨度。

但"生命结束"不等于"数据全部丢弃"。生命中的数据分两种：临时状态 和 持久记录。状态是运行时的、临时的，比如页面的滚动位置、搜索框里的关键词、表单中未提交的输入，生命结束就该消失。记录是需要留存的，比如聊天记录、用户偏好、没发出去的草稿，它们要在生命结束前持久化到数据库或本地存储，留给下一轮生命使用。

4. 生命跨度中的依赖

不同生命跨度的对象，在运行时不可避免地要协作。

  • 聊天页（短）需要读取用户信息（长），
  • 发送消息（瞬时）需要通过 WebSocket（长）传输。

这种协作就是依赖，而依赖在生命跨度的视角下，有一条天然的安全规则：

短命的依赖长命的，安全;
长命的依赖短命的，危险。

这不是一条人为规定的规则，而是生命跨度的必然推论：你依赖的东西如果比你先死，你就会引用一个不存在的东西。

那如果确实需要长命的通知短命的呢？比如 WebSocket 收到一条新消息，需要通知聊天页刷新。这时候不能让 WebSocket 直接持有聊天页的引用，而是用观察者模式：WebSocket 广播一个事件，聊天页订阅这个事件。页面打开时订阅，关闭时取消订阅。这样 WebSocket 不知道聊天页的存在，只知道有一个订阅列表——谁在谁听，谁走谁取消，互不牵连。

二、IM 前端生命跨度总览

理论讲完了，回到我们的 IM 项目。前端是用户直接接触的部分，各种对象的生死交织在一起，构成了整个应用的运行时全景。下面这张表，把一个完整 IM 前端中的典型对象，按生命跨度归类：

跨度 谁控制生死 典型对象 大概时长
全局级 操作系统 网络通道、路由、全局配置 数分钟~数天
会话级 登录 / 退出 用户身份、WebSocket、本地数据库、同步引擎、好友列表、会话列表 数分钟~数天
页面级 导航栈 push / pop 聊天页、编辑资料页、搜索页、登录流程 数秒~数十分钟
瞬时 单次调用 发送消息、上传文件、恢复会话、已读回执 毫秒~数秒
1. 全局级：地基

App 启动时，最先被创建的那些对象就是进程级的：HTTP 客户端、路由表、全局配置。它们从 main() 开始存在，直到进程被系统杀死才消失。不管用户登录还是退出，不管打开哪个页面，这些对象始终在那里。它们是整个应用的骨架，所有层级都依赖它们，但它们不直接依赖任何业务模块。

网络通道是所有网络请求的必经之路，登录、拉取资料、发送消息，都要通过它。路由表则定义了整个应用的页面地图：哪些路径对应哪些页面，页面之间怎么跳转。它在启动时就把所有路径注册好，之后只负责"指路"，不关心页面里发生了什么。

值得注意的是，网络通道需要在请求头里带上 Token，但 Token 是会话级的数据。全局级对象不能直接持有会话级数据，否则就违反了"长命依赖短命"的禁忌。解决方式是通过一个间接层去"读取"：每次发请求时，动态获取当前 Token。Token 变了、清空了，网络通道不需要知道，下次请求时自然拿到最新值。

2. 会话级：一段旅程

用户登录成功，一段新的旅程开始了。这是 IM 前端中最核心、也最复杂的生命跨度。
登录的那一刻，一系列对象同时苏醒：用户身份被存储，Token 被缓存，用户资料从服务端拉取。在一个完整的 IM 系统中，还会同时打开用户专属的本地数据库、建立 WebSocket 长连接、启动消息同步引擎、加载好友列表和会话列表。

退出登录的那一刻，这一切要彻底清理：清除 Token、关闭数据库、断开 WebSocket、停止同步、清空缓存。每个用户有自己独立的数据空间，切换账号时，上一个用户的数据不能残留。

会话级对象有一个重要特征：它们不跟随页面导航而重建。用户在聊天页、资料页、设置页之间来回切换，用户身份和 WebSocket 连接纹丝不动。但用户一退出登录，所有会话级对象都要彻底清理，为下一次登录腾出干净的空间。

这里还有一个容易犯的错误：把会话级数据放到全局级。比如把"当前用户信息"做成全局单例，用户退出登录后，单例里的旧数据还在，新用户登录后可能看到上一个用户的残留信息。容器可以是全局级的，但它管理的数据必须跟随会话的生死。

3. 页面级：一次驻足

每个页面都是一次独立的生命。打开时初始化，关闭时释放。编辑资料页打开时读取当前用户信息，关闭时释放表单控制器。聊天页进入时加载消息历史，离开时释放音频播放器。

页面级对象经常需要操作会话级状态。编辑资料页修改了昵称，要同步到用户身份管理器；聊天页发送消息，要通过 WebSocket 传输。这是"短命操作长命"，安全的。

但要注意一个时序问题：页面发起了一个网络请求，请求还在飞，用户已经按了返回键，页面死了。等请求回来，想更新界面，发现界面已经不存在了。所以异步操作回来后，第一件事是确认"我服务的那段生命还在吗"。这不是一个技巧，而是生命跨度的必然要求。

有些业务流程会跨越多个页面，比如登录流程：手机号页 → 验证码页 → 补充资料页。中间页面关了但流程还没结束。这本质上还是页面级，只是多个页面串联成了一条链，链的终点才是流程的终点。

4. 瞬时：一次呼吸

最短的生命，通常是一次网络请求或一次用户操作。发送验证码：

  • 构建请求、发出、拿到响应。
  • 修改头像：选图、上传、更新资料。
  • 恢复会话：读本地缓存、判断是否有效、决定跳转。

冷启动时的初始化任务也是瞬时的，比如检查本地是否有缓存的登录态。它的生命只有几百毫秒，但它的结果决定了后续所有页面的走向：有缓存就进主页，没缓存就去登录页。

瞬时对象的特点：用完即弃，不持有状态，失败后可以重试。

三、IM 后端生命跨度总览

后端没有页面，没有导航栈，但生命跨度的概念同样存在，只是换了一套表现形式。

跨度 谁控制生死 典型对象 大概时长
全局级 操作系统 数据库连接池、路由表、JWT 密钥、广播通道、消息分发器 数小时~数月
连接级 WebSocket 握手 / 断开 每条 WebSocket 连接、发送通道、广播订阅 数分钟~数天
请求级 HTTP 请求到达 / 响应返回 每次 API 调用、数据库查询、JWT 验证 毫秒~数秒
1. 全局级：服务器的骨架

服务启动时，最先创建的是数据库连接池、路由表、JWT 密钥、广播通道这些基础设施。它们从服务启动到服务终止，始终存在。所有请求、所有 WebSocket 连接都共享这些对象。

和前端一样，后端的全局级对象也是"无业务状态，被所有层级依赖"。数据库连接池不关心当前在处理谁的请求，JWT 密钥不关心当前在验证谁的 Token。它们只是工具，谁来都一样用。

在一个完整的 IM 后端中，全局级对象还包括：用户服务、认证服务、会话服务、消息服务、好友服务、WebSocket 状态管理器、消息分发器。这些服务本身不持有业务数据，只持有连接池的引用，所以可以安全地被所有请求共享。

后端有一个前端没有的有趣结构：连接池。数据库连接池是全局级的，但池中的每条数据库连接有自己的生命周期。空闲时回收，需要时创建，超时后断开。这种"池化"模式本身就是对生命跨度的精细管理：外层容器是长命的，内层资源是短命的、可复用的。

2. 连接级：一条长连接的生与死

后端没有前端的"会话级"（登录/退出是前端概念），但有一个前端没有的生命跨度：连接级。

一条 WebSocket 连接从建立到断开，就是一段独立的生命。它的生命历程是：

客户端发起握手 → 服务端等待认证（通常有超时限制） → 认证成功，注册到在线用户表 → 进入消息循环，收发消息 → 连接断开，从在线用户表移除，释放资源。

连接级对象嵌套在全局级容器中。服务端维护着一张"用户 → 连接列表"的映射表（全局级），每条连接在这张表中注册和注销。一个用户可以有多条连接（多端登录），第一条连接建立时广播"上线"，最后一条断开时广播"下线"。

连接级和前端的会话级是同一枚硬币的两面。用户在前端登录，前端建立 WebSocket 连接，后端开始一段连接级的生命。用户退出登录，前端断开连接，后端清理连接。两端的生命同步开始、同步结束，但各自管理各自的资源。

3. 请求级：一次问答

每个 HTTP 请求都是一段极短的生命。请求到达，处理器从全局级的共享状态中借用需要的服务，执行业务逻辑，返回响应，一切释放。

数据库连接池是全局级的，但每次查询从池中取一条连接，查询完自动归还。请求处理器本身不持有任何长期状态，它只是一个"借用者"：借用连接池查数据，借用 JWT 密钥验身份，借用消息服务发通知，用完即还。

前端发一个网络请求，后端就经历一次请求级的生命。前端的"瞬时"和后端的"请求级"是一一对应的。

4. 前后端的对照

前端和后端的生命跨度并不是一一对应的，但有清晰的映射关系：

前端 后端 共同点
全局级（网络通道、路由） 全局级（连接池、路由） 基础设施，无业务状态
会话级（用户身份、WebSocket） 连接级（WebSocket 会话） 由业务事件驱动生死
页面级（聊天页、编辑资料页） 无直接对应 前端特有，跟随导航栈
瞬时（发送消息、修改资料） 请求级（HTTP 处理器） 一次调用，用完即弃

后端没有"页面级"，因为服务器不关心用户在看哪个页面。但后端有前端没有的"连接池嵌套"：全局级的池管理着短命的、可复用的连接资源。

一条消息从发送到对方已读，跨越了前后端多个生命跨度：用户在聊天页（页面级）点击发送，触发一次瞬时操作，通过 WebSocket（会话级/连接级）传到后端，后端在一次请求级的处理中写入数据库、广播给对方。对方的 WebSocket 收到消息，通知聊天页刷新。整个过程中，每一环都在自己的生命跨度内完成自己的职责，互不越界。

四、小结

经络卷 走到这里，我们从最初的分工协作，到事物之间的关系网络，再到模块的物理边界，最后站在时间的维度上，看清了系统中各种对象的生死节奏。回头看看，当初那颗刚发芽的种子，已经长出了根系。

空间决定代码放在哪里，时间决定对象活多久。好的架构，两者都要清晰。数据放错了生命跨度，就像把旅途中的一次性雨衣塞进了永久衣柜，或者把护照丢在了景点的垃圾桶里。很多看似诡异的 Bug，追根溯源，都是时间错位。

到此为止，我们一直在用一个相对简单的项目来讲述这些认知。登录、用户资料、简单的聊天室，这些功能足以承载分层、模块化、生命周期这些概念，但还远远不是一个真正的 IM 系统。

接下来的旅程，我们将真正踏入 IM 的腹地：会话列表、消息收发、离线同步、好友关系、群聊、已读回执、消息撤回……每一个功能都会让前面学到的东西派上用场。你会发现，生命跨度不再是纸上的表格，而是每个细节都要面对的设计决策。

认知是地图，实践是旅途。地图画好了，该出发了。
