根芽#5 ｜ 解读项目，破除黑箱

显微镜看到的是细胞，X 光看到的是骨骼。理解一个系统，你需要的是 X 光。

上一篇建立了功能需求的流程方法论：分析、设计、任务、执行、验证、归档。AI 按照 tasks.md 写完了代码，你回来一看，几千行新代码出现在项目里。代码能跑，测试也过了。但这就结束了吗？你真的理解这些代码吗？

本章不仅是讲消息收发，这个具体功能的前端实现，更想聊一个更根本的问题：怎么看懂不是你写的代码。这个技能，无论是面对 AI 的产出、同事的代码、还是开源项目的源码，都一样适用。看懂代码，并不是说每一行都要完全读懂，而是要了解当前代码的结构、核心流程、实现方案，而不是技术细节。

一、黑箱一直都在

黑箱（Black Box）是 控制论 里的概念。 你有一个箱子，你能看到什么东西进去（输入），什么东西出来（输出），但你看不到里面发生了什么。你知道它能工作，但不知道它怎么工作。这其实和目前的 AI 编程非常像：

AI 写得代码能跑，测试能过，但你不理解它内部的结构和逻辑。

你知道输入（用户点发送）和输出（消息出现在屏幕上），但中间经过了哪些模块、数据怎么流转、状态怎么变化，你看不清。很多人觉得"代码黑箱"是 AI 编程带来的新问题。其实黑箱一直都在，只是以前我们习惯了，没把它当回事。

1. 传统编程里的黑箱

当你接手一个十万行的项目，打开代码，每一行都是别人写的。
或是也你用了一个开源项目库，出了 bug，想看源码排查。打开一看，几百个文件，几万行代码。
甚至你回看三个月前写的代码，可能已经不知道为什么这样写。

这些黑箱都指向了一个根源上的问题: 代码本身就人类和计算机沟通的文字记录。
它是天然对 人类阅读 不友好的，代码黑箱不是 AI 的专利。只要代码的意图不在你的记忆里，它对你就是黑箱。

写代码是正向翻译，把人的意图翻译成机器能执行的流程指令。读代码是反向翻译，倒推回人的意图。反向翻译永远比正向翻译难，因为翻译过程中信息会衰减。你写代码时脑子里想的是"这里要处理并发安全"，但代码里只有一个 mutex lock。意图丢失了，只剩下了实现。

传统编程中，人们一直在寻求通过技术手段来降低反向翻译的难度，形成编程界的公约和标准。

  • 命名规范把意图编码进变量名里（userRepository 比 ur 好读）。
  • 设计模式提供了程序员之间的共同语言（你看到 Observer 模式就知道这里有发布-订阅关系）。
  • 分层架构让你不用看代码就知道去哪找什么（数据操作在 Repository，业务逻辑在 Service，UI 在 View）。
  • 代码评审的核心问题是"我能从你的代码里读出你的意图吗"。

这些手段的本质都是在试图让代码"自解释"。但它们有一个共同的上限：只能降低黑箱的密度，不能消除黑箱。因为翻译的有损性是根本的。再好的命名也无法表达"我当时考虑了三个方案，最终选了这个，因为另外两个有什么问题"。这种决策上下文，代码本身装不下。

2. AI 编程放大了黑箱

AI 编程没有创造新的黑箱，但它把黑箱的增长速度提高了一个数量级。

以前一个开发者一天写几千行代码，你花一天时间大概能读完。现在 AI 一天能生成几万行，你的阅读速度没变，但代码的产出速度变了。黑箱在以你跟不上的速度膨胀。

更微妙的是：AI 写的代码"看起来"很合理。变量名规范，结构清晰，注释齐全。但 "看起来合理"和 "真的合理" 是两回事。AI 可能选了一个能跑但不该用的方案，可能引入了一个不必要的依赖，可能在某个边界条件上埋了一个坑。这些问题不会在"能不能跑"的层面暴露，只会在"该不该这样做"的层面暴露。

传统编程里，黑箱的来源是"别人写的代码"。你至少可以去问那个人。AI 编程里，黑箱的来源是"AI 写的代码"。你没法问 AI "你当时为什么这样写"，因为它没有"当时"，它不记得上一次生成的上下文。每一次对话都是全新的。

这意味着传统的对抗手段（代码评审、口头交流、找原作者问）在 AI 编程里部分失效了。你不能把 AI 拉进会议室问它"这个设计的考量是什么"。你能做的，是在代码之外建立一层可理解的抽象，让你不需要读每一行代码就能理解系统。

上一篇建立的功能文档体系（analysis.md、design.md、tasks.md）就是在做这件事。它们记录的不是代码，而是代码背后的决策上下文，补上了翻译过程中丢失的那部分信息。但文档解决的是"为什么这样做"的问题。还有一个问题文档不直接回答："做出来的东西长什么样"。这就需要另一种能力：读懂代码的结构。

3. 不要读代码细节，要去读结构

代码不是线性的叙事，它是网状的结构。函数调函数，模块依赖模块，数据在各层之间流转。你从任何一个点进去，都会被拉向四面八方。读完一个函数，你需要跳到它调用的三个函数，每个函数又调用了别的函数。很快你就忘了自己是从哪进来的。

问题出在焦距上。你用显微镜去看一个城市，看到的是砖头的纹理，但你不知道这是医院还是学校。你需要的不是更强的显微镜，而是一张地图。代码也一样，模块之间怎么协作、数据怎么流转、状态怎么变化，这些结构层面的东西，是代码的"地图"。

医生不会通过观察每一个细胞来诊断病人。他先看 X 光片（骨骼），再看验血报告（血液），再看 CT（器官）。每一层抽象都在回答不同的问题。对于软件工程来说，也是类似：

  • 项目有哪些模块？是如何组织的？(骨骼)
  • 每个模块负责什么？，和其他模块如何写作?（器官）
  • 数据从哪来、到哪去、在哪合并？（血液）
  • 什么时候创建、什么时候销毁、谁在监听谁？（生命周期）

这些问题比"这一行代码做了什么"重要得多。理解一个项目，可以有三个不同的焦距：

焦距 看什么 怎么看 要发现的问题
远景 模块与依赖 看 pubspec.yaml、目录结构、barrel 文件，不打开源码 不该有的依赖、循环依赖、层级混乱
中景 数据流与通道 找 Repository、Stream、emit，只看入口和出口 数据来源不清、同一份数据多处修改、通道混杂
近景 生命周期与事件 找 listen、cancel、构造函数、销毁函数，关注时序 忘记取消订阅、对象活得太长或太短、创建销毁不成对

每一层都比上一层"离代码更近"，但都不需要逐行阅读。远景不打开任何源码文件就能看到，中景只看关键文件的入口和出口，近景看构造和销毁的配对关系。三个焦距合在一起，就是项目的完整画像。

二、解读消息收发

上一章的功能文档，为我们描绘了某一功能实现过程中的所有细节。对于该功能来说，它是非常细致的。但是功能模块并非独立存在，它们将被集成到一个 骨架 中，需要和其他的模块交互、协作，完成任务。如果你无法把握这些脉络，那 AI 的工程迟早要失控。代码是 AI 写的，你可以通过和它交流，来 "看到" 当前项目的 风景，而不是对你的项目闭目不见，而置身事外。

1. 远景：模块与依赖

最远的焦距看到的是模块。一个项目有哪些模块？每个模块负责什么？谁依赖谁？ 以目前闪讯的前端为例，client/modules/ 下有七个 package：

可能是前期设计考虑不周，AI 生成的代码结构也不是百分百的完美。通过模块间的依赖关系，就可以很清晰地了解整体骨架，这样问题也容易暴露出来，比如这里发现 flash_im_conversation 依赖了 flash_session，我觉得不是很合理，于是直接询问：

Q: flash_im_conversation 为什么会依赖flash_session

此时 AI 会搜索对应模块的代码，找到 flash_im_conversation 中，哪里在使用 flash_session。最终发现，只是为了展示用户头像组件，反而引入了整个模块，这其实是不合理的：

Q: 为我在 docs\features\im\core\v0.0.3\client 修正这个不合理的依赖关系，重新更新设计和任务

发现问题后，可以及时更正。建议不要直接让 AI 写代码，而是通过修改文档，来触发 AI 更新代码。这样才能保证文档的是最新的内容，因为过时的文档不如没有文档。

在远景中，一定要关注模块间的依赖关系。比如这里会话列表需要显示头像。头像组件（UserAvatar）在 flash_session 里。AI 走了最短路径：需要头像？直接依赖 flash_session。能跑，没报错。

但这条依赖的语义是："会话列表模块知道用户登录会话的存在"。会话列表需要知道用户怎么登录的吗？需要知道 token 怎么管理的吗？需要知道密码怎么修改的吗？都不需要。它只需要一个能渲染头像的组件。

flash_session 里有几十个类：SessionCubit、SessionState、User、SessionRepository、SetPasswordPage、ChangePasswordPage、IdenticonAvatar、UserAvatar。会话列表只用了其中一个（UserAvatar），但依赖声明是模块级的。你依赖了 flash_session，就意味着 flash_session 的任何改动都可能影响你。密码管理页面重构了，会话列表要重新编译。这是不必要的耦合。

更深一层：这条依赖破坏了层级结构。flash_session 和 flash_im_conversation 都是业务模块，它们应该是平级的，各自独立。一个业务模块依赖另一个业务模块，就像两个器官直接长在一起，切一个就伤另一个。

解决方案很简单：把头像组件提到公共层（flash_shared），两个业务模块都依赖公共层，而不是互相依赖。依赖方向从"平级互相引用"变成"都向下依赖公共层"，层级就干净了。

2. 中景：事件与数据流转

整体的骨架看完了，接下来看血液怎么流。数据在项目里通过什么路径流动？有几条通道？每条通道的特点是什么？闪讯前端有三条数据通道：

通道 协议 方向 特点 例子
HTTP 请求-响应 客户端主动 拉取历史数据 打开聊天页加载消息
WebSocket 帧推送 服务端主动 实时数据，随时可能来 对方发来新消息
内存状态 Cubit emit 内部 乐观更新，纯内存，不经过网络 点发送后消息立刻上屏

三条通道的数据格式不同（JSON / Protobuf 帧 / 本地 Message 对象），但经过 ChatCubit 合并后，都变成同一个 List<Message>，按 seq 排序，去重。UI 只监听 ChatCubit 的状态，不知道也不关心某条消息是从 HTTP 拉回来的、WebSocket 推过来的、还是本地乐观创建的。

WebSocket 通道值得展开说。WsClient 是整个前端的实时数据枢纽，它从服务端收到的帧类型有很多种，但不同的业务模块只关心其中一部分。所以 WsClient 内部做了一件事：按帧类型广播到不同的 Stream。

WsClient 是广播站，它不知道有多少听众，也不关心。它只往 Stream 里扔数据。ChatCubit 订阅了 chatMessageStream 和 messageAckStream，收到后做三件事：过滤（是不是当前会话的？是不是自己发的？）、去重（message_id 有没有重复？）、合并（追加到列表，按 seq 排序）。ConversationListCubit 订阅了 conversationUpdateStream，收到后本地更新对应会话的预览、时间、未读数，然后重新排序。帧分发的代码只有一个 switch：

// ---> client/modules/flash_im_core/lib/src/logic/ws_client.dart
switch (frame.type) {
  case WsFrameType.CHAT_MESSAGE:
    _chatMessageController.add(frame);
  case WsFrameType.MESSAGE_ACK:
    _messageAckController.add(frame);
  case WsFrameType.CONVERSATION_UPDATE:
    _conversationUpdateController.add(frame);
  default:
    break;
}

三个 StreamController.broadcast()，消费者各取所需，互不干扰。新增一种帧类型时，只需要加一个 case 和一个 StreamController，不影响已有的消费者。

接着以消息收发为例，看一条消息从发送到上屏的完整事件流。下图串联了三条通道：内存状态（创建临时消息 → emit）、WebSocket（发帧 → 收 ACK → 收 UPDATE）、Cubit 状态管理（匹配 pending → 更新列表）。

ChatCubit 是消息收发的核心，它有三个关键方法，分别处理三种事件：

  final localMessage = Message.sending(localId, conversationId, currentUserId, content);
  emit(current.copyWith(messages: [...current.messages, localMessage]));

  // 2. 记录 pending，等 ACK 匹配
  _pendingMessages[clientId] = localId;

  // 3. 通过 WebSocket 发出去
  _wsClient.sendMessage(conversationId: conversationId, content: content, clientId: clientId);

  // 4. 10s 超时标记失败
  Future.delayed(Duration(seconds: 10), () {
    if (_pendingMessages.containsKey(clientId)) {
      // 更新 status: sending → failed
    }
  });
}

三个方法，三种事件来源，最终都汇入同一个 emit(ChatLoaded(messages))。这就是中景焦距要看的东西：不是每一行代码怎么写，而是数据从哪来、经过什么处理、最终到哪去。

怎么看数据流？三个关键词：找 Repository（HTTP 入口）、找 Stream 订阅（WebSocket 入口）、找 emit（状态出口）。顺着这三个词，就能画出任何一个模块的血管图。

3. 近景：生命周期与事件

最近的焦距看到的是：什么时候创建、什么时候销毁、谁在监听谁。打个比方。WsClient 像一个日更的作者，每天都在发新章节（帧数据）。ChatCubit 和 ConversationListCubit 是读者，点了"追更"（subscribe）就能收到更新。但读者是会离开的：聊天页关了，ChatCubit 就不在了。如果它走的时候没有取消追更，作者还在往一个已经注销的账号推送通知，这就是内存泄漏。

这块是最容易出 bug 的地方，也是 AI 最容易漏的地方。项目里的核心对象，生命周期长短不一：

WsClient 活得最长（登录到退出），ConversationListCubit 次之（首页存在期间），ChatCubit 最短（打开聊天页到关闭）。每次打开聊天页都会创建一个新的 ChatCubit，关闭时销毁。

短命的需要监听长命的。ChatCubit 订阅 WsClient 的 Stream，但 ChatCubit 销毁时必须取消订阅，否则 WsClient 还在往一个已经不存在的对象里塞数据：

代码上就是构造和销毁成对出现：

// 构造时订阅
ChatCubit(...) : super(const ChatInitial()) {
  _chatMessageSub = _wsClient.chatMessageStream.listen(_handleIncomingMessage);
  _messageAckSub = _wsClient.messageAckStream.listen(_handleMessageAck);
}

// 销毁时取消
@override
Future<void> close() {
  _chatMessageSub?.cancel();
  _messageAckSub?.cancel();
  return super.close();
}

如果忘了 cancel，页面关闭后 Stream 还在往一个已经销毁的 Cubit 里塞数据，轻则内存泄漏，重则崩溃。这是 Flutter 里最常见的 bug 之一，AI 生成的代码有时候会漏掉。怎么看生命周期？找构造函数里的 listen，找 close/dispose 里的 cancel，看它们是不是成对的。再看对象是在哪里创建的，就知道它的生命周期有多长。

三、宿主环境装配

我们之前把模块比作拥有独立功能的 器官，但器官不能独立存活。它们需要一个宿主，把它们组装在一起，给它们供血（数据）、传导信号（事件）、编排生命节奏。

在生物学里，宿主是寄生关系中提供生存环境的那一方。在软件里，宿主环境是模块运行的容器。模块自己不知道全局长什么样，不知道还有哪些其他模块存在，不知道自己的实例是怎么被创建的。这些都是宿主环境的事。

1. barrel 文件：模块的名片

每个模块都有一个 barrel 文件（lib/xxx.dart），它是模块对外的唯一窗口。

// ---> client/modules/flash_im_chat/lib/flash_im_chat.dart
export 'src/data/message.dart';
export 'src/data/message_repository.dart';
export 'src/logic/chat_cubit.dart';
export 'src/logic/chat_state.dart';
export 'src/view/chat_page.dart';
export 'src/view/message_bubble.dart';
export 'src/view/chat_input.dart';

上面的七行 export，就是这个模块的全部公开 API。外部只能看到这些类，内部的实现细节对外不可见。读一个陌生模块，先看 barrel 文件。它告诉你"这个模块想让你知道什么"。不在 barrel 里的东西，你不需要关心。这和人际交往一样：你认识一个人，先看他的名片，不会上来就翻他的日记。

barrel 文件还暗示了模块的内部结构。data/、logic/、view/ 三个目录，对应数据层、逻辑层、视图层。这个三层架构在项目的每个模块里都一致。一致性是理解力的加速器：看懂一个模块的结构，就看懂了所有模块的结构。

2. 宿主环境

闪讯前端的宿主环境是外层的主工程，main.dart 是它的入口。从依赖关系中可以看出，宿主环境依赖所有的子模块，实现功能。在这里就是功能拼装的场所：

宿主环境做四件事：创建所有核心对象、建立它们之间的连接、注入到 Widget 树、定义路由和启动流程。模块只暴露接口（barrel 文件），宿主负责把接口对接起来。

// ---> client/lib/main.dart
runApp(
  MultiRepositoryProvider(
    providers: [
      RepositoryProvider.value(value: wsClient),
      RepositoryProvider.value(value: conversationRepo),
      RepositoryProvider.value(value: messageRepo),
    ],
    child: BlocProvider.value(
      value: sessionCubit,
      child: FlashApp(router: router),
    ),
  ),
);

读 main.dart 能回答三个问题：项目有哪些核心对象？它们之间怎么连接？依赖注入的入口在哪？ 宿主环境不在乎任何业务逻辑。它只做组装：创建对象、建立连接、注入依赖、定义路由。用一张图看 main.dart 的装配全景：

所有对象在 main.dart 里创建，通过 Provider 注入到 Widget 树。模块之间不直接传递实例，都从 context 里取。HttpClient 的 token 来自 SessionCubit，WsClient 的 token 也来自 SessionCubit。认证状态决定路由走向和 WebSocket 连接时机。

3. 模块间的信号传递

宿主把模块组装在一起了，但模块之间不直接依赖。它们怎么协作？靠两种信号机制，一种像打电话，一种像听广播。

打电话是回调穿透。会话列表点击一个会话，需要导航到聊天页。但 ConversationListPage 和 ChatPage 在两个不同的模块里。如果它们互相 import，就像两个邻居为了说句话把墙打通了，以后一个人装修另一个人也得跟着动。

更好的方式是：ConversationListPage 暴露一个回调（"有人敲门了"），宿主环境（HomePage）决定怎么响应（"带他去聊天页"）。模块只负责报告事件，不做决策。决策权在宿主。

ConversationListPage(
  onConversationTap: (conversation) {
    // 宿主决定导航到哪
    Navigator.of(context).push(MaterialPageRoute(
      builder: (_) => ChatPage(conversationId: conversation.id, ...),
    ));
  },
)

听广播是 Stream 订阅。WsClient 像一个电台，同时开着三个频道：消息频道（chatMessageStream）、确认频道（messageAckStream）、会话更新频道（conversationUpdateStream）。ChatCubit 打开聊天页时调到消息频道和确认频道，关闭聊天页时关掉收音机。ConversationListCubit 在首页期间一直听着会话更新频道。

电台不知道有多少听众，听众也不知道还有谁在听同一个频道。两边完全解耦。新来一个听众（比如未来的"在线状态模块"），只需要调到对应频道，电台不用做任何改动。

// 电台：WsClient 开三个频道
final _chatMessageController = StreamController<WsFrame>.broadcast();
final _messageAckController = StreamController<WsFrame>.broadcast();
final _conversationUpdateController = StreamController<WsFrame>.broadcast();

// 听众 1：ChatCubit 打开聊天页时调频
_chatMessageSub = wsClient.chatMessageStream.listen(_handleIncomingMessage);
_messageAckSub = wsClient.messageAckStream.listen(_handleMessageAck);

// 听众 2：ConversationListCubit 在首页期间一直听
_updateSub = wsClient.conversationUpdateStream.listen(_handleUpdate);

// 关收音机：ChatCubit 关闭聊天页时
_chatMessageSub?.cancel();
_messageAckSub?.cancel();

打电话是一对一的、同步的：我点了，你响应。听广播是一对多的、异步的：电台播了，谁在听谁收到。两种机制配合，模块之间既能协作，又不用互相认识。

当你站在宿主环境之上，看见器官在系统中各司其职，看见血液沿着通道流向该去的地方，看见神经信号在模块之间精确地传导和断开，你对产品的生命，就有了真正的感知。不是对某一行代码的理解，而是对整个有机体的理解。

这种感知，是 AI 给不了你的，也是 AI 替代不了你的。但它可以辅助你认知，帮助你 "看见" 你的产品。代码会越来越多，黑箱会越来越大。但只要你能看见结构，黑箱就只是一层外壳。外壳里面，生命在运转。只有你真正看见了你的应用程序，理解它的骨骼、血液和神经，它才拥有广阔的成长空间。看不见的东西，你无法引导它生长。

四、本章小结

本章在分析时，修复了一些小的问题，也进行一些归档：

三个焦距，加上宿主环境的装配全景，构成了一套完整的代码阅读方法。它不依赖任何特定的技术栈，Rust 项目看 Cargo.toml，Flutter 项目看 pubspec.yaml，入口不同，方法相同。

焦距 看什么 怎么看 回答什么
远景 模块与依赖 pubspec.yaml / Cargo.toml 骨骼怎么连？
中景 事件与数据流转 Repository / Stream / emit 血液怎么流？
近景 生命周期 listen / cancel / 构造 / 销毁 神经怎么传导？

这套方法在 AI 编程时代尤其重要。不是因为 AI 写的代码更难读，而是因为代码产生的速度变了。你不可能逐行跟上，但你可以在每一轮 AI 产出之后，花十分钟做一次"体检"：依赖有没有长歪？数据流有没有绕弯路？生命周期有没有漏掉 cancel？十分钟的体检，比十小时的逐行阅读有效得多。

这也是本书一直在做的事情。从功能网络到功能文档，从交互链到逻辑树，从 analysis 到 archiver，每一个工具都在帮你"看见"。代码是 AI 写的，但看见产品的人，是你。
