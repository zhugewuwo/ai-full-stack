根芽#2 ｜ 会话列表

消息要有归处，人要有去向。会话就是消息的容器，也是人与人之间关系的载体。

上一篇搭好了通信地基：Protobuf 帧协议、WebSocket 连接管理、心跳保活、断线重连。管道铺好了，但管道里还没有东西流动。在其中注入消息之前，需要先回答一个问题：消息发给谁？

一条消息发出去，它属于哪段对话？显示在哪个页面？用户怎么找到它？这些问题都指向同一个东西：会话。消息是内容，会话是容器，没有容器，内容就是散装的。所以在做消息收发之前，应该先把容器搭好。

一、从微信出发：理解会话的价值

你每天打开多少次微信这类通信软件，可能自己都数不清。但每次打开，第一眼看到的都是同一个东西：会话列表。那一行行的对话，按时间排列，最近聊过的在最上面。

1. 会话在解决什么问题

这个列表如此理所当然，以至于没人会觉得它是一个"功能"。它就在那里，像空气一样自然。但从开发者的角度看，它是整个 IM 的门面。用户打开 App 的第一眼，看到的就是它。做一个功能之前，可以看看已经做好的产品，让 AI 为我们分析一下功能的价值。

结合微信的日常使用体验，分析会话列表背后涉及到哪些技术考量、需要解决哪些问题。

它给出的报告拆出了好几个维度的问题。归纳下来，核心问题就三个：我的结果供参考

问题 本质 解法方向
消息归属 消息属于哪段对话 引入会话，每条消息一个 conversation_id

2. 消息归属

想象一下最原始的方案：所有消息扔进一个大本子里，每条记录谁发的、发给谁。你和张三聊了 500 条，和李四聊了 200 条，群里还有上千条，全写在同一个本子上。

现在要找 "我和张三的聊天记录" ，你得从头翻到尾，每一条都看一眼：这条是我发给张三的吗？或者是张三发给我的？两个条件都要检查，漏一个就不完整。两个人的私聊还好，虽然麻烦但能翻完。

换成群聊就乱了。50 个人在群里聊天，一条消息"发给谁"？发给群里每个人？那一条消息要抄 50 份，每份标注一个接收者。群里发了 1000 条消息，本子上就是 5 万条记录。而且你想找"工作群的聊天记录"，还是得一条条翻，看接收者里有没有自己。

排序就更头疼了，"给我看最近 20 条和张三的聊天"，你得先把所有和张三相关的条目全部挑出来，排好序，再取前 20 条。本子越厚，这个过程越慢。

会话的引入就相当于，把一个大本子拆成很多小本子。你和张三一个本子，和李四一个本子，工作群又是一个本子。每条消息只需要写进对应的本子里。找"我和张三的聊天记录"，直接拿起那个本子翻就行，不用在一堆消息里大海捞针。两个人的私聊和 500 人的群聊，找法完全一样：拿起对应的本子，从最后一页往前翻。

落到数据库设计上，"本子"就是 conversations 表，每个本子有一个唯一编号（UUID）。每条消息记录一个 conversation_id，表示它写在哪个本子里。你和张三共享同一个本子，本子只有一个，不会重复创建。

3. 封面便签：效率与视角

试想一下，你有 100 个本子，每次打开书架要显示：每个本子的最后一条消息和未读数。
如果每次都把 100 个本子全翻一遍，太慢了。聪明的做法是在每个本子的封面贴一张便签：最后一条消息是什么，什么时候写的，还有几条没读。每次写新消息时顺手更新便签。打开列表时只扫封面，不翻本子。

但这里会有个问题，很多时候，同一个本子，两个人的的视角下，需要是不同的表现，比如：

  • 你把工作群的本子放在书架最显眼的位置（置顶），但同事没有。
  • 你的便签写着"3 条未读"，同事的写着"已全部读完"。
  • 你把某个本子藏起来（删除），对方书架上那个本子还好好摆着。

这说明 本子 和 便签 不能是同一个东西。本子本身的内容（聊天类型、最后一条消息、创建时间）是客观的，所有人共享。但每个人贴在封面上的便签（未读数、是否置顶、是否删除）是主观的，各管各的。一个本子配多张便签，每个参与者一张。

落到数据库设计上，就是两张表。conversations 表存本子（共享信息），conversation_members 表存便签（每人一条记录）。两张表通过 conversation_id 关联。你和张三的私聊，conversations 里一条记录，conversation_members 里两条记录，一条是你的便签，一条是张三的。

4. 两张表，两个视角

上面的分析自然指向了一个结论：会话系统需要两张表。一张记录本子本身（conversations），一张记录每个人的便签（conversation_members）。这不是拍脑袋的设计，而是三个核心问题推导出来的必然结果。消息归属要求有"本子"，列表效率要求本子封面有预存信息，多视角状态要求每个人有独立的便签。

conversations 表（本子）：

字段 说明
id UUID，会话唯一标识
type 0 单聊，1 群聊
name / avatar 群聊名称和头像，单聊为空
owner_id 群主，单聊为空
last_message_at 最后消息时间，用于列表排序
last_message_preview 最后消息预览，封面便签

conversation_members 表（便签）：

字段 说明
conversation_id + user_id 联合主键，一个人一个会话一条记录
unread_count 未读数，每个人独立
last_read_seq 读到第几条，已读回执的基础
is_deleted 软删除，你删了对方不受影响
is_pinned / is_muted 置顶和免打扰，各管各的

当前版本大部分字段都是默认值，随着后续功能推进会逐个激活。消息收发激活 last_message_preview 和 unread_count，已读回执激活 last_read_seq，群聊激活 name、avatar、owner_id。同样的两张表，承载了整个 IM 的演进。

2. 种子测试环境

在开发阶段需要测试数据，一个个手动创建数据肯定不现实。于是基于 重置数据库 --> 测试数据 --> 接口请求 这条链路，可以设计一个稳定、可定制、可重用的模拟数据环境。我称之为 种子测试环境。它的理念是：

一颗种子，在同等环境中中成长，总会生产相同的结果。

打个比方，我这里有一份 seed_data.json 的种子数据，其中包含 52 个传统中国颜色的名称，我准备把它们作为 用户 入驻到系统中：

然后再以第一个用户的身份，调用 conversations 接口的与其他 51 个用户创建会话关系：

也就是说，我只要先重置数据库，再执行这个脚本，系统就会自动完成 52 个用户注册，以及填充 51 个会话数据。另外，非常重要的一点是：

通过 HTTP 接口创建数据，走的是和真实用户完全相同的路径。

种子脚本本身就是对接口的一次完整测试。如果脚本能跑通，说明注册、登录、创建会话这条链路是通的。可能有人会问，为什么不用 SQL 直接插入数据呢？直接插入数据，会绕过业务逻辑。注册用户时，业务逻辑会创建 user_profiles 记录、分配 account_id 这些。需要手动处理这些细节，容易遗漏。而走接口除了，是和真实环境最接近的形式，出了错也可以立刻发现逻辑错误。

一开始准备用 "用户1、用户2" 这样的测试数据，但是感觉过于单调。我让 AI 从中国传统色里挑了 52 个颜色名：朱红、橘橙、藤黄、碧螺春绿、天蓝、景泰蓝、葡萄紫……每个用户的头像用 identicon 方案生成，填充色就是对应的传统色色值。

这个决策带来了一个意外的好处：会话列表变得很好看。51 个会话，每个头像颜色都不一样，一眼就能区分。比起千篇一律的灰色占位头像，开发体验好了很多。

三、测试：给 AI 编程装上安全网

传统开发中，程序员写完代码会在脑子里过一遍逻辑，大致知道对不对。AI 生成的代码，你没有这个"脑子里过一遍"的过程。代码看起来合理，但某个边界条件可能没处理好。测试就是你和 AI 之间的契约：你定义"正确"是什么样的，AI 负责让代码满足这个定义。

1. 两层测试

模块化之后，单元测试就可以在模块的内部进行，如下所示：

前端的会话模块有两层测试，各有各的用途：

层 工具 依赖后端 验证内容
单元测试 mocktail + bloc_test 不需要 Cubit 状态流转、数据模型解析
集成测试 ConversationRepository 需要 端到端数据正确性

单元测试用 Mock 把 Repository 替换掉，只验证 Cubit 的逻辑。加载成功发什么状态，加载失败发什么状态，loadMore 怎么追加数据，hasMore 怎么判断，删除后列表怎么变。这些测试几秒钟就跑完，随时可以跑，不需要启动后端。

集成测试直接调用后端 API，验证真实的数据流。分页加载 3 页共 51 条数据，创建会话的幂等性，删除后列表减少。这些测试需要后端运行，但它们验证的是从前端到数据库的完整链路。

2. 测试登录的问题

集成测试需要 token，但登录逻辑属于 flash_auth 模块，flash_im_conversation 不应该依赖它。如果每个模块的集成测试都自己写一套登录逻辑，代码重复不说，登录接口一改所有模块都要跟着改。

解决方案是一个独立的登录脚本。运行一次 dart test/login_for_test.dart，它调用登录接口，把 token 写入 client/test/.env 文件。集成测试从这个文件读取 token，直接用 ConversationRepository 发请求。token 有效期 7 天，不用每次都跑脚本。

这个机制是跨模块共享的。以后新增的模块，集成测试都可以从同一个 .env 文件读取 token。登录是环境准备，跑一次就行。测试逻辑可以反复跑，不用每次都等登录。token 有效期 7 天，足够用了。

3. 测试作为 AI 编程的安全网

在 AI 编程中，代码的产出速度很快，但"快"本身就是风险。AI 一次性生成了整个 Cubit、Repository、State、Page，看起来都对，但你没有像手写代码那样逐行思考过。测试的价值不在于"证明代码没 bug"，而在于给你信心去做下一步。

有了测试，你可以放心地让 AI 重构。"把 getList 的返回类型从 List 改成 Stream"，改完跑一遍测试，绿了就行，不用逐个页面手动验证。"把分页逻辑从 Cubit 移到 Repository 层"，改完跑一遍，绿了就行。没有测试，每次重构都是一次冒险。有了测试，重构变成了一次确认。

这也是为什么测试要在功能完成后立刻写，而不是"以后再补"。以后永远不会来。趁着对业务逻辑最熟悉的时候，把"正确"的定义固化下来。后续不管是你自己改、AI 改、还是换一个 AI 改，这份定义都在。

模块化在这里体现出另一个好处：测试的内聚性。flash_im_conversation 的测试只关心会话的逻辑，不涉及登录、不涉及 WebSocket、不涉及消息收发。测试文件就放在模块自己的 test 目录下，跑测试时 cd 到这个模块，flutter test 一敲，几秒钟出结果。不用启动整个项目，不用关心其他模块的状态。每个模块管好自己的一亩三分地，整个系统的质量就是所有模块质量的总和。

四、本章小结

存档点 tag 提交点
会话列表 + 种子数据 + 测试体系 v0.8.0 dd5274f

这一篇做了三件事：理解会话、实现会话、测试会话。
从微信的日常体验出发，拆解出消息归属、列表效率、多视角状态三个核心问题，推导出 conversations + conversation_members 两张表的设计。后端三个接口（创建、查询、删除）覆盖了会话的基本生命周期，种子数据脚本通过真实接口填充了 52 个用户和 51 个会话。前端新增 flash_im_conversation 模块，消息界面从空白变成了一个有颜色、有分页、有下拉刷新的会话列表。

想在回头看，对于一个新的功能需求，这一套流程已经跑通了：

分析需求 → Feature Designer 设计(前后端) → Feature Task Maker 拆任务(前后端) →
AI 按任务执行 → 种子数据验证链路 → Link Test Writer 生成接口文档 →
前端模块实现 → 单元测试 + 集成测试覆盖。

后续每个新功能模块，都可以沿着这条路走。流程一旦固化，人只需要做决策，AI 负责执行，效率会越来越高。这套体系会随着后续模块的增加不断复用，也会在不断使用中，打磨地更加精细。
