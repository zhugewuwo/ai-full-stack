一、 运行 Web 项目

Web 平台的宿主外壳在 web 目录下，里面是个非常简单的 index.html, 以及图标资源和配置信息。Web 的运行环境应该说是最简单的，有浏览器就可以跑。

1. 本地数据库（drift）处理

将闪讯运行到 Web 端，核心挑战是处理 dart:io 和 dart:ffi 在 Web 端不可用的问题。 原来的 AppDatabase 使用 drift/native.dart 的 NativeDatabase，依赖 dart:ffi 加载原生 SQLite 二进制。Web 端不支持 dart:ffi，编译直接报错。

但调研后，发现 drift 是支持 web 平台的。使用 drift_flutter 包的 driftDatabase 函数，它内部自动处理平台差异：

  • 原生平台：使用 NativeDatabase（通过 sqlite3_flutter_libs）
  • Web 平台：使用 WasmDatabase（通过 sqlite3.wasm WebAssembly）

改动文件：client/modules/flash_im_cache/lib/src/drift/database/app_database.dart

// 改动前
import 'dart:io';
import 'package:drift/native.dart';

static Future<AppDatabase> open(int userId) async {
  final dir = await getApplicationDocumentsDirectory();
  final file = File(p.join(dir.path, 'im_cache_$userId.db'));
  return AppDatabase(NativeDatabase.createInBackground(file));
}

// 改动后
import 'package:drift_flutter/drift_flutter.dart';

static Future<AppDatabase> open(int userId) async {
  return AppDatabase(
    driftDatabase(
      name: 'im_cache_$userId',
      native: DriftNativeOptions(
        databaseDirectory: getApplicationSupportDirectory,
      ),
      web: DriftWebOptions(
        sqlite3Wasm: Uri.parse('sqlite3.wasm'),
        driftWorker: Uri.parse('drift_worker.js'),
      ),
    ),
  );
}

# 改动后

二、打包与部署

打包部署时将 flutter 项目，构建成为 web 产品，然后放在服务器上托管。这样任何人都可以通过 浏览器 访问链接，来使用闪讯的 web 端。

1. Flutter 打包 web 项目

我想要使用 ip:端口/im/ 的链接访问 web 站点。使用 --base-href /im/ 会把 index.html 中的 <base href="/"> 改为 <base href="/im/">，所有资源（JS、CSS、字体）都会从 /im/ 路径加载。

drift 在 Web 端使用 WebAssembly 版的 SQLite。DriftWebOptions 中指定的 wasm 路径必须是绝对路径：

web: DriftWebOptions(
  sqlite3Wasm: Uri.parse('/im/sqlite3.wasm'),
  driftWorker: Uri.parse('/im/drift_worker.js'),
)

这样一行命令就可以构建出 web 产物，你可以在 client\build\web 里看到它：

flutter build web --release --base-href /im/ --dart-define-from-file=.env.production

东西有了，接下来就是，改把这个东西放在那里？

2. Rust 后端的网站托管

Rust 后端目前已经有了 tower-http 的 ServeDir + ServeFile 托管静态文件，之前隐私协议介绍通过它呈现的。这里同样也可以将 im 的 web 产物交给它：

use tower_http::services::{ServeDir, ServeFile};

let app = Router::new()
    .merge(auth_routes())
    .merge(conversation_routes())
    // ... 其他 API 路由 ...
    .nest_service("/im", 
        ServeDir::new("static/web")
            .fallback(ServeFile::new("static/web/index.html"))
    );
  • ServeDir::new("static/web") — 把 static/web/ 目录映射到 /im/ 路径，访问 main.dart.js 就返回 main.dart.js
  • .fallback(ServeFile::new(...)) — 找不到文件时返回 index.html，让 Flutter 的客户端路由接管（SPA 必须）
  • nest_service("/im", ...) — 挂载到 /im 子路径

然后把 web 放在服务器上的的 static 下，更新重启后端服务即可。文件结构如下：

├── flash-im              # 后端二进制
├── .env                  # 环境变量
├── static/
│   ├── web/              # Flutter Web 产物
│   │   ├── index.html
│   │   ├── main.dart.js
│   │   ├── sqlite3.wasm

│   └── privacy.html

三、Flutter web 的优化

禁用缓存的情况下，查看目前部署的 web 项目。下面有四个值得关注的指标:

  • transferred : 网络实际传输的字节数（压缩后的大小）。这是浏览器从服务器下载的总流量。
  • resources: 解压后的资源原始大小。浏览器收到压缩数据后解压还原的总量。
  • Finish: 从页面开始加载到最后一个请求完成的总耗时。包括所有资源（JS、Wasm、图片、字体）全部下载完毕的时间点。
  • Load: 页面 window.onload 事件触发的时间，表示初始资源（HTML 引用的 JS、CSS）加载完毕。注意它比 Finish 小，因为 Finish 包含了异步加载的资源（比如 canvaskit.wasm 是 Flutter 引擎启动后才去下载的）

目前传输 8.0/13.1M 压缩情况不佳, 首屏 Load 6.51s, Finish 需要 8.65s，这是很难忍受的。如果加载过一次，第二次进入就会非常快了，现在关键在于 用户首次进入 体感不佳。

1. 为什么首屏这么耗时

要优化之前，先搞清楚慢在哪。Flutter Web 和 React/Vue 这类传统 Web 框架的加载模型完全不同。它不是渐进式渲染 DOM，而是把整个 Dart 运行时 + 渲染引擎 + 业务代码打包成一坨巨大的 JS/Wasm 文件，浏览器必须全部下载完、解析完、执行完，才能画出第一个像素。

  1. JS Bundle 大 — main.dart.js 通常 3-5MB。这里面包含了 Dart 运行时、框架代码、所有业务逻辑。相比之下，一个典型 React 应用的首屏 JS 可能只有几百 KB。
  2. CanvasKit/skwasm 渲染引擎大 — canvaskit.wasm 有 2M 多，它本质上是 Skia 图形引擎的 WebAssembly 版本，相当于浏览器里跑了一个"迷你 GPU 驱动"。
  3. 串行加载 — 浏览器必须按顺序完成：下载 JS → 解析 → 执行 → 下载 canvaskit.wasm → 初始化渲染引擎 → 渲染第一帧。任何一步慢了都会阻塞后续步骤。
  4. 客户端渲染 — Flutter Web 是纯客户端渲染，白屏时间 = 全量加载时间，用户在引擎就绪前什么都看不到。

简单说：用户打开页面后，浏览器要先下载十几 MB 的"工具箱"（运行时 + 渲染引擎 + 业务代码），全部准备好后才开始干活。这就是白屏的本质。

2. 服务端压缩（Gzip / Brotli）

目前服务端返回的数据并未进行压缩，目前的 Rust 服务可以启用对返回数据的压缩。只需要添加一行 CompressionLayer，服务端传输的数据就从 8.0M → 4.8M。如下所示，Finsh 到了 3.69s:

use tower_http::compression::CompressionLayer;

.nest_service("/im", ServeDir::new("static/web").fallback(ServeFile::new("static/web/index.html")))
// Gzip/Brotli 压缩：JS/Wasm 文件压缩率 ~70%
.layer(CompressionLayer::new())

这对 main.dart.js 这种文本非常适应，但是对 canvaskit.wasm 这种文件是没有效力的。下面看看如何对这块进行优化。

3. 增加原生 Web 启动页

可以看到 flutter web 的包体积大小很难压到很低，因为 wasm 必然会存在。这些你删不掉也改不了，它们是 Flutter Web 能跑起来的前提。这不是说 Flutter Web 就必须在一开始等待几秒的白屏，我们可以在 web 原生写有些酷炫的加载动画，等 Flutter 准备完毕再进入，这就像游戏一样，不一定要求要秒开，它的价值在于它的内容。

实现思路：在 Flutter 引擎启动之前，用纯 HTML/CSS 在 index.html 里画一个加载动画。前面说过原生的改动需要在对应原生文件夹，这里在 web/index.html 里增加一个 loading-screen 的覆盖界面，具体可让 AI 发挥。

等 Flutter 渲染出第一帧后，把动画移除。两个世界的交接点是 flutter-first-frame 事件。

  // Flutter 第一帧渲染后移除加载页
  window.addEventListener('flutter-first-frame', function() {
    cancelAnimationFrame(animId);
    const el = document.getElementById('loading-screen');
    if (el) {
      el.classList.add('fade-out');
      setTimeout(() => el.remove(), 600);
    }
  });

这样进入后，原生的 html 就可以立刻渲染出一个等待连接的动画界面，可以缓解用户第一次进入时的等待焦虑。

四、关于 WASM 的介绍

Flutter Web 的支持，离不开 WASM ，本节我们就展开说说它是什么。

WebAssembly（简称 WASM）是一种运行在浏览器里的二进制指令格式。你可以把它理解为"浏览器的汇编语言"——不是给人读的，是给机器跑的。

1. WASM 和 JavaScript 的区别

传统 Web 应用只能用 JavaScript。JS 是文本格式，浏览器拿到后要经历：下载文本 → 解析语法 → 编译为字节码 → JIT 优化 → 执行。每一步都有开销。

WASM 换了个思路：把源代码（C/C++/Rust/Dart/Go...）在构建时就编译成紧凑的二进制格式。浏览器拿到后几乎可以直接执行，跳过了文本解析和大量 JIT 开销。好处是：

  • 更快：二进制格式加载更快，执行接近原生速度
  • 更小：同样逻辑，二进制比 JS 文本更紧凑
  • 语言无关：任何语言都可以编译为 WASM，不只是 JS
  • 更安全：二进制指令没有变量名、没有注释、没有可读结构，逆向难度极高。JS 混淆后仍然能还原出业务逻辑，而 WASM 的反编译成本和反编译 C++ 的 .so 文件差不多

WASM 不是要取代 JavaScript——它是 JS 的补充。适合 CPU 密集型的工作（图形渲染、音视频编解码、游戏引擎），而 JS 仍然负责 DOM 操作和浏览器 API 交互。

Flutter Web 的 canvaskit.wasm（Skia 图形引擎）就是 WASM 的典型应用：把 C++ 写的 Skia 编译成 WASM，浏览器里就能跑原生级的 2D 渲染。

2. Flutter 的 WASM 编译

传统模式下，Dart 代码通过 dart2js 编译成 JavaScript。浏览器拿到的是一个巨大的 main.dart.js 文件，由 JS 引擎执行。也就是上面看到的这个文件:

WASM 模式下，Dart 代码通过 dart2wasm 编译成 WebAssembly 二进制格式（main.dart.wasm）。WebAssembly 是一种紧凑的二进制指令格式，浏览器可以直接编译为机器码执行，跳过了 JS 引擎的解释和 JIT 开销。

好比把一本小说从"中文翻译成英文再给外国人读"变成"直接用他母语写"——中间损耗少了一截。
Flutter 3.24+ 稳定支持，只需在构建命令加 --wasm：

flutter build web --wasm --releas --base-href /im/ --dart-define-from-file=.env.production
3. 多线程渲染

不管选哪种编译模式，Flutter Web 都需要下载一个图形引擎——因为它不用浏览器自带的 DOM/Canvas API 画界面，而是自带了一整套 Skia 渲染引擎。这是 Flutter 跨平台一致性的代价，也是"工具箱"里最重的一块，没法去掉。

编译模式 渲染引擎文件 体积 特点
JS 模式（默认） canvaskit.wasm ~2.2 MB Skia + JS 桥接层，单线程
WASM 模式 skwasm_heavy.wasm ~1.8 MB Skia 原生 WasmGC，支持多线程

两者本质上做同一件事：提供 2D 图形绘制能力。skwasm 去掉了 JS 中间层，渲染线程可以独立于主线程运行，动画不会被业务逻辑卡住。

skwasm 支持多线程渲染，可以把绘制工作分给多个 Web Worker 并行执行，通过 SharedArrayBuffer 共享内存。但浏览器出于安全考虑默认禁用了 SharedArrayBuffer（防止 Spectre 侧信道攻击）。

要解锁它，服务端必须在响应头中声明页面处于"安全隔离"状态：

// COOP/COEP 头：启用 SharedArrayBuffer
.layer(SetResponseHeaderLayer::overriding(
    HeaderName::from_static("cross-origin-embedder-policy"),
    HeaderValue::from_static("credentialless"),
))
.layer(SetResponseHeaderLayer::overriding(
    HeaderName::from_static("cross-origin-opener-policy"),
    HeaderValue::from_static("same-origin"),
))
  • Cross-Origin-Embedder-Policy: credentialless — "我不会偷偷加载带凭证的跨域资源"
  • Cross-Origin-Opener-Policy: same-origin — "我不会和跨域窗口共享进程"

两个头配齐，浏览器才开放 SharedArrayBuffer，多线程渲染才能生效。不配的后果： 应用仍能正常运行，但默默退化为单线程，性能优势打折扣（不会报错，只是变慢）。

参考：Flutter 官方 Wasm 文档

五、本章总结

Web 端的部署比想象中简单。后端加一行 nest_service 就能托管静态文件，不需要 Nginx、不需要 Docker、不需要额外的基础设施。同源部署避免了 CORS 的所有麻烦。真正花时间的是两件事：

  • 兼容适配（一次性工作）：dart:ffi 不可用（drift_flutter 解决）、Platform 不可用（kApp 解决）、DeviceInfoPlugin 需要走 webBrowserInfo 路径。搞定之后后续迭代就和其他平台一样了。
  • 加载体验优化（持续调优）：Flutter Web 的产物天然比传统 Web 框架大。Dart 运行时 + Skia 渲染引擎 + 业务代码，压缩后仍有 4-5MB。源码层面能做的有限（编译器本身就会 tree shaking），不要试图让 Flutter Web 的首次加载比 React 更快，架构决定了做不到。但通过压缩减小实际等待时间、通过 Loading 动画掩盖等待感知、通过浏览器缓存让回访用户秒开，三管齐下用户体感就不会差。

至此，闪讯覆盖了 Android、iOS、macOS、Windows、Linux、Web 六大平台。同一套 Dart 代码，同一套业务逻辑，用户在任何设备上都能使用。
