经络#1 ｜ 模块化的分工协作

生命走向复杂的第一步，不是变大，而是学会分工。

目前我们已经拥有了一颗具有生命力的种子。这一卷将通过五章的篇幅，了解各个系统间的关系、设计这颗种子的经络，如何更好地组织、分工，共同维持生命的成长空间。

一、软件生命体的组织结构

在开始，我希望做一个有趣的思想对比。一个成年人身体大概有 30万亿~40万亿个细胞，你有没有惊讶过，为什么这么多体量的单体，可以这么有序的协作。软件工程可以从中汲取什么灵感，能有利于代码组织呢？哪怕只是亿分之一的灵感 ~

众所周知，生物学有一条非常经典的层次结构，用来描述生命从小到大的组成：

细胞 → 组织 → 器官 → 系统 → 个体

1. 细胞 - 最小功能单元

细胞 是最基础的单位，是能独立完成生命活动的最小结构。这很像软件工程中的 函数/结构体，它们都是具体功能的执行单元或数据载体。

2. 组织 - 明确分工边界

单个细胞的力量微乎其微，但多个功能相似的细胞聚集形成 组织 时，就产生了量变到质变的功能。比如大量功能相近的肌肉细胞，聚集成肌肉组织，它将零散的单元逻辑（细胞收缩）整合成可预测、可控制、高输出的服务能力。它是生命体这个复杂程序中，负责 “动作执行” 的最关键层级，有了明确的分工边界。

软件工程中，职责相近、逻辑内聚的单元聚集成 层。比如界面视图相关的表现层，由视图元素聚合而成，就像生物的上皮组织，负责与外界交换信息（皮肤、粘膜 -> 用户交互、输入），保护内部逻辑不被直接触碰(用户只看到界面，无法修改内部逻辑)。

3. 器官 - 接口契约

而当多种不同的组织，为了完成一个具体业务而垂直整合时，就构成了 器官。心脏就是一个典型的“功能模块”。它内部集成了动力（肌肉组织）、调度（自身节律与外部调节）和支撑（结缔组织），但对整个循环系统而言，它只暴露标准的接口契约。对外界而言它不解释内部如何运作，只严格遵守协议：输入什么，输出什么。

这种接口契约是复杂系统的减速器。在软件架构中，一个支付 模块 就像一个器官，它封装了从校验到持久化的所有层次，外部调用者只需通过标准的 API 契约与其交互。只要契约不变，内部逻辑的重构（组织细胞的代谢）就不会引起整个系统的崩溃。

组织解决的是“同类单元如何归纳”，而器官解决的是“多类单元如何协同并对外提供能力”。在维度扩张上：

  • 组织是同一个维度上的 横向扩张，是由无数个功能单一、同质化的单元聚合而成；
  • 器官则是纵向的穿透，同职能的单元通过契约串联调度。
4. 系统 - 全局协同

单个器官即便再精密，也无法独立支撑生命。只有当心脏、血管、肺部等器官，通过血液循环与神经调控彼此联动时，才形成完整的循环系统（功能域 / Domain）。这一层级不再关注某个局部如何运作，而是关注整体的物质与信息流转。

在软件工程中，这对应 领域驱动设计 中的子系统（Subsystem）或功能域。例如一个“电商履约域”，需要库存、物流、支付等模块协同运作。模块之间通过接口调用、事件机制或消息传递进行通信，既可以是同步的调用关系，也可以是类似“广播与订阅”的异步协作，共同完成端到端的业务流程。

5. 生命体

当多个系统 最终汇聚在一起，就形成了一个完整的 生物体，也就是软件工程中的 应用（Application） 或 平台（Platform） 。在这一层，单一的功能已经不再是主角，取而代之的是全局的资源调度与稳态维持。而一个生命体，又何尝不是社会的一个微小执行单元呢？

一个 IM 产品，认证系统、消息系统、存储系统等各自独立运行。但用户感知到的是一个完整的体验："我打开 App，登录，看到消息，回复，对方秒收到。"这个流畅的体验不属于任何一个系统，它是所有系统协作的涌现结果。

从 细胞（函数）的微观执行，到组织（层）的水平聚合，再到器官（模块）的垂直整合，最后到系统（功能域）的全局协同。我们构建的不只是一行行代码，而是一个具备生命节律的数字实体。这种类比让我们看清了一个真相：好的架构，本质上是对生命进化智慧，在某种程度上的致敬。

二、简单认识结构拆分

前面我们用生物学的视角，看到了生命体从细胞到个体的五级结构。但这引出了一个关键问题：生命为什么要走向多细胞？单细胞生物活了几十亿年，不也好好的吗？答案是：

单细胞有极限。

1. 单细胞的极限

生物学中有一个经典的物理约束： 细胞越大，表面积与体积的比值越小。表面积决定了营养交换的效率，体积决定了需要供养的内容。 当细胞长到一定大小，表面积不够用了——养分进不来，废物排不出，细胞就会窒息。所以地球上几乎不存在，巴掌大的单核细胞生物。它要么分裂，要么死亡。

细胞变大，问题不只是“交换效率下降”，本质是 边界承载能力跟不上内部复杂度增长。表面积是边界，是接口；体积是内部状态，是逻辑与负担。当增长不成比例时，系统就会失衡。

细胞并没有无限变大来解决问题，而是走向了另一条路径。它们开始分化，形成组织，再进一步形成器官与系统。也就是说，生命并没有试图优化 单个单元 ，而是通过“结构升级”，来承载更高的复杂度。也许，在亿万年的演化中，所有试图靠单一结构承载复杂性的路径，几乎都被淘汰了。只有最终留下来的，才是我们所见到的。

软件系统也是一样。当一个函数、一个文件、甚至一个模块试图承载过多复杂性时，问题并不在于“写得不够好”，而在于它违背了一个更底层的规律：

单一单元无法无限承载复杂度。

这不是工程经验，也不是某种最佳实践，而是一种跨越生物与软件的共同约束： 复杂性一旦超过边界的承载能力，系统就必须通过结构分化来继续存在。否则，它就会像那些在演化中消失的路径一样，被淘汰。

回头看看我们的后端。大约 500 行的代码都集中在 server/src/main.rs。它虽然可以继续成长，但只是停在“单细胞阶段”。
你仔细看会发现，其实结构已经“隐约存在”了。认证是一块，WebSocket 是一块，聊天室又是一块，这些逻辑本来就是不同的事情，有各自的功能和规则。但现在，它们只是被写在一起，而不是被组织起来。

4. 单元测试的信心

我们刚才相当于重构了整个后端的代码，那么问题来了。我怎么知道有没有改出 Bug 呢？前端目前用我现在的接口会不会出问题呢？

还记得之前我们写过的前端测试用例吗？它就是为了这一刻而生的。如果测试用例覆盖完全，只要跑一遍，哪里有问题，就可以立刻发现。没有问题，就说明当前的重构功能已经对齐。

我常把重构比作一种蜕变，它的结果通常是生物获得了全新的生存维度。在生物蜕变前，旧的表皮（旧代码）会变得僵硬、限制生长。此时，内部逻辑（生命体）已经演进到了旧外壳无法容纳的地步。

在自然界，蜕变失败意味着死亡，最危险的时刻是新皮尚未坚硬时。在软件工程中，重构失败意味着线上事故。此时，测试用例就是防弹衣。只要测试全绿，就意味着新旧逻辑的“功能等价性”得到了保证，而外界（前端）甚至感知不到内部已经发生了一场革命。

三、拆分之后，看看内部

拆分完成了，测试也通过了。但如果只是把代码从一个文件搬到多个文件，那和搬家没什么区别——东西还是那些东西，只是换了个房间。真正值得关注的是：拆分之后，每个模块内部长什么样？它们之间是怎么协作的？让我们打开几个文件，看看"细胞分化"之后的结果。

1. 模块的内部分层

以 auth/ 模块为例，它内部被拆成了四个文件：

auth/
├── mod.rs       # 模块声明：告诉外界"我有哪些子模块"
├── routes.rs    # 路由定义：URL 和处理函数的映射
├── handler.rs   # 业务逻辑：发验证码、登录、获取用户信息
├── jwt.rs       # JWT 工具：Token 的生成与验证
└── model.rs     # 数据模型：请求和响应的结构体定义

这不是随意的拆法。每个文件对应一种职责：

  • routes.rs 只关心"哪个 URL 对应哪个函数"，不关心函数里做了什么：
  • handler.rs 只关心业务逻辑：验证手机号、比对验证码、生成 Token，不关心自己被挂在哪个 URL 上。
  • model.rs 只定义数据的形状：SmsRequest 长什么样、LoginResponse 有哪些字段，不关心数据怎么被处理。
  • jwt.rs 只管 Token 的生成和验证，不关心谁在调用它。

当再让 AI 改代码时，这种分层的好处，会立刻体现出来。比如你想在现有验证码登录的基础上，再增加一种 密码登录 的方式，只需要告诉 AI：

具体的功能逻辑，会聚焦到 handler.rs 中, 根据类型类型进行不同的认证行为。

由于后端改动了登录的逻辑，此时可能会影响前端。这就要有请测试用例来干活了，跑一下认证相关的测试用例，确实报错了：

AI 总结: 发送验证码的 4 个测试全部通过（/auth/sms 接口没改），但所有涉及登录的测试都挂了——422 Unprocessable Entity，因为前端发的是 {phone, code}，后端现在期望 {phone, type, credential}，serde 反序列化直接拒绝了。

此时，你可以让 AI 基于测试用例的结果，来修正前端逻辑。

Q: 为我基于测试用例的异常信息，修正前端逻辑。在进行测试，直到没有问题。
另外，为我增加一下密码登录的测试用例。

可以看到，AI 编程的关键，就是在每个流程节点上，真正干活的都是 AI，我们则是把控方向。贯穿起开发的流程。比如这个密码登录这个新的功能需求，就这样被融入到了后端系统。同理，你也可以将这个功能，同步到前端界面上，最终让用户可以使用。

2. 模块之间的协作

拆分不是孤立的。看看 ws/auth.rs 里的这行代码：

use crate::auth::jwt::verify_token;

WebSocket 认证模块需要验证 Token，但它不自己实现验证逻辑，而是从 auth 模块"借用"了 verify_token 这个能力。再看 ws/chat_room.rs：

use super::auth::wait_for_auth;

聊天室需要认证用户身份，它也不自己写认证流程，而是复用了同模块下 auth.rs 提供的 wait_for_auth 函数。

这就是第一节里说的接口契约在实际代码中的体现。verify_token 的契约很简单：给我一个 Token 字符串，我还你一个 user_id。至于 Token 是用 HS256 还是 RS256 签的、密钥存在哪里、过期时间多长——调用方完全不需要知道。哪天你想把 JWT 换成 Session，只要 verify_token 的签名不变，ws/auth.rs 和 ws/chat_room.rs 一行都不用改。

用生物学的话说：心脏（聊天室）不需要知道血液（Token）是怎么造出来的，它只需要知道血液会按时送到。造血的事，交给骨髓（auth 模块）就好。

3. 共享状态：贯穿全身的血液

还有一个值得注意的角色：state.rs。它没有被放进任何模块，而是独立在 src/ 根目录下：

pub struct AppState {
    pub users: Mutex<HashMap<String, User>>,       // 用户表
    pub sms_codes: Mutex<HashMap<String, String>>, // 验证码表
    pub next_id: Mutex<i64>,                       // 自增 ID
    pub chat_tx: broadcast::Sender<String>,        // 聊天室广播通道
}

AppState 被 auth、ws、mock 三个模块共同依赖。它就像生物体中的血液——不属于任何一个器官，但流经每一个器官，为它们提供共享的资源。

这也是为什么它被放在顶层而不是某个模块内部。如果把 AppState 放进 auth/ 模块，那 ws/ 模块就要反向依赖 auth/，模块之间的关系就会变得纠缠不清。把共享的东西提到更高的层级，是保持模块独立性的一个简单但重要的原则。

4. 回头看 main.rs

最后再看一眼重构后的 main.rs：

mod state;
mod auth;
mod ws;
mod mock;
mod util;

#[tokio::main]
async fn main() {
    let state = state::create_app_state();
    let local_ip = util::network::get_local_ip();
    let app = Router::new()
        .merge(auth::routes::router())
        .merge(ws::routes::router())
        .merge(mock::routes::router())
        .nest_service("/static", ServeDir::new("static"))
        .with_state(state);
    // ...启动服务
}

它现在只做两件事：创建共享状态和组装路由。就像生物体的 DNA 不直接参与任何具体的生命活动，但它定义了整个生命体的蓝图——哪些器官要被创建、它们之间如何连接。main.rs 就是这个项目的 DNA：它不处理任何业务逻辑，但它决定了整个系统的组装方式。

四、本章小结

从 445 行到 30 行，减少的不只是代码量，而是认知负担。打开 main.rs，你一眼就能看清整个系统的骨架：有认证、有 WebSocket、有模拟数据、有静态文件服务。想深入哪个部分，再进对应的目录去看。这就是模块化带来的最直接的好处——你可以选择在什么层级上思考问题。

这种结构上的清晰，会立刻兑现为效率。比如我们给认证模块增加密码登录，整个过程只动了 auth/ 下的三个文件，其余模块完全无感。后端接口格式一变，前端测试立刻报红；改了一行请求体字段，测试重新全绿。

改动有边界，验证有手段——模块的边界限制了爆炸半径，测试用例在第一时间发出警报。两者配合，才让这个不断生长的代码体，具备了基本的自愈能力。

当然，由于目前功能较少、代码量不大，这次的结构重构是最朴素的——按功能域分目录、按职责分文件，仅此而已。没有抽象接口、没有依赖注入、没有分层架构。但这恰恰是对的：架构应该匹配当前的复杂度，而不是预支未来的复杂度。

随着功能不断生长，结构自然会跟着演化。比如当 auth/handler.rs 随着功能越来越多，它本身也会变得臃肿。我们就要考虑将认证，从 组织 到 器官 的进化。到那时候，再做更深层次的拆分和抽象也不迟。
