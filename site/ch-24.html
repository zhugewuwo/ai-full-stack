枝叶#1 ｜ 好友关系

能说话不等于认识，认识不等于信任。关系，是双向确认的产物。

上一章结束时，闪讯已经能发文字、图片、视频、文件了。但有一个尴尬的事实：任何人都可以给任何人发消息。没有好友的概念，没有申请和确认的过程，用户之间并没有存在真正的关系，如同一个个可以被任意连接的孤岛。这一章，我们要给岛屿修建专属的通路——建立好友关系系统。
最核心的是三大块，界面如下:

  • 通讯录中，展示用户的好友关系;可与好友发起对话。
  • 实现新添加朋友→搜索用户/扫码 →添加好友的流程。
  • 收到好友申请，用户可以在在审批界面进行统一和拒绝。

一、好友与会话

好友关系和会话，可能在很多人眼里看起来很像。从用户感知来说，"好友"和"聊天对象"几乎是同义词。但从系统设计的角度看，它们是两个完全不同的领域。

1. 好友与会话的区别

你认识一个人，和你跟这个人说过话，是两件事。你的通讯录里有一个人的号码，不代表你们之间有过任何对话。反过来，你在一个群里跟某人聊得热火朝天，但你们可能根本不是好友。这就是这个在概念上的本质区别：

好友是关系，会话是行为的容器。

关系是静态的、持久的、需要双方确认的。它回答的问题是 "我们之间有没有连接" 。它有状态——pending(发送中)、accepted(接收)、rejected(拒绝)——像一个有限状态机。

会话是动态的、临时的、单方面就能发起的。它回答的问题是 "消息往哪里投递"。它没有"申请"和"确认"的概念，创建即存在。

有趣的是，用户几乎感知不到这个区别。在微信里，点好友列表里的人，进入聊天；你点消息列表里的人，也进入聊天。入口不同，终点相同。用户眼里只有"人"，没有"关系"和"会话"的分别。

2.好友与会话的关系

想想现实世界。你的手机通讯录里有 500 个人，但你上周只跟其中 12 个人说过话。

通讯录是关系的存档，聊天记录是行为的痕迹。关系是"势能"，会话是"动能"。

你认识一个人，这是势能；你们开始聊天，势能转化为动能。但势能不会因为动能消失而消失——你们一个月没聊天，不代表你们不是朋友了。这揭示了一个更深的设计原则：状态和行为应该分开存储。好友关系是状态（谁认识谁），会话是行为的容器（谁在跟谁说话）。

在闪讯中，两者之间的关系是：

  • 接受好友请求之后，会自动创建一个会话，并附加对方申请时的留言。
  • 通讯录点击好友后，会进入详情页，其中可以发消息来打开或新建会话。

3. 在系统中区分的意义

理解了势能和动能的区别，再看系统设计就清晰了。好友和会话必须分开，不是因为技术偏好，而是因为它们在三个维度上有本质差异：

  • 生命周期不同。 删除好友时，聊天记录应该还在。如果好友和会话是同一个东西，删好友就意味着删会话——势能归零的同时，动能的历史痕迹也被抹去了。但用户的期望是：我不想在通讯录里看到这个人了，但我们之前聊过的东西别丢。分开存储，才能满足这种"选择性遗忘"。

  • 参与规则不同。 好友关系是点对点的、对称的、需要双方确认的。会话可以是一对多的、不对称的——群聊里的人不需要互为好友。如果把关系和会话绑在一起，群聊就没法设计了：难道群里每两个人都要先加好友？

  • 扩展方向不同。 好友关系会长出备注、分组、黑名单、权限——这些都是关系的属性。会话会长出消息类型、已读回执、置顶、免打扰——这些都是行为容器的属性。两棵树从同一个根分叉，但枝叶完全不同。把它们放在同一张表里，每加一个功能都要小心翼翼地区分"这是关系的事还是会话的事"。

分开之后，好处立竿见影：好友模块可以独立测试，不注入会话服务照样跑得通。

1. 交互链与目标

和上一章的富媒体消息不同，好友关系的交互链不是线性的"发送→接收"，而是一个双方参与的协商过程。A 发起申请，B 决定是否接受，接受后系统自动创建会话并发送打招呼消息。这个"接受后的连锁操作"是整个功能中最复杂的部分。

场景 用户故事 操作路径
搜索并添加 作为用户 A，我想搜索并添加 B 为好友 通讯录 → + → 添加朋友 → 搜索 → 点击用户 → 添加+留言 → 申请已发送
接受申请 作为用户 B，我想处理收到的好友申请 通讯录红点 → 新的朋友 → 看到申请+留言 → 接受 → 成为好友+自动创建会话
拒绝申请 作为用户 B，我想拒绝陌生人的申请 新的朋友 → 拒绝 → 申请消失
查看好友 作为用户，我想找到好友并聊天 通讯录 → 好友列表 → 点击好友 → 详情页 → 发消息
删除好友 作为用户 A，我想删除不再联系的人 好友详情页 → 删除好友 → 确认 → 双方关系解除

2. 逻辑流程树

好友系统的核心逻辑有两处：发送申请 + 申请审批，下面逐一看一下：
发送申请的逻辑比较直白：校验（不能加自己、用户存在、非好友）→ 写入申请表 → WS 通知对方。

时刻 事件 处理 产生的新事件
T0 A 发起 "添加好友" 前端调用 POST /api/friends/requests —
T1 服务端校验 不能加自己、用户存在、非好友 —
T2 校验通过 UPSERT friend_requests(status=pending) 触发 WS 通知
T3 WS 推送 FRIEND_REQUEST 帧推送给 B B 端收到通知
T4 B 端收到 FriendCubit 更新申请列表，pendingCount++ 通讯录红点

有意思的是接受申请，它触发了一连串的副作用：

时刻 事件 处理 产生的新事件
T0 B 点击"接受" POST /api/friends/requests/:id/accept —
T1 校验通过 UPDATE friend_requests SET status=accepted —
T2 创建好友关系 INSERT friend_relations 双向（A→B 和 B→A），事务 —
T3 自动创建会话 ConversationService.create_private(A, B) 会话创建
T4 发送打招呼消息 以 A 的身份发送留言内容（或默认文本） 消息广播
T5 WS 通知 A FRIEND_ACCEPTED 帧 + CONVERSATION_UPDATE 帧 A 端更新

三、后端：im-friend 模块

好友是一个独立的领域。它和会话没有从属关系，和消息也没有直接依赖。所以后端选择新建一个独立的 crate（im-friend），而不是塞进 im-conversation 里。下面是 im-friend 模块在整个后端系统中的功能和关系：

1. 数据模型：请求与关系表

好友系统只需要两张新表，friend_requests 表记录好友申请的数据；friend_relations 表记录好友关系。好友的背后都是用户，所以它们都和账户表有所关联。

先看好友申请表 friend_requests ：

-- ---> server/migrations/20260407_004_friends.sql
CREATE TABLE friend_requests (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    from_user_id BIGINT NOT NULL,
    to_user_id BIGINT NOT NULL,
    message VARCHAR(200),              -- 申请留言
    status SMALLINT NOT NULL DEFAULT 0, -- 0:待处理 1:已接受 2:已拒绝
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(from_user_id, to_user_id)   -- 同一对用户只能有一条申请
);

UNIQUE 约束 (from_user_id, to_user_id) 是关键。配合 repository 层的 ON CONFLICT DO UPDATE，实现了 upsert 语义。重复发送申请不会报错，而是覆盖旧的留言并重置状态为 pending。这个策略对齐了微信的行为——你可以反复给同一个人发申请，修改留言内容，对方会收到最新的通知。

// ---> server/modules/im-friend/src/repository.rs
fn create_request(from_user_id, to_user_id, message):
    INSERT INTO friend_requests (from_user_id, to_user_id, message)
    VALUES ($1, $2, $3)
    ON CONFLICT (from_user_id, to_user_id)
    DO UPDATE SET message = $3, status = 0, updated_at = NOW()
    RETURNING *

再看好友关系表 friend_relations。这里好友关系是要双向存储的，也就是说 A 和 B 成为好友时，插入两条记录：A→B 和 B→A。

CREATE TABLE friend_relations (
    user_id BIGINT NOT NULL,
    friend_id BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (user_id, friend_id)
);

查询"我的好友列表"时，只需要 WHERE user_id = $1，不需要 WHERE user_id = $1 OR friend_id = $1 这种 OR 条件。索引友好，查询简单。代价是写入时要在事务里插入两条记录：

// ---> server/modules/im-friend/src/repository.rs
fn create_relation(user_id, friend_id):
    BEGIN TRANSACTION
    INSERT INTO friend_relations (user_id, friend_id) VALUES ($1, $2) ON CONFLICT DO NOTHING
    INSERT INTO friend_relations (user_id, friend_id) VALUES ($2, $1) ON CONFLICT DO NOTHING
    COMMIT

删除好友同理，事务里删除两条。写入频率远低于查询频率，这个取舍是值得的。

2. 三层架构：repository → service → api

im-friend 的内部结构和 im-conversation、im-message 一致，三层各司其职：

// ---> server/modules/im-friend/src/
├── models.rs       # FriendRequest, FriendRelation, FriendError 等
├── repository.rs   # 数据库操作（申请/关系的 CRUD）
├── service.rs      # 业务逻辑（校验 + 调用 repo）
├── api.rs          # HTTP 路由（8 个好友接口 + 错误响应）
└── lib.rs          # 模块入口

models.rs 定义了错误枚举，每种错误映射到对应的 HTTP 状态码：

// ---> server/modules/im-friend/src/models.rs
pub enum FriendError {
    UserNotFound,       // → 404
    RequestNotFound,    // → 404
    RelationNotFound,   // → 404
    AlreadyFriends,     // → 400
    CannotAddSelf,      // → 400
    Forbidden,          // → 403
    Database(sqlx::Error), // → 500
}

service 层负责业务校验。以 send_request 为例，三个校验然后直接 upsert：

// ---> server/modules/im-friend/src/service.rs
fn send_request(from_user_id, to_user_id, message):
    if from_user_id == to_user_id:  return Err(CannotAddSelf)
    if !user_exists(to_user_id):    return Err(UserNotFound)
    if is_friend(from, to):         return Err(AlreadyFriends)
    // 允许重复发送（upsert 覆盖旧申请），不检查 pending 状态
    return repo.create_request(from_user_id, to_user_id, message)

accept_request 的校验更严格——只有被申请者（to_user_id）能接受，且申请必须是 pending 状态：

// ---> server/modules/im-friend/src/service.rs
fn accept_request(request_id, user_id):
    req = repo.find_request_by_id(request_id)  // → RequestNotFound
    if req.to_user_id != user_id:              return Err(Forbidden)
    if req.status != Pending:                  return Err(Forbidden)
    repo.update_request_status(request_id, Accepted)
    repo.create_relation(req.from_user_id, req.to_user_id)  // 双向事务

接受申请的 handler 是整个模块最复杂的函数，完整的连锁操作：

// ---> server/modules/im-friend/src/api.rs
fn accept_request(state, headers, path_id):
    user_id = extract_user_id(headers)
    request_id = parse_uuid(path_id)

    // 1. 获取申请信息（用于后续连锁操作）
    req_info = service.repo.find_request_by_id(request_id)

    // 2. 接受申请（校验 + 更新状态 + 创建双向关系）
    relation = service.accept_request(request_id, user_id)

    // 3. 自动创建私聊会话（幂等）
    greeting = req_info.message ?? "我们已经是好友了，开始聊天吧"
    conv = conv_service.create_private(req_info.from_user_id, user_id)

    // 4. 以申请者身份发送打招呼消息
    msg_service.send(NewMessage {
        conversation_id: conv.id,
        sender_id: req_info.from_user_id,  // 注意：是申请者发的
        content: greeting,
        msg_type: 0,  // 文本
    })

    // 5. WS 通知申请者：好友已接受
    (nickname, avatar) = service.repo.get_user_profile(user_id)
    dispatcher.notify_friend_accepted(req_info.from_user_id, ...)

    return 200 { "data": null }

// ---> server/modules/flash-user/src/handler.rs
fn search_users(keyword, limit):
    pattern = "%{keyword}%"
    id_match = keyword.parse::<i64>().unwrap_or(0)

    SELECT p.account_id, p.nickname, p.avatar
    FROM user_profiles p
    JOIN accounts a ON a.id = p.account_id
    LEFT JOIN auth_credentials c ON c.account_id = a.id AND c.auth_type = 'phone'
    WHERE a.status = 0
      AND (p.nickname ILIKE $1        -- 昵称模糊匹配
           OR c.identifier = $2       -- 手机号精确匹配
           OR a.id = $3)              -- 闪讯号精确匹配
    ORDER BY p.nickname
    LIMIT $4

2. FriendCubit：统一的状态管理

FriendCubit 是整个前端好友模块的核心。它同时管理好友列表、收到的申请、发送的申请、未读数，并订阅 WsClient 的三条好友 Stream。状态定义：

// ---> client/modules/flash_im_friend/lib/src/logic/friend_state.dart
class FriendState extends Equatable {
  final List<Friend> friends;
  final List<FriendRequest> receivedRequests;
  final List<FriendRequest> sentRequests;
  final int pendingCount;          // 未读申请数（通讯录红点）
  final bool isLoading;
  final String? error;
}

为什么好友列表和申请列表放在同一个 Cubit 里，而不是拆成 FriendListCubit 和 FriendRequestCubit？因为 pendingCount 需要跨页面同步——通讯录 Tab 的红点、好友申请页的列表、接受/拒绝后的计数更新，都要看同一份数据。拆开反而要引入额外的通信机制。

WS 帧的处理是 FriendCubit 的另一个职责。用通知里携带的数据（昵称、头像、ID）构造对象插入本地列表， 如下三个 handler 都是纯内存操作，不需要重新拉取接口：

// ---> client/modules/flash_im_friend/lib/src/logic/friend_cubit.dart

void _handleFriendRequest(WsFrame frame) {
  final notification = FriendRequestNotification.fromBuffer(frame.payload);
  final request = FriendRequest(
    id: notification.requestId,
    // ...
  );
  emit(state.copyWith(
    receivedRequests: [request, ...state.receivedRequests],
    pendingCount: state.pendingCount + 1,
  ));
}

void _handleFriendAccepted(WsFrame frame) {
  final notification = FriendAcceptedNotification.fromBuffer(frame.payload);
  final friend = Friend(
    friendId: notification.friendId,
    // ...
  );
  // 去重后插入
  if (!state.friends.any((f) => f.friendId == friend.friendId)) {
    emit(state.copyWith(friends: [...state.friends, friend]));
  }
}

void _handleFriendRemoved(WsFrame frame) {
  final notification = FriendRemovedNotification.fromBuffer(frame.payload);
  final updated = state.friends
      .where((f) => f.friendId != notification.friendId).toList();
  emit(state.copyWith(friends: updated));
}

接受申请时，先调用 HTTP 接口，成功后从 receivedRequests 移除对应条目、pendingCount--，然后重新 loadFriends()（因为新好友出现了）。删除申请记录时，同时从 receivedRequests 和 sentRequests 中移除，确保切换 Tab 不会复活已删除的条目。

好友列表 → 聊天的跳转链路涉及三个模块的协作：点击好友 → push FriendDetailPage → 点击"发消息" → pop 详情页 → ConversationRepository.createPrivate(friendId)（幂等）→ push ChatPage。createPrivate 是幂等的——如果已有会话直接返回，没有则创建。这样不需要在好友模块里维护"好友→会话"的映射关系，每次都走一遍创建接口就行，简单可靠。

还记得在发送消息时，我们写了个 send_message.py 脚本，可以以 A 的 身份发消息给 B 吗？对于好友申请来说，切换账号发送好友申请也是个非常麻烦的活，对测试很不友好。同理，可以准备一个脚本 send_friend_request.py 帮助我们批量发送好友申请:

批量发送好友申请
用法:
  # A → B 单个申请
  python scripts/server/im/send_friend_request.py 0001 0002

  # A → B,C,D 批量申请（A 发给多人）
  python scripts/server/im/send_friend_request.py 0001 0002,0003,0004

  # 连续序号：A → 0002~0010
  python scripts/server/im/send_friend_request.py 0001 0002-0010

  # B,C,D → A 反向批量（多人发给 A）
  python scripts/server/im/send_friend_request.py 0002,0003,0004 0001

  # 连续序号反向：0002~0010 → A
  python scripts/server/im/send_friend_request.py 0002-0010 0001

  # 带留言
  python scripts/server/im/send_friend_request.py 0001 0002-0005 "你好"

  # 发送并自动接受
  python scripts/server/im/send_friend_request.py 0001 0002-0005 --accept

参数:
  第1个: 发送方（单个后缀 / 逗号分隔 / 连字符范围）
  第2个: 接收方（同上）
  第3个: 留言（可选）
  --accept: 发送后自动让接收方接受

五、本章小结

存档点 tag 提交点
图片视频与文件消息 v0.12.0 0017583

这一章给闪讯的用户之间修了路。后端新建了 im-friend 独立 crate（10 个接口 + 3 种 WS 帧类型），前端新建了 flash_im_friend 模块（微信风格通讯录 + 好友详情 + 添加朋友 + 搜索 + 扫码 + 申请管理）。功能网络从 52 个节点增长到 65 个。

回头看，好友系统的核心挑战不在于某个接口有多难写，而在于"关系"这个概念本身的复杂性。它是双向的（需要双方确认）、有状态的（pending → accepted / rejected）、有副作用的（接受后连锁创建会话和消息）。把这些复杂性拆解到正确的层次——service 管校验、api 管编排、WS 管通知——是这一章最重要的架构决策。

好友关系是 IM 系统的社交基础。有了它，后续的群聊（从好友中选人建群）、朋友圈（只对好友可见）、黑名单（屏蔽特定用户）才有了依托。目前还没有做好友备注、好友分组、在线状态这些功能，但数据模型和模块边界已经为它们预留了空间。

另外值得一提的是，这一章的开发过程中，项目的脚本体系也做了一次整理：所有 PowerShell 脚本统一迁移为 Python（start.py、reset_db.py、seed.py、run.py、gen.py），支持 Windows / macOS / Linux 跨平台。这不是功能需求驱动的，而是开发体验驱动的——当你每天要跑十几次脚本时，一套统一的工具链比什么都重要。
