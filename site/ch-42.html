果实#8 ｜ 构建纯血鸿蒙产品

闪讯目前的构建，已经覆盖了 Android、iOS、macOS、Windows、Linux、Web 六大平台。这是 Flutter 官方支持的所有平台，但除此之外目前还有一个正在成长的国内操作系统： HarmonyOS 纯血鸿蒙的平台。

  • 好消息是：Flutter 可以支持构建出鸿蒙产物
  • 坏消息是: 不是 Google 官方的 Flutter，而且目前最高版本是 3.41.10

鸿蒙在对跨平台的支持上一直很用心，特别是 Flutter，从版本来看，和 Flutter 官方的稳定版已经非常接近了。我个人也在鸿蒙应用商店上架了三款 Flutter 构建的鸿蒙应用。本篇将从 0 开始，看看我们的闪讯如何构建出 HarmonyOS 的产品。

四、优化可维护性

为了支持鸿蒙，很多时候回带给项目带来一些破坏性的改变。或者某些功能因鸿蒙平台的不支持，不得不砍掉。面对这种在真实场景中存在的差异。我们需要有一定的手段去保证项目的可维护性，下面就本地缓存功能的插拔为例，介绍一下短期无法兼容功能时，该怎么办。

1. 数据库的囧境

闪讯使用 drift 作为本地数据库 ORM。drift 底层通过 dart:ffi 加载原生 SQLite 库。这条链路在六个平台上都能正常工作，但在鸿蒙上断了：

sqlite3 包的构建 hook 不认识 ohos 平台，编译直接失败。这不是运行时的问题——只要 sqlite3 出现在依赖树里，hook 就会触发，不管你运行时用不用它。

以前我使用的本地缓存是 sqflite，它已经有了鸿蒙版的兼容插件，但目前 AI 已经选用 drift 迭代了这么多版本，感觉这时候换掉动静有点大。倒不如暂且去掉本地缓存的支持，仅使用网络数据。我们目前的架构，要做到这一点有多难呢？

2. 结构分级的优势

在解决方案之前，先看看为什么闪讯的数据层 能够 被轻松拆解。航天火箭是分级结构：一级发动机负责起飞、二级负责入轨、三级负责变轨。每一级通过标准化的级间连接器对接——拆掉一级不影响二级的工作，换一个更强的一级也不需要重新设计整个火箭。

很幸运的是: 闪讯的数据层也是这样设计的。在之前的缓存章节中，我们设计了如下的分层结构：

业务模块只依赖 LocalStore 接口，不直接接触 drift 的任何类型。这意味着实现层是可更换的——如果未来需要换成 Hive、Isar、sqflite 或其他方案，只需要新建一个 XxxLocalStore implements LocalStore，业务层一行都不用改。这就像火箭的载荷舱不需要知道，下面装的是液氧煤油、发动机、还是氢氧发动机——它只关心"推力接口"是否满足。

其实，这就是 依赖倒置原则（Dependency Inversion Principle, DIP）

高层模块不应该依赖低层模块，两者都应该依赖抽象。

在这里，ChatCubit（高层）不依赖 DriftLocalStore（低层），两者都依赖 LocalStore（抽象）。正是这个原则让我们今天能把"发动机"拆下来换一个，而"载荷舱"纹丝不动。

设计原则或者是设计模式，其实并不是书本上空洞的文字，而是在非常具体的场景下，在系统中发挥效力的关键链条。它是在真实工程困境中，撑住系统不崩塌的那根关键链条。

3. 将 drift 实现独立拆分出去

首先说说我们要的结果是什么，然后再向结果去努力:

在构建 鸿蒙产物 时，不依赖 drift 插件，从源头彻底剔除。可以保障编译正常。
在构建 其他平台 时，保持之前的功能，把 drift 插件实现加进来。保证功能完整。

目前的状态缓存相关功能都内聚在 flash_im_cache 模块中，包括 drift 的实现。如果不引用这个库 LocalStore（抽象）将无法访问，而引入这个库 drift 的依赖又会被加入：

flash_im_cache/
├── local_store.dart          ← 抽象接口
├── models/                   ← 纯 Dart 模型
├── sync_engine.dart          ← 同步引擎
└── drift/                    ← drift 实现（依赖 drift/sqlite3）
    ├── drift_local_store.dart
    ├── database/
    └── dao/

在编程中，有一个概念叫做 抽象与实现分离。它不只是代码层面类与类的关系，也可以作用于模块的拆解分离。但放到眼前的困境里，它变成了一把非常具体的手术刀：把 flash_im_cache 拆分为两级：

  • flash_im_cache 是纯接口包：只装"契约"（LocalStore 抽象、纯 Dart 模型、SyncEngine），不依赖drift 等具体的库。轻如空气，谁都能引。
  • flash_im_cache_drift 实现包：只装"兑现契约的人"（DriftLocalStore + AppDatabase + DAO），依赖 drift/sqlite3 那些沉重的原生链路。

拆完之后，上层业务模块只引接口包。鸿蒙构建时不引实现包，依赖树里就不会出现 sqlite3，hook 自然无从触发。其他平台照常引入实现包，功能完整。

这就像一份合同和一个承包商的关系：甲方（业务模块）只关心合同条款（接口），不关心哪个施工队来干活。换一支施工队，合同不用重签。

4. 内聚与解耦合

"内聚"和"解耦"是一对镜像概念。

  • 内聚是向内看：一个模块内部的东西是否属于同一个关注点；
  • 解耦是向外看：模块之间是否只通过最小化的契约连接。

这里 flash_im_cache 之所以能被干净地一分为二，恰恰是因为它同时满足了这两件事：

内聚表现

drift 的所有类型（AppDatabase、Companion、TableData、DAO）被严格限制在 drift/ 目录内部。它们从不出现在 LocalStore 的方法签名里，从不被上层 import。ORM 的血液在内部闭环循环，一滴都没有泄漏到外面。这不是偶然，这是有意为之的边界纪律。

解耦表现

层模块（ChatCubit、ConversationRepository）和数据实现之间，唯一的连接点是 LocalStore 这根细线。细到二十几个方法签名，参数全是纯 Dart 模型。没有泛型绑定 drift 类型，没有 Companion 或 TableData 暴露给外部。

当这两个条件同时成立时，拆分的切面就是天然的。沿着 drift/ 目录的边界切一刀，两块组织各自完整，切面是干净的，没有粘连。如果当初偷了懒，让 ChatCubit 直接 import AppDatabase，让 ConversationRepository 直接访问 drift，今天这一刀就不是"搬个目录"，而是"全身换血"。这大概是依赖倒置原则最实在的回报。

你在设计时多花的那十分钟定义接口，在未来某个你根本无法预见的时刻，省下了你十天的重构。

如果此时想更换数据库为 sqflite，逻辑完全相同：再写一个 flash_im_cache_sqflite，实现 LocalStore 接口允诺的契约即可。系统不关心谁在兑现承诺，只关心承诺被兑现。

在代码层面，localStore 的具体实现，在 main.dart 的装配中提供。这样

  • 在 鸿蒙平台：不引入实现包，drift/sqlite3 从依赖树中彻底消失
  • 其他六个平台：引入 flash_im_cache_drift 实现包，注入 DriftLocalStore ，让功能完整。
鸿蒙：不引入实现包 其他平台，引入实现包，功能完整

切换实现只需要改 main.dart 中的一行：

---->[lib/main.dart]----
// 六平台
localStore = await DriftLocalStore.open(user.userId);

// 鸿蒙
localStore = EmptyLocalStore();
5. 构建时的切换脚本

这里构建鸿蒙和其他平台在代码层面出现了差异： yaml 的 覆写和 main.dart 里的装配。
一般会通过两个分支来维护不同的代码。打包鸿蒙时，同步最新分支的代码逻辑。但目前差别不大，只有两处，而且鸿蒙的打包构建频率也不高，所以采用了一个更柔和的方案，打包脚本自动切换代码状态：

  • 构建前自动切换为鸿蒙配置（overrides + EmptyLocalStore），
  • 构建后无论成功失败都还原为正常配置。

另外，鸿蒙的 Flutter SDK 版本也可以写在 build.json ，实现配置化的管理:

这样一行命令就可以构建出鸿蒙可以提交商店的 .app 分发包。差异性在构建流程上，几乎可以完全没有感知。

python scripts/build_center/ohos/build_ohos.py

另外，比如在调试功能时，想持续保持鸿蒙的兼容状态。脚本也提供了切换代码状态的功能 save：

python scripts/build_center/ohos/build_ohos.py save

想恢复到非鸿蒙代码状态，只需要 restore 即可：

python scripts/build_center/ohos/build_ohos.py restore

五、本章小结

到这里，闪讯的七个平台产物构建全部完成了。

回头看这段旅程，有种攀完一座山回望来路的感觉。Android 和 iOS 是熟悉的公路，Windows 和 macOS 是需要适应的山路，Linux 是人迹罕至的小径，Web 是一片看似平坦却暗藏沼泽的草地，而鸿蒙——鸿蒙是需要自己架桥才能通过的峡谷。

七个平台，一套 Dart 代码。这句话说出来轻巧，但每多覆盖一个平台，不是简单的"加一个构建命令"。每个平台都在某个你意想不到的地方挖了一个坑：Web 端 dart:ffi 不可用、鸿蒙的 native assets hook 不认识 ohos、桌面端窗口管理的差异、iOS 的签名和沙盒……

但最终能走通，靠的不是每次都想出巧妙的计策，而是最初的几个正确决策在持续发挥复利：

  • 定义 LocalStore 抽象接口时，不知道会有鸿蒙这个坑——但它让今天的适配变成了"换一行代码"。
  • 用 kApp 包装平台判断时，不知道 Web 端 Platform 会崩——但它让所有平台判断都安全了。
  • 让后端一行 nest_service 托管 Web 产物时，不知道 CORS 会有多麻烦——但同源部署让这个问题根本不存在。

好的架构不是预见了所有问题，而是在问题出现时，给了你足够的余地去应对。就像一棵树不需要知道明年的风从哪个方向吹——它只需要根扎得够深，枝干足够柔韧。

七个平台，每条命令一个产物。这本身就是 Flutter 对"一次编写，处处运行"这句古老承诺最诚实的兑现，虽然每一个"处处"都需要你亲手打磨那最后一公里。

下一篇，也是本册最后一篇，我们将目光从"构建"转向"生长"——一棵已经扎根七片土地的树，如何让它知道自己该长高了？如何让果实从枝头安全落到用户手中？

版本检测与应用升级。这不是一个华丽的功能，但它是所有后续功能抵达用户的通道。没有它，你写的每一行代码都停留在仓库里；有了它，每一次 git push 都有了变成用户指尖体验的可能。

那将是另一段冒险征程的起点。
