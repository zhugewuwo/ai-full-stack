1. 交互链：用户视角的操作路径

分析的起点是用户故事。富媒体消息涉及六个场景，每个场景都是一条完整的交互链：

场景 用户故事 操作路径
发送图片 作为用户，我想发一张图片给对方，以便用图片表达内容 点击 + → 照片/拍照 → 选择或拍摄 → 图片出现+上传进度 → 发送成功
发送视频 作为用户，我想发一段视频给对方，以便分享视频内容 点击 + → 视频 → 选择视频 → 缩略图+上传进度 → 播放按钮+时长
发送文件 作为用户，我想发一个文件给对方，以便传递文档资料 点击 + → 文件 → 选择文件 → 文件名+图标+上传进度 → 文件卡片

下载文件 作为用户，我想下载对方发来的文件，以便在本地查看 看到文件卡片 → 点击 → 文件预览页 → 下载 → 完成
2. 逻辑树：系统视角的处理流程

用户点了"发送"之后，系统内部发生了什么？这是逻辑树要回答的问题。
富媒体消息比文本消息多了一个上传环节，整条链路变成了两段式：先上传文件拿到 URL，再通过 WS 发送消息帧。以图片消息为例，完整的事件流：

时刻 事件 处理 产生的新事件
T0 用户选择图片 创建占位消息(content=本地路径)，立刻上屏 触发上传
T1 HTTP 上传 POST /api/upload/image，服务端校验+存储+生成缩略图 返回 URL 和元数据
T2 上传完成 更新消息 extra（宽高等），不替换 content 触发 WS 发送
T3 WS 发送 CHAT_MESSAGE 帧(type=IMAGE, content=服务端URL) 服务端处理
T4 服务端处理 验证成员 → 分配 seq → 存储 → 生成预览"[图片]" → 广播 ACK + 广播
T5 收到 ACK 消息状态 sending → sent 完成

视频和文件的流程结构相同，区别在于：

类型 上传前额外步骤 上传接口 服务端额外处理 预览文本
图片 读取本地文件大小 /upload/image 生成 webp 缩略图 [图片]
视频 客户端提取首帧缩略图+时长+宽高 /upload/video（含缩略图） 仅存储，不处理视频 [视频]
文件 读取本地文件大小 /upload/file 仅存储 [文件]

关键发现：文件上传和消息发送是两步操作。先上传获取 URL，再通过 WS 发送消息帧。这个解耦很重要，它意味着 存储和通信是独立的，未来切换云存储不影响消息链路。

二、后端：文件存储与消息拓展

图片、视频、文件消息，都属于存储的范畴，但现有的后端没有任何文件处理能力。消息表虽然预留了 type 和 extra 字段，但代码里从没用过。这次要做的事情分两块：建立文件存储基础设施，扩展消息链路支持多类型。

1. app-storage：独立的文件存储模块

文件存储被设计为一个独立的 crate（app-storage），不依赖任何 IM 业务模块。未来头像上传、群头像上传都可以复用它，不需要绕道 im-message。

它内部有三层：最底层是 ImageProcessor，专门处理图片。接收原始图片字节，解码获取宽高，缩放生成缩略图：

// ---> server/modules/app-storage/src/image.rs
fn process(image_bytes) -> (width, height, thumbnail_bytes):
    img = decode(image_bytes)                  // image crate 解码
    width, height = img.dimensions()
    if width > 200 or height > 200:
        img = resize(img, max=200, Lanczos3)   // 按长边等比缩放
    thumbnail = encode_webp(img)               // 编码为 webp
    return (width, height, thumbnail)

中间层是 StorageService，负责文件的存储管理。校验大小和格式，生成按日期分层的路径，写入磁盘，图片额外调用 ImageProcessor 生成缩略图：

// ---> server/modules/app-storage/src/service.rs
fn upload_image(data, filename):
    check size <= max_image_size               // 超限返回 400
    check ext in [jpg, png, gif, webp]         // 格式白名单
    path = "uploads/original/{yyyy}/{mm}/{uuid}.{ext}"
    write(path, data)                          // tokio::fs 异步写入
    (w, h, thumb) = ImageProcessor.process(data)
    thumb_path = "uploads/thumb/{yyyy}/{mm}/{uuid}.webp"
    write(thumb_path, thumb)
    return { original_url, thumbnail_url, width, height, size, format }

存储目录按类型和日期分层，文件名用 UUID，避免冲突。URL 用相对路径（/uploads/original/...），客户端拼接 baseUrl 访问。静态文件服务直接用 tower-http 的 ServeDir 挂载，不需要额外代码处理。

uploads/
├── original/2026/04/   # 原图
├── thumb/2026/04/      # 缩略图（图片 webp + 视频首帧 jpg）
├── video/2026/04/      # 视频文件
└── file/2026/04/       # 普通文件

最上层是 API 路由，提供三个 HTTP 上传接口。用 axum 的 Multipart 提取器解析请求，调用 StorageService 完成存储后返回 JSON：

POST /api/upload/image  → multipart(file)                          → ImageUploadResponse
POST /api/upload/video  → multipart(video, thumbnail, duration_ms) → VideoUploadResponse
POST /api/upload/file   → multipart(file)                          → FileUploadResponse
2. 消息链路扩展

后端消息链路的改动出奇地小，因为 v0.0.3 设计消息表时就预留了 type SMALLINT 和 extra JSONB 两个字段，只是代码里一直没用。现在要做的是"激活"它们。

第一处改动在数据模型。NewMessage 结构体原来只有三个字段（conversation_id, sender_id, content），现在加上 msg_type 和 extra：

// ---> server/modules/im-message/src/models.rs
pub struct NewMessage {
    pub conversation_id: Uuid,
    pub sender_id: i64,
    pub content: String,
    pub msg_type: i16,                        // 新增
    pub extra: Option<serde_json::Value>,     // 新增
}

第二处改动在存储层。repository 的 INSERT SQL 从只写四列变成写六列：

-- 之前
INSERT INTO messages (conversation_id, sender_id, seq, content) VALUES ($1, $2, $3, $4)

-- 之后
INSERT INTO messages (conversation_id, sender_id, seq, type, content, extra) VALUES ($1, $2, $3, $4, $5, $6)

不需要数据库迁移，因为 type 有默认值 0（文本），extra 默认 NULL。已有的消息数据完全兼容。

第三处改动在预览生成。service.send() 里原来的预览逻辑是"文本截断前 50 字符"，现在改为按类型分支：

// ---> server/modules/im-message/src/models.rs
pub fn generate_preview(content: &str, msg_type: i16) -> String {
    match msg_type {
        1 => "[图片]".to_string(),
        2 => "[视频]".to_string(),
        3 => "[文件]".to_string(),
        _ => // 文本截断前 50 字符
    }
}

这个函数决定了会话列表里显示什么预览文字。发一张图片，会话列表显示"[图片]"而不是一个 URL。

第四处改动在帧分发器。dispatcher 从 SendMessageRequest 中提取 type 和 extra，传给 NewMessage：

// ---> server/modules/im-ws/src/dispatcher.rs
let new_msg = NewMessage {
    conversation_id,
    sender_id,
    content: request.content,
    msg_type: request.r#type as i16,          // proto 枚举转 i16
    extra: if request.extra.is_empty() {
        None
    } else {
        serde_json::from_slice(&request.extra).ok()  // bytes → JSON
    },
};

广播器也改了一行：ChatMessage 的 extra 字段从写死的空 vec 改为从 Message 实体中读取实际值，这样接收方才能拿到图片的宽高、视频的时长等元数据。

proto 的 MessageType 枚举只是加了三个值，向后兼容：

// ---> proto/message.proto
enum MessageType {
  TEXT = 0;
  IMAGE = 1;
  VIDEO = 2;
  FILE = 3;
}

四处改动，没有新建表，没有新建接口，没有改变已有的数据流向。这就是预留字段的价值：设计时多想一步，扩展时少改十处。

4. 关于文件存储的选择

生产环境的文件存储通常用云服务（阿里云 OSS、AWS S3 等），客户端直传：服务端只签发临时上传凭证，文件流量不经过应用服务器。但云存储是收费的，开发阶段没必要引入额外成本。当前用本地磁盘 + tower-http 静态文件服务，是最简单的方案，先把整条流程跑通。

好在当前"先上传拿 URL，再发消息"的两步架构天然兼容云存储模式。未来切换时，服务端的上传接口从"接收文件并存储"变成"签发凭证并返回"，客户端的上传目标从自己的服务端换成云存储，消息链路完全不用动。

1. Message 模型：从纯文本到多模态

原来的 Message 只有一个 content 字段，装文本内容。现在它需要知道自己是什么类型，以及携带类型相关的元数据。

// ---> client/modules/flash_im_chat/lib/src/data/message.dart
enum MessageType { text, image, video, file }

class Message {
  // ... 已有字段 ...
  final MessageType type;                // 新增
  final Map<String, dynamic>? extra;     // 新增

  bool get isImage => type == MessageType.image;
  bool get isVideo => type == MessageType.video;
  bool get isFile => type == MessageType.file;

  VideoExtra? get videoExtra => ...;     // 从 extra 解析
  FileExtra? get fileExtra => ...;       // 从 extra 解析
}

VideoExtra 和 FileExtra 是两个数据类，从 extra Map 中解析出结构化的信息。VideoExtra 有 thumbnailUrl、durationMs、width、height、fileSize，还提供 formattedDuration（"1:23"）。FileExtra 有 fileName、fileSize、fileUrl、fileType，还提供 formattedSize（"1.5 MB"）。

一个设计决策：Message 模型用自定义的 MessageType 枚举，不直接用 proto 生成的 MessageType。这样 Message 类不需要 import flash_im_core，保持了数据层和通信层的隔离。ChatCubit 在发送时做一次转换（本地枚举 → proto 枚举），接收时做反向转换。

2. 发送流程：上传和通信的两步舞

WsClient.sendMessage 原来硬编码 type=TEXT，现在扩展为支持 type 和 extra 参数：

// ---> client/modules/flash_im_core/lib/src/logic/ws_client.dart
void sendMessage({
  required String conversationId,
  required String content,
  MessageType type = MessageType.TEXT,    // 新增
  List<int>? extra,                       // 新增
  String? clientId,
})

MessageRepository 新增三个上传方法，都支持 onProgress 回调：

// ---> client/modules/flash_im_chat/lib/src/data/message_repository.dart
Future<ImageUploadResult> uploadImage(String filePath, {onProgress?})

Future<VideoUploadResult> uploadVideo(String videoPath, String thumbPath, int durationMs, {width?, height?, onProgress?})

Future<FileUploadResult> uploadFile(String filePath, {onProgress?})

Future<String> downloadFile(String url, String savePath, {onProgress?})

发送一条图片消息，客户端内部的完整流程：用户选择图片 → ChatCubit 创建占位消息（content=本地文件路径），立刻 emit 上屏 → 调用 uploadImage 上传到服务端 → 上传完成，更新占位消息的 extra（宽高等元数据）→ 通过 WsClient.sendMessage 发送 CHAT_MESSAGE 帧 → 收到 ACK，状态从 sending 变为 sent。

视频发送多一步，选择视频后先调用 VideoThumbnailService 提取首帧缩略图、时长和宽高，再走上传流程。文件发送会先读取本地文件大小，写入占位消息的 extra，这样气泡从一开始就能显示正确的文件大小。

3. 输入栏改造：功能面板

ChatInput 原来只有文本输入框 + 发送按钮。现在在输入框左侧加了一个"+"按钮，点击弹出功能面板：

// ---> client/modules/flash_im_chat/lib/src/view/chat_input.dart
class ChatInput extends StatefulWidget {
  final ValueChanged<String> onSend;        // 已有：发送文本
  final ValueChanged<String>? onSendImage;  // 新增：图片路径
  final ValueChanged<String>? onSendVideo;  // 新增：视频路径
  final ValueChanged<String>? onSendFile;   // 新增：文件路径
}

功能面板是一个 AnimatedContainer，高度 200，2×2 网格布局，四个入口：照片（ImagePicker.gallery）、拍照（ImagePicker.camera）、视频（ImagePicker.pickVideo）、文件（FilePicker.pickFiles）。选择完成后自动关闭面板。

4. 气泡渲染：按类型分发

MessageBubble 原来只渲染文本气泡。现在根据 message.type 分发到不同的渲染方法：

// ---> client/modules/flash_im_chat/lib/src/view/message_bubble.dart
Widget _buildBubble() {
  if (message.isImage) return _buildImageContent();
  if (message.isVideo) return _buildVideoContent();
  if (message.isFile) return _buildFileContent();
  return _buildTextBubble();
}

图片气泡需要区分本地和网络：自己发的图片 content 是本地路径，用 Image.file() 显示；接收的图片 content 是服务端 URL，用 Image.network() 显示。网络图片用 Stack 叠加占位框，避免加载前尺寸为 0 的闪烁。占位尺寸从 extra 的 width/height 等比计算（限制在 250×300 内）。

视频气泡显示缩略图 + 半透明圆形播放按钮 + 底部渐变遮罩时长。同样区分本地和网络缩略图，同样用 extra 宽高做占位。

文件气泡是一个白底卡片（宽 237px），左侧文件名+大小，右侧按扩展名着色的文件图标（pdf 红色、doc 蓝色、zip 琥珀色等）。接收方未下载时整个卡片灰色调，下载中淡蓝色背景从左到右渐进填充，已下载白色背景+绿色小勾。自己发的始终白色背景。

四、体验细节：进度、预览与布局

功能跑通只是第一步。用户不会关心你的消息帧是怎么编码的，不会关心你的 seq 是怎么递增的，他们只关心：图片发出去了吗？进度到哪了？点开能看吗？文件能下载吗？这些"最后一公里"的体验细节，往往比核心链路花更多的时间去打磨。

1. 上传进度

上传进度通过 dio 的 onSendProgress 回调获取，存储在 ChatState.uploadProgress（double? 0.0~1.0）中。三种媒体类型的进度表现各不相同：

图片和视频气泡在上传中时，缩略图上叠加一层半透明黑色蒙层，中间是一个圆形进度指示器（CircularProgressIndicator），value 绑定 uploadProgress。用户能直观看到"上传了多少"。进度到 100% 后蒙层立刻消失，不等 ACK，因为从用户感知来说上传完成就是"发出去了"，ACK 只是系统内部的确认。

发送图片 发送文件

文件气泡没有缩略图可以叠蒙层，所以用另一种方式：淡蓝色背景从左到右渐进填充，宽度比例等于上传进度。用 FractionallySizedBox 的 widthFactor 绑定 uploadProgress 实现，视觉上像一个从左往右推进的进度条，但不是独立的进度条组件，而是卡片背景本身在变化。

左侧的 sending 转圈（12px CircularProgressIndicator）在整个 sending 状态期间始终显示，不受 uploadProgress 影响。上传中转圈，等待 ACK 也转圈，直到 status 变为 sent 才消失。

2. 多媒体预览

点击图片气泡进入 ImagePreviewPage。页面结构简单：黑色背景，InteractiveViewer 包裹 Image.network，支持双指缩放和平移。AppBar 透明，返回按钮白色，点击图片区域外的空白也能关闭页面。InteractiveViewer 是 Flutter 内置组件，自动处理缩放边界、惯性滑动、双击缩放等交互，开箱即用，不需要第三方库。

图片参考 视频参考

点击视频气泡进入 VideoPlayerPage。页面用 Flutter 官方的 video_player 插件，通过 VideoPlayerController.networkUrl 加载视频 URL，初始化完成后自动开始播放。底部有一个控制栏：渐变遮罩背景（从透明到半透明黑色），VideoProgressIndicator 显示播放进度（支持拖动），播放/暂停按钮。控制栏的颜色和主题保持一致（进度条蓝色 #3B82F6，按钮白色）。视频控制器在 initState 中创建，在 dispose 中销毁，生命周期和页面绑定，页面关闭时视频自动停止。

目前这两个预览页面的实现比较简单，只做了最基本的查看功能。后续随着产品演进，朋友圈、群公告、个人资料页等模块也会涉及图片预览和视频播放，到时候可以考虑把它们抽离到 flash_shared 或独立的 flash_media 模块中，作为跨模块共享的多媒体能力。不过当前阶段只有聊天页在用，过早抽取反而增加复杂度，先放在 flash_im_chat 里够用了。等真正出现第二个消费者时再抽离也不迟。

3. 文件预览与下载

文件消息和图片、视频不同，它没有可以直接渲染的视觉内容。用户看到的是一个卡片：文件名、大小、类型图标。点击后进入 FilePreviewPage，而不是直接触发下载。这个交互参考了微信的文件预览页：居中显示文件图标和信息，底部放下载按钮，下载中显示进度和暂停按钮。

文件预览 文件下载中 文件下载气泡

下载状态的管理是一个设计选择。最初考虑让 FilePreviewPage 自己管理状态（StatefulWidget 内部维护），但这样有一个问题：从预览页返回聊天页后，气泡无法知道文件已经下载完了，还是显示灰色的"未下载"状态。

所以把下载状态提升到 ChatCubit 层面。ChatState 里维护一个 fileDownloads: Map<String, FileDownloadInfo>，key 是 messageId：

// ---> client/modules/flash_im_chat/lib/src/logic/chat_state.dart
enum FileDownloadStatus { idle, downloading, done, error }

class FileDownloadInfo {
  final FileDownloadStatus status;
  final double progress;       // 0.0 ~ 1.0
  final String? localPath;     // 下载完成后的本地路径
  final String? error;
}

class ChatLoaded extends ChatState {
  final List<Message> messages;
  final double? uploadProgress;
  final Map<String, FileDownloadInfo> fileDownloads;  // key = messageId
}

ChatCubit 提供 downloadFile 方法，内部调用 dio.download，通过回调更新 Map：

// ---> client/modules/flash_im_chat/lib/src/logic/chat_cubit.dart
Future<void> downloadFile(String messageId, String fullUrl, String fileName) async {
  emit fileDownloads[messageId] = downloading(progress: 0)

  repository.downloadFile(fullUrl, savePath,
    onProgress: (p) => emit fileDownloads[messageId] = downloading(progress: p)
  )

  emit fileDownloads[messageId] = done(localPath: savePath)
  // 异常时 emit fileDownloads[messageId] = error(msg)
}

FilePreviewPage 通过 BlocProvider.value 共享 ChatCubit 实例，用 BlocBuilder 监听状态变化。气泡也从 ChatState.fileDownloads[messageId] 读取状态。两边看到的是同一份数据，在预览页点击下载后，回到聊天页气泡立刻从灰色变成蓝色渐进（下载中）或白色+绿勾（已完成）。

下载保存到临时目录（getTemporaryDirectory），文件名用原始文件名。当前没有做"保存到相册"或"保存到下载目录"的功能，后续按需加。

五、本章小结

这一章走完了从分析到归档的完整流程。后端新增了一个独立的文件存储模块（app-storage），扩展了消息链路支持多类型。前端改造了输入栏、气泡渲染、新增了三个预览/播放页面。功能网络从 37 个节点增长到 49 个。

存档点 tag 提交点
图片视频与文件消息 v0.11.0 e52c737

目前完成的是基本的发送和展示能力：
选择文件 → 上传 → 发送 → 对方收到 → 渲染气泡 → 点击预览/播放/下载。

但还有一些更深层次的问题没有解决。比如下载状态目前存在内存里（ChatCubit 的 fileDownloads Map），退出聊天页再进来就丢了，之前下载过的文件又变成"未下载"状态。图片和视频也是一样，每次进入聊天页都要重新从网络加载。这些问题的根源是缺少本地持久化。后续引入消息的本地缓存（SQLite）后，下载状态、文件本地路径、图片缓存都可以持久化，体验会进一步完善。

到这里，闪讯已经能发文字、图片、视频、文件了。一个"能用"的聊天工具的雏形已经成型。但目前用户之间的关系是"裸"的，任何人都可以给任何人发消息，没有好友的概念，没有申请和确认的过程。接下来，是时候让用户之间建立真正的联系了：好友关系。
