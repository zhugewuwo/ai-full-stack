根芽#3 ｜ 消息收发 - 后端链路

生命始于第一次呼吸，IM 始于第一条消息。

上一篇搭好了会话容器：两张表、三个接口、51 个测试会话。打开 App，会话列表满满当当，但点进任何一个，都是空的。会话是信封，现在要往里面装信。本章的目的是，实现消息收发的后端链路：

    1. A 向 B 在会话容器内发送一条消息。
    1. A 发的消息存储到后端的服务器。
    1. A 可以服务器接确认收到消息的信号。
    1. 服务端向 B 发送通知，B 收到消息。
    1. 服务端向 A、B 发送通知，更新会话。

一、消息需要什么

回到日常体验。你在微信里给女神发了一句"在吗"，这个动作看起来很简单，手指点一下就完了。但站在系统的角度，这一下触发了一连串的事情：

  • 这句话要存下来，不能丢；
  • 女神在线时要立刻看到，不能等；
  • 如果女神不在线，下次上线时要能看到这条消息；
  • 你的会话列表要更新预览，女神的未读数要加 1；
  • 如果你发了两条，顺序不能乱。

这些需求拆开来看，每一个都指向消息需要携带的某个信息，或者服务端需要完成的某个动作。

1. 一条消息长什么样

继续用上一篇的本子比喻。一条消息就是写在本子里的一行字。但光有内容不够，还需要知道：谁写的？写在哪个本子里？是这个本子里的第几行？

信息 对应字段 为什么需要
写在哪个本子里 conversation_id 消息归属
谁写的 sender_id 区分发送方
第几行 seq 排序和同步
写了什么 content 消息内容
什么时候写的 created_at 时间展示

其中 seq（序列号）是最关键的。消息在网络中传输时，到达顺序不一定和发送顺序一致。A 先发"你好"再发"在吗"，但网络波动可能导致"在吗"先到。时间戳的精度不够（毫秒级可能重复），两端的时钟也可能不同步。

seq 是服务端分配的会话内递增编号：1、2、3、4……它不依赖客户端的时钟，天然有序且唯一。后续做增量同步时，客户端只需要说"我上次看到的是 seq=42"，服务端就能返回 42 之后的所有消息，不用拉全量。

2. 为什么需要 ACK 环节

下面是 AI 给出的消息发送流程，其中有一个服务端向客户端回复 ACK 帧的环节。
想象你寄了一封挂号信。寄出去之后，你不知道对方收没收到，心里没底。挂号信的解决方案是回执：对方签收后，邮局给你一张回执单，上面写着"已签收"。你拿到回执，就放心了。

ACK 就是消息系统里的回执单。服务端收到消息、存入数据库、分配了 seq 之后，回复一个确认帧，里面包含消息的 ID 和 seq。A 收到 ACK，就知道这条消息安全落地了。

ACK 里带 seq 也很重要。A 发消息时并不知道这条消息在会话里排第几，seq 是服务端分配的。收到 ACK 后，A 才知道"我这条消息是第 42 条"。前端可以用这个 seq 来更新本地消息的排序位置。

3. 为什么服务端要通知会话更新

发一条消息，影响的不只是聊天页。回想一下微信的体验：
你给女神发了一句话，聊天页里消息出现了，同时会话列表里女神那一行也跟着变了，预览文字变成了你刚发的那句话，时间变成了"刚刚"，这一行还会跳到列表最顶部。如果是女神给你发的，你的未读数还会加 1。

这些非常细节的交互，看起来理所应当，但落到真实去做，还是需要很多考量的。如果服务端不主动通知，客户端是很难及时更新会话列表的，前端只能靠定时轮询"每隔几秒拉一次会话列表"来发现变化。比如每秒拉一次，大部分时候什么都没变，纯粹浪费流量和电量。

更好的做法是：服务端在处理完消息后，主动推送一个 CONVERSATION_UPDATE 帧给双方。帧里带着变更后的数据：conversation_id、最新预览、最新时间、未读数。前端收到后直接更新本地列表里对应的那一行，不用重新拉整个列表。

上一篇在 conversations 表里预存了 last_message_preview 和 last_message_at，在 conversation_members 表里有 unread_count。这些就是"封面便签"。发消息时顺便更新这些字段（数据库层面），再通过 WebSocket 推送变更通知（实时层面）。数据库保证持久化，推送保证实时性，两者配合。

二、协议与数据扩展

上一篇的会话系统只涉及 HTTP 接口，不需要动 WebSocket 协议。消息收发不一样，它是实时的：A 发一条消息，B 要立刻收到，不能等 B 下次刷新才看到。这意味着消息必须通过 WebSocket 传输，而 WebSocket 传输的是 Protobuf 帧。所以：

  • 第一件事是扩展协议，告诉前后端"现在有新类型的帧了"。
  • 同时，消息需要持久化，不能只在内存里转一圈就没了，所以还需要新增数据库表。
1. 协议：新增三种帧类型

第 18 篇定义的 ws.proto 只有四种帧类型：PING、PONG、AUTH、AUTH_RESULT。消息收发需要新增三种：

帧类型 编号 方向 对应步骤
CHAT_MESSAGE 4 双向 ①④ 发送和接收消息
MESSAGE_ACK 5 服务端 → 客户端 ③ 确认
CONVERSATION_UPDATE 6 服务端 → 客户端 ⑤ 会话更新

同时新增 message.proto，定义消息相关的数据结构。每种帧类型的 payload 里装什么，都在这里约定好：

消息结构 用途 关键字段
ChatMessage 完整消息（转发给接收方） id, conversation_id, sender_id, seq, type, content, status, created_at
SendMessageRequest 发送请求（客户端 → 服务端） conversation_id, type, content, client_id
MessageAck 确认回执（服务端 → 发送方） message_id, seq
ConversationUpdate 会话变更通知（服务端 → 双方） conversation_id, last_message_preview, last_message_at, unread_count

SendMessageRequest 比 ChatMessage 少很多字段。客户端发消息时只需要说"发到哪个会话、什么内容"，id、seq、created_at 这些都是服务端分配的。服务端处理完后，用完整的 ChatMessage 转发给接收方。

ConversationUpdate 是专门为会话列表设计的。前端收到后，直接用里面的字段更新本地列表对应的那一行，不用重新拉整个列表。

2. 新增数据表: messages

为了使用户发的消息可以在服务器中持久化存储，这里需要准备两张表。第一个是 messages 表，如果说会话是一个本子，那么它就是本子里的内容。每条记录是一条消息，通过 conversation_id 知道它写在哪个本子里，通过 seq 知道它是第几行。

字段 类型 说明
id UUID 消息唯一标识
conversation_id UUID 属于哪个会话（哪个本子）
sender_id BIGINT 谁发的
seq BIGINT 会话内序列号，递增
type SMALLINT 消息类型（本版本只有 0=文本）
content TEXT 消息内容
extra JSONB 扩展信息（图片宽高、文件大小等，本版本为空）
status SMALLINT 0 正常，1 已撤回，2 已删除
created_at TIMESTAMPTZ 创建时间

type、status、extra 这些字段本版本大部分用不上，但建表时就预留好。和上一篇 conversation_members 的 is_pinned、is_muted 一样的道理：给已有数据的生产表加字段是件麻烦事。

3. 新增数据表: conversation_seq

另外还有一个 conversation_seq 表, 只有两个字段：conversation_id 和 current_seq。它的作用是给每个会话维护一个独立的计数器。

为什么不直接从 messages 表里算 MAX(seq) 然后加 1？因为并发不安全。如果朱红和橘橙同时发消息，两个请求都查到 MAX=3，都用 4，seq 就重复了。

conversation_seq 就是为了解决这个问题而存在的。它是一个并发安全的计数器，每个会话一行记录，只存一个数字：current_seq。发消息时不查 messages 表，而是直接对这个计数器加 1。数据库保证这个操作是原子的，两个并发请求一个拿到 4，另一个拿到 5，绝不会重复。

用朱红和橘橙的对话举个例子：

时刻 谁发的 内容 conversation_seq 变化 消息拿到的 seq
10:01 朱红 你好 0 → 1 1
10:01 橘橙 在的 1 → 2 2
10:02 朱红 周末有空吗 2 → 3 3

current_seq 永远等于这个会话里最新一条消息的 seq。它的唯一职责就是：给下一条消息分配编号。

三、后端实现与验证

和上一篇的 im-conversation 一样，消息功能封装在独立的 im-message 模块中。模块结构也一样：models → repository → service。但这次多了几个新角色：序列号生成器、广播器、在线用户管理。同时 im-ws 模块也做了较大的重构，从只处理 PING 的简单分发器，变成了能处理消息收发的完整通信枢纽。目前模块关系如下：

1. im-message 模块

im-message 的核心是 service.send() 方法，它串联了消息发送的所有步骤。一条消息从进入到完成：

步骤 6 和 7 就是上一篇讲的"封面便签"在实际中被激活的时刻。发一条消息，conversations 表的预览信息更新了，conversation_members 表的未读数加了。两张表从"空城"变成了"活的"。 用伪代码表示整个流程：

// ---> server/modules/im-message/src/service.rs
pub async fn send(&self, msg: NewMessage) -> Result<Message> {
    // ① 验证
    validate_not_empty(&msg.content)?;
    validate_is_member(msg.conversation_id, msg.sender_id)?;

    // ② 存储
    let seq = self.seq_gen.next(msg.conversation_id).await?;
    let message = self.repo.create(&msg, seq).await?;

    // ③ 更新封面便签
    let preview = truncate(&msg.content, 50);
    update_last_message(msg.conversation_id, &preview).await;
    increment_unread(msg.conversation_id, msg.sender_id).await;

    // ④⑤ 广播
    let member_ids = get_member_ids(msg.conversation_id).await;
    self.broadcaster.broadcast_message(&message, &member_ids, true).await;
    self.broadcaster.broadcast_conversation_update(...).await;

    Ok(message)
}

验证、存储、更新便签、广播，四个阶段清晰分开。AI 生成这段代码时，只要把八个步骤的描述给它，它就能准确地写出来。

2. 广播器：解耦存储和推送

消息存储是 im-message 的职责，消息推送是 im-ws 的职责。两个模块不应该直接依赖。如果 im-message 直接调用 im-ws 的代码来推送，两个模块就耦合在一起了，改一个就要改另一个。

解决方案是一个 trait（接口）：im-message 定义 MessageBroadcaster trait，im-ws 实现它。service 在发送消息后调用 broadcaster 的方法，但它不知道也不关心消息是怎么推送出去的。这种"定义接口的人不实现接口"的模式，让 im-message 可以独立测试（用一个空的 NoopBroadcaster），也让推送方式可以被替换（比如未来换成推送服务）。

im-message 里定义 trait：

// ---> server/modules/im-message/src/broadcast.rs
#[async_trait]
pub trait MessageBroadcaster: Send + Sync {
    async fn broadcast_message(
        &self, message: &Message, member_ids: &[i64], exclude_sender: bool,
    );
    async fn broadcast_conversation_update(
        &self, conversation_id: Uuid, preview: &str,
        member_ids: &[i64], sender_id: i64,
    );
}

im-ws 里实现它，把消息编码成 Protobuf 帧，通过 WsState 推送给在线用户：

// ---> server/modules/im-ws/src/broadcaster.rs
#[async_trait]
impl MessageBroadcaster for WsBroadcaster {
    async fn broadcast_message(&self, message: &Message, member_ids: &[i64], exclude_sender: bool) {
        let chat_msg = ChatMessage { /* 从 message 构造 */ };
        let frame = WsFrame { r#type: CHAT_MESSAGE, payload: chat_msg.encode_to_vec() };
        let targets = exclude(member_ids, message.sender_id);
        self.ws_state.send_to_users(&targets, frame.encode_to_vec()).await;
    }
}

广播器做两件事：把 ChatMessage 帧转发给接收方（步骤 ④），把 ConversationUpdate 帧推送给双方（步骤 ⑤）。推送给发送者和接收者的 ConversationUpdate 内容不同：发送者的 unread_count=0，接收者的 unread_count=1。

3. 在线用户管理与帧分发

推送消息需要知道"B 当前在不在线，连接在哪"。im-ws 新增了一个 WsState，用 channel 管理在线用户。每个 WebSocket 连接建立时创建一个 channel，WsState 持有发送端。需要推送消息给某个用户时，往 channel 里扔数据，连接循环的另一端收到后写入 WebSocket。

第 18 篇的帧分发器只处理 PING，现在扩展它处理 CHAT_MESSAGE 帧。收到 CHAT_MESSAGE 后：解析 SendMessageRequest → 调用 message_service.send()（触发存储 + 广播）→ 构造 MessageAck 帧回复给发送者。分发器本身的结构不变：读 type，查表，转发。只是表里多了一行。

WsState 用 channel 管理在线用户，每个连接一个 channel：

// ---> server/modules/im-ws/src/state.rs
pub struct WsState {
    senders: RwLock<HashMap<i64, mpsc::UnboundedSender<Vec<u8>>>>,
}

impl WsState {
    pub async fn send_to_user(&self, user_id: i64, data: Vec<u8>) {
        let conns = self.senders.read().await;
        if let Some(tx) = conns.get(&user_id) {
            let _ = tx.send(data);
        }
    }
}

handler 里用 tokio::select! 同时监听两个方向：客户端发来的帧和需要推送的帧：

// ---> server/modules/im-ws/src/handler.rs
loop {
    tokio::select! {
        // 客户端发来的帧
        msg = ws_receiver.next() => {
            match frame_type {
                PING => ws_state.send_to_user(user_id, pong),
                CHAT_MESSAGE => dispatcher.handle_chat_message(user_id, &payload).await,
                _ => {}
            }
        }
        // 需要推送给客户端的帧（来自 channel）
        Some(data) = outgoing_rx.recv() => {
            ws_sender.send(Binary(data)).await;
        }
    }
}

dispatcher 处理 CHAT_MESSAGE 帧，调用 service 后发 ACK：

// ---> server/modules/im-ws/src/dispatcher.rs
pub async fn handle_chat_message(&self, sender_id: i64, payload: &[u8]) {
    let request = SendMessageRequest::decode(payload)?;
    let message = self.msg_service.send(new_msg).await?;

    // service.send() 内部已经完成了广播（步骤④⑤）
    // dispatcher 只需要发 ACK（步骤③）
    let ack = MessageAck { message_id: message.id, seq: message.seq };
    let ack_frame = WsFrame { r#type: MESSAGE_ACK, payload: ack.encode_to_vec() };
    self.ws_state.send_to_user(sender_id, ack_frame.encode_to_vec()).await;
}
4. 历史消息查询

除了 WebSocket 的实时消息，还需要一个 HTTP 接口来查询历史消息。用户打开聊天页时，需要加载之前的消息。往上滚动时，需要加载更早的消息。

为什么历史消息走 HTTP 而不是 WebSocket？WebSocket 适合实时推送：服务端有新消息了，主动推给客户端。但历史消息是客户端主动请求的，是一个"请求-响应"模式：我要第几页的数据，你给我。HTTP 天然就是干这个的，有成熟的缓存、重试、错误码机制。如果把历史查询也塞进 WebSocket，就需要自己实现请求-响应的配对（发一个请求帧，等一个响应帧，还要处理超时），没必要重新造轮子。

GET /conversations/:id/messages?before_seq=42&limit=50

两个参数：before_seq 表示"给我这个序列号之前的消息"，limit 表示"最多给我多少条"。如果不传 before_seq，返回最新的消息（打开聊天页时的场景）。 返回的消息带上发送者的昵称和头像（关联 user_profiles 表），前端不需要再单独查用户信息：

[
  {
    "id": "uuid",
    "conversation_id": "uuid",
    "sender_id": "1",
    "sender_name": "朱红",
    "sender_avatar": "identicon:1:FF461F",
    "seq": 42,
    "msg_type": 0,
    "content": "你好",
    "status": 0,
    "created_at": "2026-03-30T..."
  }
]

四、脱离前端的验证

后端代码写完了，怎么验证五个步骤都跑通了？传统做法是等前端做完，打开 App 手动测试。但这有几个问题：

  • 前端可能还没开始做，你得等前端完成；
  • 前端可能有自己的 bug，分不清是前端的问题还是后端的问题；
  • 手动测试不可重复，每次改了后端代码都要重新点一遍。

上一篇的会话接口用 Link Test Writer 生成了 HTTP 测试脚本，但消息收发走的是 WebSocket + Protobuf 二进制帧，HTTP 测试脚本搞不定。Postman 这类 GUI 工具也不方便，因为它们没法直接编解码 Protobuf。

1. 为什么用 Python

现在需要一个能同时做三件事的工具：建立 WebSocket 连接、编解码 Protobuf 帧、自动化断言。Python 刚好都能做：websockets 库处理 WebSocket，protobuf 库处理编解码，标准库处理断言和流程控制。而且 Python 是跨平台的，Windows、Mac、Linux 都能跑，不像 PowerShell 脚本有编码问题。

而且用不同语言的客户端来验证后端，本身就是一种多方验证。前端用 Dart 连 WebSocket，测试脚本用 Python 连 WebSocket，如果两边都能正确收发 Protobuf 帧，说明后端的协议实现是语言无关的，不是只对某个客户端碰巧能用。这比只用一种语言测试更有说服力。

这里有一个值得注意的点：
我们的后端用 Rust，前端用 Dart，测试脚本用 Python。多种技术栈在同一个项目里共存。在传统开发中，这可能是个问题，因为团队成员需要掌握多种语言。但在 AI 编程时代，语言不再是壁垒。你不需要精通 Python 才能写测试脚本，你只需要告诉 AI "用 Python 写一个 WebSocket 测试脚本"，它就能生成。你需要的是知道"该用什么工具解决什么问题"，而不是"怎么用这个工具的每一个 API"。希望大家可以在 AI 的加持下，尽可能拓宽自己的能力范围。

2. 测试流程

脚本模拟两个用户的完整交互。先准备好 Protobuf 帧的构造工具：

# ---> docs/features/im/core/v0.0.3/test/ws_chat_test.py
def make_auth_frame(token):
    auth = ws.AuthRequest()
    auth.token = token
    return make_frame(ws.AUTH, auth.SerializeToString())

def make_chat_frame(conversation_id, content):
    req = msg.SendMessageRequest()
    req.conversation_id = conversation_id
    req.type = msg.TEXT
    req.content = content
    return make_frame(ws.CHAT_MESSAGE, req.SerializeToString())

然后按步骤执行。登录拿 token，建立连接，发送 AUTH 帧认证：

token_a, uid_a = login(PHONE_A)
token_b, uid_b = login(PHONE_B)

ws_a = await websockets.connect(WS_URL)
ws_b = await websockets.connect(WS_URL)

await ws_a.send(make_auth_frame(token_a))
await ws_b.send(make_auth_frame(token_b))

朱红发送消息，验证收到 ACK（步骤 ③）：

await ws_a.send(make_chat_frame(conv_id, "hello from A"))

# 等待 MESSAGE_ACK
frame = parse_frame(await ws_a.recv())
assert frame.type == ws.MESSAGE_ACK
ack = msg.MessageAck()
ack.ParseFromString(frame.payload)
assert ack.seq == 1

验证橘橙收到消息（步骤 ④）：

frame = parse_frame(await ws_b.recv())
assert frame.type == ws.CHAT_MESSAGE
chat = msg.ChatMessage()
chat.ParseFromString(frame.payload)
assert chat.content == "hello from A"
assert chat.seq == 1

验证会话更新推送（步骤 ⑤），再通过 HTTP 查询确认消息已持久化：

# 橘橙收到 CONVERSATION_UPDATE，unread=1
frame = parse_frame(await ws_b.recv())
update = msg.ConversationUpdate()
update.ParseFromString(frame.payload)
assert update.unread_count == 1

# HTTP 查询历史消息
r = curl("GET", f"{BASE}/conversations/{conv_id}/messages", token=token_a)
assert r["data"][0]["content"] == "hello from A"

这一篇实现了消息收发的后端完整链路，也是整个 IM 系统中最核心的一环。开头定义的五个步骤：发送 → 存储 → 确认 → 转发 → 会话更新，每一步都有明确的理由和对应的实现。
