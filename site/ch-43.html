生生不息 ｜ 软件更新，持续成长

生命之成长，在于迭代演化、生生不息。

但软件有一个悖论：打包那一刻，它就不再生长了。

就像蝴蝶破茧而出，翅膀的花纹就定死了——它不能在飞行中重新长出新的翅膀。你在仓库里修了 bug、加了功能、优化了性能，但用户手机里的那个 App，对此一无所知。它还活在上一个时代，兢兢业业地跑着旧代码，不知道外面的世界已经变了。

软件的成长，本质是 一个封闭系统如何获得进化能力。
答案朴素得出奇：告诉它，新一代已经破茧了。 然后让它自愿让位。

一、版本更新的感知

整个升级机制，归根到底是三件事：

步骤 本质 谁做的
宣告 新版本诞生，消息存入服务器 开发者（构建脚本）
感知 旧版本发现自己落后了 客户端（启动时询问后端）
交接 下载新包、校验、安装、旧版本退场 各平台策略
  • "宣告" 是后面构建脚本做的事。
  • "感知" 这步所有平台都一样：问一个问题，得到一个答案。
  • "交接" 因平台而异，Android 下载 APK，iOS 跳商店，Windows 下载安装包。
1. 客户端 App

感知是最轻量的一环，却是整条链的起点。再好的安装包躺在服务器上，没有"你该更新了"这道信号，它就永远只是一个文件。应用产品在运行时，可以知道自己的版本，它由 pubspec.yaml 中的 version 决定：

所以 感知 最重要的就是 如何让软件知道目前最新的版本。这个问题，软件本身无法得到答案，需要 服务端 的接口数据支持。于是 App 版本管理维护，这座冰山开始显露一角。

2. 后端数据支持

此时，后端需要设计了一个 app_versions 数据表，来维护不同平台、不同版本的相关数据。

CREATE TABLE app_versions (
    id SERIAL PRIMARY KEY,
    app_id VARCHAR(64) NOT NULL,         -- 哪个应用
    platform VARCHAR(32) NOT NULL,       -- 哪个平台
    version VARCHAR(32) NOT NULL,        -- 版本号 x.y.z
    download_url VARCHAR(512) NOT NULL,  -- 去哪儿取新翅膀
    file_size BIGINT NOT NULL DEFAULT 0, -- 多大
    sha256 VARCHAR(64),                  -- 防伪指纹
    release_notes TEXT,                  -- 更新信息
    force_update BOOLEAN DEFAULT FALSE,  -- 是否强制换代
    published BOOLEAN DEFAULT FALSE,     -- 是否已公开
    created_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(app_id, platform, version)
);

App 只需要后端提供一个接口：

GET /api/app/version?app_id=flash_im&platform=android

当 App 获取到服务端返回的结果，就知道最新的版本号。和自己当前版本对比一下，就知道该不该更新了。

{
  "version": "1.0.1",
  "download_url": "http://xxxx/static/application/v1.0.1/flash_im.apk",
  "file_size": 15023104,
  "sha256": "a1b2c3d4e5f6...",
  "release_notes": "修复消息发送失败\n优化启动速度",
  "force_update": false
}

这里 published 是一道安全门，版本记录创建了不代表立刻对外公布。比如后续上传脚本自动创建版本记录，并不代表要立刻分发。

3. 检测更新

检测更新的流程比较固定，对任何应用都具有普适性。这里我将其封装为 fx_updater 包，并上传到了 pub 上。它的功能边界非常清晰：

只做版本校验和结果数据的维护工作，以及一些便于使用的相关视图。

如何通过网络请求获取新的版本信息，如何下载更新已经更新的后续工作。对于不同应用来说，各不相同，所以暴露给使用者来自行处理。

更新弹框 下载更新

从用法上来看更加明了，FxUpdater 是一个管理更新信息的单例类， check 方法负责检测和存储更新信息。需要传入当前版本号和获取更新信息的函数，根据返回 UpdateCheckResult 结果，使用者可以做不同的逻辑处理：

---->[home/view/home_page.dart]----
import 'package:fx_updater/fx_updater.dart';

final PackageInfo packageInfo = await PackageInfo.fromPlatform();
final UpdateCheckResult result = await FxUpdater().check(
  packageInfo.version,
  _fetchFromServer,
);
if (result is UpdateAvailable && context.mounted) {
  /// 根据更新结果处理
}

获取最新版本，闪讯中使用下面的方法，从服务端接口访问数据。这样 fx_updater 感知更新的具体实现，就被分离到了模块之外。其他人可以用不同的 _fetchFromServer 方法，定制自己的功能。而 fx_updater 所做的是订立 UpdateInfo 这个结果 契约 。和上一篇本地数据库分离的思想是一样的，这也是 依赖倒置原则 在代码层面的体现。

/// 从后端获取更新信息
Future<UpdateInfo?> _fetchFromServer() async {
  try {
    final response = await _dio.get(
      '/api/app/version',
      queryParameters: {
        'app_id': appId,
        'platform': Platform.operatingSystem,
      },
    );
    if (response.statusCode == 200) {
      return UpdateInfo.fromJson(response.data);
    }
    return null;
  } catch (_) {
    return null; // 静默失败
  }
}

二、软件版本的维护

当一次迭代完成，我们需要向用户宣布，软件已经更新。此时 "感知" 解决了读的问题，那谁来负责把 "1.0.1 已经诞生了" 这条消息存进后端？其中涉及到一些细节:

  • 需要确定一个分发包的指纹，能确定这个包的正确性。因为网络传输的不稳定因素，可能导致下载包损坏。
  • 尽量避免人为的手动录入更新信息、上传安装包，人的操作有错误的风险，而且效率很低。
  • 最终的发布的确认需要人来决策，确保宣告的时机由你掌控。
1. 第一步：计算安装包的信息 - calculate

安装包打好了，但光有文件不够。后端需要知道它的"身份证"：多大、指纹是什么、属于哪个版本。
calculate.py 就是那个"质检员"，它会读取产物文件，计算 SHA256 哈希和文件大小，把结果写进同目录的 meta.json：

python scripts/build_center/upload/calculate.py dest/android/arm64-v8a/flash_im.apk android

这些就是一个分发包的元数据，其中 sha256 就是这个包的指纹。文件的任何字节的变化，都会导致这个值的变动。

{
  "file_name": "flash_im.apk",
  "version": "1.0.1",
  "platform": "android",
  "file_size": 15023104,
  "file_size_mb": 14.33,
  "sha256": "a1b2c3d4e5f6..."
}

另外，这一步已经内嵌在 Android、Windows、Linux 的打包脚本里了，构建完产物自动跑，不需要单独执行。因为这三个平台可以允许用户自己下载安装包来升级。

2. 第二步：安装包上传入库 - update

有了 meta.json，下一步就是把安装包送到服务器、把版本记录写进数据库。同样也是一条命令搞定，比如上传 Android 的安装包 ：

python scripts/build_center/upload/update.py android

这个脚本做四件事：

  1. 读 meta.json，拿到版本号、平台、哈希
  2. 问后端"你那儿最新是几版？" 确认新版本号确实更高（防止误传旧版本）
  3. scp 把 APK 传到服务器的静态文件目录（/static/application/v1.0.1/flash_im.apk）
  4. 调 POST /api/app/version 创建版本记录

注意：创建完的记录 published=false。还没对外公开，只是存进了数据库。另外，如果你别想上传到自己的服务器，比如需要放在阿里云、腾讯云等 oss 上，第三步你也可以让 AI 自定义上传逻辑，对于流程来说这一步的目的只是为了获取一个可下载的链接。

为了更好地可视化呈现目前的版本信息，我让 AI 基于 Vue 做了一个简单的版本管理系统。脚本上传产生记录后，刷新就能看到：

3. 第三步：确认发布 — publish

最后一步是人做的决定：确认这个版本没问题，可以让用户看到了。

curl -X POST "http://server/api/app/version/publish?app_id=1&platform=android&version=1.0.1"

这行命令执行的瞬间，published 变成 true。下一个打开闪讯的用户，就会收到更新提示。为什么要分这一步？

因为自动化不代表无脑。构建脚本可以自动打包、自动上传、自动入库。但"让全世界用户看到"这个决定，应该是人拍板的。万一包有问题呢？万一是不小心触发的呢？published 就是那道最后的闸门。

另外，通过命令行请求来更新，交互起来比较麻烦，一不小心输入错了，也有风险。所以 web 管理器的发布操作就非常关键，二次确认也避免了误触的风险：

其实这个按钮做的事，和命令行是一样的，都是调用接口。但是交互操作在这个场景下是非常适合的。

4.完整发版流程

以 Android 为例，从代码写完到用户收到更新：

# 1. 构建（自动计算 meta）
python scripts/build_center/build_android.py

# 2. 上传产物 + 创建版本记录（published=false）
python scripts/build_center/upload/update.py android

# 3. 确认发布（published=true，用户开始收到通知）
curl -X POST "http://server/api/app/version/publish?app_id=1&platform=android&version=1.0.1"
或 web 操作确认发布

就三条命令，大概五分钟。从仓库里的一个 commit，变成用户手机里弹出的那个"发现新版本"对话框。 宣告完成了，后端有了最新版本的记录。接下来的故事，就交给客户端，在检查完版本信息之后，如何完成这场新旧时代的交接。

三、更新处理

感知是统一的，但交接是分裂的。一个 HTTP 请求就能知道"有新版本了"，但把新版本装到用户设备上这件事，七个平台，七套规则。好在归纳之后，其实只有三大类别：

类型 平台 做什么
自己下载安装 Android（自有渠道）、Windows、Linux 下载文件 → SHA256 校验 → 触发安装
跳转商店 iOS、macOS、Android（Google Play） 一行 url_launcher，把用户交给平台方
不需要做 Web 刷新浏览器就是最新版，不存在"旧版本"
1. 下载与校验

下载本身不复杂，如下所示，加一个进度回调，弹窗里实时显示百分比。

下载中 下载完成

真正重要的是下载之后的那一步：SHA256 校验。 为什么要校验？因为网络不是可靠的。文件可能在传输途中损坏一个字节，用户装上之后莫名闪退，你排查半天以为是代码 bug。更严重的情况：中间人攻击，把你的安装包替换成了别的东西。下载完后本地再算一遍，和接口返回值对得上就是对的：

// 流式计算，不把整个 APK 加载到内存
final Digest fileDigest = await sha256.bind(file.openRead()).first;
if (fileDigest.toString() != info.sha256) {
  await file.delete();
  throw Exception('SHA256 校验失败：文件可能被篡改或损坏');
}
2. Android 安装：最复杂的一环

Windows 和 Linux 的安装很简单，下载完调 launchUrl(Uri.file(filePath)) 打开文件，系统会接管后续流程。但 Android 不一样，它有一整套安全机制挡在你面前。

  • FileProvider：Android 7.0 以后，App 之间不能直接传 file:// 路径了。你得通过 FileProvider 生成一个 content:// URI，授权系统安装器读取你的文件。
  • 安装权限：Android 8.0 以后，应用需要 REQUEST_INSTALL_PACKAGES 权限才能调起安装界面。而且这个权限不是声明了就有，用户得在系统设置里手动开启。
  • 双渠道分离：Google Play 以及国内各大应用市场，禁止应用内安装 APK。如果你的 Manifest 里有安装权限，审核直接拒。

所以安卓构建需要支持不同的版本，比如这里分为 standard 和 google 两个渠道，每个都可以定制 AndroidManifest.xml 的内容。standard 的声明权限、走下载安装；google 的用 tools:node="remove" 移除权限、走跳转商店。

为了解决这些问题，我们封装了 fx_install_android 这个原生 Plugin（同样已发布到 pub）。它做三件事：

  1. 自带 FileProvider——使用方不需要额外配置 res/xml/file_paths.xml
  2. 自动检测安装权限——无权限时跳转系统设置页请求，用户授权后自动继续安装
  3. 返回结果，告诉你安装成功了、用户取消了、还是权限被拒了
/// 安装本地文件
Future<void> _installFile(String filePath) async {
  if (Platform.isAndroid) {
    await FxInstall.apk(filePath);
  } else {
    final Uri fileUri = Uri.file(filePath);
    if (await canLaunchUrl(fileUri)) {
      await launchUrl(fileUri);
    }
  }
}

Dart 层只需要一行 FxInstall.apk 即可安装下载好的 apk 文件。这样闪讯在安卓上就有了更新的能力：

3. 渠道策略的代码实现

fx_updater 只负责检测和弹窗，它不关心"检测完之后怎么办"。具体的下载、校验、安装逻辑，由主项目中的 UpdateTrigger 类完成。它是闪讯里连接 fx_updater 和各平台能力的胶水层：注入网络请求、驱动下载进度、分发安装策略。

检测到有新版本后，第一个问题是：这个平台应该下载安装，还是跳转商店？

---->[client/lib/src/update/update_trigger.dart]----
/// 是否走"下载安装包"路径
bool _shouldDownload() {
  // Google Play 渠道禁止应用内安装 APK
  if (Platform.isAndroid && AppChannel.isGoogle) return false;
  // 自有渠道的 Android、Windows、Linux 走下载
  return Platform.isAndroid || Platform.isWindows || Platform.isLinux;
}

这里出现了 AppChannel 类，它是一个编译时常量，通过 --dart-define=CHANNEL=standard 在构建时注入。代码里长这样：

---->[modules/flash_shared/lib/src/channel.dart]----
class AppChannel {
  static const String value = String.fromEnvironment('CHANNEL', defaultValue: 'standard');
  static bool get isGoogle => value == 'google';
  static bool get isStandard => value == 'standard';
}

同一份源码，通过渠道的标识，可以进行一些行为和视图的区别化处理。决策在编译那一刻就定了，运行时零开销。

  • standard 渠道构建出来 AppChannel.isGoogle 是 false，走下载安装；
  • google 渠道构建出来是 true，走跳转商店。
  • 如果国内其他的商店渠道要做差异化，也可以定义不同的 CHANNEL 值，进行处理。
4. 跳转商店

对于 iOS、macOS 以及 Android Google Play 渠道，更新的交接不由我们控制。用户点击"立即升级"后，直接跳转到对应的商店页面，后续由平台方接管。UpdateTrigger 中预定义了各商店的链接：

---->[client/lib/src/update/update_trigger.dart]----
static const String _playStoreUrl =
    'https://play.google.com/store/apps/details?id=xxxx';
static const String _appStoreUrl =
    'https://apps.apple.com/app/idxxxx';

iOS 和 macOS 共用同一个 App Store 链接，因为它们在 App Store Connect 里是同一个应用（Universal Purchase），系统会自动根据设备展示对应版本。

跳转逻辑也很直接：

Future<void> executeUpdate(UpdateInfo info) async {
  final String storeUrl = _getStoreUrl();
  if (storeUrl.isNotEmpty) {
    await launchUrl(Uri.parse(storeUrl), mode: LaunchMode.externalApplication);
  }
}

String _getStoreUrl() {
  if (Platform.isIOS) return _appStoreUrl;
  if (Platform.isMacOS) return _appStoreUrl;
  if (Platform.isAndroid && AppChannel.isGoogle) return _playStoreUrl;
  return '';
}

相比自有渠道的下载安装流程，跳转商店简单得多。但它背后意味着一个产品决策：把更新的控制权让渡给平台方。好处是审核保障和用户信任；代价是你无法控制更新的时机和速度，需要主动提交更新以及等待审核。

四、本章总结

回到开篇那个问题：一个封闭系统如何获得进化能力？生命给出过答案:

不是让个体永生，而是让信息流动。DNA 不在乎哪一代蝴蝶飞得更远，它只在乎自己能不能传下去。软件的版本更新，本质上是同一件事：
让代码里凝结的意志，从一个躯壳流向下一个躯壳。

我们所做的一切：后端那张表、客户端那次请求、SHA256 那串指纹，不过是在模拟一个最古老的生命机制：感知环境的变化，接受新的可能，然后完成一次安静的新陈代谢。

旧版本不是被杀死的，它是功成身退的。

尾声: 冒险的新起点

这本书从一颗概念的种子开始，我们见证它的萌芽、成长和果实，走过了一段完整的旅程。

从零开始，让两个终端之间跑通了第一条消息。那时候它什么都不是，没有好友、没有群聊、没有历史记录、没有表情包。只有一条孤零零的 "hello"，证明这件事是可能的。

然后它开始生长。数据库给了它记忆，WebSocket 给了它实时的脉搏，本地缓存让它在断网时也能回忆过去。好友系统让它有了社交关系，群组让它有了聚集的场所，搜索让它有了回溯的能力，语音让它有了声音。

我们带它做过体检，给它做过手术，把 772 行的代码拆到 250 行，把职责不清的模块重新划界。我们把它从花盆移栽到了大地上，让它在 Android、iOS、macOS、Windows、Linux、Web、鸿蒙，这七片土地上生根。

而这最后一章，是教它最后一个本领：知道自己该长高了，并且能自己完成生长。 一个系统，当它具备了感知自身不足、获取更新、完成自我替换的能力时，它就不再需要你时刻看护了。它会自己进化，自己迭代，生生不息。

在 AI 的驱动下，这个进化将会异常迅速，但是面临的挑战也将更加艰巨。它会长成一个笔直的参天大树，还是逐渐走向腐败的一滩泥沼，这将取决于 你自己 ：

  • 是否能驯服产品野蛮生长的功能；
  • 能否及时驱除，藏在那头野兽内部滋生的瘟疫；
  • 是否不断完善 AI 驱动开发的技能于流程。

这不是结束，而是所有故事真正开始的地方，这是真正的战场的起点。从这里往后，每一个功能、每一次优化、每一个 bug fix，都有了抵达用户的通道。你不再是一个人在仓库里写代码，你是在和成千上万个用户的设备对话。每一次 push，都是一次呼吸；每一次更新，都是一次心跳。

生命之成长，在于迭代演化、生生不息。
