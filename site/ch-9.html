种子#3 ｜ 让心脏开始跳动

一个生命体最初的标志，不是它有多复杂，而是它的心脏开始跳动——持续地、不间断地跳动。

在生物学中，心脏是最早发育成熟的器官之一。人类胚胎在第三周就开始出现心跳，比大脑、四肢、眼睛都要早。因为生命的第一要务不是思考，不是行动，而是——循环。血液必须流动起来，养分才能被输送到每一个正在生长的细胞。

对一个即时通信产品来说，道理是一样的。它的"心跳"不是某个接口能返回一次数据，而是：客户端和服务端之间，建立一条持续的、双向的通信通道，随时可以互相感知对方的存在。

一、后端支持 WebSocket 接口

在前面的章节中，我们已经在 playground 里跑通了 HTTP 接口请求——前端发一个请求，后端返回一个响应。那是一次性的交互，像用电极刺激了一下肌肉，看到它抽动了一下。请求结束，连接就断了。

真正的心跳不是这样的。心脏不会跳一下就停，它是持续跳动的。对应到技术世界，这种"持续跳动"的能力，叫做 WebSocket。

1. 了解 HTTP 和 WebSocket 的区别

在动手之前，我想先搞清楚这两个东西的本质区别。直接问 AI 吧：

Q: 我在做一个即时通信产品，之前用 HTTP 实现了接口请求。现在需要实时通信能力。
请为我对比 HTTP 和 WebSocket 的区别，重点说明为什么 IM 产品必须用 WebSocket。
用通俗易懂的方式，合理使用 mermaid 展示通信流程的差异。
写到 docs/research/project/websocket_vs_http.md 中

AI 给了一份非常清晰的对比文档。如果觉得不直观，或看不懂，甚至你可以让 AI 为你设计漫画分镜，再让支持绘制的 AI 根据分镜文案，制作图片，如下所示，可以非常直观地可看出 HTTP 和 WebSocket 的区别：

Q: 我觉得是不是可以通过可爱漫画，来展示知识，这样平淡的知识也能更丰富。为我准备可爱卡通角色的对话场景和分镜。

如果 HTTP 是心脏跳一下就停，WebSocket 就是心脏持续跳动。所以对于即时通信来说，这个区别是致命的：

  • 用 HTTP，客户端只能主动问服务端"有没有新消息？"——这叫轮询，效率低，延迟高
  • 用 WebSocket，服务端可以主动推送"你有一条新消息"——实时、高效、自然

好，概念清楚了。接下来让 AI 帮我们在 playground 里把这颗心脏装上去。

2.后端：给服务器装上 WebSocket

来看看核心代码——这是 axum 处理 WebSocket 连接的关键部分:
注: 毕竟是编程方面的书籍，文中会放置一些核心的代码，来介绍具体实现。如果不太在意的话，也可以忽略。或者你对实现有任何问题或感兴趣的点，AI 也可以为你解答。

/// GET /ws — WebSocket 升级端点
async fn ws_handler(ws: WebSocketUpgrade) -> impl IntoResponse {
    ws.on_upgrade(handle_socket)
}

/// 处理单个 WebSocket 连接
async fn handle_socket(mut socket: WebSocket) {
    println!("🔗 WebSocket 连接已建立");

    let welcome = "欢迎连接 Flash IM WebSocket 服务！";
    let _ = socket.send(Message::Text(welcome.into())).await;

    while let Some(Ok(msg)) = socket.next().await {
        match msg {
            Message::Text(text) => {
                println!("📨 收到文本: {text}");
                let reply = format!("echo: {text}");
                if socket.send(Message::Text(reply.into())).await.is_err() {
                    break;
                }
            }
            Message::Close(_) => break,
            _ => {}
        }
    }

    println!("❌ WebSocket 连接已断开");
}

这段代码值得仔细看一下。ws.on_upgrade(handle_socket) 是整个 WebSocket 的入口——它把一个普通的 HTTP 请求"升级"为 WebSocket 连接。升级之后，handle_socket 函数接管了这条连接，进入循环来持续监听客户端发来的消息。

注意这个 while let 循环。它不会主动退出，只有当客户端断开连接（recv() 返回 None）或者收到 Close 帧时才会结束。这就是"持续连接"的本质——一个不会主动结束的循环，一直在等待、接收、响应。

2. 前端实现的核心逻辑

AI 为我在练习场内生成了 heartbeat 文件夹，并分成 model/api/view 三个层级，分别表示数据层、逻辑层、视图层:

数据层

最简单的是 model，其中定义了 WsMessage 来承载消息的数据：

/// WebSocket 消息实体
class WsMessage {
  final String text;
  final bool isMe; // true=我发的, false=服务端回的
  final DateTime time;

  const WsMessage({
    required this.text,
    required this.isMe,
    required this.time,
  });

  @override
  String toString() => '${isMe ? "→" : "←"} $text';
}

逻辑层

api 中是前端和后端链接通信的核心，使用了 WebSocketChannel 进行连接，通过连接的 _channel 通道对象，可以得到 Stream 流：

  • 你可以把它看成一个信息的小河流，每次后端发的消息，都会通过这条河流，飘到前端。
import 'package:web_socket_channel/web_socket_channel.dart';
import '../../config.dart';

/// 连接状态
enum WsStatus { disconnected, connecting, connected }

/// WebSocket 通信层
class WsApi {
  WebSocketChannel? _channel;
  WsStatus _status = WsStatus.disconnected;

  WsStatus get status => _status;

  /// 建立连接，返回消息流
  Stream<dynamic> connect() {
    _status = WsStatus.connecting;
    final uri = Uri.parse(
      'ws://${PlaygroundConfig.host}:${PlaygroundConfig.port}/ws',
    );
    _channel = WebSocketChannel.connect(uri);
    _channel!.ready.then((_) => _status = WsStatus.connected);
    return _channel!.stream;
  }
}

另外，前端也可以使用 通道 中的 sink 向后端发消息。比如现在后端的逻辑是: 当接收到前端的文本消息，将文本原封不动地还回去：

  /// 发送文本消息
  void send(String text) {
    _channel?.sink.add(text);
  }

  /// 断开连接
  void disconnect() {
    _channel?.sink.close();
    _channel = null;
    _status = WsStatus.disconnected;
  }

视图层

视图层的核心是，点击按钮，触发 connect 连接逻辑。然后监听 Stream 流, 每次变化时，会更新消息列表的信息。

三、单元测试保障逻辑正确性

回头看一下刚才 AI 生成的心跳模块，它把代码分成了三层：model（数据）、api（逻辑）、view（界面）。之前的会话列表模块也是这个结构。这不是巧合，而是一种刻意的分层习惯。

1. 为什么要分层

你可能会想：代码量这么少，全写在一个文件里不也行？当然行。但分层带来的好处，在项目长大之后会越来越明显：

  • 职责清晰：model 只管数据长什么样，api 只管怎么和后端通信，view 只管界面怎么画。改一个地方不会牵连其他地方。
  • 可替换：比如以后把 WebSocket 换成别的协议，只需要改 api 层，view 层完全不用动。
  • 可测试：这是最关键的一点——分层之后，每一层都可以单独拿出来验证。

最后这一点，引出了一个非常重要的开发习惯：单元测试。

2. 单元测试是什么

简单说，单元测试就是：写一小段代码，去验证另一小段代码的行为是否符合预期。

刚才我们验证 WebSocket 是否正常工作，靠的是打开 UI 手动点"连接"、输入消息、看回复。这当然可以，但问题是——无论是启动，还是交互，检验，都要耗费时间和精力。每次改了代码都要重复这套操作。如果有 10 个功能要验证呢？

单元测试就是把这个"手动验证"的过程变成代码。写一次，以后每次改完代码跑一下，几秒钟就知道有没有破坏已有的功能。这就像体检。你不会等到身体出了大问题才去医院，定期体检能提前发现隐患。单元测试就是代码的体检。

但是，在古法编程开发中，写测试是一件"知道该做但经常偷懒"的事。原因很简单：写测试本身也需要时间和精力，尤其是要构造各种测试数据、模拟各种边界情况。

3. AI 时代的单元测试

但在 AI 时代，这件事变得轻松多了。刚才我们费了不少功夫在 UI 上点来点去验证 WebSocket，现在让 AI 帮我们把这个验证过程自动化：

Q: 帮我验证一下心跳通信模块的代码逻辑是否正确，脱离 UI，直接测试 WebSocket 的连接和收发消息

这样查看 api 层的逻辑是否正确，就可以脱离 UI，直接验证 WebSocket 连接逻辑：

#启动后端
cargo run

#运行测试
flutter test test/playground/heartbeat/ws_api_test.dart

注意看这几个测试做了什么：连接后能收到欢迎消息、发送文本能收到 echo 回复、断开后状态正确。这些就是我们刚才在 UI 上手动验证的那些事情，现在全部变成了可重复执行的代码。

4. 测试的本质是信心

写测试不是为了追求覆盖率的数字，而是为了给自己信心：改了代码之后，我敢说它还是对的。

在 AI 辅助开发的模式下，这一点尤其重要。AI 帮你生成了大量代码，你不可能逐行去审查每一行。但如果有一套测试在那里守着，你就有了一道安全网——AI 写的代码对不对，跑一下测试就知道。所以我的建议是：

每完成一个模块，顺手让 AI 帮你生成测试。成本几乎为零，但收益是持续的。
