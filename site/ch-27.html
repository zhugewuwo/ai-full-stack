枝叶#4 ｜ 群聊管理

建城是一次性的浪漫，治城是重复性的琐碎。前者需要魄力，后者需要耐心。

上一章给群聊装上了"正门"——用户可以搜索群聊、主动申请加入，群主可以审批。但群主的权力仅限于"开门"和"关门"。一个真正可用的群聊还需要更多治理能力：邀请新成员、踢人、退群、转让群主、解散群聊、发布群公告、修改群名。这一章要把群聊从"能用"推向"好用"。

一、需求分析

邀请、踢人、退群、转让、解散、群公告、改群名——每个操作的权限要求不同，完成后可能触发一连串副作用（刷新头像、发系统消息、标记状态）。复杂度不在于单个接口有多难，而在于它们之间的权限模型和副作用链条。本版本会引入群主和普通成员两级角色，群主拥有对群的一些管理操作权限。

2. 逻辑流程树

邀请入群是这批接口中最复杂的——涉及批量操作、ON CONFLICT 恢复、宫格头像刷新、系统消息。其他接口（踢人、退群、转让、解散、公告、改名）都是"校验权限 → 操作数据库 → 发系统消息"的标准模式。

邀请入群事件流

时刻 事件 处理 产生的新事件
T1 用户选好友点击完成 前端 POST /groups/{id}/members，body: { member_ids } HTTP 请求
T2 后端校验 群存在、当前用户是成员、不超过 max_members、群未解散 —
T3 批量加入 INSERT conversation_members × N（ON CONFLICT 恢复已删除成员）+ 刷新宫格头像 成员加入
T4 系统消息 send_system "XXX 邀请了 YYY、ZZZ 加入群聊" 所有成员收到

邀请入群和"群主同意入群申请"复用同一个 join_group_direct 方法——数据库操作完全一样，只是触发入口不同。

解散群聊事件流

解散的逻辑不复杂，但有一个操作顺序的陷阱——系统消息必须在标记 status=1 之前发送，否则 send 会被自己的 status 校验拦截。

时刻 事件 处理 产生的新事件
T1 群主确认解散 前端 POST /groups/{id}/disband HTTP 请求
T2 后端校验 当前用户是群主 —
T3 系统消息 send_system "群聊已解散"（此时 status 还是 0，消息能广播） 所有成员收到
T4 标记解散 UPDATE conversations SET status=1 群聊状态变更

权限校验的代码模式完全一样——service 层开头查 owner_id，和当前 user_id 比较，不匹配返回 403：

1. 数据模型

本章新增一个迁移文件，做两件事：给 conversations 加 status 字段，给 group_info 加 announcement 相关字段。

-- ---> server/migrations/20260420_007_group_manage.sql
ALTER TABLE conversations ADD COLUMN IF NOT EXISTS status SMALLINT NOT NULL DEFAULT 0;
-- 0=正常, 1=已解散

ALTER TABLE group_info ADD COLUMN IF NOT EXISTS announcement TEXT;
ALTER TABLE group_info ADD COLUMN IF NOT EXISTS announcement_updated_at TIMESTAMPTZ;
ALTER TABLE group_info ADD COLUMN IF NOT EXISTS announcement_updated_by BIGINT;

决策 理由
status 放 conversations 而非 group_info MessageService.send 需要校验解散状态，放 conversations 查询更直接（不需要 JOIN group_info）
解散不删成员和消息 历史消息仍可查看，用 status=1 标记即可
announcement 放 group_info 群公告是群配置的一部分，和 join_verification 同级
announcement_updated_by 记录发布者 未来可能展示"谁发布的"，预留字段
2. 核心逻辑

新增的接口模式高度一致：routes 解析请求 → service 校验权限 → repository 操作数据库 → routes 发系统消息。踢人、退群、转让、群公告、改群名都是这个套路，不再逐个展开。这里只完整展开邀请入群——它是唯一涉及批量操作和多重副作用的接口。

邀请入群：批量操作与副作用链

邀请入群是唯一允许普通成员操作的接口（其他都要求群主）。一次请求可能加入多个成员，每个成员都可能触发 ON CONFLICT（之前被踢过的成员重新加入），加完后还要刷新宫格头像、发系统消息。

// ---> server/modules/im-group/src/service.rs
fn add_members(user_id, conversation_id, member_ids):
    // 1. 校验群未解散
    status = repo.get_conversation_status(conversation_id)?
    if status != 0: return Err(AppError::bad_request("群聊已解散"))

    // 2. 校验当前用户是群成员
    if !repo.is_member(conversation_id, user_id): return Err(AppError::forbidden("非群成员"))

    // 3. 校验不超过 max_members
    current_count = repo.get_member_count(conversation_id)?
    max = repo.get_max_members(conversation_id)?
    if current_count + member_ids.len() > max: return Err(AppError::bad_request("超过群人数上限"))

    // 4. 批量加入（ON CONFLICT 恢复已删除成员）
    added = repo.add_members(conversation_id, member_ids)?

    // 5. 刷新宫格头像
    repo.build_grid_avatar(conversation_id)?

    return added

repository 层的 add_members 用循环逐个 INSERT，每个都带 ON CONFLICT (conversation_id, user_id) DO UPDATE SET is_deleted = false。返回实际新增的数量（跳过已在群中的成员）。

routes 层拿到结果后，查邀请者昵称和被邀请者昵称，拼接系统消息"XXX 邀请了 YYY、ZZZ 加入群聊"。

为什么不用一条 INSERT ... VALUES (...), (...), ... 批量插入？因为需要统计"实际新增了几个"——ON CONFLICT 时 PostgreSQL 的 affected_rows 行为不够可靠（有些版本把 UPDATE 也算进去）。逐个 INSERT 虽然多几次 IO，但语义清晰，群成员数量级（≤200）下性能不是问题。

解散群聊

解散的代码很短，但有一个容易踩的坑：

// ---> server/modules/im-group/src/routes.rs
async fn disband(state, headers, path):
    state.service.disband(user_id, conv_id)?          // 1. 校验群主身份
    state.msg_service.send_system(conv_id, "群聊已解散")  // 2. 先发系统消息
    state.service.update_status(conv_id, 1)?           // 3. 再标记解散

第 2 步和第 3 步的顺序不能反。如果先标记 status=1，MessageService.send 内部的 status 校验会拦截自己的系统消息，群成员永远不知道群被解散了。解散后，前端会禁用输入框。但如果有人绕过 UI 直接调 API 发消息呢？MessageService.send 开头加了一道防线：

-- ---> server/modules/im-group/src/repository.rs
SELECT COALESCE(status, 0::SMALLINT) FROM conversations WHERE id = $1

0::SMALLINT 的类型标注不能省。如果写成 COALESCE(status, 0)，PostgreSQL 会把 0 当作 INT4，COALESCE 的返回类型提升为 INT4，但 Rust 端用 i16 接收——运行时 sqlx 解码报错。

3. AppError：一个 500 错误催生的基础设施

这个 bug 也直接促成 AppError 的诞生。我也在一直等待这一刻，之前 AI 在后端实现上一直没出问题，接口测试也是一次通过，所以没有异常捕捉的契机。

实现完 7 个接口后跑测试，接口 POST /groups/{id}/members 返回 500。客户端看到的是一个光秃秃的状态码，服务端终端什么都没有——没有错误日志，没有 panic，没有任何线索。

根因是目前项目中大量使用的反模式：

// ❌ 这行代码吞掉了所有错误信息
.map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)

下划线 _ 把 sqlx 返回的详细错误信息丢掉了。服务端只知道"出错了"，不知道"出了什么错"。每次遇到 500 都要重复"加 println → 编译 → 测试"的循环。

解决方案是在 flash-core 中新增统一错误类型 AppError：

// ---> server/modules/flash-core/src/error.rs
pub struct AppError {
    pub status: StatusCode,
    pub message: String,
    pub detail: Option<String>,
}

三个关键实现让它成为"装上就有效"的基础设施：

// 1. sqlx::Error 自动转换——数据库错误不再被吞
impl From<sqlx::Error> for AppError {
    fn from(err: sqlx::Error) -> Self {
        AppError::internal(err, "database")
    }
}

// 2. IntoResponse——自动打印日志 + 返回结构化 JSON
impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        if let Some(ref detail) = self.detail {
            println!("❌ {}", detail);  // 服务端自动打印
        }
        let body = json!({
            "error": self.message,
            "status": self.status.as_u16(),
            "detail": self.detail,  // 客户端也能看到
        });
        (self.status, Json(body)).into_response()
    }
}

// 3. From<StatusCode>——旧代码不用改
impl From<StatusCode> for AppError {
    fn from(status: StatusCode) -> Self { AppError::status(status) }
}

有了 AppError，原来五行的 .map_err 变成一个 ?：

// 旧：错误被吞，500 时无法排查
let status = repo.get_status(id).await
    .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)?;

// 新：错误自动捕获 + 打印 + 返回给客户端
let status = repo.get_status(id).await?;

这样，在接口测试时，异常信息就可以立刻定位到，大大节省排查的精力。另外统一的异常处理，也会让代码的可读性增加。

统一错误处理应该是基础设施的一部分——不是等出了问题再加，而是项目初期就该有。这次是被一个 COALESCE 类型不匹配的 bug 逼出来的，但它的价值远超这一个 bug。以后的项目就可以在一开始引入异常捕捉的机制。

4. GROUP_INFO_UPDATE：群信息变更的实时推送

改群名后，所有成员的会话列表和 ChatPage 标题需要实时更新。改公告后，ChatPage 的黄色横幅也要同步刷新。这些如果全靠 ConversationUpdate 帧来做，感觉会话更新承担的职责就太重了，会引入不必要的属性。而且群组的信息更新，更适合引入一个独立的帧来处理，这样群组管理需要增加其他功能，也不会引发会话模块的变动。

所以新增一个独立的 WS 帧类型 GROUP_INFO_UPDATE（type = 11），只在群信息变更时才推送：

// ---> proto/message.proto
message GroupInfoUpdate {
    string conversation_id = 1;
    optional string name = 2;
    optional string avatar = 3;
    optional string announcement = 4;
    optional int32 status = 5;
}

MessageDispatcher 新增 notify_group_info_update 方法，通过 ws_state.send_to_users 推送给所有群成员。routes 层在改名/改公告时通过 tokio::spawn 异步调用：

// ---> server/modules/im-group/src/routes.rs（update_group handler 末尾）
let member_ids = state.service.repo().get_member_ids(conv_id).await?;
tokio::spawn(async move {
    dispatcher.notify_group_info_update(&member_ids, &conv_id_str, name, avatar, None, None).await;
});

ConversationUpdate 负责消息预览和未读数（每条消息触发，保持轻量），GROUP_INFO_UPDATE 负责群信息变更（改名/改公告/解散时触发，语义清晰）。两种帧各司其职，不互相污染。

4. 异步拉取与 WS 实时同步

ChatPage 新增三个参数：isDisband（bool）、announcement（String?）、groupDetailFetcher（异步回调）。

进入时异步拉取：groupDetailFetcher 由 home_page 注入（调 GroupRepository.getGroupDetail），ChatPage 在 initState 中异步调用，拿到最新的 announcement 和 status。
WS 实时同步：ChatPage 监听 WsClient.groupInfoUpdateStream，收到 GROUP_INFO_UPDATE 帧时动态更新 _title（群名）、_announcement（公告横幅）、_isDisband（解散状态）。A 改了群名，B 在 ChatPage 里立刻看到标题变化——不需要退出重进。

// ---> client/modules/flash_im_chat/lib/src/view/chat_page.dart
_groupInfoSub = context.read<WsClient>().groupInfoUpdateStream.listen((frame) {
    final update = GroupInfoUpdate.fromBuffer(frame.payload);
    if (update.conversationId != widget.conversationId) return;
    setState(() {
        if (update.hasName()) _title = update.name;
        if (update.hasAnnouncement()) _announcement = update.announcement;
        if (update.hasStatus()) _isDisband = update.status == 1;
    });
});

ConversationUpdate 负责消息预览和未读数（每条消息触发），GROUP_INFO_UPDATE 负责群信息变更（改名/改公告时触发）。ChatPage 和 ConversationListCubit 各自监听自己关心的帧，互不干扰。

会话列表实时同步

ConversationListCubit 也监听 groupInfoUpdateStream。收到 GROUP_INFO_UPDATE 帧时，更新匹配会话的 name 和 avatar。这样改群名后，会话列表的群名也实时更新——和 ChatPage 标题同步。

// ---> client/modules/flash_im_conversation/lib/src/logic/conversation_list_cubit.dart
_groupInfoSub = _wsClient?.groupInfoUpdateStream.listen(_handleGroupInfoUpdate);

void _handleGroupInfoUpdate(WsFrame frame):
    update = GroupInfoUpdate.fromBuffer(frame.payload)
    conversations = current.conversations.map((c) {
        if c.id == update.conversationId:
            return c.copyWith(
                name: update.hasName() ? update.name : c.name,
                avatar: update.hasAvatar() ? update.avatar : c.avatar,
            )
        return c
    })
    emit(ConversationListLoaded(conversations))

6. 主应用集成与模块协作

client/lib/src/home/view/home_page.dart

home_page 是所有群聊功能的组装点——它不实现业务逻辑，只负责把各个模块的能力串联在一起。这一章它要注入三个新回调，每个都解决一个跨模块的协作问题。

groupDetailFetcher：让 ChatPage 不依赖 GroupRepository

ChatPage 在 flash_im_chat 模块中，GroupRepository 在 flash_im_group 模块中。如果 ChatPage 直接 import GroupRepository，两个模块就产生了耦合。解法是通过回调注入——home_page 同时认识两个模块，由它负责"翻译"：

// ---> client/lib/src/home/view/home_page.dart
ChatPage(
    conversationId: conversation.id,
    isGroup: true,
    groupDetailFetcher: () =>
        context.read<GroupRepository>().getGroupDetail(conversation.id),
    // ...
)

ChatPage 只知道"调这个回调能拿到群详情"，不知道数据从哪来。和第 25 章 friendsFetcher 的设计思路一样——模块只定义自己需要什么，由组装层负责提供。

friendsFetcher：好友数据到选人页的桥梁

邀请入群需要好友列表，但 GroupChatInfoPage 不认识 FriendCubit。home_page 复用已有的 _friendsToMembers() 方法，把 Friend 转为 SelectableMember 后注入：

// ---> client/lib/src/home/view/home_page.dart
GroupChatInfoPage(
    friendsFetcher: () async => _friendsToMembers(),
    // ...
)

这个方法在第 25 章创建群聊时就写好了，现在邀请入群直接复用——同一个转换逻辑，两个使用场景。

onLeaveOrDisband：退两层的导航回调

退群或解散成功后，需要从 GroupChatInfoPage → ChatPage 连续退两层回到会话列表。这个导航逻辑不能写在 GroupChatInfoPage 里——它不知道自己外面套了几层页面。由 home_page 注入：

// ---> client/lib/src/home/view/home_page.dart
GroupChatInfoPage(
    onLeaveOrDisband: () {
        Navigator.of(context).popUntil((route) => route.isFirst);
        _convCubit.loadConversations();
    },
    // ...
)

popUntil((route) => route.isFirst) 退到根路由，不管中间套了几层页面都能正确退回。比 ..pop()..pop() 硬编码层数更健壮，万一以后中间多插一层页面，不用改这里。

四、本章小结

群聊管理其实还有非常多的细碎功能，比如群体禁言、对每个成员禁言、修改头像、管理员机制等。限于篇幅，这里只介绍最核心的功能。大家有兴趣的也可以，自己继续建一个分支处理这些功能。

群成员管理与群详情 v0.15.0 commit

群聊从"能建能搜能审批"走到了"能管"。后端 im-group 路由翻倍到 14 个，前端 GroupChatInfoPage 从信息展示页变成了群管理中心。功能网络从 81 个节点增长到 93 个。

这一章最有价值的不是那些 CRUD 接口——踢人、退群、转让的代码模式几乎一样。真正值得带走的是设计决策：

两种 WS 帧各司其职。ConversationUpdate 每条消息触发，只带预览和未读数，保持轻量；GROUP_INFO_UPDATE 只在群信息变更时触发，带 name/avatar/announcement/status。不把低频信息塞进高频通道，是实时系统的基本纪律。

组件下沉的时机。MemberPickerPage 不是一开始就设计为通用组件的——第 25 章它叫 CreateGroupPage，和"创建群聊"绑在一起。直到这一章邀请入群和踢人都需要选人交互时，才把它提取到 flash_shared。第一次写的时候不需要通用，第三次复用的时候自然下沉。

意外收获是 AppError： 一个 COALESCE(status, 0) 的类型不匹配 bug，暴露了项目中 .map_err(|_| StatusCode) 反模式的危害。最好的基础设施不是提前规划的，而是被一个具体的痛点逼出来的。
