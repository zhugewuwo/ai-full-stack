经络#2 ｜ 后端 - 认证系统升级

记忆是生命的根基，当数据有了归宿，服务便有了灵魂。

上一篇我们完成了模块化拆分，后端从一个巨型单细胞进化成了多器官协作的结构。但拆开只是第一步。器官之间如果没有血管、神经、激素这些"关系通道"，生命体就只是一堆零件的集合，而不是一个有机的整体。这一篇，我们要给认证系统做一次真正的升级——从内存玩具变成可持久化的真实系统。

一、从内存到数据库

目前认证系统有一个致命问题：所有数据都在内存里的模拟认证，没有真正操作用户的途径。
服务一重启，发的验证码也好、聊天室的内容也好、一切归零。这就像一个只有短期记忆的生物——能对眼前的刺激做出反应，但记不住任何东西。我们需要引入一种手段，可以持久化存储必要的数据。这就是 数据库。

二、从后端认证升级，审视需求

想在数据库环境已经准备完毕，即将进入真正的需求实现流程。从这里开始，我就有意识地进行 文档结构化拆分 。但目前不是一步到位，因为我希望让你看到，AI 文档演化的过程，你才知道哪块为什么该放在这里。我希望一切的发展，沿着它最自然的方向。

1. 一个合格的需求文档

这里我以，让 AI 生成个 需求分析规划师 角色为目的。和它讨论了很久：一个合格的需求文档，该长什么样。 这一步的目的是，为以后的需求分析，给出固定的回报格式。一致性，对于流程化来说是非常必要的。

一旦需求分析规划师这个角色完善了，任何功能需求，都可以让它来规划，就避免了很多前置条件的赘述。可以基于结构化的文档设定，赋予 AI 智能体某种能力。比如我这里的 feature-designer.md, 规定了设计报告的统一格式。

  • 顶部用 YAML 记录模块名、版本号、日期和标签，方便检索。
  • 开头说做什么，结尾说不做什么，中间全是怎么做。
  • 正文分六个章节：目标、现状分析、数据模型与接口、核心流程、项目结构与技术决策、暂不实现。

有了这个统一格式，不管是哪个模块，AI 拿到设计报告都知道去哪找什么信息。而"暂不实现"这一节尤其重要，它是给 AI 画的红线，防止它过度发挥去实现不该做的东西。

另外，目前 AI 编辑器都有类似 规则、技能、全局上下文 等概念，可以让开发者保存这些设定。比如我用的 kiro ，可以通过 / 唤出设定来引用。如果不知道怎么设置，很简单: 和 AI 聊天，让它帮你设置。

3. 任务拆解

当有了一份详尽的设计文档，AI 就可以非常明确你想做什么。但是设计文档的不确定性 ，说 AI 的可发挥空间，还是太大了。设计文档是架构师视角，它说的是"做什么、为什么"，但没有精确到 "该做什么"。如果直接把 design.md 丢给 AI 让它写代码，它可能会按自己的理解去组织代码，结果和你预期的不一样。

所以我们需要再往下走一步：把设计方案拆解成一份任务清单（tasks.md）。这就像施工图纸和施工工序的关系——图纸告诉你房子长什么样，工序告诉你先打地基还是先砌墙，每一步用什么材料、什么规格。同样的思路，我设计了一个 feature-task-maker.md，它规定了任务清单的统一格式：

  • 每个任务对应一个具体的文件改动
  • 给出关键代码片段——不是完整实现，而是骨架：结构体的字段定义、函数的签名和逻辑步骤、关键的 SQL 语句
  • 任务之间有明确的依赖顺序，按顺序执行不会卡住
  • 每个任务带状态标记（⬜ 待处理 / 🔧 进行中 / ✅ 已完成），方便检阅进度

数据库的骨架搭好了——四张表各司其职，静静地等在那里。但表只是容器，就像铺好了血管却还没有血液流过。接下来我们要做的，是让 Rust 代码真正连上数据库，把"发验证码、验证登录、创建用户"这些动作，从内存里的 HashMap 模拟，变成对数据库的真实读写。这一步完成后，服务重启不再失忆，用户数据真正活了起来。

环境变量配置

数据库地址、JWT 密钥这些配置信息，不应该硬编码在代码里。不同的环境（开发、测试、生产）配置不同，写死了就没法灵活切换。通用的做法是用一个 .env 文件集中管理。比如服务已经打包了，但想改个端口号，如果写死在代码里，就需要重新打包，发版上线。
像这些和业务逻辑无关的配置项，可以定义在外面的配置文件，方便快速修改，然后重启服务即可。

DATABASE_URL=postgres://postgres:postgres@localhost:5432/flash_im
JWT_SECRET= 你自己随便定义
SERVER_PORT=9600
  • DATABASE_URL：告诉 sqlx 连哪个数据库，格式是 postgres://用户:密码@地址:端口/库名
  • JWT_SECRET：签发和验证 Token 的密钥，生产环境务必换成随机长字符串
  • SERVER_PORT：服务监听端口

代码通过 dotenvy 库在启动时读取。 在 server/ 目录下创建 .env 文件。这个文件应该加入 .gitignore，不要提交到仓库里——每个人的本地配置可能不同，密钥更不能泄露。

数据库连接池

这次认证流程的成长，最主要是使用数据库来承载数据的流转。也就是数据访问、数据存储的节点，都要换成数据库创作。在这里，负责操作数据库的就是 数据库连接池(PgPool)。它是将血液(数据)流入各个系统的关键枢纽，后端几乎在全周期都要访问它。
目前 state.rs 里的 AppState 盛放全局对象，可以把它放到这里。之前其中存放的内存数据就可以去掉了：

/// 应用共享状态
pub struct AppState {
    pub db: PgPool,                             // 数据库连接池
    pub chat_tx: broadcast::Sender<String>,     // 聊天室广播
}

通过读取 .env 的 DATABASE_URL 配置，在 PgPoolOptions 对象在创建时，链接到的数据库路径。

async fn main() {
    dotenvy::dotenv().ok();
    let database_url = std::env::var("DATABASE_URL")
        .expect("DATABASE_URL must be set in .env");

    let db = PgPoolOptions::new()
        .max_connections(10)
        .connect(&database_url)
        .await
        .expect("Failed to connect to database");

    println!("✅ Database connected");

四、本章小结

存档点 tag 提交点
后端认证系统升级 v0.4.0 4e66f04

这一章，我们完成了后端认证系统从"玩具"到"真实"的跨越：

  • 引入 PostgreSQL 数据库从选型、安装到脚本化管理，让数据有了持久化的归宿。服务重启不再失忆。
  • 建立结构化的开发流程——需求分析规划师、设计文档、任务清单，三层递进。从"做什么"到"怎么做"再到"具体改哪个文件"，颗粒度逐步收敛。
  • 落地四张核心数据表——accounts、user_profiles、auth_credentials、sms_codes 各司其职，用数据库关系表达了账户、身份、凭据之间的真实结构。
  • 代码真正连上数据库——PgPool 替代了内存 HashMap，验证码、登录、注册这些动作变成了对数据库的真实读写。

到这里，后端不再是一个只有短期记忆的生物。它有了长期记忆，有了结构化的数据骨架，有了可重复的开发流程。认证系统的地基，算是真正打下来了，为后续的发展打下来很好的基础。

另外这一章在升级过程中，花了不少篇幅在"怎么让 AI 做事"上——设计文档的格式、任务清单的结构、脚本化的环境管理。这些看起来不是在写代码，但它们决定了代码的质量。

很多人觉得 AI 编程就是"把需求丢给它，让它写"。但你会发现，需求描述得越模糊，AI 的发挥空间越大，结果和你预期的偏差也越大。反过来，当你把需求拆解到"改哪个文件、函数签名长什么样、SQL 怎么写"这个粒度，AI 几乎不会出错。这就是流程的价值。好的流程不是束缚，而是把 不确定性 逐层消解的过程：

  • 设计文档消解的是"做什么"的不确定性
  • 任务清单消解的是"怎么做"的不确定性
  • 脚本化工具消解的是"环境能不能跑"的不确定性

每消解一层，AI 的输出就更可控一分。最终你会发现，驾驭 AI 的能力，本质上是把问题结构化的能力。 你能把问题拆得多细，AI 就能帮你做得多准。这不是 AI 的局限，而是所有协作的本质——无论对面坐的是人还是机器。

目前仅划分了 设计 desgin 和 任务 tasks 两个最朴素的流程节点，后面随着复杂性的增加，还会继续拆解需求的相关文档。下一章，将继续完善对前端的认证流程进行升级，并且脱离游乐场，真正进入闪讯 APP 的开发。
