##### 3. 认知拓展 

接下来，基于当前 AI 生成的代码进行一些评鉴。整体主流程的设计，我也参与很多讨论。其中最丰富的是我和它探讨启动模块和认证模块的关系。在启动时，要查看用户是否已经认证过，所以启动模块 `starter` 和认证模块 `auth` 的边界，一开始容易被混淆。最初 AI 的方案，是让启动页直接依赖 `auth` 模块来判断登录状态。这种做法的问题在于：

> 它把“流程控制”和“业务能力”耦合在了一起，启动不再只是启动，而是掺入了认证逻辑。

后来它又尝试反过来设计，让启动模块变成一个被观察者，由各个需要认证的模块去监听它的状态变化。这个思路看似解耦，实际上是把问题转移了：  
启动模块本来是一个短生命周期的流程节点，却被强行提升成了一个全局状态源。结果是，其他模块开始依赖一个本不该长期存在的对象，这种依赖关系在时间维度上是不合理的。

---

本质上，启动模块的职责很单一，就是完成初始化工作，比如加载本地配置、读取缓存、恢复必要的运行上下文，以及在这个过程中 `“顺带”` 检查一次当前的认证状态。一旦这些工作完成，它的使命就结束了，它不应该继续参与系统的长期状态维护。就像你进入游乐园检票之后，检票员和你再无瓜葛，你在园内的任何设施的游玩，都和检票员无关。

认证状态的维护，是一个应用全生命周期的状态，它和认证流程是紧密相关的。理应在认证模块本身去独立维护，启动器只需要负责 `告知` 即可。仅一次的交互之后，它们再无关联。它为我更新了流程图：

##### 2. 交流过程中的细节

这里来分享一下和 AI 交流的细节。对登录状态管理，有三个阶段的烟花。一开始，它的设计是将登录状态 LoginState 作为 sealed class，每种状态一个子类：

```dart
sealed class LoginState {}
class LoginInitial extends LoginState { final bool isSmsMode; }
class SmsSending extends LoginState {}
class SmsSent extends LoginState { final String code; final bool isSmsMode; }
class LoginLoading extends LoginState {}
class LoginSuccess extends LoginState { final LoginResult loginResult; final User user; }
class LoginFailure extends LoginState { final String message; final bool isSmsMode; }
```

我看起来就很别扭，就让它分析了一下，这种方式存在的潜在风险，下面是它的回复:

1. **状态维度混淆**：`isSmsMode`（UI 模式）是持久的，`SmsSending`/`LoginLoading`（操作状态）是瞬时的。两个维度被拆成不同的子类，每次状态切换都会丢失另一维度的信息。
2. **信息丢失**：`SmsSending` 和 `LoginLoading` 没有 `isSmsMode`，emit 后 UI 不知道当前模式。发完验证码（`SmsSent`）点登录变成 `LoginLoading`，验证码信息丢了。
3. **扩展性差**：加新登录方式需要在每个子类里都带上模式标识，子类数量膨胀。

Sealed class 适合状态之间互斥且信息不重叠的场景。登录页的状态有两个独立维度（模式 + 操作），不适合用互斥子类建模。

---

然后我意识到其实登录界面也是短生命周期的。它的目的就是校验用户是不是有资格进入，然后给张门票。和游乐园检票的职能很类似，所以它和启动时校验一下，本质上明没有太大区别，只不过这里多了一些表单的填写。登录页的状态是 **页面级**的，生命周期随页面销毁，不需要跨组件共享，用状态管理框架是过度设计。

> Q: 其实我感觉登录本质上是一个得到 token 的抽象能力，它的界面数据也只是在自己的生命周期内，没有复杂的共享需求，有必要使用状态管理吗？


然后让它用 mixin 把状态数据和业务逻辑从 State 类里抽出来，LoginPage 的 State 只管 UI 构建，mixin 管数据和方法。职责分离，但不引入额外框架。然后是方案二：

```dart
mixin LoginMixin on State<LoginPage> {
  bool isSmsMode = true;
  bool isLoading = false;
  bool agreed = false;
  int countdown = 0;
  final phoneCtrl = TextEditingController();
  final credentialCtrl = TextEditingController();
  // sendSms(), login(), toggleMode()...
}

class _LoginPageState extends State<LoginPage> with LoginMixin {
  @override
  Widget build(BuildContext context) { /* 纯 UI */ }
}
```

- 职责分离：逻辑在 mixin，视图在 State
- 无框架开销：不需要 BlocProvider、BlocConsumer
- 生命周期自然：页面销毁时 mixin 的 dispose 自动清理

---

当时代码上它已经为我写了一版，然后我看着 `LoginMixin` 里复杂的变量，感觉不同的认证方式所需的数据全部杂糅到了一块，后面要增加其他认证，就要在这锅粥里折腾。于是让它帮我在好好设计一些，能让不同的登录方式维护自身必要的数据。下面是 AI 的建议:

不同登录方式有各自的输入控件和校验逻辑，它们不是继承关系，而是组合关系——LoginMixin 同时持有多个策略对象，按需激活。切换模式只是换个状态，各策略的状态互不丢失。

同时，"怎么登录"这件事应该留在策略内部。如果 `login()` 写死在 Mixin 里，每种登录方式的调用逻辑都耦合在一起，新增方式要改 Mixin。更关键的是，三方登录（微信/Google）的流程完全不同——不是"填表单 → 调接口"，而是"OAuth 回调 → 拿 token"，写死在 Mixin 里根本塞不进去。

所以策略需要一个轻量的抽象基类，只约束共性：能校验、能登录、能销毁。`login()` 下沉到策略自身，Mixin 只做调度。抽象基类 `LoginStrategy`：

```dart
abstract class LoginStrategy {
  bool get isValid;
  Future<LoginResultData> login(AuthRepository repo);
  void dispose();
}
```

- `isValid` — 当前输入是否满足登录条件
- `login(repo)` — 执行登录，返回统一结果 `({LoginResult loginResult, User user})`
- `dispose()` — 释放资源

这里不强制 `sendSms()`、`countdown` 等特有能力——这些是具体策略的私有行为，不属于公共契约。

```
LoginStrategy（抽象基类）
├── isValid
├── login(repo) → LoginResultData
├── dispose()

LoginMixin（持有 + 调度）
├── agreed、isLoading、mode
├── smsStrategy: SmsLoginStrategy
├── passwordStrategy: PasswordLoginStrategy
├── currentStrategy → 当前激活的策略
├── login() → currentStrategy.login(repo) → AuthCubit.login → go('/home')
├── toggleMode() → 切换 mode

SmsLoginStrategy extends LoginStrategy
├── phoneCtrl、codeCtrl、countdown
├── login(repo) → repo.login(phone, credential, 'sms')
├── sendSms()（特有）

PasswordLoginStrategy extends LoginStrategy
├── accountCtrl（手机号/用户名/邮箱）、passwordCtrl
├── login(repo) → repo.login(phone, credential, 'password')
```

写完后，我觉得还不错，虽然可能好没有尽善尽美。但后续增加一个认证方式，改动就会小很多：

- 加邮箱验证码登录：新建 `EmailLoginStrategy extends LoginStrategy`，LoginMixin 里注册，LoginPage 加一套输入 UI
- 加三方登录（微信/Google）：新建 `WechatLoginStrategy extends LoginStrategy`，OAuth 回调拿到 token 后走 `login(repo)` 统一返回
- 所有方式最终都通过 `LoginStrategy.login(repo)` 返回统一的 `LoginResultData`，汇入 `AuthCubit.login()`

##### 1. 目录结构


乍一看文件不少，但规律很明显。`src/` 下分成三类东西：

- `application/` — 应用基础设施，配置、路由、网络客户端，只在启动时组装一次
- `domain/` — 跨模块共享的业务模型，比如 User，后续还会有 Message、Contact
- 业务模块（starter、auth、home）— 每个内部都是 `data / logic / view` 三层

这不是我们预先规定的模板，而是在和 AI 反复讨论中自然收敛出来的。

##### 2. 职责与通信

用一句话概括每层干什么：

| 层 | 职责 | 典型产物 |
|---|------|---------|
| data | 和外部世界打交道——网络请求、本地缓存读写 | AuthRepository、StartupRepository、LoginResult |
| logic | 业务规则和状态管理——不关心 UI 长什么样 | AuthCubit、LoginMixin、LoginStrategy |
| view | 纯 UI 构建——不关心数据从哪来 | LoginPage、ProfilePage、SmsLoginForm |

依赖方向是单向的：`view → logic → data`。view 层可以调用 logic 层的方法，logic 层可以调用 data 层的接口，但反过来不行。这条规则保证了每一层都可以**独立替换**。

> 换个 UI 框架不影响业务逻辑，换个后端接口不影响界面。

---


在这两个模块的开发中，我们用了两种不同的状态管理方式，这不是随意的，而是根据状态的生命周期来选择的：

| 状态 | 方式 | 理由 |
|------|------|------|
| 认证状态（是否登录、Token、用户信息） | AuthCubit（flutter_bloc） | 应用全生命周期，多个页面需要读取 |
| 登录表单状态（手机号、验证码、倒计时） | StatefulWidget + Mixin | 页面级，随页面销毁，无共享需求 |

简单来说：需要跨页面共享的状态，用 Cubit 挂在 App 顶层；只在当前页面用的状态，`setState` 就够了。不是所有状态都值得上框架，过度设计反而增加复杂度。

---

目前模块之间的通信方式很克制，只有两种：

**回调通知**：starter 完成启动后，通过 `onStartupComplete` 回调把结果交给 main.dart，main.dart 再调用 `AuthCubit.applyStartupSnapshot()`。starter 不知道 AuthCubit 的存在，它只管把数据交出去。

**读取全局状态**：HomePage、ProfilePage 通过 `context.read<AuthCubit>()` 读取认证状态。这是 flutter_bloc 提供的标准方式，AuthCubit 挂在 Widget 树顶层，任何子节点都能访问。

没有事件总线，没有全局单例，没有全局注入。通信路径越少，代码越容易理解。后续如果模块变多、通信变复杂，再考虑引入更重的机制也不迟。

##### 3. 对 AI 编程的意义

这套结构不复杂，但它有一个好处：**每个文件该放在哪里，不需要想。** 新加一个模块，照着 data / logic / view 三层建目录；新加一个登录方式，在 strategy 里加一个文件。结构本身就是文档，打开目录树就知道项目在干什么。

这种分层对 AI 编程有很实际的意义。AI 在处理你的需求时，首先要做的就是定位——改哪个文件、加在哪里。如果代码是一锅粥，所有逻辑混在几个大文件里，AI 需要通读大量代码才能理解上下文，定位成本很高，出错概率也大。

而分层结构给了 AI 一套明确的寻址规则：你说"改登录逻辑"，它知道去 `logic/login/`；你说"加个接口调用"，它知道去 `data/repository/`；你说"调整界面"，它知道去 `view/`。层次越清晰，AI 的定位越准，生成的代码越容易落在正确的位置。

对人来说也一样。接手一个陌生项目，最怕的不是代码复杂，而是不知道从哪看起。分层结构提供了一张地图——先看 `application/` 了解应用怎么启动和组装，再看某个模块的 `data/` 了解它和外部怎么交互，`logic/` 了解业务规则，`view/` 了解界面长什么样。每一层的职责是确定的，你不需要把整个项目读一遍才能开始干活。

- **启动模块落地**——SplashPage 读取本地缓存，判断认证状态，一次性交接给 AuthCubit 后退场。启动器和认证模块的边界，在反复讨论中变得清晰：短生命周期的流程节点，不该承担长期状态维护的职责。

- **分层结构浮现**——`application/` 放应用基础设施，`domain/` 放跨模块共享模型，业务模块内部 `data / logic / view` 三层各司其职。

我们目前还是采用的 `文件夹` 隔离模块的方式，这种方式便于初期的理解。但这种隔离方式并不是模块化的最优解。比如想在 starter 的模块中，代码文件可以访问 auth 的内容，我们只是 **人为规定** 不要乱依赖。而这种认为，可能在某些为了便利性时而被破坏。  

后面的随着前后端代码的增长，以及我们对事物之间联系的深入理解。会陆续将 `模块` 的概念，分化为物理层面独立的 `"器官"`，甚至通过接口契约，这个 `"器官"` 可以直接移植到其他的项目中工作。下一篇，我们将不忙着赶进度，而是基于目前已经完成的认证系统，好好探讨一下 **事物之间联系** 这一个非常重要的认知。

**认知拓展：和 AI 一起做架构决策**

这一章里，很多架构决策不是我一个人拍板的，而是在和 AI 的对话中逐步收敛出来的。比如登录状态管理的三次演化——第一版 Sealed Class 是 AI 给的方案，我看着别扭，让它自己分析问题；第二版单 Mixin 是我提出的方向，AI 帮我实现后我发现了新的问题；第三版策略模式是我们一起讨论出来的。

这个过程有点像结对编程，但节奏更快。AI 的优势是它能迅速给出一个完整方案，让你看到全貌；你的优势是你能从全貌中嗅到不对劲的地方。它写得快，你看得准，两者配合起来，架构决策的质量反而比一个人闷头想要高。

但有一点要注意：AI 给的第一版方案，往往不是最优的。不是因为它能力不够，而是因为它还不够了解你的偏好和项目的上下文。你需要把"这里不对"说出来，它才能往更好的方向调整。**沉默地接受，是 AI 编程中最大的浪费。**

再回首，你可以看到和 AI 讨论的过程中，我们已经不知不觉积攒了对项目来说，最宝贵的文档资产。这不只是让 AI 了解该干什么，更可以让人了解功能需求在干什么，这也是项目成长的轨迹。
