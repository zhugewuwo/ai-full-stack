##### 2. 逻辑流程树

**综合搜索：三路并发**

用户输入关键词后，前端 300ms 防抖，然后并发调用三个搜索 API。三个请求各自独立 try-catch，好友搜索失败不影响群聊和消息搜索的展示。

| 时刻 | 事件      | 处理                                              | 产生的新事件     |
| -- | ------- | ----------------------------------------------- | ---------- |
| T1 | 用户输入关键词 | 前端 300ms 防抖                                     | —          |
| T2 | 防抖结束    | 并发调用好友搜索、已加入群搜索、消息搜索                            | 三个 HTTP 请求 |
| T3 | 后端处理    | 好友：ILIKE 匹配昵称；群聊：ILIKE 匹配群名；消息：ILIKE 匹配内容，按会话分组 | 三个响应       |
| T4 | 前端收到响应  | 各自独立处理，部分失败不影响其他分区                              | UI 刷新      |

![mermaid-diagram - 2026-04-28T072224.919.png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/6cadac5dc9014cc094d786d4e8b30913~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=2348\&h=1612\&s=210098\&e=png\&a=1\&b=eaeaea)

***

**消息搜索：按会话分组**

消息搜索不是逐条返回，而是按会话分组。每个分组包含会话信息（名称、头像、类型）、匹配总数和最近 3 条匹配消息。这样用户一眼就能看到"在哪个聊天里提到了这个关键词"。

后端分两步查询：先找匹配的会话及匹配数（GROUP BY conversation\_id），再对每个会话取最近 3 条匹配消息和会话信息。分步查询比一个巨大的 JOIN 更可控。

> 消息搜索只搜文本消息（msg\_type = 0），过滤系统消息（sender\_id != 0）。图片、视频、文件的 content 是 URL，搜索无意义；系统消息（"XXX 创建了群聊"）也不是用户想找的内容。

##### 1. 搜索范围：只搜"我的"

综合搜索和添加好友页的用户搜索、搜索加群页的群搜索有本质区别。后者是 **"找陌生人/公开群"**，前者是 **"找我已有的东西"**。好友搜索查 `friend_relations` 表，只返回当前用户的好友：

```sql
-- ---> server/modules/im-friend/src/api.rs
SELECT fr.friend_id, COALESCE(up.nickname, '?') AS nickname, up.avatar
FROM friend_relations fr
LEFT JOIN user_profiles up ON up.account_id = fr.friend_id
WHERE fr.user_id = $1 AND up.nickname ILIKE $2
ORDER BY up.nickname
LIMIT $3
```

已加入群搜索通过 `INNER JOIN conversation_members` 过滤，只返回用户已加入且未解散的群：

```sql
-- ---> server/modules/im-conversation/src/routes.rs
SELECT c.id, c.name, c.avatar,
    (SELECT COUNT(*) FROM conversation_members
     WHERE conversation_id = c.id AND is_deleted = false) AS member_count
FROM conversations c
INNER JOIN conversation_members cm
    ON cm.conversation_id = c.id AND cm.user_id = $1 AND cm.is_deleted = false
WHERE c.type = 1 AND COALESCE(c.status, 0::SMALLINT) = 0 AND c.name ILIKE $2
ORDER BY c.name
LIMIT $3
```

`COALESCE(c.status, 0::SMALLINT) = 0` 过滤已解散的群（status=1）。`0::SMALLINT` 的类型标注不能省，否则 sqlx 在运行时解码时会因为 INT4 和 SMALLINT 不匹配而报错。

> 为什么不复用已有的 `GET /api/users/search` 和 `GET /groups/search`？因为它们搜的是"所有用户"和"所有群"，综合搜索需要的是"我的好友"和"我加入的群"。搜索范围不同，SQL 的 WHERE 条件完全不同，硬塞一个 `scope` 参数进去不如各写各的清晰。

##### 2. 消息搜索：分组 + 过滤 + 分页

消息搜索是这一章最复杂的接口。它不是简单地 `SELECT * FROM messages WHERE content ILIKE`，而是按会话分组返回，每组包含会话信息和最近匹配的消息。

**跨会话搜索（综合搜索用）**

分两步查询。第一步找匹配的会话及匹配数：

```sql
-- ---> server/modules/im-message/src/routes.rs
SELECT m.conversation_id, COUNT(*) AS match_count
FROM messages m
INNER JOIN conversation_members cm
    ON cm.conversation_id = m.conversation_id
    AND cm.user_id = $1 AND cm.is_deleted = false
WHERE m.type = 0 AND m.sender_id != 0 AND m.content ILIKE $2
GROUP BY m.conversation_id
ORDER BY MAX(m.created_at) DESC
LIMIT $3
```

三个过滤条件各有用意：`m.type = 0` 只搜文本消息（图片/视频/文件的 content 是 URL，搜索无意义），`m.sender_id != 0` 过滤系统消息（"XXX 创建了群聊"不是用户想找的内容），`INNER JOIN conversation_members` 限制只搜用户参与的会话。

第二步对每个会话取最近 3 条匹配消息和会话信息。单聊需要取对方的昵称和头像，群聊直接用群名和群头像：

```python
for conv_id, match_count in groups:
    # 查会话类型
    conv_type = SELECT type FROM conversations WHERE id = conv_id

    if conv_type == 0:  # 单聊：取对方信息
        name, avatar = SELECT nickname, avatar FROM conversation_members
            WHERE conversation_id = conv_id AND user_id != current_user
    else:  # 群聊：用群名
        name, avatar = SELECT name, avatar FROM conversations WHERE id = conv_id

    # 最近 3 条匹配消息
    messages = SELECT id, nickname, avatar, content, created_at
        FROM messages JOIN user_profiles
        WHERE conversation_id = conv_id AND type = 0
            AND sender_id != 0 AND content ILIKE pattern
        ORDER BY created_at DESC LIMIT 3
```

> 为什么分两步而不是一个大 JOIN？因为一个查询要同时做 GROUP BY（按会话分组）和 LIMIT（每组取 3 条），SQL 写起来很别扭（需要窗口函数 ROW\_NUMBER），分步查询更直观，性能在小数据量下没有差别。

**会话内搜索（详情页用）**

会话内搜索比跨会话搜索简单，不需要分组，直接返回消息列表。支持 `offset` 分页，前端 MessageDetailPage 每页加载 20 条，滚动到底部自动加载更多：

```sql
SELECT m.id, COALESCE(up.nickname, '?'), up.avatar,
    m.content, m.seq, m.created_at
FROM messages m
LEFT JOIN user_profiles up ON up.account_id = m.sender_id
WHERE m.conversation_id = $1 AND m.type = 0
    AND m.sender_id != 0 AND m.content ILIKE $2
ORDER BY m.created_at DESC
LIMIT $3 OFFSET $4
```

返回的 `seq` 字段是消息的序列号，前端用它在消息详情页显示 `#42` 这样的编号，方便用户定位。

##### 1. SearchCubit：三路并发 + 部分失败容忍

SearchCubit 是这个模块的核心。用户每次按键都会触发 `search(keyword)`，300ms 防抖后并发调用三个 API。关键设计是部分失败容忍：

```dart
// ---> flash_im_search/lib/src/logic/search_cubit.dart
final results = await Future.wait([
    _repository.searchFriends(keyword: keyword)
        .then<Object?>((v) => v).catchError((e) => e),
    _repository.searchJoinedGroups(keyword: keyword)
        .then<Object?>((v) => v).catchError((e) => e),
    _repository.searchMessages(keyword: keyword)
        .then<Object?>((v) => v).catchError((e) => e),
])

// 类型判断区分成功和失败
if results[0] is List<FriendSearchItem>: friends = results[0]
else: friendError = results[0].toString()
```

`Future.wait` 等所有请求完成后，根据每个结果的类型判断成功还是失败。三个都成功 emit `SearchSuccess`，至少一个失败 emit `SearchPartialSuccess`。UI 层对两种状态的渲染逻辑一样，只是 `SearchPartialSuccess` 可以额外显示错误提示。

> 为什么不用三个独立的 `setState`？因为搜索结果要一次性展示，不能联系人先出来、群聊再出来、消息最后出来。`Future.wait` 保证三个请求都完成后才更新 UI，用户看到的是一个完整的搜索结果，不是逐步加载。

##### 3. 综合搜索页

SearchPage 是用户看到的主界面。顶部是输入框，右侧"取消"按钮。Body 根据 SearchCubit 的状态切换：

*   `SearchInitial` → 搜索历史（SharedPreferences 存储，最多 20 条，Wrap 流式布局）
*   `SearchLoading` → 加载指示器
*   `SearchSuccess` / `SearchPartialSuccess` → 分区结果

每个分区默认展示 3 条，点击"更多联系人"/"更多群聊"/"更多消息"展开全部。聊天记录分区的点击逻辑稍复杂：如果该会话只有 1 条匹配消息，直接跳转 ChatPage；如果有多条，先进入 MessageDetailPage。

MessageDetailPage 不依赖综合搜索返回的 3 条预览，而是进入时重新调用会话内搜索 API 获取完整列表，每页 20 条，滚动到底部自动加载更多。综合搜索的 3 条预览只是"入口"，详情页才是"全貌"。

##### 4. 主应用集成

搜索入口有两个：消息 Tab 和通讯录 Tab 顶部的 `FlashSearchBar`（占位模式），点击后都跳转到同一个 `SearchPage`。

```dart
// ---> client/lib/src/home/view/home_page.dart
void _openSearch(BuildContext context):
    Navigator.push(SearchPage(
        repository: context.read<SearchRepository>(),
        onFriendTap: (friendId) => _openFriendDetail(...)
        onGroupTap: (conversationId) => _openChatById(...)
        onMessageTap: (conversationId, messageId) => _openChatById(...)
    ))
```

`SearchRepository` 在 `main.dart` 中通过 `RepositoryProvider` 注入，和其他 Repository 一样。

搜索模块通过三个回调（`onFriendTap` / `onGroupTap` / `onMessageTap`）与外部通信。搜索模块不知道怎么创建 ChatPage 或 FriendDetailPage，它只负责告诉外部"用户点了什么"，导航逻辑由 home\_page 处理。

> 为什么用回调而不是直接在搜索模块里导航？   
> 因为搜索模块是一个独立的 package，它不依赖 flash\_im\_chat 或 flash\_im\_friend。如果让它直接 import ChatPage，就引入了对业务模块的依赖，模块边界就破了。回调把"做什么"和"怎么导航"分开，搜索模块只管前者。

会话内搜索的入口在 ChatPage 的 `onSearchChat` 回调里，通过 ChatPage → 详情页 → ConversationSearchPage 的链路传递。  
GroupChatInfoPage 和 PrivateChatInfoPage 都新增了"查找聊天内容"设置项。
