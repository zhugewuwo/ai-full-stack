#### 功能版本开发流水线

经过这十几章的演化和验证，**Feature Workflow — 功能版本开发流水线** 这套 `全栈功能迭代` 工厂已经可以稳定工作了。虽然各大 AI 编程 IDE 都有自己的类似方式，但是可定制性一般，对历史需求的管理也很不到位，而且和编程 IDE 强绑定。我想做的是:

> 打造一个可以稳定运行的，全栈功能需求迭代流水线角色，  
> 任意的编程 AI 工具都可以给这个技能工作。

本章将结合这次的功能实现，来详细说明一下这套流水线的工作流程。

![image.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/d6f134bae7d24d959e6610f84d1ba5da~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1024&h=559&s=355648&e=png&b=f5ece8)


这套流水线的核心思想是 **面向文档编程**，从 `需求分析` 到 `开发设计` 再到 `任务落地`，甚至是 `测试产物` 、都要落实到文档上，这些文档会记录在项目里，伴随项目一生。这些将成为项目最完善的 **产品文档**、**开发文档**、**测试文档**。  
工作目录在 docs/features 下进行迭代版本的管理，每个功能需求有 5 大核心文档：

```
docs/features/{模块}/{版本}/
├── analysis.md              # 第 1 步：需求分析
├── server/
│   ├── design.md            # 第 2 步：后端设计
│   └── tasks.md             # 第 3 步：后端任务
├── client/
│   ├── design.md            # 第 7 步：前端设计
│   └── tasks.md             # 第 8 步：前端任务
└── api/                     # 第 6 步：后端测试
    └── {module}/
        ├── request/
        │   └── {module}.py  # 测试脚本（Python + curl），手动编写
        └── doc/             # 接口文档（脚本运行后自动生成，不要手动编辑）
            ├── 00_link.md   # 大纲索引
            └── 01_xxx.md    # 各接口文档
```

#### 一、需求分析

Feature Workflow 里有对需求分析的简单描述，介绍一下三个投影面的基本概念，以及注意事项：

```
角色：Feature Analyst
输出：`analysis.md`
规范具体详见：#[[file:.kiro/steering/feature-analyst.md]]

包含三个投影面：
- **交互链**：用户走什么路（用户故事 + 操作路径 + mermaid flowchart，每个场景必须附图）
- **逻辑树**：系统做什么（事件流表格 + 状态流转 + mermaid sequenceDiagram，每条事件流必须附图）
- **功能编号**：在网络中的位置（新增节点 + 前置依赖 + 边界接口）

这一步决定"做什么"和"不做什么"，是后续所有文档的源头。
```

通过 `#[[file:xxx]]` 可以引入其他文件。这样 AI 在工作时，可以根据具体的角色技能，生成我们预定格式的分析文件。需求分析的具体角色，会从 `交互链`、`逻辑树`、`功能编号` 三个角度去分析需求，产出 `analysis.md` 文件。

通过这个工作节点，能分析出当前的功能具体是在干什么；有多少个潜在的交互流程；对用户有什么作用；具体流程中的逻辑决策是什么；当前的功能的边界在哪里；和当前整个应用功能网络的联系等。比如新增的消息置顶功能，这一步可以得到如下文件: [analysis.md](https://github.com/toly1994328/flash_im_by_ai/tree/v0.20.0/docs/features/im/operation/v0.0.4/analysis.md) 


![image.png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/6db1732c813246a2851ae7997bb41a2c~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1276&h=497&s=95134&e=png&b=eeedf1)

---

这个环节需要注意的是：**合理把握需求的颗粒度**。  
颗粒度指的是这个需求有多大，比如 `制作微信` 是一个需求，`消息置顶` 也是一个需求。但你如果把前者作为需求分析的目标，基本上是无解的，它本身就不是一个合理的颗粒度。

`消息置顶` 作为一个需求点就刚刚好，它是有着非常明确的功能特性、交互流程、完成指标。而且体量不算太大，可以一次流程完成。另外，颗粒度也不要划分地太小，比如把它再拆成 `消息置顶`、`消息取消置顶` 等更细的功能点，虽然最后也能完成，但是流程就要跑多遍，有些浪费。

如果是一些非常小的需求，甚至都没有必要通过流程来做。或者也可以攒着一批小需求，通过一次流程来一起完成。所以 AI 开发流程的起点非常重要，你需要对所使用 AI 单次战斗的上限做到心中有数。这样才能合理的评估，这项需求，适不适合通过这个开发流程一波完成。这个心中有数，需要你对 AI 的长时间使用累积经验。

比如这章 `消息转发、@提及、消息置顶` 三个功能，我是放在一起做的，虽然最终完成了，但是过程上并不是太顺利。第一版时，完全不能工作，后面我和它讨论很久，才逐渐优化、迭代完成。这就是很典型的，前期没有做好准备，后期就需要更多的返工和验证。

如果每一轮只做一个需求，无论是人还是 AI 都可以更专注，每一个需求的实现都是一针强心剂。而三个一起做，一鼓作气、再而衰，三而竭，错误多了，你自己也会跟着泄气。这个确实是我在开始没有做好分析，毕竟三者是完全独立的功能，体量也都不小。在 AI 编程的探索中，这种曲折也是成长的养分，真正走过的坑，在以后才会更容易避免。

#### 二、后端

后端是所有客户端数据访问的中枢，它提供接口契约、数据持久化和实时推送能力。后端的三步——设计、任务、实现——本质上是在回答三个递进的问题：系统长什么样？怎么拆着建？按什么顺序砌？

---

##### 第 2 步：后端设计

**feature-designer** 技能角色，负责 `design.md` 文档的建设工作。

> 角色定位: 需求设计师。当用户提出一个功能需求时，你需要输出一份结构化的设计报告（design.md），为后续的任务拆解和 AI 编码提供清晰的上下文。

```
角色：Feature Designer
输出：`server/design.md`
规范具体详见: #[[file:.kiro/steering/feature-designer.md]] 
模块化拆分参考: #[[file:.kiro/skills/modular-design/SKILL.md]]
前置参考文件: 第 1 步产物的 analysis.md
包含：
- 数据模型（SQL + ER 图 + 设计决策表）
- 接口契约（请求/响应 JSON + 错误码）
- 核心流程（时序图）
- 技术决策（方案 + 理由）
- 文件结构（新建/修改的文件清单，标注每个文件的单一职责）
```

后端设计的核心是**定义契约**。数据模型定义了"数据长什么样"，接口契约定义了"对外暴露什么能力"，核心流程定义了"数据怎么流转"。这三者构成了后端的骨架，后续的任务拆解和编码都是在这个骨架上填肉。

技术决策表是一个容易被忽略但很重要的部分。每个决策必须附带理由——不是"我选了方案 A"，而是"我选了方案 A，因为 B 有什么问题"。这样做的好处是：当后续需要修改时，能快速判断当初的假设是否还成立。

文件结构也很重要，新建/修改的文件清单，标注每个文件的单一职责。这不是走形式，而是在告诉 AI "你的战场在哪里"。没有这个清单，AI 可能把本该放在 repository 里的逻辑写进 routes，或者在 service 里直接操作数据库。明确了文件边界，代码才不会长歪。

有一点很关键：design.md 是架构师视角，不要深入代码实现细节，那些留给 tasks.md。另外"暂不实现"这一节别小看它，它是给 AI 编码画红线的——AI 有时候会"好心办坏事"，把你明确说不做的功能也给实现了。写清楚边界，能省掉不少返工。比如新增的消息置顶功能，这一步可以得到如下文件: [design.md](https://github.com/toly1994328/flash_im_by_ai/tree/v0.20.0/docs/features/im/operation/v0.0.4/server/design.md)

##### 第 3 步：后端任务


**feature-task-maker** 技能角色，负责 `tasks.md` 文档的建设工作。

> 角色定位: 任务规划师。基于已有的设计报告（design.md），将设计方案拆解为可逐条执行的任务清单（tasks.md），让 AI 编码时每一步都有明确的指令，消除歧义和发挥空间。

另外在设计时增加另一个 `modular-design` 的 SKILL ，把之前章节对模块化的拆分考量，进行总结成思考流程，便于在前端设计时，及时考量这方面。

```
角色：Feature Task Maker
输出：`server/tasks.md`
规范具体详见：#[[file:.kiro/steering/feature-task-maker.md]]
前置参考文件：第 1 步产物的 analysis.md + 第 2 步产物的 server/design.md

把 design.md 拆成可逐条执行的任务：
- 每个任务对应一个文件
- 给出函数签名和关键 SQL
- 标注依赖顺序和执行顺序
```

design.md 说"做什么"，tasks.md 说"怎么做"。每个任务对应一个具体的文件改动，粒度到函数/结构体级别。给出关键代码片段（签名、结构体、SQL），不是完整实现，而是"骨架"。任务之间有明确的依赖顺序，AI 按顺序执行不会卡住。

任务状态标记也是一个重要设计：`⬜ 待处理` → `🔧 进行中` → `✅ 已完成`。AI 每完成一个子任务后更新标记，打开 tasks.md 就能一眼看到整体进度。

这里有个度的问题。一个任务对应一个文件的改动，如果一个文件改动点很多，就用子任务拆分。代码片段给骨架就好——结构体给完整定义，函数给签名加逻辑步骤，不用写完整实现。给多了 AI 反而会照抄不思考，给少了又容易跑偏。另外，执行顺序要讲究：数据结构先行，服务层跟上，路由和 UI 最后，编译验证收尾。这个顺序是为了让 AI 每一步都能编译通过，不会因为依赖还没建好就卡住。

新增的消息置顶功能，这一步可以得到如下文件: [tasks.md](https://github.com/toly1994328/flash_im_by_ai/tree/v0.20.0/docs/features/im/operation/v0.0.4/server/tasks.md) |

##### 第 4 步：三文档交叉审查

这一步没有独立的角色技能，但它是整个流水线中最容易被忽略、也最有价值的环节。

```
联合后端 analysis + design + tasks 检查一致性：
- 接口路径是否对齐
- 功能编号是否覆盖
- 遗漏的校验逻辑
- 数据库字段是否齐全
- analysis 中标注"不做"的功能是否在 design/tasks 中被移除
```

为什么需要交叉审查？因为三个文档是不同视角对同一个功能的描述：analysis 是产品视角，design 是架构视角，tasks 是执行视角。三个视角放在一起看，比一个文档反复看三遍更容易发现问题。

常见的发现：
- analysis 里写了"@所有人权限仅群主"，但 design 里的接口没有权限校验
- design 里定义了一个字段，但 tasks 里忘了写对应的 SQL
- tasks 里多出了一个 analysis 标注"暂不实现"的功能

跳过这一步直接写代码，大概率要返工。审查的重点不是文字表述好不好看，而是逻辑一致性——接口路径、字段名、错误码这些"硬对齐"最容易出错。发现问题就回去改文档，不要在脑子里记着"到时候注意一下"，那基本等于没注意。

##### 第 5 步：后端实现

这一步是 AI 的主战场。tasks.md 已经把每个文件要改什么、函数签名是什么、SQL 怎么写都定义好了，AI 只需要按图施工。这也是为什么前面花那么多精力写文档的原因——文档越清晰，AI 编码越准确，返工越少。


```
按 tasks.md 顺序实现，每完成一个任务标记 ✅。
每项任务完成后，自行编译验证一下是否有异常，及时修改。
参考规范：#[[file:.kiro/steering/rust-error-handling.md]]
```

后端实现有一个独立的错误处理规范（rust-error-handling.md），确保所有接口的错误响应格式统一、状态码正确。如果有其他的风格、注意事项，可以在这里增加一下。

实践中有几个经验教训：   
- 一是让 AI 实现完后自行跑 `cargo build` 编译验证——不要等到所有任务都做完才编译，每完成一批相关任务就编译一次，发现问题及时修，不然错误会像滚雪球一样越积越多。
- 一是每完成一个任务就标记 ✅，如果中途被打断（比如去修个别的 bug），下次回来能立刻知道做到哪了。  
- 二是遇到 tasks.md 没覆盖到的边界情况，先回去补文档再写代码，不要"先写了再说"——那个"再说"往往就没有然后了。这是为了保证文档的实时最新

##### 第 6 步：后端测试

**link-test-writer** 技能角色，负责接口测试脚本的编写和接口文档的自动生成。

> 角色定位：API 测试链编写者。基于已有的后端接口，为指定功能模块编写测试链 Python 脚本，脚本运行后自动测试所有接口并生成接口文档。

```
用 Link Test Writer 生成测试脚本，覆盖所有正常和异常场景。
测试通过后自动生成接口文档。
参考规范：#[[file:.kiro/steering/link-test-writer.md]]
```

**link-test-writer** 是一个很有意思的设计：测试脚本既是测试工具，也是文档生成器。一个 Python 脚本，用 curl 调用所有接口，验证响应是否正确，同时把请求和响应记录下来，自动生成接口文档。

这意味着：
- 接口文档永远是最新的（因为是跑出来的，不是手写的）
- 接口文档里的 curl 命令是可以直接复制执行的（带真实 token）
- 测试覆盖了正常流程和错误场景（403、404、400 等）

测试脚本按业务流程串联，形成有意义的"链"。比如先创建会话，再发消息，再转发，再置顶——模拟真实的用户操作序列。

编排测试步骤时，要有业务含义，不是随机调接口。错误场景（4xx）紧跟在对应的正常步骤后面——先测"置顶成功"，紧接着测"重复置顶返回 400"，这样读起来像一个故事。另外 `doc/` 目录下的文件全部是自动生成的，千万不要手动编辑，每次跑脚本会覆盖掉你的改动。比如新增的消息置顶功能，这一步可以得到如下文件: []()

#### 三、前端

前端是用户直接触碰的那一层，所有的交互体验最终都要落到这里。和后端不同，前端的复杂度不在数据流转，而在状态管理和 UI 表现。同一份数据，在列表页是一行文字，在聊天页是一个气泡，在选择器里是一个可勾选的条目。前端的四步（设计、任务、交叉审查、实现）本质上是在回答：界面长什么样？状态怎么流？组件怎么拆？  
前端的流程和后端对称：设计 → 任务 → 交叉审查 → 实现 → 验证。

---

##### 第 7 步：前端设计

前端设计和后端设计用的是同一个 feature-designer 角色。 `modular-design` 的模块拆分的技能是通用的视角进行审视，同样也适用于前端设计。

```
角色：Feature Designer
输出：`client/design.md`
规范具体详见：#[[file:.kiro/steering/feature-designer.md]]
模块化拆分参考：#[[file:.kiro/skills/modular-design/SKILL.md]]
前置参考文件：第 1 步产物的 analysis.md + 第 6 步产物的 api/doc/（接口文档）

包含：
- 文件结构（新建/修改的文件清单，标注每个文件的单一职责）
- 职责隔离（组件只管渲染，Cubit 只管状态，Repository 只管数据）
- 页面结构、交互流程（mermaid 流程图）
- 技术决策（方案 + 理由）
- 变更范围（新建文件 + 修改文件，明确边界）
```

前端设计的核心是**职责隔离**。这个项目用的是 BLoC/Cubit 架构，层次分明：View 层的 Widget 只管渲染和用户交互，Cubit 层只管业务状态的流转，Repository 层只管数据的获取和缓存。不要把网络请求写在 Widget 里，不要让 Cubit 去操作 Widget 的 controller，不要让 Repository 知道 UI 长什么样。这些边界看起来是常识，但 AI 写代码时经常会"图方便"把逻辑塞到不该放的地方，所以设计文档里必须把职责划分写清楚。

写前端设计时，文件结构要标注每个文件的单一职责。变更范围要明确区分"新建"和"修改"，修改已有文件时说清楚改哪里、为什么改，不然 AI 容易改错地方或者改多了。技术决策要优先考虑复用已有组件，比如这次的会话选择器就是复用 MemberPickerPage 加了几个参数，而不是从零写一个新页面。

新增的消息置顶功能，这一步可以得到如下文件:  [design.md](https://github.com/toly1994328/flash_im_by_ai/tree/v0.20.0/docs/features/im/operation/v0.0.4/client/design.md)

##### 第 8 步：前端任务

同样使用 **feature-task-maker** 角色，产出 `client/tasks.md`。

```
角色：Feature Task Maker
输出：`client/tasks.md`
前置参考：analysis.md + client/design.md + api/doc/（接口文档）

把 client/design.md 拆成可逐条执行的任务：
- 每个任务对应一个文件改动，粒度到 Widget / Cubit 方法级别
- UI 组件给出关键 Widget 树结构和交互行为描述
- 状态管理给出 Cubit 方法签名和 State 字段变化
- 修改已有文件时精确到"在哪个方法里加什么"
- 标注依赖顺序和执行顺序
```

和后端任务的思路一样，把 design.md 拆成可逐条执行的任务。但前端任务有自己的特点：它会涉及更多的 UI 描述。一个后端任务可能就是"写一个 SQL 查询 + 一个 handler"，但前端任务可能是"一个带动画的展开面板 + 状态联动 + 手势交互"。

UI 组件的描述要给出关键 Widget 树结构，但不用写完整的 build 方法。涉及状态管理的部分，要明确 Cubit 的方法签名和 State 的字段变化。如果是修改已有文件，要精确到"在哪个方法里加什么"，含糊地说"修改 XXX 文件"，AI 大概率会改错位置或者改多了。前端代码的上下文依赖比后端强得多，一个 Widget 的行为可能取决于它在树中的位置、父级传入的回调、Cubit 的当前状态，这些都要在任务描述中交代清楚。

##### 第 9 步：前端交叉审查


和第 4 步同理，确保前端的设计和任务与需求分析对齐。但前端的交叉审查范围更广：不仅要看前端三份文档的一致性，还要和后端的 server/design 以及 api/doc 对齐，确保前端调用的接口路径、参数、响应格式和后端实际提供的一致。

```
联合 analysis + server/design + api/doc + client/design + client/tasks 综合审查：
- analysis 中的每条交互链是否在前端设计中都有对应的页面和流程
- 前端调用的接口路径、参数、响应格式是否与 server/design 和 api/doc 一致
- 组件复用的边界是否合理（扩展已有组件时，是否会破坏其他调用方的行为）
- design 中的文件职责划分是否在 tasks 中得到体现
- "暂不实现"的功能是否已从 tasks 中移除
```


另一个常见问题是组件复用的边界。设计里说"复用 MemberPickerPage"，但 tasks 里写的改动可能会破坏 MemberPickerPage 在其他场景（比如创建群聊、移除成员）的行为。交叉审查时要想一想：这个改动会不会影响已有的调用方？

##### 第 10 步：前端实现

前端实现是整个流水线中代码量最大的一步。AI 按 tasks.md 的顺序逐条实现，同时受两个规范约束：UI 风格规范确保界面视觉统一，构建验证规范确保编译零错误。    
这两个规范也拆分出去，被纳入了 SKILL 中。这样一方面可以保持，流水线本身简洁；到对应的流程时，也可以主动去读取加载特定规则。另一方面，独立出去也便于更新和维护，在实践中不断优化升级这些技能。

```
按 tasks.md 顺序实现。
UI 风格规范：#[[file:.kiro/skills/flash-im-ui-style/SKILL.md]]
构建验证规范：#[[file:.kiro/skills/flutter-build-verify/SKILL.md]]

完成后必须执行全量构建验证（详见 flutter-build-verify 技能），零错误才能进入下一步。
```

前端实现完成后，有一个**强制门禁**：必须执行全量编译分析。这是在实践中加上的，早期没有这个要求，AI 经常改了 A 文件导致 B 文件编译失败，但因为没有全量检查，问题被带到了后面才发现，修复成本更高。

比如涉及 drift 表定义变更，要先跑一遍代码生成再 analyze。AI 最容易犯的错是：改了模型字段但忘了更新 copyWith，改了接口签名但忘了更新调用方。多模块项目中，跨模块的类型变更是编译错误的重灾区——你改了 core 包里的一个类，chat 包和 conversation 包可能同时炸。所以全量 analyze 不是走形式，是真的能救命。必须全量类型检查和跨模块依赖验证，零错误才能进入下一步。

##### 第 11 步：前端测试

在真机或模拟器上手动验证关键路径，确认功能正常工作。

验证范围：
- 覆盖 analysis 中定义的所有交互链场景（正常流程）
- 异常路径：网络断开、数据为空、权限不足等边界情况
- 多端协同：A 发消息 B 收到、A 置顶所有人看到、A 转发后本地缓存同步等
- UI 表现：动画流畅度、布局溢出、键盘弹起后的适配

发现 bug 时的处理：
- 修复后回到第 10 步重新 flutter analyze，确保修复没有引入新问题
- 设计缺陷直接修复并更新到对应的 design/tasks 文档中

##### 第 12 步: 归档


很多人觉得功能做完、代码合并就结束了。但如果你不归档，下一次开新功能时会发现：上次加了哪些节点？哪些接口是新的？哪些模块被改过？全靠记忆和翻 git log。项目越大，这种"记忆负担"越重，到后面每次开新功能都要花大量时间"回忆上次做了什么"。


归档解决的就是这个问题。它把每次迭代的成果沉淀到一张持续生长的功能网中，让项目的全貌始终可见。新功能的需求分析可以直接引用已有节点的编号和依赖关系，不用从头梳理。AI 在做需求分析时，也能通过功能网快速理解"当前系统已经有什么能力"，避免重复建设或遗漏依赖。

```
角色：Feature Archiver
归档规范：#[[file:.kiro/steering/feature-archiver.md]]
- 更新 `docs/features/archiver/index.md`：节点编号表 + 网络图 + 存档记录
- 更新 `docs/features/archiver/modules/{域}/`：局域网络
- 创建 `docs/features/archiver/trace/{版本}_{日期}.md`：存档快照
- git tag + 提交 + 推送 + 合并到 master
```

**feature-archiver** 负责把这次迭代的成果归档到全局功能网中。功能网是整个项目的"地图"，每个功能是一个节点，节点之间有依赖关系。随着版本迭代，这张网越来越完整，新功能的分析也越来越快，因为前置依赖都已经清晰标注了。

归档的三件事：
1. **更新全局索引**（index.md）：新增节点编号，更新网络图。这是功能网的"目录"，一眼看到系统有多少个功能节点、它们之间怎么连接。
2. **维护局域网络**（modules/）：用"三焦距"方法梳理模块。远景看骨骼（模块与依赖），中景看血液（数据通道与事件流），近景看神经（生命周期与订阅）。不需要读源码就能理解一个模块的全貌。
3. **创建存档快照**（trace/）：记录这次变更的摘要，打 git tag。快照是只读的，创建后不修改，它是项目演进历史的时间线。

有几个规矩：编号一旦分配就不能变，废弃的节点标记 ❌ 而不是删除，因为其他地方可能引用了这个编号。归档完成后才合并到 master，确保 master 分支始终是稳定的、有完整归档的状态。

归档看起来是"额外工作"，但它的回报是复利式的。第一次归档可能觉得麻烦，但到第十次、第二十次功能迭代时，你会发现每次需求分析的速度越来越快，因为功能网已经帮你把上下文都准备好了。这就是"归档是可持续的基础"这句话的含义。

#### 小结

回到本书一直在讲的"生命"隐喻。如果说代码是生命体的细胞，那流水线就是这个生命体的新陈代谢系统。每一次功能迭代，就是一次完整的代谢循环：从外界摄入需求（分析），在体内合成新的结构（设计 + 实现），排出废物（交叉审查剔除不一致），最终将成果固化为身体的一部分（归档）。

没有代谢系统的生命体，只能长一次就停下来。有了代谢系统，生命可以持续生长，每一轮循环都让身体更强壮、更完整。这套流水线做的就是这件事：让项目的每一次功能迭代都是可持续的、可追溯的、可复用的。

十几章走下来，从最初的手忙脚乱到现在的按部就班，最大的感受是：AI 编程不是"让 AI 写代码"这么简单。它更像是带一个能力极强但缺乏上下文的新人——你给的指令越清晰、边界越明确、上下文越完整，它的输出就越稳定。流水线的每一步，本质上都是在为 AI 准备上下文。

这套方法论还在演化中。也许再过十章，会有新的步骤加入，也会有现在的步骤被简化或合并。但核心不会变：先想清楚再动手，做完了要留痕，留痕是为了下一次更快。
