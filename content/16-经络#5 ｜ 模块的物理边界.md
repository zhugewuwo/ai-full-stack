> 好的隔离不是让彼此疏远，而是让协作更清晰

上一章我们建立了"关系视角"，其中在模块级说过：**模块之间的关系应该比类之间更加克制。**
但回头看我们自己的代码，"克制"二字做得并不好。

- auth 目录下的内部组件被 home 随意 import，
- AuthCubit 从启动活到关闭却管着用户资料
- ActionButton 放在 auth 里却被 home 拿去用。

目录结构看着像模块化，实际上没有任何隔离。就像在地上画了几条线，说 `"这是你的地盘，那是我的地盘"` ，但谁都可以随意跨过去。这一章，我们要把地上的线变成真正的围墙。

---

#### 一、假模块化与真模块化

我们已经按职责，把代码分进了不同的文件夹，看起来井井有条。但如果你试着从 home 模块里 import auth 的一个内部组件——编译器不会拦你，甚至不会给你一个警告。这说明我们的"模块"只是视觉上的分区，只是一种 `"人为约定"`, 不是真正的隔离。

---

##### 1.目录不是边界

在上一次的认证升级过程中：
- 后端的模块化,把 main.rs 拆成 auth、ws、mock、util 四个目录。
- 前端也按 auth、starter、home 分了文件夹。

但这只是"目录级模块化"，本质上是把代码分了类，没有建立真正的边界。看一个具体的问题。如下，三行 import 表示: home 模块不仅知道 auth 模块的存在，还知道它内部的目录结构、文件命名、甚至组件的具体位置。

```dart
// home/profile/set_password_page.dart
import '../../auth/view/components/action_button.dart';  // 直接 import auth 的内部组件
import '../../auth/logic/auth/auth_cubit.dart';           // 直接 import auth 的内部状态
import '../../auth/data/repository/auth_repository.dart'; // 直接 import auth 的内部仓库
```



如果 auth 内部重构，比如把 `action_button.dart` 从 `components/` 移到 `widgets/`。那么home 模块就会编译失败。这就是假模块化的代价：**内部变化会波及外部。** 模块的"内部实现"根本不是内部的，因为没有任何机制阻止外部直接访问。

---

##### 2.真正的物理隔离(前端)

真正的模块化，是让每个模块成为独立的 **类库** ——前端是独立的 Dart package，后端是独立的 Rust crate。每个类库有自己的依赖声明（`pubspec.yaml` / `Cargo.toml`），通过显式的导出文件（barrel file / `pub` 可见性）控制公开 API。

那怎么把 auth 从一个目录变成一个独立的 Dart package？(你也可以和 AI 谈论一下)  
我在 `client` 前端目录创建一个 `modules` 的文件夹，统一维护模块。这条命令创建一个标准的 Dart package 结构

> Q: 在 client/modules 中为我创建 flash_auth 的独立 package，  
> 并将之前的 auth 转移到独立模块

```bash
cd client/modules
flutter create --template=package flash_auth
```

模块目录结构的项目结构如下：


![image.png](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/b5373ff27e4b453aa259acde54600051~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1478&h=592&s=110355&e=png&b=fffdfd)

`lib/flash_auth.dart` 是这个模块的入口文件（barrel file）。外部 import 这个 package 时，只能看到这个文件里导出的内容。把 auth 相关的代码搬进 `lib/src/` 目录后，在 barrel file 里声明公开 API。导出的几个可见类，就是 auth 模块的全部公开 API。外部只能写：

```dart
import 'package:flash_auth/flash_auth.dart';
```

拿到 AuthRepository、LoginResult、LoginPage。至于 auth 内部用了什么策略模式、LoginMixin 怎么组织、SmsLoginForm 长什么样——外部完全不知道，也不可能知道。Dart 的 package 机制保证了 `src/` 目录下的文件对外不可见，这不是约定，是语言级别的 **硬约束**。

---

主 app 通过 `pubspec.yaml` 的 path 依赖引入这个 package：

```yaml
# client/pubspec.yaml
dependencies:
  flash_auth:
    path: modules/flash_auth
```

之前 home 模块那三行越界的 import：

```dart
import '../../auth/view/components/action_button.dart';  // ❌ 编译错误
import '../../auth/logic/auth/auth_cubit.dart';           // ❌ 编译错误
import '../../auth/data/repository/auth_repository.dart'; // ❌ 编译错误
```

现在全部编译失败。想用 AuthRepository？可以，它在 barrel file 里导出了。想用 ActionButton？不行，它是 auth 的内部组件，没有导出。  你被迫去思考：这个组件是不是应该放到一个共享的地方？     

这就是物理隔离：**不是靠自觉，而是靠编译器。** 你想越界？编译器直接报错。

---

##### 3.真正的物理隔离(后端)


后端的思路一样，但每种语言都有自己特有的类库管理方式。Rust 用 workspace 机制实现物理隔离。它会把一个项目拆成多个 crate，每个 crate 有自己的 `Cargo.toml`，通过 `pub` 关键字控制哪些内容对外可见。当目前的后端是一个标准的 **单项目**：

```
server/
├── Cargo.toml          # 一个 [package]，所有依赖都在这里
└── src/
    ├── main.rs          # 入口
    ├── state.rs         # AppState
    ├── auth/            # 目录
    ├── ws/              # 目录
    ├── mock/            # 目录
    └── util/            # 目录
```

这里的问题和前端一样，`ws/auth.rs` 可以直接访问 auth 文件夹下的内部实现，编译器不会拦你。

#### 二、认证与用户的拆分

模块化不只是把代码搬到不同的 package 里。如果只是原封不动地搬，问题还是在——只不过从"目录里的混乱"变成了"package 里的混乱"。真正的模块化，要求我们重新审视每个模块的职责边界。让模块物理隔离，可以更好地暴露目前已知的依赖关系。

---

##### 1. AuthCubit 的身份危机

先看当前的 AuthCubit：

```dart
class AuthCubit extends Cubit<AuthState> {
  void login({required String token, required User? user, required bool hasPassword}) { ... }
  void logout() { ... }
  void onPasswordSet() { ... }
}
```

它叫"Auth"Cubit，但它持有的东西——token、user、hasPassword——并不全是认证的。token 是认证的产物，但 user（昵称、头像、手机号）是用户资料，hasPassword 是用户属性。它从应用启动活到关闭，管着用户的一切信息。如何增加用户资料的编辑，功能该放在哪里? 

---

问题出在哪？**认证和用户被混为一谈了。**

- 认证回答的是"你是谁"——验证身份、拿到 Token、结束。它是一个短生命周期的动作，到登录成功那一刻就完成了使命。
- 用户回答的是"你是什么样的人"——昵称、头像、手机号、密码状态。它是一个长生命周期的实体，跟随整个会话存在。

---

##### 2. 三个模块的关系

经过拆分，客户端形成了三个职责清晰的模块：启动（flash_starter）、认证（flash_auth）、用户会话（flash_session）。它们之间的关系如下：


![mermaid-diagram (23).png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/62c6ec647d764c8e95636dfedcdf9a34~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=2479&h=1108&s=208541&e=png&a=1&b=f7f1ef)

图中用四种颜色区分数据流转：

- **蓝色**：启动流程，SplashPage 通过 StartupTask 抽象执行任务，结果回调到 main.dart 统一处理跳转
- **橙色**：认证流程，登录 → Token 回传 → activate 激活会话
- **绿色**：会话生命周期，拉取资料、读取状态、退出登录


这样处理后，可以看到这三个模块完全独立，没有任何的直接相互依赖。组装区的 main.dart 成为它们彼此沟通的场所，下面是TM的职责边界：

| 模块 | 生命周期 | 职责 | 公开 API |
|------|---------|------|---------|
| flash_starter | 一次性——冷启动时 | 执行启动任务列表，回调结果给组装层 | SplashPage, StartupTask\<T\>, OnStartupComplete |
| flash_auth | 短——登录动作开始到 Token 获取 | 发送验证码、验证身份、返回 Token | AuthRepository, LoginPage, LoginResult |
| flash_session | 长——从 activate 到 deactivate | 维护用户会话：Token、资料、密码状态、本地缓存 | SessionCubit, SessionRepository, SessionState, User |

三个模块现在都是独立的 Dart package，统一放在 `client/modules/` 下。它们之间互不依赖——没有任何 import 指向彼此。连接它们的是主工程的 `main.dart`——组装层。

```
flash_auth ──LoginResult──→ main.dart ──activate()──→ flash_session
                              ↑
                          组装层：唯一知道三个模块的地方
```

认证模块只管"证明你是谁"，拿到 Token 就交出去；  
会话模块只管"你在这段时间里是什么样的"，接到 Token 就开始工作；
启动模块只管"冷启动时该做什么"，执行完任务就通过回调，交还控制权。  

三个模块各自独立演进，互不干扰。这就是物理隔离带来的好处——不是不让它们合作，而是让合作只发生在一个明确的、可控的地方。未来的更新迭代，也可以在内部进化，就像前后端分离，只要保证接口不变，内部可以翻天覆地 —— 这就为成长留足了空间。

#### 四、本章小结

这一章做了三件事：**隔离、拆分、实践**。可以发现 `用户功能增加` 的这个需求，代码的改动，几乎都被收敛到一个模块，认证、启动这些纹丝不动。不知道你能不能体会这种、如器官般的协作方式。

> 📌 **存档点 v0.6.0**

| 存档点 | tag | 提交点 |
| --- | --- | --- |
| session v0.0.2 完成（服务端+客户端） | [v0.6.0](https://github.com/toly1994328/flash_im_by_ai/releases/tag/v0.6.0) | [c7467c4](https://github.com/toly1994328/flash_im_by_ai/tree/c7467c4) |


第一件事是把"目录级模块化"升级为"物理隔离"。之前的 auth 文件夹只是视觉上的分区，任何人都可以 import 内部文件，编译器不会拦你。把它变成独立的 Dart package / Rust crate 后，`src/` 下的文件对外天然不可见——不是靠自觉，而是靠编译器。barrel file 成为模块的唯一出口，你想越界，编译器直接报错。

第二件事是拆分认证与用户会话。AuthCubit 之前既管 Token 又管用户资料，职责模糊。拆分后，flash_auth 只负责"证明你是谁"，生命周期到拿到 Token 就结束；flash_session 负责"你在这段时间里是什么样的"，从 activate 到 deactivate 全程维护。三个模块（starter、auth、session）互不依赖，只在 main.dart 组装层连接。

```
flash_session/lib/src/
├── data/       # SessionRepository, User
├── logic/      # SessionCubit, SessionState
└── view/       # EditProfilePage, SetPasswordPage, ChangePasswordPage
    └── widget/ # IdenticonAvatar, UserCard, UserAvatar
```

第三件事是在实践中验证这套架构。新增用户资料编辑、密码管理拆分、默认头像渲染，所有改动都收敛在 flash_session 模块内部，不波及 flash_auth，也不波及 flash_starter。ProfilePage 留在主工程，因为它未来会聚合多个模块的内容——这本身就是模块边界的一次判断：**属于单一模块的放进去，属于组装层的留外面**。

测试链机制的引入，让后端接口验证脱离前端独立运行，产出的接口文档又反哺前端开发，形成闭环。link_test_writer 角色的诞生，是从具体痛点出发，逐步引导 AI 形成可复用能力的典型过程。

物理隔离的本质不是让模块彼此疏远，而是让协作只发生在明确的、可控的地方。模块内部可以翻天覆地，只要暴露给外界的功能不变，外界无感。这就为每个模块的独立演进，留足了空间。
