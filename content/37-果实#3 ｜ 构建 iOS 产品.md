上一篇我们把闪讯打包成了 Android APK，朋友们已经能装在手机上用了。但如果你的朋友用的是 iPhone，他需要的是一个 iOS 版本。这篇来聊聊 iOS 构建和发布的全流程。本章围绕以下几个点展开:

- 如何打包构建 iOS 应用产物。
- 发布到 Apple 应用市场的准备和流程。
- 优化登录方式 `Apple 登录` + `邮箱登录`

> 提前说明：iOS 构建必须在 macOS 上进行，Windows 无法编译 iOS 应用。这是 Apple 的限制，不是 Flutter 的问题。

#### 一、构建 iOS 产物的前置准备

在动手之前，先理解 iOS 和 Android 在发布上的根本差异：

| 对比项 | Android | iOS |
|--------|---------|-----|
| 构建环境 | Windows / macOS / Linux 都行 | 只能 macOS |
| 签名方式 | 自己生成 keystore | Apple 开发者证书 |
| 分发方式 | APK 随便发，商店可选 | 必须通过 TestFlight 或 App Store |
| 开发者费用 | Google Play $25（一次性） | Apple Developer $99/年 |
| 侧载安装 | 允许（设置里开启即可） | 基本不允许（越狱除外） |

一句话总结：Android 是开放的，iOS 是封闭的。iOS 的每一步都需要 Apple 的"许可"。

##### 1. Apple 登录 — 全链路流程

Apple 登录和 GitHub OAuth 的思路类似，但有一个关键区别：**Apple 不需要用授权码换 token**。客户端直接从系统获取一个已签名的 `identity_token`（JWT），后端只需要验证这个 JWT 的签名即可。


| 步骤 | GitHub OAuth | Apple Sign In |
|------|-------------|---------------|
| 1 | 打开网页授权 → 获取 code | 系统弹窗 Face ID → 获取 identity_token |
| 2 | 后端用 code 换 access_token | 不需要（token 已经在手） |
| 3 | 后端用 token 请求用户信息 | 不需要（信息在 token 里） |
| 4 |  验证 access_token 有效性 | 验证 JWT 签名（RS256） |

Apple 把所有信息都打包在一个 JWT 里了，后端只需要验证签名真伪。


![mermaid-diagram - 2026-05-25T075643.623.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/ad3e52a4247b44e68766ed251c14d4ed~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=2934&h=2618&s=393018&e=png&a=1&b=e8e8e8)

前端的处理比较简单，使用 `sign_in_with_apple` 插件即可获取 `identityToken`，传给后端处理即可：

```dart
--->[client/modules/flash_auth/lib/src/view/login_page.dart]---
Future<void> handleAppleLogin() async {
  // 1. 调用系统 API（sign_in_with_apple 插件）
  final credential = await SignInWithApple.getAppleIDCredential(
    scopes: [AppleIDAuthorizationScopes.email],
  );
  
  // 2. 获取 identity_token
  final identityToken = credential.identityToken;
  if (identityToken == null) throw Exception('未获取到授权信息');
  
  // 3. 发送到后端验证
  final result = await authRepository.loginWithApple(identityToken);
  
  // 4. 登录成功，写入 session 跳转主页
  onLoginSuccess(result);
}
```

另外在 iOS 项目也要增加一些配置，刚才创建 Identifiers 时已经勾选了 `"Sign in with Apple"`。现在只需要在 `Xcode` 中配置即可：

1. Xcode → Runner → Signing & Capabilities → `+ Capability` → "Sign in with Apple"
2. Apple Developer 后台 → Identifiers → App ID → 勾选 "Sign in with Apple"（前面已经做过了）

##### 2. 后端处理

后端收到前端传来的 `identity_token` 后，需要做的事情很明确：验证这个 token 是不是 Apple 签发的，然后从中提取用户信息。整个验证过程复用了项目已有的 `OAuthProvider` trait 模式（和 GitHub 登录共用同一套流程）。路由注册和 handler 入口：

```rust
---->[server/modules/flash-auth/src/routes.rs]----
.route("/auth/apple", post(apple_login))

---->[server/modules/flash-auth/src/handler.rs]----
pub async fn apple_login(
    State(state): State<Arc<AppState>>,
    ConnectInfo(addr): ConnectInfo<SocketAddr>,
    Json(req): Json<AppleLoginRequest>,
) -> Result<Json<LoginResponse>, StatusCode> {
    let provider = AppleProvider::from_env();
    let ip = addr.ip().to_string();
    // 复用 OAuth 通用流程（和 GitHub 登录共用）
    oauth_login_flow(&provider, &req.identity_token, &req.device_info, Some(&ip), &state.db)
        .await
        .map(Json)
        .map_err(|e| { println!("❌ Apple login error: {:?}", e); StatusCode::UNAUTHORIZED })
}
```

核心验证逻辑在 `AppleProvider` 中，它实现了 `OAuthProvider` trait：

```rust
---->[server/modules/flash-auth/src/oauth/apple.rs]----
#[async_trait::async_trait]
impl OAuthProvider for AppleProvider {
    /// Apple 不需要换 token，直接验证 identity_token 的签名
    async fn exchange_token(&self, identity_token: &str) -> Result<String, AppError> {
        // 1. 解析 token header 获取 kid
        let header = decode_header(identity_token)?;
        let kid = header.kid.ok_or("identity_token 缺少 kid")?;

        // 2. 获取 Apple JWKS 公钥
        let jwks: JwksResponse = self.client
            .get("https://appleid.apple.com/auth/keys")
            .send().await?.json().await?;

        // 3. 找到对应 kid 的公钥
        let key = jwks.keys.iter().find(|k| k.kid == kid)
            .ok_or("Apple JWKS 中未找到对应的公钥")?;

        // 4. 用公钥验证 JWT 签名（RS256）
        let decoding_key = DecodingKey::from_rsa_components(&key.n, &key.e)?;
        let mut validation = Validation::new(Algorithm::RS256);
        validation.set_issuer(&["https://appleid.apple.com"]);
        validation.set_audience(&[&self.bundle_id]);

        decode::<serde_json::Value>(identity_token, &decoding_key, &validation)?;
        Ok(identity_token.to_string())
    }

    /// 从已验证的 token 中提取用户信息
    async fn get_user_info(&self, token: &str) -> Result<OAuthUserInfo, AppError> {
        // 解码 payload（签名已在 exchange_token 中验证）
        let claims: AppleClaims = decode_without_verify(token)?;
        Ok(OAuthUserInfo {
            provider: "apple".to_string(),
            provider_id: claims.sub,
            nickname: claims.email.map(|e| e.split('@').next()).unwrap_or("Apple用户"),
            avatar: None,
        })
    }
}
```

验证通过后，`oauth_login_flow` 会调用 `find_or_create_by_oauth` 查找或创建用户（和 GitHub 登录完全复用同一段逻辑），然后签发 JWT、记录登录日志、首次登录发送欢迎消息。identity_token 解码后的结构如下：

```json
{
  "iss": "https://appleid.apple.com",
  "aud": "com.toly1994.flashIm",
  "exp": 1716700000,
  "sub": "xxxxxx",
  "email": "xxxxxx",
  "email_verified": "true"
}
```

- `sub` — 用户在你的 App 中的唯一标识（同一用户在不同 App 中 sub 不同）
- `email` — 可能是真实邮箱，也可能是 Apple 的隐私中转邮箱
- 首次授权时才会返回 email，后续登录可能不返回

配置只需要一个环境变量：

```env
---->[server/.env]----
APPLE_BUNDLE_ID=com.toly1994.flashIm
```

##### 2. 数据库改造


之前短信验证码用的是一张独立的 `sms_codes` 表，现在加了邮箱验证码，如果再建一张 `email_codes`，未来每加一种验证方式就多一张表，结构完全重复。

所以这次做了一个小重构：合并成一张通用的 `verify_codes` 表，用 `channel`（通道）和 `scene`（场景）两个字段区分用途。

```sql
---->[server/migrations/20260524_011_verify_codes.sql]----
CREATE TABLE IF NOT EXISTS verify_codes (
    identifier  VARCHAR(255) NOT NULL,  -- 手机号或邮箱
    channel     VARCHAR(10) NOT NULL,   -- 'sms' / 'email'
    scene       VARCHAR(20) NOT NULL DEFAULT 'login',  -- 'login' / 'reset_password' / 'bind'
    code        VARCHAR(6) NOT NULL,
    status      SMALLINT NOT NULL DEFAULT 0,  -- 0=待验证 1=已使用 2=已过期
    expires_at  TIMESTAMPTZ NOT NULL,
    request_ip  VARCHAR(45),
    sender      VARCHAR(255),  -- 发送方邮箱，用于统计每日发送量和多邮箱切换
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (identifier, channel, scene)
);
```

对比旧方案：

| 旧方案 | 新方案 |
|--------|--------|
| `sms_codes` 表（手机号验证码） | 统一 `verify_codes`，channel='sms' |
| `email_codes` 表（邮箱验证码） | 统一 `verify_codes`，channel='email' |
| 验证成功后 DELETE 记录 | UPDATE status=1（保留记录，可审计） |
| 只有登录场景 | scene 字段预留找回密码、绑定等场景 |

主键是 `(identifier, channel, scene)` 的组合，意味着同一个邮箱在"登录"和"找回密码"场景下可以各自独立持有一个验证码，互不干扰。

查询时加 `AND status = 0` 只匹配未使用的验证码：

```rust
"SELECT code, expires_at FROM verify_codes 
 WHERE identifier = $1 AND channel = 'email' AND scene = 'login' AND status = 0"
```

验证成功后标记为已使用，而不是删除：

```rust
"UPDATE verify_codes SET status = 1 
 WHERE identifier = $1 AND channel = 'email' AND scene = 'login'"
```

这样做的好处是保留了完整的验证码发送记录，后续可以用来做安全审计（比如某个 IP 频繁请求验证码）或数据统计。

另外增加 `sender` 字段，后续可以通过下面的 SQL 统计每个邮箱的日发送量，达到上限时切换到备用邮箱。

> `SELECT sender, COUNT(*) FROM verify_codes WHERE created_at > today GROUP BY sender`

发送验证码的核心逻辑：

```rust
---->[server/modules/flash-auth/src/handler.rs]----
pub async fn send_email_code(
    State(state): State<Arc<AppState>>,
    ConnectInfo(addr): ConnectInfo<SocketAddr>,
    Json(req): Json<EmailCodeRequest>,
) -> Result<Json<EmailCodeResponse>, StatusCode> {
    // 1. 校验邮箱格式
    if !req.email.contains('@') || !req.email.contains('.') {
        return Err(StatusCode::BAD_REQUEST);
    }
    let ip = addr.ip().to_string();

    // 2. 频率限制：同邮箱或同 IP，60 秒内只能发一次
    let recent = sqlx::query_as(
        "SELECT created_at FROM email_codes 
         WHERE email = $1 OR request_ip = $2 
         ORDER BY created_at DESC LIMIT 1"
    ).bind(&req.email).bind(&ip).fetch_optional(&state.db).await?;

    if let Some((created_at,)) = recent {
        if (Utc::now() - created_at).num_seconds() < 60 {
            return Err(StatusCode::TOO_MANY_REQUESTS);
        }
    }

    // 3. 生成 6 位验证码，UPSERT 到 email_codes 表（5 分钟有效）
    let code = format!("{:06}", rand::rng().random_range(0..1000000));
    sqlx::query("INSERT INTO email_codes ... ON CONFLICT (email) DO UPDATE ...")
        .execute(&state.db).await?;

    // 4. debug 模式直接返回 code；正式模式调 sender 发邮件
    if sender::is_debug_mode() {
        return Ok(Json(EmailCodeResponse { code: Some(code), message: "验证码已发送(debug)" }));
    }
    sender::send_code(&SmtpConfig::from_env(), &req.email, &code)?;
    Ok(Json(EmailCodeResponse { code: None, message: "验证码已发送" }))
}
```

async fn login_with_email(state, req) -> Result<Json<LoginResponse>, StatusCode> {
    let email = &req.phone; // phone 字段复用传邮箱

    // 1. 先尝试验证码匹配
    let row = sqlx::query_as("SELECT code, expires_at FROM email_codes WHERE email = $1")
        .bind(email).fetch_optional(&state.db).await?;

    if let Some((stored_code, expires_at)) = row {
        if stored_code == req.credential && Utc::now() <= expires_at {
            sqlx::query("DELETE FROM email_codes WHERE email = $1").execute(...);
            let (user_id, has_password) = find_or_create_user_by_email(state, email).await?;
            return Ok(Json(LoginResponse { token: generate_token(user_id), user_id, has_password }));
        }
    }

    // 2. 验证码不匹配 → 尝试密码登录（兜底）
    let (account_id, password_hash) = query auth_credentials WHERE auth_type='email';
    Argon2::default().verify_password(req.credential, &password_hash)?;
    Ok(Json(LoginResponse { token, user_id: account_id, has_password: true }))
}

pub fn send_code(config: &SmtpConfig, to: &str, code: &str) -> Result<(), AppError> {
    let body = format!("欢迎使用闪讯，您的验证码为：{code}，5 分钟内有效。");
    let email = Message::builder().from(...).to(to).subject("闪讯 验证码").body(body)?;

    mailer.send(&email)?;
    Ok(())
}

#### 五、本章总结

现在我们有点亮了一个平台的软件产品。本章做了三件事：把闪讯装进 iPhone、把它送上 App Store、让用户多几种方式登录。

回头看，iOS 和 Android 的构建本身没什么本质区别——都是一条命令出包。真正的差异在于生态：Apple 要求你有 Mac、有付费账号、有证书、有审核。这些不是技术门槛，是商业门槛。但一旦跨过去，Flutter 的跨平台能力就体现出来了：同一份 Dart 代码，两个平台各自打包，业务逻辑一行不改。

Apple 登录的接入比想象中简单。前端一个插件调用系统 API，后端验证一个 JWT 签名，复用已有的 OAuth 流程。整个链路比 GitHub OAuth 还短——因为 Apple 把授权码交换和用户信息获取都省了，一个 identity_token 里什么都有。

邮箱登录则是一个"几乎零成本"的方案。QQ 邮箱 SMTP 每天免费额度，对于一个初创产品绰绰有余。而且我们顺手做了一个小重构：把 `sms_codes` 和 `email_codes` 合并成了通用的 `verify_codes` 表，用 channel + scene + status 三个字段覆盖所有验证码场景。这种"做一个功能顺手优化一个结构"的节奏，是项目健康演进的标志。

到这一步，闪讯已经是一个双平台可用、多方式登录的正式产品了。剩下的就是填充内容、打磨体验、通过审核——但那些是运营的事，不是工程的事。下一步，我们将把焦点放在桌面端 -- **MacOS 平台**
