> 所有通信协议解决的都是"送达"，但人真正在意的从来都是"被感知"。

群聊的管理能力做完了，闪讯已经是一个基本功能完整的 IM。但用起来总觉得少了点什么，发出去的消息像石沉大海，不知道对方看没看；好友列表没有状态，不知道谁在线谁不在。这一章补上两个"感知"能力：**在线状态** 和 **已读回执**。下图 `朱红` 和 `橘橙` 两个人的对话，可以很好地说明本章的核心功能：

*   聊天页和会话列表，都能展示用户的在线状态
*   两者都在聊天界面聊天时，发送的消息都会被立刻标记已读。
*   `朱红` 不在聊天界面时， `橘橙` 发送的消息不会被已读。`朱红` 进去之后才会已读。

##### 2. 逻辑流程树

**在线状态：只通知好友**

一开始就要想清楚广播范围：用户上线时通知谁？全量广播在人数少时没问题，但 1000 人在线时每次上线/下线都推 1000 帧，大部分人根本不关心。合理的做法是只通知在线的好友，查 `friend_relations` 表取好友列表，和在线用户集合取交集。

| 时刻 | 事件      | 处理                                                    | 产生的新事件       |
| -- | ------- | ----------------------------------------------------- | ------------ |
| T1 | WS 认证成功 | `ws_state.add(user_id, conn_id, sender)` 返回 is\_first | —            |
| T2 | 首次上线    | 查好友列表 → 过滤在线好友 → 广播 USER\_ONLINE                      | 在线好友收到通知     |
| T3 | 推送在线列表  | 查好友中谁在线 → 发送 ONLINE\_LIST 给当前用户                       | 当前用户收到在线好友列表 |

![mermaid-diagram (98).png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/855651d5fe2c4355b5d33cca410a919d~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=2914\&h=1462\&s=214272\&e=png\&a=1\&b=ebebeb)

**已读回执：水位线模型**

已读回执有两种思路：逐条标记和水位线。逐条标记意味着每条消息都有一个"已读/未读"状态，存储成本是 `消息数 × 成员数`，群聊里一条消息 200 个成员就是 200 行记录。

水位线只需要一个数字，`last_read_seq`。水位线以下的消息都已读，以上的都未读。这行得通，因为聊天消息是线性流，用户几乎不会跳着看：打开聊天页，从最新的消息往上扫一眼，就算"读过了"。每个成员只存一个数字，群聊 200 人也只是 200 个整数。

| 时刻 | 事件      | 处理                                                                           | 产生的新事件             |
| -- | ------- | ---------------------------------------------------------------------------- | ------------------ |
| T1 | 用户进入聊天页 | 前端计算当前最大 seq，1 秒防抖后上报                                                        | READ\_RECEIPT WS 帧 |
| T2 | 后端处理    | `UPDATE last_read_seq = GREATEST(last_read_seq, readSeq)` + 重算 unread\_count | 数据库更新              |
| T3 | 通知对方    | 向会话其他在线成员推送 READ\_RECEIPT 帧                                                  | 对方收到已读通知           |
| T4 | 前端更新    | 对方 ChatCubit 更新 peerReadSeq → 消息气泡显示"已读"                                     | UI 刷新              |

水位线只能升不能降。后端更新时用 SQL 的 `GREATEST` 函数取新旧值中的较大者：`SET last_read_seq = GREATEST(last_read_seq, readSeq)`。这样即使乱序上报（先报 seq=10，再报 seq=5），水位线仍然停在 10。

#### 二、后端：WsState 的第二次进化

WsState 在第 18 章诞生时只是一个 `HashMap<i64, WsSender>`——一个用户一个连接，够用。这一章要让它支持多端连接、上线/下线广播、在线列表查询。同时 handler.rs 要处理一种全新的帧类型——READ\_RECEIPT，这是第一次在 WS 层直接操作数据库。

##### 1. WsState 多端连接

旧的 WsState 一个用户只能有一个连接。如果同一用户建立第二个 WS 连接，`HashMap::insert` 会覆盖旧的 sender，导致旧连接的推送静默丢失。

新的 WsState 用 `Vec<ConnectionInfo>` 存储同一用户的多个连接，每个连接有唯一的 `conn_id`（UUID）。`add` 返回 `is_first`（首次上线），`remove` 返回 `is_last`（完全下线）：

```rust
// ---> server/modules/im-ws/src/state.rs
pub async fn add(&self, user_id: i64, conn_id: String, sender: WsSender) -> bool {
    let entry = conns.entry(user_id).or_insert_with(Vec::new);
    let is_first = entry.is_empty();
    entry.push(ConnectionInfo { id: conn_id, sender });
    is_first
}

pub async fn remove(&self, user_id: i64, conn_id: &str) -> bool {
    user_conns.retain(|c| c.id != conn_id);
    if user_conns.is_empty() { conns.remove(&user_id); is_last = true; }
    is_last
}
```

`send_to_user` 也要适配，发给同一用户的所有端：

```rust
pub async fn send_to_user(&self, user_id: i64, data: Vec<u8>) {
    if let Some(user_conns) = conns.get(&user_id) {
        for conn in user_conns {
            let _ = conn.sender.send(data.clone());
        }
    }
}
```

> 多端连接的关键不是"怎么存"，而是"什么时候广播"。同一用户的第二个连接上线时不应该再广播一次 USER\_ONLINE，只有首次上线（`is_first`）和完全下线（`is_last`）才触发广播。

##### 2. 只通知好友

dispatcher 新增 `PgPool` 依赖，上线/下线时查 `friend_relations` 表取好友列表，和在线用户集合取交集：

```rust
// ---> server/modules/im-ws/src/dispatcher.rs
async fn get_online_friend_ids(&self, user_id: i64) -> Vec<i64> {
    let friend_rows = sqlx::query_as("SELECT friend_id FROM friend_relations WHERE user_id = $1")
        .bind(user_id).fetch_all(&self.db).await?;
    let online_set: HashSet<i64> = self.ws_state.get_online_users().await.into_iter().collect();
    friend_rows.into_iter().map(|(id,)| id).filter(|id| online_set.contains(id)).collect()
}
```

`broadcast_user_online` 和 `send_online_list` 都调这个方法，只通知好友，不广播给陌生人。

##### 3. 已读回执：handler 直接操作数据库

已读回执不是"消息"，它不需要存储、不需要序列号。它只需要更新一个数字（`last_read_seq`），然后通知会话中的其他成员。所以不走 MessageService，handler 直接操作数据库：

```rust
// ---> server/modules/im-ws/src/handler.rs
async fn handle_read_receipt(user_id: i64, payload: &[u8], state: &WsHandlerState) {
    // 1. 更新 last_read_seq（GREATEST 防止回退）
    UPDATE conversation_members SET last_read_seq = GREATEST(last_read_seq, $3)
    WHERE conversation_id = $1 AND user_id = $2

    // 2. 重新计算 unread_count
    UPDATE conversation_members SET unread_count = (
        SELECT COUNT(*) FROM messages m
        WHERE m.conversation_id = cm.conversation_id
          AND m.seq > cm.last_read_seq
          AND m.sender_id != cm.user_id
    )

    // 3. 查询会话成员，推送已读通知给其他人
    state.dispatcher.broadcast_read_receipt(conv_id, user_id, read_seq, &member_ids)
}
```

> 为什么 handler 需要 PgPool？因为已读回执是唯一一个在 WS 层直接操作数据库的场景。其他帧（CHAT\_MESSAGE）都是通过 MessageService 间接操作的。这是一个有意的设计选择，已读回执的逻辑太简单，目前不值得为它建一个 Service。

##### 4. 两个 HTTP 接口

WS 负责实时推送，但有两个场景需要 HTTP：

*   **GET /conversations/{id}/read-seq**：进入聊天页时调一次，拿到所有成员的初始已读位置。单聊和群聊通用，单聊只有一个 entry，群聊有多个。
*   **GET /conversations/{id}/messages/{mid}/read-status**：点击"N人已读"时调，返回已读/未读成员列表（头像 + 昵称）。

```json
// GET /conversations/{id}/read-seq
{ "members_read_seq": { "2": 42, "3": 38 } }

// GET /conversations/{id}/messages/{mid}/read-status
{ "read_members": [{ "user_id": 2, "nickname": "橘橙" }],
  "unread_members": [{ "user_id": 3, "nickname": "藤黄" }] }
```

后端完成之后，应该用 Python 写了一个测试脚本，WS 和 HTTP 混合调用，覆盖在线状态和已读回执的完整链路。但这里一个小插曲，一开始 AI 不太想做测试，如果那时我心软一下，或者觉得测试无所谓。那会为很后面的环节埋下隐患。

##### 5. 不确定性中的确定性

> 虽然 AI 的创作带着一定的 **不确定性**，但在不确定中，设定领域和规格，用确切性的网固定 AI 的行为边界，让它的行为变得预期。而这个测试就是现阶段的 **确定性** 的成功，如果说一个功能需求的像一个随风飘动的丝带，那么这个测试就像一个图钉，把它固定在了一个可以预期的位置。

我和 AI 针对这个观点进行了细致讨论，总结了下面三层：

**第一层: 路径不确定，终点确定。**

让 AI 实现一个功能，它走的路径我们无法完全预测。同样的 prompt，今天生成的代码和明天的可能不一样。变量名不同，拆分方式不同，甚至架构选择都可能不同。这是路径的不确定性。

但我们有测试。测试不关心路径，只关心终点：给定输入，输出是否正确。这和量子力学有一个微妙的相似之处。粒子在被观测之前，状态是不确定的叠加态；一旦观测，就坍缩到一个确定的值。测试就是那次观测。AI 的代码在测试通过之前，是"可能正确也可能不正确"的叠加态；测试通过的那一刻，坍缩为确定。

***

**第二层：单次不确定，统计确定**

一次 AI 生成可能出错，但我们的流程不是一次性的。analysis → design → tasks → 实现 → 测试 → 交叉审查，每一步都是一个过滤器。单个过滤器可能漏掉问题，但串联起来，漏网的概率指数级下降。这是大数定律的工程版本：单次随机，多次收敛。

热力学里有个概念叫"熵减"。孤立系统的熵只增不减，但开放系统可以通过输入能量来降低局部的熵。八步流水线就是那个"能量输入"。AI 的每次生成都在增加熵（不确定性），而我们的每一步审查都在减少熵。最终系统的熵低于任何单次生成。

***

**第三层：内容不确定，结构确定。**

这是最深的一层。我们不能控制 AI 写出什么代码，但能控制它在什么框架里写。Proto 定义了通信契约，数据库 schema 定义了存储边界，tasks.md 定义了执行顺序。AI 在这些约束里自由发挥，就像河水在河道里自由流淌。水的每一个分子的运动轨迹是不确定的，但河流的方向是确定的。

河道越窄，水流越可预测。设计文档就是在收窄河道。

***

所以"不确定性中的确定性"不是一个悖论，而是一个分层结构：

> 放弃对微观路径的控制，换取对宏观行为的确定。

这其实是所有复杂系统管理的本质。操作系统不控制每个进程的每条指令，但通过调度算法保证整体行为可预期。市场经济不控制每个人的交易决策，但通过价格机制让资源配置趋向最优。我们在做的事情，本质上是在设计一个"AI 治理框架"。不是控制 AI 的每一步，而是设计约束，让不确定的个体行为涌现出确定的系统行为。

回到图钉的比喻：不需要把整条飘带钉死。只需要在关键位置钉几枚图钉，飘带自然会呈现出想要的形状。钉得太密，飘带失去灵动；钉得太疏，形状不可控。找到那个平衡点，就是这件事最有技术含量的地方。

##### 1. WsClient：在线状态集合 + 已读回执发送

WsClient 内部维护一个 `Set<String> _onlineUserIds`，收到 ONLINE\_LIST 时初始化，收到 USER\_ONLINE 时 add，收到 USER\_OFFLINE 时 remove，断连时清空。外部通过 `isUserOnline(userId)` 查询。

```dart
// ---> client/modules/flash_im_core/lib/src/logic/ws_client.dart
void _handleUserOnline(WsFrame frame):
    notif = UserStatusNotification.fromBuffer(frame.payload)
    _onlineUserIds.add(notif.userId)

void _handleOnlineList(WsFrame frame):
    notif = OnlineListNotification.fromBuffer(frame.payload)
    _onlineUserIds.clear()
    _onlineUserIds.addAll(notif.userIds)
```

`sendReadReceipt` 构建 `ReadReceiptRequest` proto 帧发送：

```dart
void sendReadReceipt({required String conversationId, required int readSeq}):
    req = ReadReceiptRequest()..conversationId = conversationId..readSeq = Int64(readSeq)
    frame = WsFrame()..type = WsFrameType.READ_RECEIPT..payload = req.writeToBuffer()
    sendFrame(frame)
```

> 在线状态放 WsClient 而不是单独建 Cubit，因为它和 WS 连接的生命周期绑定。断连时必须清空，放在 WsClient 里，断连逻辑自然在 `_onDisconnected` 中处理。

##### 2. ChatCubit：已读上报与状态管理

ChatCubit 新增 `isGroup` 参数，内部维护 `_peerReadSeq`（单聊）和 `_membersReadSeq`（群聊）。三个时机触发已读相关逻辑：

- **进入聊天页时**：`loadMessages` 完成后调 `_loadReadSeq()`（HTTP 获取初始已读位置）和 `_reportReadSeq(maxSeq)`（WS 上报自己的已读位置）。
- **收到新消息时**：`_handleIncomingMessage` 末尾调 `_reportReadSeq(newMsg.seq)`。
- **收到对方已读通知时**：监听 `readReceiptStream`，更新 `_peerReadSeq` 或 `_membersReadSeq`。

```dart
// ---> client/modules/flash_im_chat/lib/src/logic/chat_cubit.dart
void _reportReadSeq(int maxSeq):
    if maxSeq <= 0: return
    _readReceiptTimer?.cancel()
    _readReceiptTimer = Timer(Duration(seconds: 1), () {
        _wsClient.sendReadReceipt(conversationId: conversationId, readSeq: maxSeq)
    })
```

> 1 秒防抖避免快速滚动时频繁发送 WS 帧。同一会话内多次触发只发最后一次。

##### 5. 过程中两个问题的处理

**注意 Equatable 对象**

实现完后发现一个 bug：进入聊天页时已读标记不显示，退出重进也不行。`_loadReadSeq` 拿到了正确的 `peerReadSeq`，但 UI 不刷新。

根因：`ChatLoaded` 用 Equatable 比较 props，`peerReadSeq` 存在 ChatCubit 的实例变量里，不在 ChatState 的 props 中。`_loadReadSeq` 完成后调 `emit(s.copyWith())`，但 copyWith 没改任何 props 字段，Equatable 判断新旧 state 相等，BlocBuilder 跳过重建。

修复：给 `ChatLoaded` 加一个 `readSeqVersion` 计数器，每次已读位置变化时递增。

```dart
// ---> client/modules/flash_im_chat/lib/src/logic/chat_state.dart
class ChatLoaded extends ChatState {
    final int readSeqVersion;  // 每次已读变化时 ++
    @override
    List<Object?> get props => [..., readSeqVersion];
}
```

> Bloc + Equatable 的经典陷阱：state 外部的变量变了，但 state 本身没变，UI 就不会重建。解法要么把变量放进 state，要么用一个 version 计数器"戳"一下 Equatable。

***

**让活跃会话不累加未读**

功能验证时发现另一个体验问题：用户正在聊天页看消息，对方发来新消息，返回会话列表时该会话显示"1 条未读"。明明刚看过，为什么还有未读？

原因是 `ConversationListCubit` 收到 `ConversationUpdate` 帧时无脑累加 `unreadCount`，不管用户是否正在看这个会话。修复思路很直接，给 `ConversationListCubit` 加一个 `_activeConversationId` 标记，进入聊天页时设置，返回时清除：

```dart
// ---> client/modules/flash_im_conversation/lib/src/logic/conversation_list_cubit.dart
final isActive = _activeConversationId == update.conversationId;
if (isActive && update.unreadCount > 0) {
    _repository.markRead(update.conversationId).catchError((_) {});
}
// ...
unreadCount: c.unreadCount + (isActive ? 0 : update.unreadCount),
```

注意 `markRead` 那一行，不只是前端不显示，还要通知后端清零。否则 app 如果在这个窗口期被杀掉，后端 unread\_count 还是 1，重启后会出现幽灵未读。实际上这里有两道保险：`markRead`（HTTP，立即清后端）和 `_reportReadSeq`（WS，1 秒后重算），谁先到都能把后端清零。
