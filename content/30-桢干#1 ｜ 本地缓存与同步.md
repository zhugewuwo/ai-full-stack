> 断网的那一刻，才知道你的 app 到底拥有什么。

闪讯能聊天、能建群、能搜索，但有一个根本性的脆弱点：**它完全依赖网络**。\
打开 app，会话列表是空的，要等 HTTP 回来才能看到。进入聊天页，消息也是空的，又等一次。网络慢就转圈，网络断就白屏。这不是"体验差"的问题，是"能不能用"的问题。

这一章引入本地数据库，让客户端拥有自己的数据。这不是在做一个新页面，而是在改变所有页面的数据来源。从而让数据 **服务端优先** 转变成 **本地优先**。五个场景，覆盖从"打开 app"到"断网重连"的完整生命周期：

#### 一、需求分析

本地缓存听起来像是"加个数据库存一下"，但它引入的复杂度远超表面。数据有两份了，本地一份服务端一份。WS 实时推送和 HTTP 增量同步同时往本地写，怎么去重？用户离线期间错过的消息，上线后怎么补？补的过程中又收到新消息怎么办？

这些问题的本质是分布式系统的一致性问题，只不过"分布式"的两个节点是服务端和客户端本地数据库。

##### 1. 交互链分析


**启动即可见**

`用户故事`：作为用户，我打开 app 就想看到会话列表和聊天记录，不想等 loading。

现在打开 app，会话列表是空的，要等 HTTP 回来才能看到。网络慢的时候，用户盯着一个空白页面转圈。改造后，会话列表从本地 SQLite 读取，瞬间展示。后台静默向服务端同步最新数据，有更新时通过 SyncEngine 回调通知 Cubit 刷新。用户感知不到网络请求的存在。


![image.png](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/35a8456633dd4228977f029b6f24d8df~tplv-k3u1fbpfcp-jj:0:0:0:0:q75.image#?w=1024&h=559&s=565085&e=png&b=fdf7f6)

***

**离线浏览**

`用户故事`：作为用户，没有网络时我也想翻看之前的聊天记录。

网络断开后，会话列表和已缓存的消息仍然可以正常浏览。翻页从本地 SQLite 读取。只有本地没有的更早消息才需要网络，此时提示"无网络"而不是白屏。进入聊天页也是同理，已缓存的消息立即展示。

![image.png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/4b9b2bd06b3f453ba4aea98243b9f986~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1024&h=559&s=650522&e=png&b=f9e6dc)

***

**重连补漏**

`用户故事`：作为用户，我离线了一段时间，重新上线后想看到离线期间的新消息。

WS 重连成功后，SyncEngine 自动触发增量同步。对每个有缓存的会话，查询本地最大 seq，用 `after_seq` 参数向服务端请求差量消息，写入本地 SQLite。同步完成后通过回调通知 Cubit 刷新，用户看到离线期间的新消息自动出现，不需要手动下拉。

seq 是服务端分配的单调递增序列号。本地存了 seq=42，服务端最新是 seq=58，那 43\~58 就是缺口。用 `after_seq=42` 请求服务端，拿回差量。但每个会话的 seq 是独立的，10 个会话要发 10 次请求，200 个群就是 200 次请求。


![image.png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/87b6c02f38f1483b8ec8d3feb01fe4d6~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1024&h=559&s=551764&e=png&b=fdf9f8)

***

**实时消息写入本地**

`用户故事`：作为用户，收到新消息时，消息同时存到本地，下次打开不用重新拉取。

WS 推来的 CHAT\_MESSAGE 帧，SyncEngine 解析 protobuf 后写入本地 SQLite。ChatCubit 仍然通过 WS 事件更新内存状态（和之前一样），SyncEngine 额外做一次持久化。会话更新帧（ConversationUpdate）也会被 SyncEngine 写入本地并触发 `onConversationChanged` 回调，让会话列表的最后消息预览实时更新。下次打开 app 时，Repository 从本地读取，消息还在。

这是一个"双写"模式：Cubit 管内存实时状态，SyncEngine 管持久化。两者同时监听 WS 事件，互不干扰。


![image.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/9f17943dfd2241d69547d03b5331ee7c~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1024&h=559&s=705702&e=png&b=fcf6f4)

***

**首次登录全量拉取**

`用户故事`：作为新用户或换设备用户，首次登录后需要从服务端拉取所有数据。

首次登录时本地数据库是空的。SyncEngine 检测到 `isFirstLogin()` 为 true，先拉取会话列表写入本地，再对每个会话拉取最近 50 条消息。拉取过程中 Repository 的 fallback 策略保证不白屏：本地为空时自动走 HTTP，SyncEngine 同步完后通过回调触发 Cubit reload。

> 首次登录和重连补漏走的是同一套代码，区别只在于消息同步的策略：首次登录对每个会话拉最新 50 条（全量），重连补漏对每个会话用 after\_seq 拉差量（增量）。


![image.png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/6a69fdc9d1c0420f8cd1c41de3bf5b17~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1024&h=559&s=512028&e=png&b=fcf5f4)

##### 2. 逻辑流程树

**数据链路变更：读写分离**

引入本地数据库后，数据链路发生了根本性的变化。改造前，客户端是一个"无状态的渲染终端"，所有数据都从服务端实时拉取，网络慢就转圈，网络断就白屏。

| 操作     | 改造前                 | 改造后                    |
| ------ | ------------------- | ---------------------- |
| 展示会话列表 | UI → Dio → 服务端 → UI | UI → SQLite → UI（后台同步） |
| 展示消息列表 | UI → Dio → 服务端 → UI | UI → SQLite → UI（后台同步） |
| 展示好友列表 | UI → Dio → 服务端 → UI | UI → SQLite → UI（后台同步） |
| 发送消息   | WS → 服务端            | WS → 服务端（不变）           |

改造后，客户端变成了一个"有记忆的本地应用"——读操作优先走本地 SQLite，瞬间展示；写操作仍走服务端，由服务端分配 seq 和 id 后通过 WS 推回本地持久化。服务端依然是权威数据源，但用户感知到的响应速度完全由本地决定。本地数据的更新靠两条通道 —— WS 实时推送和 HTTP 增量同步。


![mermaid-diagram - 2026-05-05T143041.946.png](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/68f0c195d3664d308156eea511791385~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1473&h=385&s=83907&e=png&a=1&b=e6eef4)

---

**重连同步：三步补漏**

用户离线期间错过的消息，上线后怎么补？SyncEngine 监听 WsClient 的连接状态，检测到重连认证成功后，自动触发三步同步：


![mermaid-diagram - 2026-05-05T145909.692.png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/d12602fb4cad48e993911ff7e6fb830e~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1685&h=426&s=67780&e=png&a=1&b=fef1e0)


- **步骤 1：会话 diff** : 拉取远程会话列表，和本地做对比。远程有本地没有的（离线期间被拉入新群）→ 插入；本地有远程没有的（退群、被删好友）→ 删除；都有的 → 更新字段。完成后回调通知会话列表 Cubit 刷新。
- **步骤 2：好友 diff**: 同理，拉取远程好友列表和本地对比。完成后回调通知好友列表 Cubit 刷新。
- **步骤 3：消息增量**: 对每个有缓存的会话，查本地最大 seq，用 `after_seq` 参数向服务端请求差量消息，写入本地。比如本地存了 seq=42，服务端最新是 seq=58，那 43~58 就是缺口，一次请求补齐。

三步必须串行。原因：步骤 3 依赖步骤 1 的结果——如果离线期间被拉入新群，步骤 1 先把新会话写入本地，步骤 3 才能对它拉消息。每一步完成后立即回调刷新 UI，用户看到的是"边同步边出现"，不是等全部完成才一次性刷新。


---

**首次登录 vs 增量同步**

首次登录时本地消息表是空的，没有 maxSeq 可用，所以从上面步骤 1 同步完的会话列表出发，对每个会话拉最新 50 条作为初始缓存。增量同步时本地已有数据，只需要补齐 maxSeq 之后的缺口。

![mermaid-diagram - 2026-05-05T152423.532.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/8e5786bf296c426da3608d60b0066e2a~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1978&h=2204&s=256464&e=png&a=1&b=ebebeb)

> 性能瓶颈：200 个群就要发 200 次请求，当前串行执行。在测试规模（< 20 个会话）下不是问题，未来可加并发池或后端批量接口优化。

#### 二、后端消息双向查询

本地缓存是纯前端的事，后端几乎不用动。唯一的改动是给消息查询接口加一个 `after_seq` 参数，让客户端能说"给我 seq 大于 42 的消息"。


***

##### 1. 为什么不新建接口

现有的 `before_seq` 是"向上翻页"，返回比某个 seq 更早的消息，按 seq 降序排列。`after_seq` 是它的镜像，"向下同步"，返回比某个 seq 更新的消息，按 seq 升序排列。一个端点，三种模式：

| 参数            | 含义       | 排序   | 场景      |
| ------------- | -------- | ---- | ------- |
| 无参数           | 最新 N 条   | DESC | 首次进入聊天页 |
| before\_seq=N | seq < N  | DESC | 向上翻页    |
| after\_seq=N  | seq \> N | ASC  | 增量同步    |

可以单独建一个 `GET /conversations/{id}/sync?since_seq=42`，但没必要。三种查询操作的是同一张表，返回的是同一个数据结构（MessageWithSender），区别只在 WHERE 条件和 ORDER BY 方向。复用一个端点，加一个查询参数，比维护两个端点更简洁。如下所示：

    GET /conversations/{id}/messages
    GET /conversations/{id}/messages?before_seq=42&limit=50
    GET /conversations/{id}/messages?after_seq=42&limit=100



如果同时传了 after\_seq 和 before\_seq，after\_seq 优先。不会有场景需要同时"向上翻页"和"向下同步"。

***

##### 2. 核心改动

改动涉及三层：模型定义 → Service 分发 → Repository 查询。每层只加几行代码。
MessageQuery 新增 after\_seq 字段：

```rust
// ---> server/modules/im-message/src/models.rs
pub struct MessageQuery {
    pub before_seq: Option<i64>,
    pub after_seq: Option<i64>,   // 新增
    pub limit: i32,
}
```

Service 层用 match 分发三种模式：

```python
# ---> server/modules/im-message/src/service.rs（伪代码）
def get_history(conversation_id, before_seq, after_seq, limit):
    limit = clamp(limit, 1, 100)
    if after_seq:
        return repo.find_after_with_sender(conversation_id, after_seq, limit)
    if before_seq:
        return repo.find_before_with_sender(conversation_id, before_seq, limit)
    return repo.find_latest_with_sender(conversation_id, limit)
```

Repository 新增 `find_after_with_sender`，注意排序是 ASC：

```sql
-- ---> server/modules/im-message/src/repository.rs
SELECT m.id, m.conversation_id, m.sender_id,
       COALESCE(p.nickname, '?') as sender_name,
       p.avatar as sender_avatar,
       m.seq, m.type as msg_type, m.content, m.extra, m.status, m.created_at
FROM messages m
LEFT JOIN user_profiles p ON m.sender_id = p.account_id
WHERE m.conversation_id = $1 AND m.seq > $2 AND m.status != 2
ORDER BY m.seq ASC
LIMIT $3
```

> 排序方向是关键。before\_seq 返回 DESC（从新到旧，用户向上翻页），after\_seq 返回 ASC（从旧到新，客户端追加到本地末尾）。如果 after\_seq 也返回 DESC，客户端拿到的消息是倒序的，还要自己翻转一遍。

后端改动虽小，但必须确保不破坏已有的翻页逻辑。测试脚本覆盖 5 个场景：

|------|--------|
| 无参数查询 | 回归：返回最新 N 条，DESC 排序 |

##### 1. 存储层：三层模型 + LocalStore + drift

一条消息在系统中有三种形态：

| 层   | 类型                        | 所在位置                    | 职责                            |
| --- | ------------------------- | ----------------------- | ----------------------------- |
| 业务层 | `Message`                 | flash\_im\_chat         | UI 展示，DateTime、MessageType 枚举 |
| 接口层 | `CachedMessage`           | flash\_im\_cache/models | 纯 Dart，LocalStore 的数据契约       |
| 存储层 | `CachedMessagesTableData` | flash\_im\_cache/drift  | drift 代码生成，和 SQLite 列一一对应     |



写入时从上往下：JSON / protobuf → CachedMessage → drift Companion → SQLite。读取时从下往上：SQLite → drift TableData → CachedMessage → Message。converters.dart 负责中间层的双向转换，Repository 里的 `_fromCached` 负责最后一步。

> 为什么不让 CachedMessage 直接用 DateTime 和 MessageType 枚举？因为它是 LocalStore 接口的数据契约，不应该依赖业务层的类型定义。int 类型的 msgType 和 createdAt 是最通用的表示，任何存储实现都能处理。

**LocalStore 接口**定义了读写契约，方法签名只用纯 Dart 模型：

```dart
// ---> flash_im_cache/lib/src/local_store.dart
abstract class LocalStore {
  Future<void> cacheMessages(List<CachedMessage> messages, {String? conversationId});
  Future<List<CachedMessage>> getMessages(String conversationId, {int? beforeSeq, int limit});
  Future<int> getMaxSeq(String conversationId);
  Future<void> syncConversations(List<CachedConversation> remote);
  Future<void> syncFriends(List<CachedFriend> remote);
  Future<bool> isFirstLogin();
  // ...
}
```

如果不做这层抽象，三个 Repository 会直接 import drift 的类型，将来换其他方式实现缓存的话，要改一大片。有了 LocalStore 接口，换数据库只需要写一个新的实现类，改一行初始化代码。


![mermaid-diagram - 2026-05-05T231020.648.png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/255b1b9ba2da466d9964608c5fac8492~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=3246&h=856&s=213562&e=png&a=1&b=f9f9f9)

**drift 实现**包含三张缓存表和三个 DAO。消息表有 UNIQUE(conversation\_id, seq) 约束，upsert 的冲突检测依据。数据库文件名包含 userId（`im_cache_1.db`），切换用户时切换文件。

DAO 层封装了 drift 的 CRUD。以 MessageDao 的 `getMaxSeq` 为例，增量同步的关键查询：

```dart
// ---> flash_im_cache/lib/src/drift/dao/message_dao.dart
Future<int> getMaxSeq(String conversationId) async {
  final expr = _db.cachedMessagesTable.seq.max();
  final query = _db.selectOnly(_db.cachedMessagesTable)
    ..addColumns([expr])
    ..where(_db.cachedMessagesTable.conversationId.equals(conversationId));
  final result = await query.getSingleOrNull();
  return result?.read(expr) ?? 0;
}
```

ConversationDao 的 `syncAll` 实现了会话列表的全量 diff：

```dart
// ---> flash_im_cache/lib/src/drift/dao/conversation_dao.dart
Future<void> syncAll(List<CachedConversationsTableCompanion> remote) async {
  final remoteIds = remote.map((c) => c.id.value).toSet();
  // 删除本地有但远程没有的（退群、被删好友等）
  await (_db.delete(_db.cachedConversationsTable)
        ..where((t) => t.id.isNotIn(remoteIds))).go();
  // upsert 远程数据（新增插入，已有更新）
  await _db.batch((batch) {
    batch.insertAllOnConflictUpdate(_db.cachedConversationsTable, remote);
  });
}
```


![mermaid-diagram - 2026-05-05T231348.648.png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/557045017dbc4f43913a6c061d403837~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=2782&h=1878&s=249463&e=png&a=1&b=eaeaea)


> 为什么不直接 DELETE ALL + INSERT ALL？因为 DELETE ALL 会丢失本地的 unread\_count 等状态。upsert 保留已有行的主键，只更新变化的字段。`isNotIn(remoteIds)` 只删除远程确实不存在的会话，不会误删。

**DriftLocalStore** 是胶水层，每个方法都是同一个模式：纯 Dart 模型 → converter → DAO 操作 → converter → 纯 Dart 模型。`isFirstLogin()` 的判断依据是 cached\_conversations 表是否为空，空表意味着本地从未同步过会话数据。

##### 2. SyncEngine：事件监听 + 实时写入 + 重连同步

SyncEngine 监听 WsClient 的 5 个事件流，把实时数据写入本地，重连后拉差量补漏，同步完成后通过回调通知 Cubit 刷新。

| 事件流                      | 处理                        | 回调                    |
| ------------------------ | ------------------------- | --------------------- |
| stateStream              | 检测 authenticated → 触发重连同步 | —                     |
| chatMessageStream        | 解析 protobuf → upsert 消息   | —                     |
| conversationUpdateStream | 更新会话字段                    | onConversationChanged |
| friendAcceptedStream     | 新增好友                      | —                     |
| friendRemovedStream      | 删除好友                      | —                     |


![mermaid-diagram - 2026-05-05T231431.610.png](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/07ea3c077a934cfcbf4628f4a72a28b8~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=2893&h=839&s=215998&e=png&a=1&b=ededed)

**实时消息写入**：收到 CHAT\_MESSAGE 帧，解析 protobuf，逐字段映射成 CachedMessage：

```dart
// ---> flash_im_cache/lib/src/sync_engine.dart
void _handleChatMessage(WsFrame frame) {
  final chatMsg = ChatMessage.fromBuffer(frame.payload);
  final message = CachedMessage(
    id: chatMsg.id,
    conversationId: chatMsg.conversationId,
    senderId: chatMsg.senderId,
    senderName: chatMsg.senderName,
    senderAvatar: chatMsg.senderAvatar.isEmpty ? null : chatMsg.senderAvatar,
    seq: chatMsg.seq.toInt(),           // protobuf Int64 → Dart int
    msgType: chatMsg.type.value,        // protobuf enum → int
    content: chatMsg.content,
    extra: chatMsg.extra.isNotEmpty ? utf8.decode(chatMsg.extra) : null,
    createdAt: chatMsg.createdAt.toInt(),
  );
  _store.cacheMessages([message], conversationId: chatMsg.conversationId);
}
```

> protobuf 的 `extra` 是 bytes，需要 `utf8.decode` 转 JSON 字符串。`senderAvatar` 可能是空字符串（protobuf 默认值），需要转 null。这些边界转换是最容易出 bug 的地方。

**重连同步**是最复杂的流程，分三步。首次登录和增量同步走同一套代码，区别在消息拉取策略：

```python
# ---> flash_im_cache/lib/src/sync_engine.dart（伪代码）
async def sync_after_reconnect():
    is_first = await store.is_first_login()

    # 1. 会话 diff
    remote_convs = await dio.get('/conversations?limit=200')
    await store.sync_conversations(remote_convs)
    on_conversation_changed()

    # 2. 好友 diff
    remote_friends = await dio.get('/api/friends?limit=1000')
    await store.sync_friends(remote_friends)
    on_friend_list_changed()

    # 3. 消息：首次全量 vs 增量
    if is_first:
        for conv in await store.get_conversations():
            await pull_latest(conv.id, limit=50)
    else:
        for conv_id in await store.get_cached_conversation_ids():
            max_seq = await store.get_max_seq(conv_id)
            await pull_after_seq(conv_id, max_seq, limit=100)
```

> 为什么首次登录用 `getConversations()` 而增量同步用 `getCachedConversationIds()`？首次登录时消息表是空的，`getCachedConversationIds()` 返回空列表。所以首次要从刚同步完的会话列表出发拉消息。增量同步只需要对有缓存消息的会话拉差量，没缓存过的不需要补。

HTTP 响应的 JSON 和 protobuf 结构不同，SyncEngine 里有一套 `_jsonToMessage` / `_jsonToConversation` / `_jsonToFriend` 转换函数，处理类型映射（`sender_id` int → String、`created_at` ISO8601 → 毫秒时间戳、`extra` Map → JSON 字符串）。

##### 3. 集成：Repository 改造 + 冷启动 + 初始化

**Repository 改造**：三个 Repository 加一个 `LocalStore? _store` 字段，读取优先本地，本地为空时 fallback HTTP：

```dart
// ---> flash_im_conversation/lib/src/data/conversation_repository.dart
Future<List<Conversation>> getList({int limit = 20, int offset = 0}) async {
  if (_store != null) {
    final cached = await _store!.getConversations(limit: limit, offset: offset);
    if (cached.isNotEmpty) return cached.map(_fromCached).toList();
  }
  // fallback: HTTP
  final res = await _dio.get('/conversations', ...);
  return ...;
}
```


![mermaid-diagram - 2026-05-05T232845.965.png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/1b05390f75884a93b9849665ac45564a~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=2182&h=2398&s=265035&e=png&a=1&b=ebebeb)

写入操作（发消息、创建会话）不变，仍走 HTTP。服务端确认后通过 WS 推送回来，SyncEngine 写入本地。

> 为什么不在发消息时也写本地？因为消息需要服务端分配 seq 和 id。本地先写"待确认"消息再回滚，复杂度太高。当前版本保持简单：写操作走服务端，读操作走本地。

**冷启动时序**：Cubit 先从本地读（可能是旧数据），SyncEngine 后台同步完后回调触发 reload。首次登录时本地为空，Repository fallback HTTP 兜底。

#### 四、本章小结

这一章做了一件事：让客户端拥有自己的数据库。听起来简单，但它改变了整个数据流的方向。之前客户端是一个"无状态的渲染终端"，所有数据都从服务端实时拉取。现在客户端有了自己的 SQLite，Repository 从"HTTP 客户端的封装"变成了"本地数据库的封装"，HTTP 退到后台变成 SyncEngine 的事。

| 存档点 | tag | 提交点 |
| --- | --- | --- |
| 本地缓存与离线同步 | [v0.18.0](https://github.com/toly1994328/flash_im_by_ai/tree/v0.18.0) | [commit](https://github.com/toly1994328/flash_im_by_ai/tree/ebc5f41591c11a79de53e9c067438d3c71a91671) |



核心挑战不在于"怎么建表"或"怎么写 SQL"，而在于两个数据源同时变化时的协调。实时推送和增量同步可能写入同一条消息，upsert 保证幂等。冷启动时 Cubit 和 SyncEngine 有时间窗口不同步，Repository 的 fallback 策略兜底。SyncEngine 通过回调通知 Cubit 刷新，参考腾讯 IM SDK 的模式，让上层不需要关心同步细节。

架构上有一个值得注意的设计：LocalStore 抽象接口把 drift 的类型封锁在 `drift/` 子目录里，上层模块只依赖纯 Dart 模型。这不是过度设计，而是为未来留了一扇门。drift 今天是 Flutter 生态最好的 SQLite ORM，但技术栈会变，需求会变。有了这层接口，换数据库只需要写一个新的实现类，改一行初始化代码。

> 本地缓存的本质不是"加速"，而是"自治"。加速是副产品，自治才是目的。一个依赖网络才能展示数据的客户端，不是一个完整的应用，只是一个远程桌面。

接下来章节，我们将扩展消息的功能。比如消息撤回、删除、引用、@提及、消息置顶、消息转发，这些功能单独看都不大，但组合起来让 IM 的体验从"能用"变成"好用"。同时在成长过程中，这些将逐渐让小树苗成长为可靠的枝干。
