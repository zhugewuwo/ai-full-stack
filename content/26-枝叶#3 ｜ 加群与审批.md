> 最好的规则不是挡住所有人，而是让对的人走最短的路。

上一章我们让闪讯从两人对话走向了多人群聊，群主可以选人建群，成员可以在群里收发消息。但有一个问题：用户只能通过"被邀请"的方式进入群聊。这就像一个只有后门的餐厅，菜再好，路人也进不来。这一章要给群聊装上"正门"，核心功能和界面效果如下所示 ：

##### 2. 逻辑流程树

交互链画的是用户走的路，逻辑树画的是系统跑的路。本章有三条关键事件流：搜索、入群申请（分支逻辑）、群主审批。其中入群申请是最复杂的——同一个接口根据群的配置走两条完全不同的路径。

**搜索事件流**

搜索看起来简单，但后端要在一次查询中返回四个维度的信息（成员数、是否已加入、是否需验证、是否已申请），前端根据这四个字段渲染四种按钮状态。

| 时刻 | 事件      | 处理                                                                                                       | 产生的新事件                  |
| -- | ------- | -------------------------------------------------------------------------------------------------------- | ----------------------- |
| T1 | 用户输入关键词 | 前端 300ms 防抖后 `GET /groups/search?keyword=xxx`                                                            | HTTP 请求                 |
| T2 | 后端搜索    | 纯数字按群号精确匹配，非数字按群名 ILIKE 模糊搜索，关联查 member\_count / is\_member / join\_verification / has\_pending\_request | 返回 GroupSearchResult 列表 |
| T3 | 前端渲染    | 根据三个字段决定按钮状态                                                                                             | 搜索结果展示                  |

![](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/81f4265332934a39936d6ec78023c22e~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=2285\&h=2498\&s=334991\&e=png\&a=1\&b=eaeaea)

搜索结果中每个群的按钮状态由三个布尔字段决定，形成一张决策表：

| is\_member | has\_pending\_request | join\_verification | 按钮状态           |
| ---------- | --------------------- | ------------------ | -------------- |
| true       | —                     | —                  | "已加入"（灰色，不可点击） |
| false      | true                  | —                  | "已申请"（灰色，不可点击） |
| false      | false                 | false              | "加入"（蓝色）       |
| false      | false                 | true               | "申请"（橙色）       |

> 四种状态全部由后端一次查询返回，前端不需要额外请求。这是"胖查询"的典型场景——多做一点 SQL 关联，省掉前端多次网络往返。

***

**入群申请事件流（分支逻辑）**

这是本章最核心的逻辑。同一个 `POST /groups/{id}/join` 接口，根据群的 `join_verification` 设置走两条完全不同的路径：无需验证时直接加入（同步），需要验证时创建申请并通过 WS 推送通知群主（异步）。

| 时刻  | 事件            | 处理                                                                  | 产生的新事件  |
| --- | ------------- | ------------------------------------------------------------------- | ------- |
| T1  | 用户点击"加入"或"申请" | 前端 `POST /groups/{id}/join`，body: `{ message? }`                    | HTTP 请求 |
| T2  | 后端校验          | 群存在且 type=1、用户非成员、无待处理申请                                            | —       |
| T3a | 无需验证          | 直接 INSERT conversation\_members + 刷新宫格头像 → 返回 `auto_approved: true` | 用户立即加入  |
| T3b | 需要验证          | INSERT group\_join\_requests → 返回 `auto_approved: false`            | 申请已创建   |
| T4  | 需审批时          | 后端通过 WS 推送 GROUP\_JOIN\_REQUEST 帧给群主                                | 群主收到通知  |

T3a 和 T3b 的分叉点在 `join_verification` 字段——这个字段存在 `group_info` 表中，上一章创建群聊时默认为 false，本章新增的群详情页允许群主切换它。

![mermaid-diagram (84).png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/82a49804ecf846988d4df91b4e6c2ccd~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=3164\&h=2504\&s=393396\&e=png\&a=1\&b=eaeaea)

> 注意 T4 的 `tokio::spawn`——WS 推送是异步的，不阻塞 HTTP 响应。用户点击"申请"后立即收到 200，WS 通知在后台发送。如果群主不在线，通知会丢失，但申请已写入数据库，群主下次打开群通知页时能看到。

***

**群主审批事件流**

群主收到 WS 推送后，通讯录 Tab 显示红点角标。进入群通知页看到申请列表，点击"同意"或"拒绝"触发审批。

| 时刻  | 事件            | 处理                                                              | 产生的新事件  |
| --- | ------------- | --------------------------------------------------------------- | ------- |
| T1  | 群主点击"同意"或"拒绝" | 前端 `POST /groups/{id}/join-requests/{rid}/handle`               | HTTP 请求 |
| T2  | 后端校验          | 当前用户是群主、申请存在且 status=0                                          | —       |
| T3a | 同意            | UPDATE status=1 + INSERT conversation\_members + 刷新宫格头像 + 发系统消息 | 申请者加入群聊 |
| T3b | 拒绝            | UPDATE status=2                                                 | 申请被驳回   |

![mermaid-diagram (86).png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/6e1977bb546b4d29bb5a872795462b5f~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=2760\&h=1944\&s=279730\&e=png\&a=1\&b=ebebeb)

**状态流转**

入群申请的生命周期很清晰——从不存在到待处理，再到已同意或已拒绝。被拒绝后可以重新申请（创建新记录），不会阻塞。

| 实体                   | 触发事件            | 前状态      | 后状态           |
| -------------------- | --------------- | -------- | ------------- |
| GroupJoinRequest     | POST /join（需审批） | 不存在      | status=0（待处理） |
| GroupJoinRequest     | 群主同意            | status=0 | status=1（已同意） |
| GroupJoinRequest     | 群主拒绝            | status=0 | status=2（已拒绝） |
| ConversationMember   | 直接加入 / 群主同意     | 不存在      | joined        |
| conversations.avatar | 新成员加入           | 旧宫格头像    | 刷新后的宫格头像      |

从依赖关系看，新节点和已有网络的接触点集中在三个方向：

*   D-20（入群申请）依赖 I-09（帧分发器）做 WS 推送，这是群聊模块第一次和 WS 模块产生直接依赖

#### 二、后端：im-group 从 1 个接口扩展到 7 个

上一章 im-group crate 只有一个 `POST /groups` 创建群聊。这一章要扩展到 7 个路由，覆盖搜索、入群、审批、通知查询、群详情、群设置。更重要的变化是 im-group 第一次依赖了 im-ws——入群申请需要通过 WS 推送通知群主，这意味着 `GroupApiState` 要注入 `MessageDispatcher`。

```rust
// ---> server/modules/im-group/src/routes.rs
#[derive(Clone)]
pub struct GroupApiState {
    pub service: Arc<GroupService>,
    pub msg_service: Arc<MessageService>,
    pub dispatcher: Arc<MessageDispatcher>,  // 新增：WS 推送
}
```

##### 1. 数据模型

本章新增一张表 `group_join_requests`，同时给 `group_info` 加了一个 `group_no` 字段。数据表关系如下：

![mermaid-diagram-2026-04-19-233706.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/70834b8e1fe44967930aa1599186c7c9~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=3012\&h=1345\&s=288434\&e=png\&b=fffefe)

**群号（group\_no）**

群号是用户搜索群聊的另一种方式——除了按群名模糊搜索，还可以输入群号精确匹配。用 PostgreSQL 的 `SEQUENCE` 自增，从 10001 开始：

```sql
-- ---> server/migrations/20260419_006_group_join.sql
CREATE SEQUENCE IF NOT EXISTS group_no_seq START WITH 10001;
ALTER TABLE group_info ADD COLUMN IF NOT EXISTS group_no BIGINT UNIQUE DEFAULT nextval('group_no_seq');
```

群号在创建群聊时自动分配（`DEFAULT nextval`），不需要业务代码干预。从 10001 开始而不是 1，是为了避免和用户 ID 混淆——用户搜索时输入一个数字，后端需要判断是群号还是群名，如果群号从 1 开始就容易和用户 ID 撞车。

***

**入群申请表（group\_join\_requests）**

```sql
-- ---> server/migrations/20260419_006_group_join.sql
CREATE TABLE IF NOT EXISTS group_join_requests (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL,
    user_id BIGINT NOT NULL,
    message VARCHAR(200),
    status SMALLINT NOT NULL DEFAULT 0,  -- 0=待处理 1=已同意 2=已拒绝
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_group_join_requests_conv ON group_join_requests(conversation_id, status);
CREATE INDEX idx_group_join_requests_user ON group_join_requests(user_id, status);
```

| 决策                                    | 理由                                                                 |
| ------------------------------------- | ------------------------------------------------------------------ |
| 独立表而非复用 friend\_requests              | 好友是双向关系（from\_user → to\_user），入群是单向申请（user → conversation），字段语义不同 |
| status 用 SMALLINT 而非 ENUM             | 和项目其他表保持一致（conversations.type 也是 SMALLINT），扩展方便                    |
| 不加 UNIQUE(conversation\_id, user\_id) | 允许同一用户对同一群有多条历史记录（被拒绝后可重新申请），通过业务逻辑限制"同时只有一条 status=0 的申请"         |
| 两个索引分别覆盖群维度和用户维度                      | 群主查询按 conversation\_id + status，用户查询按 user\_id + status，各走各的索引     |

##### 2. 三层架构

im-group 的路由从 1 个扩展到 7 个，但三层架构不变。\
routes 解析请求、service 校验逻辑、repository 操作数据库。变化的是每一层的"厚度"。

    server/modules/im-group/src/
    ├── models.rs       # 扩展：GroupSearchResult / JoinRequestItem / JoinResult / GroupDetail ...
    ├── repository.rs   # 扩展：search_groups / join_group_direct / create_join_request / ...
    ├── service.rs      # 扩展：search_groups / join_group / handle_join_request / ...
    ├── routes.rs       # 扩展：7 个路由 handler
    └── lib.rs          # 不变

**routes.rs — 从 1 个路由到 7 个**

上一章 routes.rs 只有一个 `create_group`。现在它是 im-group 的"门面"，7 个路由覆盖群聊的完整生命周期：

```rust
// ---> server/modules/im-group/src/routes.rs
pub fn group_routes(state: GroupApiState) -> Router {
    Router::new()
        .route("/groups", post(create_group))                                      // 创建群聊（已有）
        .route("/groups/search", get(search_groups))                               // 搜索群聊
        .route("/groups/{id}/join", post(join_group))                              // 入群申请
        .route("/groups/{id}/join-requests/{rid}/handle", post(handle_join_request)) // 群主审批
        .route("/groups/join-requests", get(list_join_requests))                   // 入群通知列表
        .route("/groups/{id}/detail", get(get_group_detail))                       // 群详情
        .route("/groups/{id}/settings", put(update_group_settings))                // 群设置
        .with_state(state)
}
```

routes 层除了解析请求和调 service，还负责两件"跨模块"的事：发系统消息（调 `msg_service.send_system`）和推送 WS 通知（调 `dispatcher.notify_group_join_request`）。这两个依赖通过 `GroupApiState` 注入，service 层不感知——service 只返回结果，由 routes 决定"接下来通知谁"。

***

**service.rs — 校验 + 分支判断**

service 层是业务规则的守门人。它不碰数据库（那是 repository 的事），只做三件事：校验输入、判断分支、编排调用。
本章最有意思的设计是 `join_group` 的返回值——它不返回 HTTP 响应，而是返回一个枚举 `JoinResult`，让 routes 层根据枚举值决定后续动作：

```rust
// ---> server/modules/im-group/src/models.rs
pub enum JoinResult {
    AutoApproved,                                          // 无需验证，已直接加入
    PendingApproval { request_id: Uuid, owner_id: i64 },   // 需要验证，申请已创建
}
```

> 为什么不在 service 层直接发 WS 通知？因为 service 不知道 `MessageDispatcher` 的存在——它只依赖 `GroupRepository`。WS 推送是"通知"而非"业务逻辑"，放在 routes 层更合适。这和上一章系统消息放在 routes 层是同一个原则。

***

**repository.rs — 从 2 个方法到 12 个**

repository 层是最"重"的一层，从上一章的 `create_group` + `build_grid_avatar` 扩展到 12 个方法。但它们可以分成四组：

| 组  | 方法                                                                                                 | 职责              |
| -- | -------------------------------------------------------------------------------------------------- | --------------- |
| 搜索 | `search_groups`                                                                                    | 一次查询返回 4 个维度的信息 |
| 入群 | `join_group_direct` / `create_join_request` / `find_pending_request`                               | 直接加入 or 创建申请    |
| 审批 | `get_join_request` / `update_join_request_status` / `list_join_requests`                           | 查询和更新申请状态       |
| 详情 | `get_group_info` / `get_group_members` / `update_group_settings` / `get_group_owner` / `is_member` | 群信息和权限校验        |

其中 `join_group_direct` 被两个场景复用——无需验证时的直接加入，和群主同意后的加入。它做两件事：INSERT conversation\_members（ON CONFLICT 恢复已删除成员）+ 刷新宫格头像。

##### 3. 核心逻辑

7 个接口中，入群申请是最值得展开的——一个接口、两条路径、三层协作。其他接口的模式都能从它身上找到影子。

**搜索群聊：一条 SQL 返回四个维度**

搜索的挑战不在于"怎么搜"，而在于一次查询要带回前端渲染四种按钮状态所需的全部信息。service 层判断 keyword 是纯数字（走群号精确匹配）还是文本（走群名 ILIKE），repository 层用子查询一次性关联出四个字段：

```sql
-- ---> server/modules/im-group/src/repository.rs
SELECT c.id, c.name, c.avatar, c.owner_id, gi.group_no,
    (SELECT COUNT(*) FROM conversation_members
     WHERE conversation_id = c.id AND is_deleted = false) AS member_count,
    EXISTS(SELECT 1 FROM conversation_members
     WHERE conversation_id = c.id AND user_id = $1 AND is_deleted = false) AS is_member,
    COALESCE(gi.join_verification, false) AS join_verification,
    EXISTS(SELECT 1 FROM group_join_requests
     WHERE conversation_id = c.id AND user_id = $1 AND status = 0) AS has_pending_request
FROM conversations c
LEFT JOIN group_info gi ON gi.conversation_id = c.id
WHERE c.type = 1 AND c.name ILIKE $2
LIMIT 20
```

> EXISTS 子查询找到一条就返回，不会全表扫描。多做一点 SQL 关联，省掉前端多次网络往返。

**入群申请：一个接口，两条路径**

这是本章的技术核心。service 层做三重校验（群存在、非成员、无待处理申请），然后根据 `join_verification` 分支，返回枚举告诉 routes 层"走哪条路"：

```rust
// ---> server/modules/im-group/src/service.rs
fn join_group(user_id, conversation_id, message):
    owner_id = repo.get_group_owner(conversation_id)?       // 群不存在 → 404
    if repo.is_member(conversation_id, user_id): return 400  // 已是成员
    if repo.find_pending_request(...).is_some(): return 400   // 有待处理申请

    if !repo.get_join_verification(conversation_id):
        repo.join_group_direct(conversation_id, user_id)     // 直接加入 + 刷新头像
        return AutoApproved
    else:
        request_id = repo.create_join_request(conversation_id, user_id, message)
        return PendingApproval { request_id, owner_id }
```

routes 层根据枚举值决定"通知谁"——`AutoApproved` 同步发系统消息，`PendingApproval` 异步推送 WS 通知：

```rust
// ---> server/modules/im-group/src/routes.rs
match result {
    AutoApproved => {
        msg_service.send_system(conv_id, "{name} 加入了群聊")
        return { auto_approved: true }
    }
    PendingApproval { request_id, owner_id } => {
        tokio::spawn(async move {
            dispatcher.notify_group_join_request(owner_id, ...)
        });
        return { auto_approved: false }
    }
}
```

> `tokio::spawn` 把 WS 推送从请求链路中剥离——通知失败不影响申请创建，这是"最终一致性"的选择。群主不在线时通知丢失，但申请已入库，下次打开群通知页能看到。

***

**入群审批与群详情**

审批（`POST /groups/{id}/join-requests/{rid}/handle`）的模式和入群申请对称：校验群主身份 → 校验申请 status=0 → 同意则复用 `join_group_direct` 加成员，拒绝则更新 status=2。

```rust
// ---> server/modules/im-group/src/service.rs
fn handle_join_request(owner_id, conversation_id, request_id, approved):
    actual_owner = repo.get_group_owner(conversation_id)?
    if actual_owner != owner_id: return 403

    (_, applicant_id, status) = repo.get_join_request(request_id)?
    if status != 0: return 400  // 已处理

    if approved:
        repo.update_join_request_status(request_id, 1)
        repo.join_group_direct(conversation_id, applicant_id)
        return Some(applicant_id)  // routes 层据此发系统消息
    else:
        repo.update_join_request_status(request_id, 2)
        return None
```

service 返回 `Some(applicant_id)` 而不是 `bool`——routes 层需要知道"谁被同意了"，查昵称后发系统消息"XXX 加入了群聊"。

群详情（`GET /groups/{id}/detail`）和群设置（`PUT /groups/{id}/settings`）是两个轻量接口，源码在同一个 service.rs 中。两者共享一个权限模式：先查身份，再决定放行。区别在于群详情是"群成员可看"（`is_member` 校验），群设置是"群主可改"（`owner_id` 校验）。

```rust
// ---> server/modules/im-group/src/service.rs
fn get_group_detail(user_id, conversation_id):
    if !repo.is_member(conversation_id, user_id): return 403
    return GroupDetail { repo.get_group_info(...)?, repo.get_group_members(...)? }

fn update_group_settings(user_id, conversation_id, join_verification):
    if repo.get_group_owner(conversation_id)? != user_id: return 403
    repo.update_group_settings(conversation_id, join_verification)
```

##### 1. WS 扩展

入群申请的实时通知需要一条完整的链路：后端 `MessageDispatcher` 推送 GROUP_JOIN_REQUEST 帧 → WsClient 接收并分发 → GroupNotificationCubit 监听并更新 pendingCount → 通讯录 Tab 红点角标刷新。WsClient 是这条链路的中间节点。

```dart
// ---> client/modules/flash_im_core/lib/src/logic/ws_client.dart

// 1. 新增 StreamController（和 friendRequestStream 同级）
final _groupJoinRequestController = StreamController<WsFrame>.broadcast();
Stream<WsFrame> get groupJoinRequestStream => _groupJoinRequestController.stream;

// 2. 帧分发 switch 中新增 case
case WsFrameType.GROUP_JOIN_REQUEST:
    _groupJoinRequestController.add(frame);

// 3. dispose 中关闭
_groupJoinRequestController.close();
```

这是项目中第四次用这个模式了（前三次是 chatMessage、friendRequest、friendAccepted）。每种帧类型一个独立的 Stream，消费方按需订阅，互不干扰。WsClient 不解析 payload——它只负责按帧类型分发，具体的 Protobuf 解码留给消费方。

> 这种"分发不解析"的设计让 WsClient 保持轻量。它不需要知道 GroupJoinRequestNotification 长什么样，只需要知道帧类型是 10 就往对应的 Stream 里扔。新增帧类型时只改三行代码。

##### 4. 主应用集成与模块协作

> client/lib/src/home/view/home_page.dart

home_page 是所有新功能的组装点。上一章它负责串联好友模块和群聊模块（Friend → SelectableMember 转换），这一章它的组装工作更多——要注入 Cubit、合并角标、注入回调、传递群详情入口。

---

**GroupNotificationCubit 注入**

home_page 创建 GroupNotificationCubit，传入 GroupRepository 和 WsClient.groupJoinRequestStream。Cubit 创建后立即调 `loadPendingCount()` 从服务端加载初始值：

```dart
// ---> client/lib/src/home/view/home_page.dart
_groupNotifCubit = GroupNotificationCubit(
  repository: context.read<GroupRepository>(),
  groupJoinRequestStream: context.read<WsClient>().groupJoinRequestStream,
)..loadPendingCount();
```

> 为什么在 home_page 创建而不是用 BlocProvider 在 widget tree 顶层注入？因为 GroupNotificationCubit 需要 WsClient 的 Stream，而 WsClient 是登录后才创建的。home_page 是登录后的第一个页面，在这里创建时机刚好。

---

**通讯录 Tab 角标合并**

通讯录 Tab 的红点角标需要合并两个来源——好友通知的 pendingCount 来自 FriendCubit，群通知的来自 GroupNotificationCubit。两者独立管理，Tab 角标显示两者之和：

```dart
// ---> client/lib/src/home/view/home_page.dart
Widget _buildPendingBadge():
    return BlocBuilder<FriendCubit, FriendState>(
      builder: (context, friendState) =>
        BlocBuilder<GroupNotificationCubit, GroupNotificationState>(
          bloc: _groupNotifCubit,
          builder: (context, groupState) {
            total = friendState.pendingCount + groupState.pendingCount
            if total <= 0: return SizedBox.shrink()
            return Badge(count: total)
          },
        ),
    )
```

通讯录列表中，"群通知"入口用 `BlocBuilder` 监听 GroupNotificationCubit，根据 pendingCount 显示独立的红点角标。进入群通知页返回后，调 `loadPendingCount()` 重新校准。

---

**搜索群聊入口：回调注入**

AddFriendPage 的"搜索群聊"入口通过 `onSearchGroup` 回调接入。home_page 在构造 AddFriendPage 时注入这个回调，点击后 push SearchGroupPage。这个模式和上一章的 `onCreated` 回调一样——模块不直接认识对方，组装层负责串联：

```dart
// ---> client/lib/src/home/view/home_page.dart
AddFriendPage(
  repository: context.read<FriendRepository>(),
  onSearchGroup: () => Navigator.push(context, MaterialPageRoute(
    builder: (_) => SearchGroupPage(
      repository: context.read<GroupRepository>(),
      baseUrl: AppConfig.baseUrl,
    ),
  )),
)
```

---

**群详情入口：三处 ChatPage 构建**

用户有三条路径进入群聊 ChatPage（主页会话列表、我的群聊列表、创建群聊后跳转），每处构建 ChatPage 时都要传入 `onGroupInfo` 回调，跳转 GroupChatInfoPage 页面：

```dart
// ---> client/lib/src/home/view/home_page.dart
ChatPage(
  conversationId: conversation.id,
  isGroup: true,
  onGroupInfo: () => Navigator.push(context, MaterialPageRoute(
    builder: (_) => GroupChatInfoPage(
      repository: context.read<GroupRepository>(),
      conversationId: conversation.id,
      baseUrl: AppConfig.baseUrl,
      currentUserId: user.userId.toString(),
    ),
  )),
)
```
