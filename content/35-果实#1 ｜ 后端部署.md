##### 1. 什么是服务器

 `服务器` 顾名思义，是提供服务的机器。其实之前我们一直在运行服务，本机也可以视为一个服务器。从客户端的访问来看，其实服务器最重要的有两个东西 **ip** 和 **端口号**，其中端口号是我们可以自定义的。所以最重要的就是这个 ip。
 
 正是因为本机的 ip 只能在局域网内使用，所以目前只是一个无法对外公开的服务。服务器和你的电脑之前最大的差异性在于:

> 它可以提供一个公网 ip ，任何人都可以通过这个 ip 接入你的服务。

也就是说，如果你有公网 ip，那本机也完全可以作为服务器，不过公网IP的获取方式目前应该很难了。

##### 3. 访问你的服务器

服务器供应商还会给你三个重要的东西：

- **公网 IP**（比如 `82.157.176.209`）—— 你服务器在互联网上的门牌号
- **用户名**（通常是 `root`）—— 最高权限管理员
- **密码** —— 开门的钥匙

有了这三样，表示你对这个服务器的控制权，就可以从你的电脑"走进"服务器了。打开终端输入：

```bash
ssh root@82.157.176.209
```

把 IP 换成你自己的。第一次连会问你信不信任这台机器，输入 `yes`。然后输入密码（输入时屏幕不会显示任何字符，这是正常的，盲打完回车就行）。

##### 2. 什么是交叉编译

你的开发电脑是 Windows（或 macOS），服务器是 Linux。它们的操作系统不同，编译出来的程序格式也不同：

| 系统 | 可执行文件格式 | 例子 |
|------|-------------|------|
| Windows | .exe（PE 格式） | flash-im.exe |
| macOS | Mach-O 格式 | flash-im |
| Linux | ELF 格式 | flash-im |

在 Windows 上直接 `cargo build` 出来的是 `.exe`，传到 Linux 上跑不了。我们需要"交叉编译"：在 Windows 上编译出 Linux 格式的程序。

> 交叉编译就像翻译：你说中文（Windows），但要写一封英文信（Linux 程序）。你需要一个翻译工具。

这个"翻译工具"就是 **Docker**。Docker 可以在你的电脑上模拟一个 Linux 环境，在里面编译出 Linux 程序。

---

当然，构建的事也是 AI 来写脚本处理，我们也不用自己埋头干。项目里的 `scripts\deploy\build.py` 就是使用 Docker 一套龙的构建流程。第一次运行，它会提示你安装 **Docker**，你根据提示里的链接下载启动一下即可。

#### 四、启动流程优化

现在 `build.py` 可以打包上传一条龙服务。但启动流程有点单薄，命令行里手动执行可执行文件一个问题：当命令行关闭，服务也就停了。我们需要一个更优雅的方式来管理服务的启停。  

---

##### 1. 使用脚本启停

项目里准备了一个管理脚本 `flash.sh` 负责维护后端的运行事宜，把它上传到服务器的部署目录：

```bash
# 在本地执行
scp scripts/deploy/flash.sh root@82.157.176.209:~/server/flash_im/
```

上传后，在服务器上就可以用它来管理服务了：

```bash
cd ~/server/flash_im
bash flash.sh          # 后台启动（关闭终端不停止）
bash flash.sh stop     # 停止
bash flash.sh restart  # 重启
bash flash.sh status   # 查看状态（PID、内存、运行时间）
bash flash.sh log      # 看实时日志
bash flash.sh clear    # 清空日志文件
```

`flash.sh` 用 `nohup` 在后台运行服务，日志写到 `flash-im.log`。关闭 SSH 终端不会影响服务。

##### 2. 使用 systemd 创建服务 - 开机自启

目前这还不够，因为 **服务器重启后，服务不会自动恢复**。你得重新 SSH 连上去手动启动。
对于一个 7×24 小时在线的 IM 服务来说，这不够可靠。我们需要让系统帮我们管理进程：开机自动启动、崩溃自动重启、日志自动收集。Linux 上做这件事的标准工具叫 **systemd**。

你可以把 systemd 理解为 Linux 的"管家"。它负责管理系统上所有的服务（service）：哪些开机要启动、哪些挂了要重启、日志存在哪里。

systemd 的服务配置是一个 `.service` 文件，放在 `/etc/systemd/system/` 目录下。我们写一个 `flash.sh` 的子命令来自动创建它：

```bash
bash flash.sh install    # 注册为系统服务 + 开机自启
bash flash.sh uninstall  # 移除系统服务
```

这个命令会做三件事：
1. 创建 `/etc/systemd/system/flash-im.service` 配置文件
2. 让 systemd 重新加载配置
3. 设置开机自启

注册后，可以直接用 systemd 命令：

```bash
systemctl start flash-im # 启动
systemctl stop flash-im # 停止
systemctl restart flash-im  # 重启
journalctl -u flash-im -f    # 查看日志
```

#### 四、小结

回顾一下这一章做了什么：我们把闪讯后端从开发机搬到了云端，让它变成了一个真正的、任何人都能访问的在线服务。整个部署体系由四个脚本组成，各司其职：

| 脚本 | 在哪里跑 | 做什么 |
|------|---------|--------|
| `build.py` | 本地电脑 | 交叉编译 + 上传 + 自动重启远程服务 |

| `flash.sh` | 服务器 | 服务管理（启停/日志/注册系统服务） |

日常更新只需要一行命令：

```bash
python scripts/deploy/build.py root@你的服务器IP
```

它会自动编译、停止旧服务、上传新二进制、重启。整个过程不需要 SSH 登录服务器。

#### 小思考: 为什么不能直接把代码丢到服务器里跑

你可能会想：把 Rust 源码传到服务器上，然后 `cargo run` 行不行？
理论上可以，但实际上欠佳。原因有两个：

- **编译太吃资源**。Rust 编译器是出了名的"慢但精"，编译一个中等项目需要 2~4G 内存。我们的服务器只有 2G，跑着 MySQL 和 PostgreSQL 之后剩余不到 1G，编译到一半就会被系统杀掉。
- **没必要在服务器上装开发工具**。服务器的职责是"跑服务"，不是"写代码"。装一堆编译工具既浪费空间又增加安全风险。而且服务器资源可谓寸土寸金，被必要做这些没有太大意义的事。

所以正确的做法是：**在本地编译好，把编译产物（一个二进制文件）上传到服务器**。

> 这就像开餐厅：你不会在店里现磨面粉、现榨油。你在工厂把半成品做好，运到店里直接加热上桌。服务器就是那个"店"，你的开发电脑就是那个"工厂"。
