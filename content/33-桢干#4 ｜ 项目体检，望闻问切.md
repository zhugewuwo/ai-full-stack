> 复杂性是沉默的，直到它不再沉默。

#### 项目体检，望闻问切

一棵树苗刚种下的时候，你一眼就能看到它的全貌：几片叶子、一根细茎、一小撮根。哪里有虫咬了一口，哪里叶子发黄了，肉眼可见。但当它长成一棵三米高的树，枝繁叶茂，你站在外面看，觉得一切都好。可能树干里已经被蛀空了一半，你浑然不知。

我们的闪讯项目走到这里，已经不是当初那棵小苗了。二十多个版本的迭代，前后端加起来几万行代码，十几个模块交织在一起。每次新功能都能跑通，测试也过了，看起来一切正常。但"能跑"和"健康"是两回事。一个人能走路不代表他没有高血压，一棵树能开花不代表它里面没有白蚁。

前面十几章我们一直在"长"——长新功能、长新模块、长新接口。生长是好事，但只顾着长不顾着养，迟早会出问题。果农都知道，果树长到一定阶段要修剪、要打药、要检查有没有病虫害。不是等到果子掉了才去看，而是在一切看起来还好的时候就主动检查。

接下来两章，我们就来做这件事。这一章是"体检"：用望闻问切的方式，把项目里潜藏的问题找出来。下一章是"养护"：建立长期的防护机制，让这些问题不再复发。先发现，再预防。

---

#### 一、为什么需要体检

人年轻的时候不体检，因为身体底子好，小毛病自己能扛过去。项目也一样，早期代码少、逻辑简单，即使有些不规范的写法，也不会出大问题。但随着代码量增长，那些"小毛病"会慢慢积累，直到某天突然爆发。

常见的"慢性病"：

- **依赖纠缠**：A 模块悄悄 import 了 B 模块的内部文件，改 B 的时候 A 莫名其妙编译失败
- **职责漂移**：某个 Cubit 一开始只管聊天状态，后来顺手加了网络请求、加了文件操作，变成了一个什么都管的"万能类"
- **死代码堆积**：早期的原型代码、调试用的 print、注释掉的旧逻辑，像落叶一样堆在角落
- **命名混乱**：同一个概念在不同模块里叫不同的名字，或者同一个名字在不同地方表示不同的东西

这些问题单独看都不致命，但它们会互相叠加。依赖纠缠让重构变得困难，职责漂移让 bug 难以定位，死代码让新人（包括 AI）读代码时产生困惑。就像一个人同时有高血压、高血糖、高血脂，每个单独看都"还行"，但三个加在一起就是定时炸弹。

##### 1、望：看数字，看结构

中医讲"望闻问切"，第一步是"望"——看气色。项目的"气色"藏在两个地方：一是数字（文件数、行数、模块大小），二是结构（目录组织、命名、模块划分）。这里以前端项目为例，看看它的气色如何：

##### 2、闻：跑静态分析

"闻"是听声音。项目的"声音"就是编译器和 lint 工具的输出。同样写了另一个脚本（`scripts/checkup/client_analyze.py`），它会自动跑 `flutter analyze`，解析输出，按类型分类统计，然后保存到体检目录。  
但在闻之前，先在 `analysis_options.yaml` 里上加了排除规则，避免非项目代码和自动生成代码的分析，这些是没有分析意义的噪点。

```yaml
analyzer:
  exclude:
    - lib/playground/**       # 废弃的原型代码
    - "**/*.g.dart"           # build_runner 生成
    - "**/*.freezed.dart"     # freezed 生成
```

---

跑完之后的结果：

| 级别 | 数量 |
|------|------|
| 🔴 error | 0 |
| 🟡 warning | 15 |
| 🟢 info | 92 |

零 error 是底线，这个过了。重点看 warning 和 info。

##### Warning（15 个）

| 类型 | 数量 | 典型例子 |
|------|------|---------|
| unused_element | 3 | `_confirmForward`、`_showEditAvatar`、`_showManageSheet` 方法写了但没用 |
| unused_local_variable | 3 | `replyName`、`isLoadingMore`、`menuPadding` 声明了但没用 |
| unused_shown_name | 2 | import 里 show 了 WsFrame/WsFrameType 但没用到 |
| unused_element_parameter | 3 | `strokeWidth`、`dashWidth`、`dashSpace` 参数从没被传值 |
| unused_field | 1 | `_showMentionPicker` 字段没用 |
| unused_import | 1 | group_models.dart 被 import 但没用 |
| unnecessary_non_null_assertion | 1 | 对不可能为 null 的值用了 `!` |
| unnecessary_cast | 1 | 多余的类型转换 |

这些 warning 有个共同特征：都是"写了但没用到"。这在快速迭代中很常见，改了方案但忘了删旧代码。单个看都不严重，但积累多了说明代码里有"死肉"。

##### Info（92 个）

| 规则 | 数量 | 说明 |
|------|------|------|
| avoid_print | 46 | 生产代码里不该有 print |
| unnecessary_underscores | 21 | 多余的下划线命名 |
| use_null_aware_elements | 6 | 可以用 `?` 简化的空检查 |
| use_build_context_synchronously | 5 | 异步操作后使用了 BuildContext |
| unnecessary_import | 3 | 多余的 import |
| deprecated_member_use | 0 | 排除 playground 后没有了 |

46 个 `avoid_print` 占了一半。这些是开发调试时加的日志，功能做完后忘了清理。它们不影响功能，但会在控制台产生噪音，也暴露了内部实现细节。

5 个 `use_build_context_synchronously` 值得关注。这意味着有 5 处代码在 async 操作后使用了 BuildContext，如果页面在等待期间被关闭，可能会报错。虽然目前没出过问题，但这是潜在的运行时风险。

#### 3、问：让 AI 审查代码

"问"是问诊。你主动把代码拿给 AI 看，让它帮你找问题。这里有个有趣的悖论：
>代码是 AI 写的，现在又让 AI 来审查自己写的代码，这有用吗？

答案是：有用，而且很有用。原因是 AI 写代码时的上下文和审查时的上下文不同。写代码时它专注于"完成任务"，审查时它可以站在更高的视角看"这段代码合不合理"。就像一个人写文章时沉浸在思路里，过两天回头看才发现"这段话说得不清楚"。

这一阶段，让 AI 深入阅读关键模块的代码，从设计角度审查，结合望、闻阶段的结果，产出代码质量与问题汇报。产出 `03_问_代码审查.md`, 这里把流程性的处理，也提取为一个 [**project-doctor**](https://github.com/toly1994328/flash_im_by_ai/blob/master/.kiro/skills/project-doctor/SKILL.md) 技能角色。  
我这里跑出的结果在 [03_问_代码审查.md](https://github.com/toly1994328/flash_im_by_ai/blob/master/docs/project/checkup/v0.20.0/client/03_%E9%97%AE_%E4%BB%A3%E7%A0%81%E5%AE%A1%E6%9F%A5.md)，其中检测到最严重的问题就是 : **ChatCubit 职责过多**，承担了以下所有职责：

| 职责 | 方法 |
|------|------|
| 消息加载与分页 | loadMessages, loadMore |
| 文本消息发送 | sendMessage |
| 图片发送（含上传） | sendImageFromFile |
| 视频发送（含上传） | sendVideoFromFile |
| 文件发送（含上传） | sendFileFromPicker |
| 文件下载 | downloadFile |
| WS 消息接收 | _handleIncomingMessage |
| 消息确认 | _handleMessageAck |
| 发送超时处理 | _setupTimeout, _markFailed |
| 消息撤回 | recallMessage, _handleMessageRecalled, _replaceWithRecalled |
| 引用回复 | setReplyTo, clearReplyTo |
| 多选模式 | enterMultiSelect, exitMultiSelect, toggleSelect, deleteSelected |
| 转发 | forwardMessages |
| 置顶 | loadPinnedMessages, pinMessage, unpinMessage |
| 复制与删除 | copyMessage, deleteMessage |
| 已读回执 | _loadReadSeq, _reportReadSeq |

共 30+ 个公开/私有方法。虽然它们都和"聊天"相关，但文件上传、文件下载、已读回执这些可以拆到独立的 mixin 或 service 中。
**严重程度**：🟡 一般。目前还能维护，但再加功能会失控。

##### 4. 切：深入诊断

针对前三步发现的疑似问题，深入确认。

```
操作：
- 对"望"发现的结构问题：打开具体文件，确认是否真的有问题
- 对"闻"报出的 warning：判断是误报还是真问题
- 对"问"发现的设计问题：评估影响范围和修复代价

输出：确诊问题清单，分三级：
- 🔴 严重：阻塞后续开发或有运行时风险，建议立即修复
- 🟡 一般：不影响功能但影响可维护性，建议近期修复
- 🟢 轻微：代码风格或命名问题，可以顺手修或暂时不管
```

我这里跑出的结果在 [04_切_确诊处方](https://github.com/toly1994328/flash_im_by_ai/blob/master/docs/project/checkup/v0.20.0/client/04_%E5%88%87_%E7%A1%AE%E8%AF%8A%E5%A4%84%E6%96%B9.md)，发现了一个严重问题，下面是医嘱：

**立即处理**

- **#1 StreamController 关闭后 add**：这是唯一的运行时炸弹。虽然目前没有复现过，但在网络波动导致异步操作延迟返回时有可能触发。修复成本低（加一个 bool 标志位），建议立即修。

**近期关注**

- **#2 syncAll 事务性**：当前数据量小，崩溃概率低，但随着用户增多和数据量增长，风险会上升。下次改 cache 模块时顺手修。
- **#3 日期判断 bug**：影响会话列表的时间显示，用户可能看到"今天"的消息实际是昨天的。修复简单，近期处理。
- **#5 搜索防抖**：目前用户少感知不明显，但如果搜索接口变慢或用户输入快，会产生大量无效请求。

**长期改善**

- **#4 空 catch 模式**：这是一个系统性问题，需要建立统一的错误处理策略。可以引入一个 `safeCall` 工具方法，统一处理异常日志。
- **#6 chat_cubit 拆分**：等下次有新的聊天功能需求时，借机重构。不要为了重构而重构。
- **#7 print 清理**：可以一次性批量处理，或者引入 logger 后逐步替换。

#### 二、报告留存的重要性

体检做完了，问题也找到了，然后呢？很多人的做法是：修完 bug，关掉对话，继续写下一个功能。体检报告？不存在的，它只活在那次对话的上下文里。这是一个巨大的浪费。

---


##### 1、AI 对话是易逝品

和 AI 的对话有一个致命缺陷：**它没有长期记忆**。这次对话里 AI 帮你找到了 13 个问题，你修了 3 个最紧急的，剩下 10 个打算"以后再说"。两周后你开了一个新对话，AI 对之前的体检结果一无所知。那 10 个问题就这样消失在时间里了。

更糟糕的是，你自己也会忘。两周前觉得"这个问题不急"，两周后连这个问题的存在都不记得了。直到某天它真的爆了，你才想起来"好像之前发现过这个"。

这就像去医院做了全套体检，医生口头告诉你"血脂偏高，注意饮食"，但你没拿到纸质报告。当时你点点头记住了，三个月后复查，换了个医生，你说"上次血脂偏高"，医生问"偏高多少？哪项偏高？上次的具体数值是多少？"你答不上来。没有留存的数据，每次都是从头来过。

所以体检报告必须**落盘**——写成文件，存在项目里，跟着代码一起走。它不是给"现在的你"看的，是给"两周后的你"、"两个月后的你"、"下一个接手项目的人"看的。

---

##### 2、报告是给未来的自己看的

我们的体检报告存在 `docs/project/checkup/{版本号}/` 下，按前后端分目录：

```
docs/project/checkup/v0.20.0/
├── client/
│   ├── 01_望_结构统计.md
│   ├── 02_闻_静态分析.md
│   ├── 03_问_代码审查.md
│   └── 04_切_确诊处方.md
└── server/
    ├── 01_望_结构统计.md
    ├── 02_闻_静态分析.md
    ├── 03_问_代码审查.md
    └── 04_切_确诊处方.md
```

这些文件的价值不在于"写完那一刻"，而在于**下一次体检时**。

当你在 v0.21.0 再做一次体检，你可以对比：
- 上次 15 个 warning，这次多了还是少了？
- 上次发现的 13 个问题，修了几个？新增了几个？
- chat_cubit 上次 773 行，这次是变长了还是拆分了？
- 上次的 🔴 严重问题还在不在？

没有历史数据，你就无法判断项目是在变好还是变差。就像体检报告上的血压值，单次看只是一个数字，连续看三年才能看出趋势。130/85 是高还是低？如果去年是 120/80，今年是 130/85，那是在往高走，需要注意。如果去年是 140/90，今年是 130/85，那是在好转，继续保持。**同一个数字，有没有参照系，结论完全不同。**

举个具体的例子。我们这次体检发现前端有 46 个 `avoid_print`（生产代码里的 print 语句）。如果这是第一次体检，你只知道"有 46 个"，不知道这是多还是少。但如果上次体检是 30 个，这次变成 46 个，说明最近几个版本的开发中又新增了 16 个 print 没清理——问题在恶化。反过来，如果上次是 80 个，这次降到 46 个，说明清理工作在起效——方向是对的。

这就是"趋势"的力量。单点数据是噪音，连续数据才是信号。

---

##### 3、AI 加持下的体检报告

这一点容易被忽略，但在 AI 辅助开发的工作流里极其重要。

首先，报告的书写者是 AI。这和传统开发流程有本质区别——以前写体检报告是一件苦差事，你得自己跑工具、自己整理数据、自己写分析、自己排优先级。现在这些全交给 AI 来做。你只需要说一句"给项目做个体检"，望闻问切四步走完，四份报告自动生成。写报告的成本从"半天"降到了"一句话"，这才是 AI 时代体检能真正落地的原因。

其次，留存的报告反过来又能喂给 AI。当你下次让 AI 做体检时，你可以把上次的报告给它：

> "这是上次 v0.20.0 的体检报告，现在是 v0.21.0，请对比分析变化。"

AI 有了历史基线，就能给出更有价值的判断：
- "上次发现的 #1 StreamController 问题已修复，确认不再出现"
- "warning 从 15 个降到 3 个，说明清理工作有效"
- "im-message/routes.rs 从 601 行增长到 720 行，建议拆分的优先级应该提高"
- "上次标记为 🟡 的 syncAll 事务性问题仍未修复，已经跨了两个版本，建议提升优先级"

没有留存的报告，每次体检都是从零开始——AI 不知道哪些问题是"老毛病"，哪些是"新发现"，只能把所有问题平等对待。有了留存的报告，每次体检都是在上一次的基础上递进——AI 能区分"已知未修"和"新增问题"，给出的建议也更有针对性。

更进一步，如果你把体检报告放在 `.kiro/steering/` 或者作为技能的参考文件，AI 在日常开发中也能参考它。比如你让 AI 改 im-message 模块的代码，它看到体检报告里写着"routes 层业务逻辑过重，应下沉到 service"，就会自觉地把新逻辑写在 service 层而不是 routes 层。**报告不只是诊断结果，还是行为指南。**

---

##### 4、报告是团队的共识载体

如果你是一个人开发，报告是给未来的自己看的。如果是团队协作，报告还有另一个作用：**对齐认知**。

技术债是一个很模糊的概念。你问三个开发者"项目有什么技术债"，可能得到三个完全不同的答案。一个人觉得"命名不规范是最大的问题"，另一个人觉得"架构需要重构"，第三个人觉得"现在挺好的没什么问题"。每个人基于自己接触的那部分代码形成判断，视角不同，结论自然不同。

体检报告把这些模糊的感受变成了**具体的、可量化的、有优先级的清单**。"这个项目有什么技术债？"——不用开会讨论，打开最近一次体检报告的确诊处方就行。哪些是 🔴 必须修的，哪些是 🟡 可以缓的，哪些是 🟢 随手改的，白纸黑字写得清清楚楚。

新人入职，看一遍体检报告，就知道项目的"病史"和当前状态。不用老员工口头交代"那个模块别乱动"、"这个文件有坑"——报告里都写着呢。这比任何口头传承都可靠，因为口头的东西会失真、会遗漏，文字不会。

更重要的是，当这些报告跨越多个版本积累起来，它就不再只是"问题清单"了，而是**经验的财富**。

v0.18.0 的报告里发现"routes 层写了太多业务逻辑"，v0.19.0 又发现了同样的问题，v0.20.0 还是这个问题——三次体检指向同一个模式，说明这不是某个人的偶然失误，而是团队的习惯性倾向。这时候你就可以把它沉淀为一条规范："routes 层只做参数解析和响应，业务逻辑必须放在 service 层"，写进 steering 文件，让 AI 在日常开发中自动遵守。

再比如，连续几次体检都发现"新增功能后忘了清理调试 print"，这说明开发流程里缺了一个环节。于是你加一条 lint 规则或者一个 pre-commit hook，从源头杜绝。问题不再是"每次体检都发现然后手动清理"，而是"从此不会再出现"。

这就是从"发现问题"到"沉淀规范"的升华。单次体检是治病，多次体检的积累是养生。一个项目如果能坚持做五次、十次体检，那些反复出现的问题会自然而然地变成团队的编码规范、变成 AI 的 steering 指令、变成 CI 的自动检查。**体检报告的终极归宿不是躺在 docs 目录里吃灰，而是化为项目的免疫系统。**

---

#### 三、体检报告的天花板

前面说了这么多体检的好处，但有一个问题必须正视：**体检报告的质量上限在哪里？**

它由三个因素共同决定。你可以把体检想象成用望远镜观星：大模型是镜片的口径，决定了能收集多少光；提示词是镜筒的设计，决定了光怎么汇聚、对焦到哪里；而你自己的认知，是那个站在目镜后面的人。同一片星空，天文学家能看出星系的旋臂结构，普通人只看到"好多亮点"。三者叠加，口径越大看得越远，设计越精看得越清，观测者越专业读出的信息越多。

---

##### 1、大模型的本身能力

第一层是 AI 模型本身的能力边界。

模型能看到代码结构，能识别重复模式，能根据 lint 规则判断对错。但它有天然的盲区：

- **上下文窗口有限**。一个几万行的项目，模型不可能同时"看到"所有代码。它只能在有限的窗口里做局部判断，跨模块的隐性耦合可能被遗漏。
- **训练数据有时差**。模型的知识截止于某个时间点，最新的框架版本、最新的最佳实践，它可能还不知道。
- **推理深度有上限**。"这段代码有 bug"它能发现，"这个架构在三个月后会成为瓶颈"它很难预判。模式匹配是强项，前瞻性思考是弱项。

这一层会随着模型迭代不断抬高。今天的模型比一年前强太多，明年的模型又会比今天强。但在任何一个时间点，它都有上限。你不能指望模型发现它能力范围之外的问题。

---

##### 2、技能提示词的表述

第二层是你怎么"教" AI 做体检，也就是技能（skill）的提示词写得好不好。

同样一个模型，给它不同的指令，输出质量天差地别。我们的 `project-doctor` 技能里定义了望闻问切四步流程、每步的检查维度、输出格式、严重程度分级标准。这些提示词就像给医生的"诊疗规范"，规范写得越细，医生的诊断越靠谱。

提示词的质量体现在：
- **检查维度是否全面**？如果你只写了"检查代码风格"，AI 就不会去看架构设计、依赖方向、生命周期管理这些更深层的问题。
- **判断标准是否明确**？"大文件需要拆分"太模糊，"超过 500 行的文件需要评估是否拆分"才是可执行的标准。
- **输出格式是否结构化**？自由发挥的报告每次格式不同，无法做版本间对比。固定格式的报告才能形成时间序列。

这一层是可以持续打磨的。每次体检做完，你觉得"这个维度没覆盖到"、"那个判断标准不够精确"，就回去改提示词。技能文件本身也在迭代，和代码一样。

---

##### 3、个人能力的上限

第三层，也是最关键的一层：**你自己的认知水平**。

AI 能帮你跑静态分析、能帮你统计行数、能帮你逐文件审查代码。但有一类问题，AI 很难独立发现，就是**方向性的问题**：

- "这个模块的抽象层次对不对？"AI 能看到代码结构，但它不知道你的业务未来会往哪个方向演进。你打算加视频通话功能，那 im-ws 模块的设计是否能承载？这需要对产品路线图的理解。
- "这个性能瓶颈在当前规模下重要吗？"AI 能指出"这里有 N+1 查询"，但它不知道你的用户量是 100 人还是 10 万人。100 人的时候 N+1 无所谓，10 万人的时候就是灾难。这需要对业务规模的判断。
- "这个技术债现在该还吗？"AI 能列出所有技术债，但它不知道你下个月要上线一个大功能，现在重构会不会影响进度。这需要对项目节奏的把控。

AI 擅长"发现事实"，人擅长"做出判断"。你的认知决定了你能从报告里"看出"什么。同一份体检报告，一个初级开发者看到的是"哦，有 15 个 warning 要修"；一个资深架构师看到的是"warning 集中在 im-message 模块，说明这个模块的迭代速度超过了它的设计承载力，需要重新划分边界"。数据是一样的，解读完全不同。

---

##### 4、人在回路中

体检报告不是 AI 的自说自话。如果你只是让 AI 跑一遍然后看看结果，那你得到的只是一份"机器眼中的代码现状"，充其量是一份初筛报告。真正有价值的体检，需要开发者全程参与。你要告诉 AI 哪些模块是核心、哪些是边角；你要在 AI 列出问题后追问"这个影响范围有多大"；你要根据自己对业务的理解去质疑、去补充、去纠正 AI 的判断。

确诊清单是事实，但医嘱里的优先级排序，哪个立即修、哪个缓一缓、哪个不用管，这背后是人的决策。🔴🟡🟢 的定级，涉及业务影响、时间窗口、团队状态，这些信息只有你知道。AI 给出的分级是建议，你拍板的分级才是最终方案。

所以体检的最佳实践是：

1. **AI 负责发现和呈现**：跑数据、找问题、写报告，把事实摆在桌面上
2. **人负责判断和决策**：看报告、定优先级、决定什么时候修什么不修
3. **AI 负责执行**：人决定了要修哪些，AI 去改代码、跑验证

这个"人在回路中"的模式，才是体检流程的完整形态。你不是在旁边看 AI 表演，你是这场体检的主治医生，AI 是你手里的检测仪器。仪器能告诉你血压是 130/85，但要不要开药、开什么药、什么时候复查，是医生说了算。

**体检报告的天花板 = 模型能力 + 提示词质量 + 个人认知**。回到望远镜的比喻：口径在变大（模型每年都在进步）、镜筒在优化（提示词随着每次体检不断打磨）、观测者也在成长（你对项目和业务的理解越来越深）。三者叠加，每一层进步一点，你能从体检中看到的东西就多一点、深一点。

---

#### 本章小结

这一章我们用望闻问切的方式给项目做了一次完整体检：看数字、跑工具、让 AI 审查、确诊开处方。发现问题只是第一步，把报告留存下来才能看到趋势、沉淀经验。而体检的天花板取决于三者叠加：模型能力、提示词质量、你自己的认知。AI 是检测仪器，你是主治医生。



下一章，我们来聊怎么把这些"体检发现"转化为长期的防护机制，让问题不再复发，而不是每次体检都发现同样的毛病。把体检中沉淀的经验变成自动化的防护机制。
