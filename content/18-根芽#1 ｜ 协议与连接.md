> 语言不通的两个人，再怎么努力也无法对话。通信的第一步，不是说话，而是约定沟通的规则。

在经络卷的最后，我们站在时间维度上，看清了系统中各种对象的生死节奏。现在，是时候让这些认知落地了。而落地的第一步，不是写聊天页面，不是建消息表，而是解决一个更基础的问题：前端和后端之间，到底怎么"说话"。

之前游乐场实现了简单的聊天室：客户端连上来，发一条 JSON 文本，服务端把这条文本广播给所有在线的人。就像一个没有隔间的大厅，所有人说的话所有人都能听到。它的目的是验证 WebSocket 通信链路能跑通。但作为一个正式的 IM 系统，它有几个根本性的问题：

- 用 JSON 文本传输，没有统一的消息格式，前后端各自解析，容易出错
- 所有消息都是广播，没有"发给谁"的概念
- 没有心跳机制，连接断了谁也不知道
- 客户端没有重连逻辑，断了就只能推出重进
- 消息都是内存里的，退出就丢失了，后端没有落实到数据库。

---

#### 一、协议设计

从上面说的问题出发，我们需要设计一套正式的通信协议。协议不是什么高深的东西，它就是前后端之间的"语言规范"：用什么格式说话，怎么区分不同类型的话，怎么保证说的话不会被误解。

---

##### 1. 为什么需要协议

两个人面对面聊天，不需要协议，因为人类天生能理解自然语言。但两个程序之间的通信，每一个字节都必须有明确的含义。协议要回答的核心问题是：

> 这一串字节，是什么类型的消息？它的内容从哪里开始、到哪里结束？

如果没有协议，前端发了一段数据过来，后端不知道这是一条聊天消息、一个心跳包、还是一个认证请求。就像收到一封没有信封的信，不知道是寄给谁的，也不知道该怎么拆。
一个 IM 协议至少要解决三件事：

- 消息分类 ： 这是聊天消息、心跳、认证、还是系统通知？
- 消息边界 :  一条消息从哪里开始、到哪里结束？
- 编解码 : 用什么格式把数据序列化成字节，再从字节还原回来？


---

##### 2. 帧：通信的最小单位

IM 系统中，所有通过 WebSocket 传输的数据，都被封装成统一的结构，叫做 **帧**（Frame）。一个帧只有两个字段：

- `type` : 这是什么类型的消息（数字编号）
- `payload` : 消息的具体内容（二进制数据）


就像一个信封，`type` 是信封上的标签（"这是情书"、"这是账单"、"这是广告"），`payload` 是信封里的内容。收到信封后，先看标签决定怎么处理，再拆开读内容。

这个设计的好处是：无论未来增加多少种消息类型，帧的结构永远不变。只需要新增一个 type 编号，定义对应的 payload 格式就行。当前系统需要的帧类型并不多：

| type | 方向 | 用途 |
|------|------|------|
| PING | 客户端 → 服务端 | 心跳探测 |
| PONG | 服务端 → 客户端 | 心跳响应 |
| AUTH | 客户端 → 服务端 | 发送 Token 认证 |
| AUTH_RESULT | 服务端 → 客户端 | 认证结果 |


随着后续功能的增加，这张表会不断扩展：好友申请、会话更新、在线状态、消息撤回、已读回执……但帧结构本身不需要改动。这就是协议设计的核心思想：**用一个稳定的外壳，包裹不断变化的内容。**

---

##### 3. 为什么选 Protobuf

帧的 payload 里装的是二进制数据，那这些数据用什么格式编码？常见的选择有三种：

| 格式 | 优点 | 缺点 |
|------|------|------|
| JSON | 人类可读，调试方便 | 体积大，解析慢，没有类型约束 |
| MessagePack | 二进制，比 JSON 小 | 没有 Schema，前后端容易不一致 |
| Protobuf | 二进制，体积小，有 Schema 约束 | 需要预定义 .proto 文件 |

对于 IM 系统，Protobuf 是最合适的选择。原因不在于性能（虽然它确实快），而在于 **Schema**。

一个 .proto 文件就是前后端之间的契约。它明确定义了每种消息有哪些字段、什么类型、是否可选。前端和后端各自根据这份契约生成代码，编码和解码的逻辑是自动的，不存在"前端传了个字符串，后端以为是数字"这种问题。

这在 AI 编程中尤其重要。当你让 AI 实现一个新的消息类型时，只需要先在 .proto 文件里定义好结构，AI 就能根据这份契约准确地**自动生成前后端代码**，不会出现两端对不上的情况。.proto 文件本身就是最好的上下文。

##### 1. proto 长什么样子

proto 是前端和后端共同遵守的数据类型协议，所以它放在项目的最外层，如下所示，准备了 `proto` 文件夹：

![image.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/572ea3c625354fb2b8547e3eeffd99f2~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=710&h=220&s=10958&e=png&b=f1f0f3)

下面是具体的 `ws.proto` 文件，可以看出它是 **对数据的定义** ，包括类型和对应值：

| 定义 | 说明 |
|------|------|
| WsFrameType 枚举 | 所有帧类型的编号：PING(0)、PONG(1)、AUTH(2)、AUTH_RESULT(3)|
| WsFrame 消息 | 帧结构：type(int32) + payload(bytes) |
| AuthRequest 消息 | 认证请求：token(string) |
| AuthResult 消息 | 认证结果：success(bool) + message(string) |

```c
syntax = "proto3";
package im;

enum WsFrameType {
  PING = 0;
  PONG = 1;
  AUTH = 2;
  AUTH_RESULT = 3;
}

message WsFrame {
  WsFrameType type = 1;
  bytes payload = 2;
}

message AuthRequest {
  string token = 1;
}

message AuthResult {
  bool success = 1;
  string message = 2;
}

```

WsFrameType 枚举当前只用到 0~3，后续的好友申请、会话更新、在线状态、消息撤回、已读回执等功能，只需要追加新编号，不影响已有定义。

---

##### 2. 代码生成

其实说通俗一点， `ws.proto` 文件就是一个格式的定义，相当于一个说明书。但说明书本身是无法承担使用功能，所以想要它生效，最终都要落实到项目的代码里。好消息是: 

> proto 文件写好后，不需要手动编写编解码逻辑。Protobuf 的工具链会自动生成 **前后端代码**。


后端（Rust）使用 `prost` 库，在构建时通过 `build.rs` 自动编译 .proto 文件，生成 Rust 结构体和编解码方法。每次修改 .proto 文件后，`cargo build` 会自动重新生成。

前端（Dart）使用 `protoc` 编译器配合 `protoc-gen-dart` 插件，生成 Dart 类。生成的代码放在模块的 `src/proto/` 目录下，直接 import 使用。


![mermaid-diagram (26).png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/29412345aa5f476888b074058deab6b3~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1501&h=398&s=78678&e=png&a=1&b=eeeeee)

这个流程的价值在于：**协议定义是唯一的真相来源**。前后端的编解码代码都从同一份 .proto 文件生成，天然保持一致。改了协议，两端重新生成一次就行，这就从物理上，断绝了 "改了后端忘了改前端"的问题。

在 AI 编程中，这个流程更加顺畅。你只需要告诉 AI "在 ws.proto 里新增一个 FRIEND_REQUEST 帧类型"，AI 改完 .proto 文件后，两端的代码自动就有了对应的结构体。协议驱动开发，AI 执行生成，人只做决策。

> 读入 .proto 文件（协议定义），输出目标语言的代码。

##### 2. 心跳保活

连接建立后，如果双方都不说话，谁也不知道对方是否还在。网络可能已经断了，但两端都以为连接还好好的。就像两个人打电话，一方已经挂了，另一方还以为对方在听。

心跳机制就是为了解决这个问题。客户端每隔一段时间（比如 30 秒）发一个 PING 帧，服务端收到后回一个 PONG 帧。如果客户端连续几次没收到 PONG，就认为连接已断，触发重连。


![image.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/4ec07154a6c840bea548e9cdeae43610~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1400&h=818&s=58075&e=png&b=f8f8f8)

心跳的间隔不能太短（浪费流量和电量），也不能太长（断线发现太慢）。30 秒是一个常见的折中值。

---

##### 3. 断线重连

移动端的网络环境是不稳定的。用户进电梯、切换 WiFi 和蜂窝、手机锁屏后系统回收资源，都可能导致 WebSocket 断开。一个正式的 IM 客户端，必须有自动重连的能力。

重连策略通常采用 **指数退避** ：第一次断开后立即重连，失败后等 1 秒再试，再失败等 2 秒、4 秒、8 秒……直到一个上限（比如 30 秒）。这样既能快速恢复，又不会在网络持续不可用时疯狂重试。


![image.png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/4ec5e17a20934b1a9e22c26bd6b5d101~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1346&h=406&s=42069&e=png&b=e9e7f4)

重连成功后，客户端需要重新走一遍认证流程（发送 AUTH 帧）。因为服务端在连接断开时已经清理了旧连接的状态，新连接对服务端来说就是一个全新的陌生人。

#### 四、服务端与前端的职责

协议是前后端共同遵守的规则，但具体到落地，两端各有各的侧重。

- 服务端负责验证身份、分发帧、响应心跳；
- 前端负责把底层的连接细节封装起来，让业务层只关心"收到了什么消息"。

---

##### 1. 服务端：帧分发

服务端收到一个帧后，根据 type 字段决定交给谁处理。这个过程叫做 **帧分发** 。当前阶段的分发逻辑很简单：

| 帧类型 | 处理方式 |
|--------|---------|
| PING | 直接回复 PONG |
| CHAT_MESSAGE | 交给消息处理器（下一篇实现） |

随着功能增加，分发表会不断扩展。但分发器本身的结构不变：读 type，查表，转发。这和帧结构的设计思想一致：稳定的骨架，可扩展的内容。

---

##### 2. 前端：WebSocket 管理器

前端需要一个统一的 WebSocket 管理器来封装连接、认证、心跳、重连这些底层逻辑，让业务层不需要关心这些细节。

| 职责 | 说明 |
|------|------|
| 连接管理 | 建立连接、断开连接、状态监听 |
| 认证握手 | 连接成功后自动发送 AUTH 帧 |
| 心跳保活 | 定时发送 PING，监测 PONG 响应 |
| 自动重连 | 断线后指数退避重连 |
| 帧编解码 | 将业务数据封装成帧发送，将收到的帧解析后分发 |
| 事件分发 | 收到不同类型的帧，通知对应的业务模块 |

---

##### 3. 生命跨度与事件流

从生命跨度的角度看，前端 WebSocket 管理器是会话级的对象。它在用户登录后创建（或激活），退出登录时断开并销毁。它不跟随页面导航而重建，用户在聊天页和资料页之间切换时，连接始终保持。

后端的连接处理函数（handler）是连接级的，每条 WebSocket 连接对应一个独立的异步任务。连接建立时任务启动，断开时任务结束，资源自动释放。帧分发器（dispatcher）是全局级的，所有连接共享同一套分发逻辑。

管理器对外暴露的是事件流：消息流、连接状态流、认证状态流。业务层通过订阅这些流来获取数据，而不是直接操作 WebSocket 连接。这正是上一章说过的，"长命通知短命"的观察者模式。

这一篇的实现过程，体现了 AI 编程中一个重要的节奏：**协议先行**。

虽然 .proto 文件只有几十行，但它是整个通信系统的契约。有了它，AI 在实现后端帧解析时，知道每种帧长什么样；在实现前端编解码时，知道是什么结构体；在实现心跳逻辑时，知道 PING 和 PONG 的帧类型编号是什么。

这和传统开发中"先写接口文档再写代码"是同一个道理，但在 AI 编程中效果更显著。因为 AI 不会"猜"你的意图，它需要明确的上下文。.proto 文件就是最精确、最无歧义的上下文。

> 给 AI 一份清晰的契约，它能交付精确的实现。给 AI 一段模糊的描述，它只能交付一堆需要反复修改的代码。

这个原则不仅适用于协议设计，也适用于后续的数据库表设计、API 接口设计。在 AI 编程中，"设计"的价值被放大了，因为好的设计直接决定了 AI 产出的质量。
