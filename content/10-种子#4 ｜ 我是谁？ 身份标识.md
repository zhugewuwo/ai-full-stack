> 生命的第一个问题，不是"我能做什么"，而是"我是谁"。

上一章，闪讯的心脏开始跳动了。WebSocket 通道建立起来，前后端之间有了持续的、双向的实时通信能力。但目前后端还是一个"匿名"的系统——任何人都可以连上来，服务端也不知道对面是谁。

在现实世界中，一个人从出生起就会被赋予身份：姓名、出生证明、身份证号。这些标识让社会系统能够识别你、记住你、为你提供个性化的服务。

应用系统也是一样。没有身份认证，所有用户在系统眼中都是没有区别。消息不知道发给谁，会话不知道属于谁，数据不知道归谁所有。
如果说心脏的跳动，是生命的起点，那么身份认证，就是一切业务逻辑的起点。

#### 一、认证到底是怎么回事

在动手之前，先让 AI 帮我们梳理一下认证的基本概念。

> Q: 我在做一个即时通信产品，现在需要实现用户认证系统。  
> 先不要写代码，请为我梳理一下认证的基本概念。  
> 用通俗易懂的方式，合理使用 mermaid 展示认证流程。  
> 写到 docs/research/project/auth_overview.md 中


AI 给了一份非常清晰的 [梳理文档](https://github.com/toly1994328/flash_im_by_ai/blob/master/docs/research/project/ws_auth_flow.md)。其中几个核心概念值得记住：  
**认证（Authentication）**  
回答的是一个最基本的问题：你是你所声称的那个人吗？日常生活中我们无时无刻不在进行认证——进小区刷门禁卡、登录银行 App 输入密码、刷脸进站。形态各异，但本质上都在做同一件事：用某种凭证，证明你的身份。  
**Token（令牌）**   
解决的是"记住你是谁"的问题。想象你去游乐园，入口处检票员验证了你的门票（认证），然后给你戴上一个手环（Token）。之后你在园区内玩任何项目，只需要出示手环就行，不用每次都回入口重新买票。

`JWT（JSON Web Token）` 是目前最常用的 Token 方案。它的精妙之处在于：Token 本身就携带了用户信息，并且通过签名机制防止篡改。服务端不需要在数据库中存储会话状态，只需要验证签名是否合法。AI 绘制了一个认证的流程图：

![mermaid-diagram (6).png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/1793a8ced8284aca859e1f9b5e114354~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1097&h=1065&s=145520&e=png&a=1&b=e9e9e9)

> 总的来说，认证是"证明你是谁"，Token 是"记住你是谁"。

![image.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/9aa7dae4a3aa41e19bed9be450593d4a~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=840&h=157&s=52162&e=png&b=efeef1)

AI 在后端项目中添加了认证相关的处理逻辑。虽然是 playground 阶段数据仅存在内存，但 JWT 部分用的是真实的库。因为 Token 的生成和验证是认证系统的核心机制，用真实实现才能让你感受到它的工作原理。来看看 JWT 的核心代码，这是整个认证系统最关键的部分：

```rust
/// JWT 载荷——Token 里装的东西
#[derive(Debug, Serialize, Deserialize)]
struct Claims {
    sub: String,   // 用户 ID
    exp: i64,      // 过期时间
    iat: i64,      // 签发时间
}

/// 生成 Token
fn generate_token(user_id: i64) -> String {
    let now = Utc::now().timestamp();
    let claims = Claims {
        sub: user_id.to_string(),
        exp: now + 7 * 24 * 3600, // 7 天
        iat: now,
    };
    encode(&Header::default(), &claims, &EncodingKey::from_secret(JWT_SECRET.as_bytes())).unwrap()
}

/// 验证 Token，提取用户 ID
fn verify_token(token: &str) -> Result<i64, &'static str> {
    let data = decode::<Claims>(
        token,
        &DecodingKey::from_secret(JWT_SECRET.as_bytes()),
        &Validation::default(),
    )
    .map_err(|_| "Token 无效")?;
    data.claims.sub.parse().map_err(|_| "用户 ID 解析失败")
}
```

这段代码揭示了 JWT 的本质：
- `Claims` 结构体就是 Token 里携带的信息——用户是谁（`sub`）、什么时候过期（`exp`）、什么时候签发的（`iat`）。
- `encode` 把这些信息加上密钥签名，变成一串不可篡改的字符串。  
- `decode` 则反过来，用同一个密钥验证签名并还原信息。  

关键在于 `secret`——这个密钥只有服务端知道。任何人都可以看到 Token 里的内容（它只是 Base64 编码，不是加密），但没有密钥就无法伪造签名。这就像一封盖了公章的介绍信：内容谁都能看，但章是假的一眼就能识破。

##### 3. 沉淀一套可复用的开发节奏

再回顾整个登录功能的开发流程：  


![mermaid-diagram (7).png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/7e0a89d120404b4680c586f7baa98505~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1532&h=130&s=29492&e=png&a=1&b=ececec)


这不是一次性的操作，而是一套可以反复套用的节奏。后面做好友系统、做消息收发、做文件上传，流程几乎一模一样——只是填进去的内容不同。

在这个节奏里，人和 AI 的分工也逐渐清晰：

- **人决定做什么**: 选择验证码登录而不是密码登录，选择 JWT 而不是 Session，这些是产品和架构层面的决策，AI 可以给建议，但最终拍板的是你。
- **AI 负责怎么做**: 写接口、写页面、写测试，这些是执行层面的工作。AI 的速度和覆盖面远超手写，但它不会主动思考"该不该做"。
- **人校验做得对不对**: 跑一遍测试、看一眼代码结构、试一下边界情况。AI 生成的代码不是交付物，而是草稿，需要你的审阅才能变成可信赖的产品代码。

这也是本册开始时说过的：在 AI 编程时代，开发者的角色从`搬砖工`转向`建筑师`。你不需要亲手砌每一块砖，但你要知道墙该砌在哪里、砌多高、用什么材料。这种判断力，才是 AI 时代开发者最核心的竞争力。  
整个流程，只是在用自然语言个 AI 聊天。真正编程方面的技术壁垒，在 AI 面前，已经不是不可逾越的高山了。我们也将有更多的精力，投身于产品本身的设计、代码结构模块的思考。

#### 四、具有身份的聊天系统

下面我们将遇到第一个模块衔接问题，这是一个很好的思考练习。


- 我们目前有两个独立的模块：心跳通信（WebSocket）和用户认证（JWT）。  
- 它们各自运行良好，但彼此不认识。WebSocket 通道不知道连接的是谁，认证系统也不知道有实时通道的存在。

如何使两者功能进行叠加，形成具有认证功能的聊天系统？这种功能与功能间的整合与衔接，才是人作为指挥官，布局决策的意义所在。

---

##### 1. 整合方案

在真正开始之前，还是可以和 AI 来探讨一下方案：

> Q: 目前我们有两个独立模块：WebSocket 心跳通信和 JWT 用户认证。  
> 在正式的 IM 产品中，WebSocket 连接建立后应该如何进行身份认证？  
> 请描述一下整体流程，用 mermaid 画出时序图。

下面是 AI 给的方案和流程，连接建立后，客户端必须在第一条消息中发送 JWT Token。服务端收到后：

-   验证 Token 签名是否合法，检查 Token 是否过期
-   提取 `user_id`，将此连接与用户身份绑定
-   如果验证失败或超时（通常设置 10 秒），服务端主动关闭连接。

![mermaid-diagram (8).png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/5809d40272454bbf85f44a06b6ce00fd~tplv-k3u1fbpfcp-jj-mark:0:0:0:0:q75.image#?w=1380&h=2158&s=250646&e=png&a=1&b=e9e9e9)

为什么要和 AI 讨论一下方案？如果你直接让它给你写代码，那你它在干什么，对你而言是一个黑箱。这对于一个决策者来说是很危险的，你无法把控战局，整体就有跑偏的风险，特别是在模块衔接的核心节点。

##### 3. 保持好奇，掌控战局

AI 为你每做完一个功能，最好你要沉淀一下，不要蹭蹭蹭的一个接着一个功能叠加。你可以抽些时间，和它讨论一下，比如 ：

- 找一些你感兴趣的点，和它探讨；
- 或者聊聊当前的欠缺、后续的发展方向；
- 或者聊聊项目的结构，有哪些优化的空间。

这里我问了一个比较关键的技术问题：

> Q: 我一个小问题向和你探讨一下，A 发送消息后，后端是怎么通知其他人的吗？   
> 为我指出当前代码的实现位置

- **让身份流入实时通道**: WebSocket 连接建立后，通过首消息认证将 JWT 与连接绑定。匿名的心跳，变成了有身份的通信。
- **第一次模块衔接**: 把独立的认证模块和通信模块整合成聊天室，体验了"功能叠加"的决策过程。这种衔接能力，是 AI 无法替你做的。

到这里，Flash IM 已经有了心跳（WebSocket）、有了身份（JWT）、有了第一个真正的业务场景（聊天室）。它不再是一堆孤立的技术练习，而是开始像一个真正的产品了。但目前的聊天室还很粗糙：  
- 所有人在同一个房间里，没有私聊、没有消息持久化、没有离线消息。
- 代码几乎没有组织，都是堆叠功能，特别是后端，所有的逻辑都在一个文件。


后续，我们将开始处理这些问题——让消息不再是转瞬即逝的广播，而是可以被存储、被检索、被送达的真正的"信"。
